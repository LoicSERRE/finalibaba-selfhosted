# Platform: PWA, i18n, theme, backup, CI, containers

### PWA / offline support

Installable (`app/site.webmanifest/route.ts`, with its `<link>` rendered by hand in `app/layout.tsx` - it started as the `app/manifest.ts` file convention, auto-linked by Next like `app/icon.tsx`/`app/apple-icon.tsx`, and had to move off it in v2.1; see "Per-user Trade Republic" below for why) - replaced an earlier static `public/manifest.json` that pointed both its "any" and "maskable" icon entries at the same unpadded `icon.svg`, which is wrong for maskable specifically (Android's circular/rounded-square mask would crop it). `app/icon-512/route.tsx` and `app/icon-512-maskable/route.tsx` are plain Route Handlers (not the `icon.tsx` file-convention - those are for the browser tab/iOS home screen, already covered separately) returning a 512×512 `ImageResponse` each, `force-static` since neither has any request-time data. Both render `components/shared/pwa-logo-512.tsx`'s `Logo512`, which computes every coordinate from `icon.svg`'s own 100×100 viewBox via real arithmetic (a `VIEWBOX_TO_CANVAS` scale factor, plus a `MASKABLE_SAFE_ZONE` shrink-and-recenter for the maskable variant) rather than hand-copied decimals, so the two variants (and any future logo edit) can't visually drift apart. `appleWebApp` (`app/layout.tsx`'s `metadata`) and the `env(safe-area-inset-bottom)` padding on `<main>` predate this - already handled iOS home-screen install and notch/home-indicator spacing.

**Service worker (`public/sw.js`)** also handles Web Push (v1.15) - `push`/`notificationclick` listeners, unrelated to the caching logic below (see "Alerts & webhooks" for the full design). Runtime caching only, no precache list: every route in this app is dynamic/server-rendered (see the route table under "File layout" above - almost nothing is `○` static), so there's no build-time HTML to precache against. Instead it caches whatever the browser actually requests as it browses - "cache what you've seen", the same model as the browser's own disk cache, just surviving offline too. Registered by `components/layout/service-worker-registration.tsx` (mounted once in the root layout) as `/sw.js?offlinePages=0|1`.

- Deliberately excludes every non-`GET` request (Server Actions POST to the same URL as the page that calls them - a mutation must never be served from or silently absorbed into the cache) and everything under `/api/` (session-sensitive or mutating either way).
- `_next/static/*` (content-hashed, genuinely immutable per build) always gets cache-first, regardless of `offlinePages`.
- **With `offlinePages=0` it does not intercept navigations at all** (v2.1.1). It used to fetch and return the response, caching successes "so a repeat visit loads faster" - which was simply false: only `cacheFirst` and `networkFirstWithFallback` ever read the cache, and neither runs on that path, so it wrote entries nobody read. It also broke real page loads. Once `respondWith` has been called the worker owns the response, and a rejected `fetch()` becomes an unrecoverable network error - which is what a user hit behind Cloudflare Access: an expired Access session answers a navigation with a cross-origin redirect to its login host, `public/sw.js` is served with the app's own `connect-src 'self'` CSP, so following that redirect from inside the worker is blocked and the page fails with "the promise was rejected" until a manual refresh. Not intercepting lets the browser follow the redirect at the top level, where it is allowed. Worth remembering as a class: **a service worker should only call `respondWith` when it can both add value and handle failure**, because after that call there is no way to hand the request back.
- Everything else (page navigations) is `offlinePages`-dependent: `1` does network-first-with-cache-fallback (a real offline experience - the point of this feature); `0` still caches successful responses for faster repeat loads, but never reads from the cache to answer a request that *failed* - a network error surfaces as a normal connection error, exactly what would happen without a service worker at all.
- **Why it's conditional on `AUTH_ENABLED` at all** (the query param is the only way this static file can know a server-only env var, short of a network round-trip on every install - `app/layout.tsx` reads `process.env.AUTH_ENABLED` server-side and passes the resolved boolean down as a prop): falling back to a cached authenticated page on network failure would bypass the server-side session check that page normally goes through on every load. A session can expire (30d JWT, see "Authentication" below) or be revoked without this service worker ever finding out, if it's just replaying a stale cached response instead of hitting the network. `AUTH_ENABLED` is not `"true"` (the documented default - private-network trust model, see "Authentication" below) is the one case genuinely safe to give the fuller offline experience to.
- **Cache cleared on logout** (`components/layout/sidebar.tsx`'s only `signOut()` call site, gated the same as that button - `showLogout`, i.e. `AUTH_ENABLED=true`) - `offlinePages=0` already stops a network failure from ever serving stale cached data, but successful responses are still cached along the way for the speed benefit; without this, that cached (real, once-authenticated) data would keep sitting in Cache Storage on a shared/public device after an explicit logout.
- `components/layout/offline-banner.tsx` is a `navigator.onLine` indicator, deliberately independent of the service worker's own cache-hit/miss logic - simpler and more robust than threading a custom "served from cache" signal back from the SW, and honesty matters here specifically: a stale cached balance shown with no indication it might be out of date would be actively misleading for a wealth-tracking app, not just a missing nice-to-have. Built on `useSyncExternalStore` (not `useEffect`+`useState`, which the lint config's `react-hooks/set-state-in-effect` rule rejects for exactly this "subscribe to a browser API" shape) - `getServerSnapshot` always returns `false` since `navigator` doesn't exist during SSR, so the banner never flashes on the server-rendered HTML, only after real client-side hydration confirms the browser is actually offline.
- `next.config.ts`'s CSP gained an explicit `worker-src 'self'` - would fall back to `script-src` without it (already `'self'`-scoped, so functionally the same), added anyway rather than relying on every browser's CSP3 fallback behavior being implemented identically.

**App-icon badging (v2.0)** - `public/sw.js`'s `push` handler calls `navigator.setAppBadge()` alongside `showNotification`, and `service-worker-registration.tsx` calls `clearAppBadge()` on mount **and on every `visibilitychange` to visible**. The second listener is the one that matters: an installed PWA is resumed far more often than cold-started, so a badge cleared only on a fresh load would sit there for days. Called with **no count** on purpose - this app dispatches alerts but stores no read/unread state anywhere, so any number would be invented; a bare dot is the honest signal, and opening the app is the only read receipt that exists. Supported on iOS 16.4+ for home-screen web apps (the same gate Web Push already requires) and on desktop Chrome/Edge; Android shows its own badge for unread notifications and ignores the call; feature-detected because it is absent in Firefox and in a plain browser tab. Added by v2.0's native-mobile-app scoping pass (see `ROADMAP.md`), which found it had been available all along and unused - it closes most of the "a native app feels more present" gap that scoping pass was weighing, for a few lines.

**"Swipe-friendly views for phones"** (the other half of this ROADMAP item's original wording) was dropped rather than built - no concrete gap was found (no tab/carousel UI that would clearly benefit from a swipe gesture), and inventing one to fill the wording would have been scope creep, not a real fix. The mobile-responsiveness half of "PWA/mobile-optimised" was already substantially done incrementally by earlier real-usage-driven releases (44×44 touch targets, `overflow-x-auto` on every table, the searchable Woob bank picker, etc.) before this feature was ever scoped - confirmed by grep, not assumed, before writing any of the above.

**`proxy.ts`'s matcher gained real gaps from this feature, found and fixed in the same pass.** `app/icon.tsx`/`app/apple-icon.tsx` (pre-existing) and the four new routes above (`icon-512`, `icon-512-maskable`, `manifest.webmanifest`, `sw.js`) have no literal file extension in their URL for the matcher's pre-existing `.(?:png|jpg|ico|webp)` branch to catch - on an `AUTH_ENABLED=true` instance, every one of them would have been silently redirected to `/login` instead of serving the real content, breaking browser-tab favicons, iOS home-screen install, and the PWA install prompt alike (the icon fetches never carry a session cookie a human hasn't logged in with yet). Every alternative added for this is `$`-anchored (added to the pre-existing `icon\.svg` too, while touching this line anyway) - confirmed live against a real `AUTH_ENABLED=true` dev server that an unanchored `icon-512` alternative matches as a bare *prefix*, not an exact path: a nonexistent `/icon-512999` was bypassing auth entirely (harmless here since it 404s either way, but the wrong reason - not a path this matcher was ever meant to exempt). Deliberately **not** extending this same anchoring pass to the pre-existing, unrelated `api/*`/`shared`/`_next/*` alternatives in the same matcher - `shared`/`_next/*` are meant to match subpaths (`/shared/<token>`, `/_next/static/...`), so naively `$`-anchoring them the same way would break them outright; `api/*` likely has the identical latent prefix-match quirk but is pre-existing and untouched here, out of scope for this fix.

### i18n

Implemented via `next-intl`. Locale detection order: `NEXT_LOCALE` cookie → `Accept-Language` header → `DEFAULT_LOCALE` env var (defaults to `"fr"`). Supported locales: `fr` (default) and `en`. No URL prefix per locale.

UI strings live in `messages/fr.json` and `messages/en.json`. When adding new strings, update both files. Institution logos are fetched from Google Favicons using domain mappings in `lib/domain/institutions.ts`.

### Light theme

Explicit opt-in only (Settings → Apparence), same cookie-based pattern as locale above rather than an automatic `prefers-color-scheme` switch for an unset/new preference - deliberately. This app has always been dark-only; silently switching a user to light on their very first visit (or an existing user with no stored preference) just because their OS happens to be set that way for reasons unrelated to this app would be a surprising regression, not a feature. Dark stays the bare `:root` default in `globals.css` for that case; `:root[data-theme="light"]` is the explicit-light override, applied server-side on `<html>` in `app/layout.tsx` from a `THEME` cookie so there's no flash-of-wrong-theme on load. `lib/actions/theme.ts` (`setTheme`) and `app/api/set-theme/route.ts` mirror `lib/actions/locale.ts`/`app/api/set-locale/route.ts` exactly - same cookie name shape, same 1-year `maxAge`, same reason both a Server Action and a GET route exist side by side (the client `ThemeSwitcher` calls the route via `fetch` + `router.refresh()`, not the action directly). `lib/domain/theme.ts`'s `resolveThemePreference()` is the single shared cookie-parsing function every one of the three read sites (`app/layout.tsx`'s `generateViewport()` and `RootLayout`, `app/settings/page.tsx`) calls, so "dark" being the safe default for an unset/invalid cookie is only ever asserted in one place.

**"Auto" (v1.15)** - a 3rd explicit choice alongside Sombre/Clair, additive to the opt-in-only decision above, not a reversal of it: it only ever applies when the user themselves picks it (`THEME=auto`), never as the default for someone who hasn't chosen anything. Live-follows the OS scheme while the tab stays open (e.g. a phone's own scheduled day/night switch) with **zero JavaScript** - `app/globals.css`'s `@media (prefers-color-scheme: light) { :root:not([data-theme]) {...} }` block handles both the initial paint (resolved at CSS-parse time, before hydration - no flash) and every live OS change automatically, since media queries re-evaluate on their own. `app/layout.tsx` renders **no** `data-theme` attribute at all for `THEME=auto`, letting that rule decide; it renders an explicit `data-theme="dark"` for an explicit "Sombre" choice (even though the value duplicates the bare `:root` default's own colors) specifically so the media query's `:not([data-theme])` condition excludes it - without that, an explicit dark choice could get silently overridden the moment the OS happened to prefer light, exactly the kind of surprise this feature's own opt-in philosophy exists to prevent. `generateViewport()`'s `colorScheme` becomes `"light dark"` (not a fixed value) in auto mode, so native browser chrome (scrollbars, form controls) follows the OS live too, not just this app's own CSS tokens. **Verified live with Playwright** (`page.emulate_media(color_scheme=...)`, changed mid-session with no reload): auto mode's background genuinely swaps in the same page load when the emulated OS scheme flips, an explicit dark/light choice each correctly resists the opposite OS preference, and a brand-new visitor with no cookie at all and an OS set to light still renders dark - confirming the core "never silently switch a user who hasn't chosen" property survived adding this feature, not just asserting it.

`--accent`/`--accent-strong` are deliberately **not** overridden for light - the brand indigo works as a button/highlight background regardless of overall theme (a white-text button's own contrast requirement doesn't depend on what's around it). Only `--background`/`--foreground`/`--surface`/`--surface-elevated`/`--border`/`--muted`/`--accent-text`/`--positive`/`--negative`/`--warning` get light-specific values - the semantic-status colors (`--positive`/`--negative`/`--warning`) in particular need darker shades than dark mode's bright versions, since the same hue at dark-mode brightness reads as washed out on a light background and fails WCAG AA as text. Every light-mode pairing was verified against the real WCAG relative-luminance contrast formula (a Python script, not eyeballed) before being written into `globals.css` - values are commented inline with their measured ratio.

`app/layout.tsx`'s `viewport` export became `generateViewport()` (async, reading the same `THEME` cookie) specifically so `colorScheme` can follow the resolved theme - Next only allows one or the other per segment, not a static object for some fields and a dynamic one for others. Leaving `colorScheme: "dark"` hardcoded while a user had explicitly switched to light would misstyle every native browser control (scrollbars, `<select>` popups, checkboxes) with the wrong-theme defaults, a real regression this specifically avoids. `themeColor` (the browser chrome/status-bar tint) stays a constant brand indigo across both themes, not made theme-conditional - out of scope for a UI toggle, not part of the installable app's identity the way the manifest's own `theme_color` isn't either.

Verified the codebase was actually ready for this before writing any palette: grepped for raw Tailwind gray/black/white color classes and stray hex literals across `app/`/`components/` first - zero found outside expected data-color files (`lib/utils/palette.ts`, `mcc-categories.ts`, `merchant-categories.ts` - allocation/category swatch colors, intentionally independent of the UI theme) and `app/layout.tsx`'s own `themeColor`. The existing "never use raw Tailwind colour classes for brand colours" discipline (see "Design tokens" below) meant this was close to a pure CSS-variable-table addition, not a per-component audit.

### GoCardless (Open Banking PSD2)

Optional. EU + UK bank connections via the official PSD2 API (free tier: 50 connections, 90-day history).

Credentials: `GOCARDLESS_SECRET_ID` + `GOCARDLESS_SECRET_KEY`. Set `APP_URL` to the app's public URL when behind a reverse proxy - it's used as the OAuth callback after bank authentication. Leave `APP_URL` blank for localhost use.

GoCardless logic lives in the Next.js app (not the `sync/` service).

**Transactions, not just balances.** `syncGocardlessBalances` (writes a `HistoricalBalance` row) originally had no counterpart at all for individual transactions - GoCardless-linked accounts got a moving balance with no explanation, the same gap Trade Republic's cash account had before its own timeline sync was added (see "Sync service - optional modules" below). Fixed by `syncGocardlessTransactions` (`lib/actions/gocardless.ts`), which fetches `GET /accounts/{id}/transactions/` (`getTransactions` in `lib/services/gocardless.ts`) and writes `Transaction` rows via `createMany({ skipDuplicates: true })` keyed on `syncId: gocardless_${transactionId}` - transactions are immutable once synced here, so there's never a reason to update an already-known row, only insert new ones. Both syncs are combined behind the same "Sync" button (`syncGocardlessAccount`, called from `SyncOpenBankingButton`) rather than adding a second button, since the transactions and balances endpoints have independent rate-limit quotas (GoCardless: up to 4-10 requests/day per account per endpoint) - calling both on every click doesn't cost either one anything.

- Only `booked` transactions are processed, never `pending` - the Berlin Group/PSD2 schema's `pending` array routinely lacks a stable `transactionId`, which the `syncId`-based dedup above needs; a transaction becomes syncable once the bank moves it to `booked` on a later sync, same as it would show up late in the bank's own app.
- The label is built from `remittanceInformationUnstructured`, falling back to `creditorName`/`debtorName` when that's blank - mirrors Trade Republic's own title/subtitle fallback chain in spirit, just against PSD2's field names instead.
- `merchantCategoryCode` (when the account's bank actually populates it - it's optional per the spec) is captured into `Transaction.merchantCategoryCode` and feeds the MCC-based categorization signal - see "Automatic categorization" below.
- `autoCategorizeTransactions` runs immediately after a transaction sync completes, same reasoning as every other trigger point for it - a freshly-synced transaction with a populated MCC gets a chance to land in a category in the same sync, not a cycle behind.

### Revalidation, and what actually makes a screen update

`v2.3`, prompted by a report that many components do not update when you change them. The finding is worth recording mostly because **the obvious explanation was wrong**, and it was only settled by measuring.

The tidy theory - `revalidatePath`'s own documentation says it "updates the UI immediately (if viewing the affected path)", so an action that revalidates five pages but not the one on screen leaves it stale - predicts a real bug, and several action files did omit the page they were called from. Three experiments against a production build, each a category assignment on `/transactions` filtered to uncategorised rows so the server-rendered row count is the evidence:

1. every path revalidated, the one on screen included -> refreshes
2. the path on screen deliberately **removed** -> still refreshes
3. `revalidatePath` stubbed out entirely -> stays stale

So for this app the rule is: **a mutating action must revalidate something, and which path it names does not decide what you are looking at.** The narrower behaviour has a local cause - every page is `force-dynamic`, so there is no Full Route Cache to purge, and Next's default `staleTimes.dynamic` of 0 makes other routes refetch on navigation regardless. Experiment 3 confirmed that half too: with nothing revalidated at all, navigating from `/transactions` to `/budgets` still showed the new figure.

`lib/domain/revalidation-surfaces.ts` (pure, which pages show which entity) plus `lib/actions/revalidate.ts` (calls `revalidatePath` over the result) replace hand-listed paths in ten action files. The honest justification is modest: one call instead of five, route lists in one place instead of 27, and a test that pins them to routes that exist. The load-bearing part is the last block of `__tests__/revalidation-surfaces.test.ts`, which asserts **every mutating Server Action revalidates something**, with an explicit allowlist of the ones that legitimately need not (an internal recompute, transient WebAuthn challenges, and two that navigate away before a refresh could land).

**Nine real edit flows were then exercised in a production build - rename an account, edit a category budget, pause a recurring transaction, save alert channels, create a share link, create an API key, create a goal, assign a category, split a transaction - and every one refreshed correctly.** The reported symptom was not reproduced, so no component was "fixed" on speculation. If it recurs, the thing to capture is which screen and which edit; the guard test above now covers the one mechanism that is known to cause it.

### Backup & restore

Two paths, both wrap `pg_dump`/`psql` (full DB dump - schema + data, never a hand-rolled Prisma export, to avoid drift and BigInt/Decimal serialization issues):

- **CLI**: `scripts/backup.sh` / `scripts/restore.sh` - call `docker compose exec db pg_dump|psql`. `restore.sh` pauses `app`/`sync` if present and requires typed confirmation.
- **UI**: Settings → Backup & restore (`components/settings/backup-restore-section.tsx`), backed by `app/api/backup/route.ts` (`GET` streams a gzip dump, `POST` restores from an uploaded file, auto-detecting gzip vs plain `.sql`). This runs `pg_dump`/`psql` from inside the `app` container itself - that's why the `runner` stage in `Dockerfile` installs `postgresql16-client` (must track the `postgres:16-alpine` server version; a client older than the server can't dump it). Hidden entirely in `DEMO_MODE` (matches the auto-sync section's pattern).

**Optionally passphrase-encrypted since v2.10.6** (`lib/domain/backup-encryption.ts`). The backup is the one artefact that LEAVES the machine - a Downloads folder, a cloud sync, a mail to yourself - which for a home instance is far and away the most likely way data ever escapes. Encrypting the file covers what the columns cannot, balances and transaction labels included, and costs no query anything. Opt-in, with a passphrase the user chooses rather than the instance key: a backup exists to survive a disaster, disasters take `.env` with them, and a backup only the dead server could read is not a backup. scrypt, because unlike every other secret here this one is human-chosen. gzip first then encrypt, so the compression ratio leaks no more than the file size. The download streams; the restore buffers, because GCM only authenticates at the tag and feeding `psql` unverified bytes is not an option when a restore drops the database first. A wrong passphrase and a damaged file give the SAME message - telling them apart tells whoever holds a stolen backup which of the two they are up against. The file is named `.sql.gz.enc` so somebody finds it months later and knows they will be asked for something.

Both directions use `pg_dump --clean --if-exists` (so restore drops/recreates objects first) and `psql --single-transaction` (restore is all-or-nothing, no partial state on error). Never echo raw `pg_dump`/`psql` stderr to the client - log it server-side and return a generic error message, per the exception-exposure fix in commit `1ae43c0`.

Implementation notes (post-v1.2.0 audit fixes):

- **A local `pg_dump` older than the server produces an EMPTY file and exit code 1**, and a test that then greps it for secrets reports "no secrets found" - which is how the first verification of backup encryption passed while measuring nothing. `wc -c` the dump before believing anything about its contents. The app image pins `postgresql16-client` precisely so this cannot happen in production; a dev machine on Ubuntu 22.04 has 14.
- `buildConnectionString()` passes the *whole* `DATABASE_URL` (password stripped, everything else - including query params like `?sslmode=require` - intact) as a single positional arg to `pg_dump`/`psql`, with the password supplied separately via `PGPASSWORD`. Don't go back to manually extracting `host`/`port`/`user`/`database` into separate `-h`/`-p`/`-U`/`-d` flags - that approach silently drops any connection query params.
- The `GET` handler's `ReadableStream` only closes successfully once **both** `gzip`'s `"end"` (all bytes flushed) and `pg_dump`'s `"close"` (exit code known) have fired, and only if the exit code was `0`. A pg_dump that dies mid-dump after already writing valid-looking output must **error**, not silently succeed - a truncated "successful" backup is far worse than a visibly failed download, since the corruption would otherwise only surface during an actual restore. The `settled` flag guards every controller call this can race with (`enqueue`, `close`, `error`) - including `cancel()`, which must also set it (a client aborting mid-download must not let a still-queued `gzip.on("data")` callback call `enqueue()` on an already-cancelled stream and crash the process).
- After a successful restore, the process calls `process.exit(0)` (gated to `NODE_ENV === "production"`, so local `pnpm dev` isn't killed) so the container's `restart: unless-stopped` policy hands the app a fresh Prisma connection pool - the restore just dropped and recreated the whole schema out from under any pooled connections' cached query plans, the same reason `scripts/restore.sh` stops the `app` container before restoring. `components/settings/backup-restore-section.tsx` polls the current page with a `HEAD` request (never `/api/backup` - that would trigger another full `pg_dump`) until the app responds again before reloading.

### Container image hardening

`docker.yml`'s `trivy-scan` job scans the published `app`/`sync` images for OS-package-level CVEs (npm audit/pip-audit only ever see `package.json`/`requirements.txt`, never what's baked into the base image layer). Two things have already been removed from the runtime images because they were pure dead weight *and* a real CVE surface, not just untested risk:

- **`Dockerfile` (app)**: `node:22-alpine` bundles `npm` (and its own vendored `node_modules`) even though this project only ever uses `pnpm` via `corepack` - `npm`/`npx` are never invoked anywhere in this Dockerfile or its `CMD`. Removed via `rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/npm /usr/local/bin/npx` at the end of the `runner` stage. Verified `pnpm`/`node`/`prisma` still work with it gone; confirmed 0 CRITICAL/HIGH findings afterward (previously 6, including one CRITICAL in a vendored `tar`).
- **`sync/Dockerfile`**: `gcc`/`g++` (and the headers/`libc6-dev`/`linux-libc-dev` they pull in via `apt-get autoremove`) are only needed to compile `requirements.txt`'s native extensions (woob's `lxml`, `cryptography`, `psycopg2`) - the compiler itself is dead weight once the `.so` files exist. Removed right after `pip install` in the same `RUN` layer. Verified all sync modules (`woob`, `pytr`, `playwright`, `psycopg2`) still import fine afterward; this alone accounted for 47 of 117 CRITICAL/HIGH findings.
- **`sync/Dockerfile`, round two**: `git` is only needed for `pip install` to clone `pytr`'s pinned git commit (no PyPI release) - never used again afterward, and removing it cascades (via `apt-get autoremove`) to `perl`/`liberror-perl`/`libcurl3t64-gnutls`, which nothing else needs either. `xvfb`/`xserver-common` come bundled with `playwright install --with-deps chromium`'s headed-**and**-headless dependency union, but this project only ever launches Chromium headless (`setup_tr.py`) and never starts an X server (grep confirms `Xvfb`/`DISPLAY` are never referenced in `sync/`) - removing them cascades to the Mesa GL/Vulkan/X11-window-manager stack they alone pulled in (Chromium's own `ldd` output has no `libGL`/`libEGL` dependency - it ships its own software renderer for headless use). Verified together, not just individually: after removing all of it, headless Chromium still launches, executes JS, renders a canvas element, and produces a correct screenshot (byte-identical across two independent test runs) - cut CRITICAL/HIGH findings on this image roughly in half (66 → 33; see #22 for the full investigation, including why `perl-base` specifically is *not* touched - it's a Debian-essential package apt itself refuses to remove without `--allow-remove-essential`).

**Known accepted risk**: the sync image's CRITICAL/HIGH count is not a fixed number - it drifts upward over time purely from newly-disclosed CVEs against packages that were already there, with no code or Dockerfile change on this project's side. It was ~33 right after the hardening pass above; the v1.14 audit measured it at **66** (60 HIGH + 6 CRITICAL across 27 distinct CVEs, via `gh api .../code-scanning/alerts?ref=refs/tags/v1.13.1`) against the same trimmed Dockerfile - `libglib2.0`, `perl-base`, the `util-linux`/`ncurses` family, `libcups2t64`, `libxml2`, and a handful of single-count Debian base packages, either genuine Chromium runtime dependencies (`libglib2.0`, `libblkid1`, `libmount1` are all in its own `ldd` output) or Debian-essential base packages nothing here installed on purpose. **Don't treat a re-measured count higher than the last note as a regression to chase** - re-verify the Dockerfile still has the same trimming (`git`/`gcc`/`g++`/`xvfb` still absent) before concluding anything changed on this project's end; if it does, the growth is upstream Debian/Chromium CVE disclosure, not a fix that got un-done. `trivy-scan` therefore runs **non-blocking** (`exit-code: 0`) for the `sync` matrix entry specifically, while staying fully blocking (`exit-code: 1`) for `app`, which is clean as of v1.13.1 (see the pnpm/tar note below - it was briefly not clean at the v1.13.0 tag). This is deliberately narrower than the `find-my-way`/`valibot` exemptions under "pnpm overrides" below (those are unreachable *code paths* in an otherwise-used dependency; this is Chromium's own real runtime footprint) - it's accepted because `sync/`'s HTTP API is Docker-network-only per `SECURITY.md`, never internet-exposed, not because the CVEs don't matter. Findings still upload to the Security tab either way (`if: always()` on the SARIF upload), so they stay visible.

**Recurring pattern, not a one-off**: the app image's own blocking gate has now been tripped twice by the exact same root cause - a `tar` version vendored *inside* corepack's cached pnpm single-executable build (`home/node/.cache/node/corepack/v1/pnpm/<version>/...`), never this project's own dependency tree. First occurrence (v1.4.4-v1.4.11, GHSA-r292-9mhp-454m, MEDIUM) never actually blocked anything - `limit-severities-for-sarif: true` fixed a *different* bug that happened to also reveal this finding in a debug dump, and it sat below the CRITICAL/HIGH gate. Second occurrence (v1.13.0, CVE-2026-73566, HIGH) did block the release. Root cause both times: the pinned `packageManager` version in `package.json` was simply old enough that corepack's cached pnpm build still bundled a vulnerable `tar`. Fixed in v1.13.1 by bumping `pnpm@11.17.0` → `pnpm@11.22.0` (bundles `tar@7.5.22`, verified via `npm pack pnpm@11.22.0` and reading the bundled `tar/package.json` directly, not just trusting a changelog). There is no deeper structural fix available short of not caching corepack at all (which would break the Dockerfile `CMD`'s `pnpm exec prisma migrate deploy` at every container start) - this is accepted, expected maintenance: when it recurs again, re-check whether the currently-pinned pnpm version's bundled `tar` is still ahead of the latest disclosed CVE, and bump if not, the same way the "pnpm overrides" table below gets bumped for transitive-dependency CVEs.

**Three real, distinct bugs made `trivy-scan(app)` look broken across v1.4.4-v1.4.10, in order**: (1) `aquasecurity/trivy-action` pinned as `@0.36.0` instead of the real tag `@v0.36.0`, failing before any scan ran; (2) a raw `${{ github.repository }}`-built `image-ref` scanning `ghcr.io/LoicSERRE/...` (capitalized, matching this repo's real GitHub owner) instead of the required-lowercase GHCR path, also failing before any scan ran - fixed by lowercasing it explicitly, then hardened further by scanning `build-app`/`build-sync`'s own `digest` output instead of the mutable `:latest` tag (immune to any registry tag-propagation lag, a real but secondary bug this surfaced); (3) `/root/.cache/pnpm` (410MB of npm-registry metadata left over from `pnpm install --prod`, never read at runtime) made Trivy's secret scanner slow enough to occasionally exceed its 5-minute default timeout mid-scan - reproduced locally with the exact same timeout, fixed by removing that cache (keep `/root/.cache/node/corepack` though, that one **is** needed at runtime - see the `Dockerfile` comment). After all three were fixed, one real (if minor) finding was still failing the gate: a MEDIUM-severity `tar` DoS (`GHSA-r292-9mhp-454m`) vendored *inside* corepack's own cached pnpm single-executable build, not this project's dependency tree. It was slipping through a `severity: CRITICAL,HIGH` filter that should have excluded it, because `aquasecurity/trivy-action`'s `format: sarif` mode builds its report **"with all severities" regardless of the `severity` input** unless `limit-severities-for-sarif: true` is also set - a real trivy-action gotcha, not a workflow logic bug, and the actual root cause of most of this saga's apparent flakiness. All fixed; see the commit history around v1.4.4-v1.4.11 for the full trail if this class of "images build and push fine, but the gate after them behaves unpredictably" resurfaces.

**A third, different root-cause class tripped the same gate at the v1.16.0 tag: a floating base-image tag, not a vendored dependency.** `Trivy` failed on `CVE-2026-14456` (Alpine's `libssl3` 3.5.7-r0, a HIGH-severity unbounded-memory-growth DoS in OpenSSL's QUIC server) even though the patched `3.5.8-r0` was already available in Alpine's own package repo at build time (confirmed live: `apk upgrade --no-cache` against the same `node:26-alpine` tag pulled it immediately) - nothing in this `Dockerfile` ever installs `libssl3` directly, it only arrives transitively via the base image. Unlike the `pnpm`/`tar` saga above, there was no pinned version to bump - `node:26-alpine` is an unpinned floating tag by design (tracking Node 26's latest Alpine build), so its baked-in package snapshot can simply be stale relative to Alpine's live repo on any given day. Fixed by adding `apk upgrade --no-cache` as the first command in the `runner` stage, before installing anything else - this makes every build pull current Alpine packages regardless of how stale the pulled base-image layer happens to be, rather than trusting whatever snapshot the tag last baked in. Same category of fix as `sync/Dockerfile`'s existing `apt-get update` pattern before its own package installs, just not previously applied to this Dockerfile's `runner` stage.

**A red `trivy-scan(app)` is not always a finding - check that the scan ran at all.** At the v2.10.1 release it failed with no CVE anywhere in the log: `trivy-action`'s own binary install exited 35 (a curl SSL connect error fetching the release), so nothing scanned and the job died on `Path does not exist: trivy-results.sarif`. Transient, and a plain re-run of the failed job was the whole fix - but it blocks `notify-deploy` exactly like a real finding, so the images sit in GHCR while the private deploy pipeline is never told. Read the log for a CVE line before touching the `Dockerfile`.

### CI quality gates

`quality.yml` is a second, separate scanning workflow from `docker.yml`'s `trivy-scan` above - lightweight, stateless scanners (actionlint, zizmor, SonarQube, a duplication/complexity ratchet) adapted from an internal template workflow set. Tool versions are pinned inline in `run:` lines rather than via `uses:`, so Dependabot's `github-actions` ecosystem entry won't auto-bump them - bump manually on a new CVE class or rule-pack update. `zizmor` (workflow security posture) runs non-blocking by design: this repo pins actions by tag, not SHA, and that's its dominant finding class - informational until that's revisited.

The duplication/complexity ratchet job compares each run against a baseline artifact from a prior run via `gh api`; a transient GitHub API error on that lookup used to hard-fail the whole job instead of just skipping the comparison. Both the "list artifacts" and "download artifact zip" calls now fail open (treated as "no baseline yet") - don't re-tighten this to fail closed, a flaky `gh api` call isn't a real quality regression.

### Do not squash the migrations

Asked directly, measured rather than argued, and the answer is no for this
project specifically. There are 56 of them, 116 KB, 1006 lines of SQL, 11 of
which carry data backfills rather than schema alone.

**What keeping them costs: about five seconds per container start.** Measured
against a real PostgreSQL 16: `migrate deploy` on an up-to-date database takes
57s with all 56 in the folder and 51s with one. `prisma --version` alone takes
81s in the same environment, so almost all of it is Prisma CLI startup over a
slow filesystem, not the migrations. On a real VPS the gap is smaller still.

**What squashing costs: every existing install breaks at container start.**
Also measured, not assumed. A database with all 56 applied, given a folder
holding one new squashed file, fails with `P3018`:

    ERROR: type "AccountType" already exists
    A migration failed to apply. New migrations cannot be applied before
    the error is recovered from.

That is not a warning it recovers from on the next boot - it leaves the
database in a failed-migration state needing `prisma migrate resolve` by hand.
For an app whose whole promise is `docker compose up`, that is a manual
database operation demanded of every self-hoster to save five seconds.

Worth knowing the shape of the near miss: `migrate deploy` does **not** mind
applied migrations that have vanished from the folder - it reports "no pending
migrations" and exits 0. So deleting old ones looks harmless right up until a
fresh install needs them, or until the squashed replacement carries a name the
database has never seen. The safe route is Prisma's own baselining, and it
still needs that manual step from everyone.
