# Investments, tax, goals & charts

### Tax treatment

Latent (unrealized capital-gains) tax is a **per-account** setting, not a global one: `Account.taxTreatment` (`TaxTreatment` enum: `EXEMPT` | `DEFERRED` | `TAXABLE`) + `Account.taxRatePct` (0-1 ratio, meaningful only when `TAXABLE`). `lib/domain/tax.ts`'s `getAccountTaxRate(account)` is the single shared resolver - `EXEMPT`/`DEFERRED` both return `0`, `TAXABLE` returns `taxRatePct` - used by all four pages that compute latent tax (`app/page.tsx`, `app/accounts/page.tsx`, `app/accounts/[id]/page.tsx`, `app/analytics/page.tsx`), replacing 4 previously-duplicated `account.type`/`investmentSubtype` branching helpers.

- This exists so non-French wrappers have somewhere to go: a UK ISA or US Roth IRA is `EXEMPT`, a PER/401k is `DEFERRED` (not taxed until withdrawal - not taxed for latent/net-worth purposes today either), anything else is `TAXABLE` at whatever rate the user enters. `investmentSubtype` (`"PEA"`/`"CTO"`, cosmetic label only) is fully decoupled from this - an ISA doesn't need to pretend to be a "CTO" to get taxed correctly.
- Set at account creation (`components/accounts/add-account-dialog.tsx` + `createAccount`, rate pre-filled with a hardcoded 18.6%/31.4% suggestion based on the PEA/CTO/Crypto choice, always editable) or afterward via an inline form in the account detail page's fiscal summary (`updateAccountTaxTreatment` in `lib/actions/accounts.ts`, same `<form action={...}>` pattern as `updateInvestmentStartDate`) - there was no prior UI to edit `investmentSubtype` post-creation either, so this is the first edit surface for either field.
- `UserSettings.taxRatePea`/`taxRateCto`/`taxRateCrypto` (Settings → Fiscalité) still exist, but only as **defaults offered when creating a new account** - they are no longer read per-render for existing accounts. Migration `20260727141819_add_account_tax_treatment` backfilled every pre-existing account's `taxRatePct` from these same global rates at the time it ran, so upgrading never changes a displayed number: CRYPTO → `taxRateCrypto`, PEA → `taxRatePea`, CTO → `taxRateCto`, INVESTMENT with no subtype set → `EXEMPT` (reproducing the old chain's `null` = "no tax computed" outcome exactly, not a claim that the account is a real tax-exempt wrapper).

### Country presets, and why there is no tax engine

`v2.4`. `Account.taxTreatment` (`EXEMPT`/`DEFERRED`/`TAXABLE`) plus `taxRatePct` was already country-agnostic and already correct - a UK ISA and a US Roth IRA are both EXEMPT, a PER and a 401(k) are both DEFERRED. That model did not need replacing. What needed replacing were the places that bypassed it with French assumptions compiled into code.

**The worst of them, and the reason this exists.** `lib/domain/analytics.ts` estimated savings interest by matching account *names* against French product names - `"lep"`, `"livret a"`, `"ldds"`, `"livret jeune"` - with rates hardcoded "as of 2026-06-01, update when rates change". Two consequences, both silent: a savings account anywhere outside France contributed exactly **zero** passive income, indistinguishable on screen from an account that genuinely pays none; and a French user could not correct a stale rate without editing TypeScript. It also ran on every render, forever, for a value that changes about once a year.

That is now `Account.interestRatePct`, a real nullable column read by the estimate. `lib/domain/tax-locale.ts` still *suggests* the same French rates, once, at account creation, for a France-configured user - and the v2.4 migration ran the old name matching one final time to backfill every existing account, so an upgrading French instance sees identical figures. Verified against a real database: the seeded Livret A shows 1.5% in the new field and the analytics totals are unchanged.

**`UserSettings.country` drives suggestions and labels, never computation.** Picking a country decides which wrappers the pickers offer (PEA/CTO in France, ISA/SIPP/GIA in the UK, Roth IRA/401(k)/Brokerage in the US) and what gets pre-filled. `getAccountTaxRate` remains the only resolver and still reads the rate stored on the account.

**Deliberately not a tax engine, and that is the load-bearing decision.** Real rules are per-country, per-wrapper, per-holding-period, and change annually - France alone has PEA, PEA-PME, CTO, assurance-vie and PER, each with its own clock. An app that computes a confidently *wrong* tax figure is strictly worse than one that asks. So several countries carry a deliberate `null` rate: where the real number depends on an income band (UK, US, Spain), a deemed-return regime (Netherlands), or rules not worth encoding second-hand (Belgium, Luxembourg), the field starts empty rather than inventing precision. `null` cannot quietly become a wrong net worth; a plausible-looking wrong default can.

**The country is nullable and does NOT default to France.** An unset country resolves to the neutral `OTHER` preset - no French wrappers, no suggested rates. The migration backfills *existing* rows to `FR` because those instances were French by construction (the app offered nothing else), but a fresh install is asked rather than assumed. `__tests__/tax-locale.test.ts` pins both halves.

**A suggested rate carries the date it was known, because a regulated rate is a fact with an expiry.** Prompted by a direct question - the Livret A sits at 1.5% and is about to move to 1.7% - which exposed that the preset perpetuated the very problem it was introduced to fix: this section's own rule says a confidently wrong figure is worse than one that asks, and a hardcoded 1.5% with no date is exactly that. `SavingsPreset` now carries `knownAt` (`SAVINGS_RATES_KNOWN_AT`), the account form prints it ("proposé d'après les barèmes connus au 01/02/2026, vérifie-le auprès de ta banque"), so a dated suggestion is distinguishable from a value the user checked. France remains the only country with a `savings` list at all, and a test pins that: everywhere else a savings rate is whatever the bank offers, so suggesting one would be inventing a fact rather than recalling one.

**An unset rate is now visible rather than silently zero.** This was the real gap in the first cut, and the same bug class as the name matching it replaced: a null rate contributes nothing, which is correct, but on screen it is indistinguishable from an account that genuinely pays none - and `annualInterestCents` is rendered **nowhere in the UI**, only in the markdown export, so nobody could ever notice the shortfall. The account form now says so explicitly, and `computeAnalytics` returns `accountsMissingInterestRate` so the export discloses "estimation partielle : N comptes rémunérés sans taux renseigné" instead of presenting a partial total as a complete one. Empty and 0% still compute identically; the difference is that empty announces itself.

**A rate is a fact with a date on BOTH ends, and one number for the year was wrong for half of it.** `Account.interestRatePct` is what the account pays now; `AccountInterestRate` records what it paid *until* a date. That direction is the design decision: France's Livret A paid 1.5% until 31 July 2026 and 1.7% from 1 August, and one row plus the current field says exactly that, where storing changes as "became X on this date" would need two rows for one change and leave every day before the first row undefined. `rateAtDate` (`lib/domain/savings-projection.ts`) answers with the earliest row still open on a day, and the year-end estimate resolves the rate per fortnight rather than once. Measured on a real portfolio: **486,35 EUR** dated, against 503,45 EUR at a flat 1.7% and 476,98 EUR at a flat 1.5%. The migration backfills the one change it can state rather than guess - French instances, savings accounts, sitting at exactly 1.7% today - and leaves every other account alone.

**The rate field wants a NET figure** and now says so. The calculation was right once you knew the convention; nothing on screen told you, so entering the gross rate a bank advertises inflated the estimate on a taxable account.

**Why per-account entry rather than fetching rates automatically.** Checked before committing to it: PSD2/GoCardless returns balances and transactions, not a contract's interest rate - the field does not exist in that schema - and Woob scrapes the same surfaces. A national schedule only ever covers the *regulated* subset, so even in France a Livret Bourso+, a promotional booster, a PEL, a CEL or a compte a terme would still need asking. Deriving a rate from interest transactions (credit divided by average balance) is genuinely possible later, since the categorization engine already recognises those labels (see `normalizeLabelForCategorization`'s year-stripping, written for exactly these once-a-year credits), but it needs a full year of history and breaks on a mid-year rate change - an estimate of an estimate. Per-account entry is correct in every country today, at the cost of one number per account.

**Still French, and knowingly so**: `dividendEffectiveTaxRate` (`lib/domain/analytics.ts`) models the French PFU for the dividend-calendar estimate, and the Trade Republic cash fallback bakes in the French flat tax to turn 2% gross into 1.372% net. Both are now *fallbacks* - a stored `interestRatePct` wins over the TR figure - but neither is country-aware yet. They are the next thing to generalise if a non-French user reports a wrong passive-income figure.

### Realized gains & annual tax report

Before this feature, selling a holding meant retyping a smaller `quantity`/`costBasisCents` on the existing `Holding` row (`upsertHolding` in `lib/actions/holdings.ts`) - a blind overwrite with no history, no gain ever computed. `Sale` (`ticker`, `quantity` sold, `proceedsCents`, `costBasisCents` of the *sold portion*, `date`) now records disposals as discrete events, the same shape as `IncomeEvent`. Realized gain is always `proceedsCents - costBasisCents`, never stored.

- **Recording a sale** (`components/account-detail/sell-holding-dialog.tsx`, "Sell" button next to each holding row in `app/accounts/[id]/page.tsx`) uses the **average-cost method**, not per-lot FIFO/LIFO: the sold portion's cost basis defaults to `holding.costBasisCents * (soldQty / holding.quantity)`, always user-editable. `recordSale` (`lib/actions/sales.ts`) wraps creating the `Sale` row and adjusting the `Holding` in one `prisma.$transaction` - full disposal (`quantitySold >= holding.quantity`) deletes the `Holding`, partial disposal reduces `quantity` and `costBasisCents` proportionally, then calls the same `refreshAccountBalance` helper `upsertHolding`/`deleteHolding` already use (exported from `lib/actions/holdings.ts` for this reason). `recordSale` also rejects a sold-portion `costBasisCents` that's negative or exceeds the holding's own remaining `costBasisCents` - without that guard the remaining `Holding.costBasisCents` can go negative, which then inflates the displayed gain (and latent tax) beyond the position's actual market value indefinitely.
- **No backfill and no `updateSale`**: past sales already lost to the old overwrite behavior can't be reconstructed, and editing a past `Sale`'s quantity/proceeds after the fact would need the same retroactive-holding-adjustment problem `deleteSale` already punts on (**record-only deletion** - it does not reverse the `Holding` change, since the holding may have had further buys/sells/price updates since; correcting a mistake means deleting the `Sale` row *and* manually fixing the `Holding` via the existing edit dialog).
- **`/tax-report`** aggregates `Sale` + `IncomeEvent` for a given calendar year (`?year=` search param). Estimated tax on gains reuses `getAccountTaxRate()` from "Tax treatment" above (`EXEMPT`/`DEFERRED` sales show €0 tax, same semantics as latent tax elsewhere) - it does not attempt to model additional income tax on dividends/interest beyond what `IncomeEvent.taxWithheldCents` already nets out, by design (country-agnostic scope, not a French PFU/social-charges calculator). No sidebar nav item - linked instead from the Analytics "Passive income" card and the account detail page's fiscal summary, to avoid further crowding the already-7-item mobile bottom nav.
- The estimated tax figure **nets gains and losses per account for the year** before taxing (grouping `Sale` rows by `accountId`, only taxing a positive net) - same convention as the account-detail page's aggregate tax figure. The per-row "Tax" column in the sales table is a per-sale reference figure only (as if that were the year's only sale) and intentionally won't sum to the displayed total whenever an account had both a gain and a loss sale that year - disclosed in the page's footnote.
- Markdown export (`components/shared/export-tax-report-button.tsx`) reuses `lib/utils/markdown-export.ts`'s `fmt`/`sign`/`downloadFile`, same convention as `components/shared/export-analytics-button.tsx`/`components/shared/export-accounts-button.tsx` - this is the "country-agnostic, exportable" part of the roadmap wording; the report itself is presented as an estimate for informational purposes, not an official tax document or a literal French IFU form mapping. Unlike those other two exports, every per-row figure here (sale proceeds/cost basis/gain/tax, each dividend/interest line) is passed `fmt(x, 2)` explicitly rather than `fmt`'s own 0-decimal default - matching the page's own `formatCurrency(x)` calls for these same rows (2 decimals, no override), which the export originally didn't. Found in production: a real dividend of 0,46€ was rounding to "0 €" in the downloaded file while the page correctly showed "0,46 €" right next to it - real money silently disappearing from a document whose whole purpose is being accurate enough to declare. The summary card figures stay at the export's 0-decimal default, matching the page's own `formatCurrency(x, 0)` summary cards.

### Benchmark comparison

`app/analytics/page.tsx`'s "Comparaison aux indices" section, right after the investment performance table. Deliberately **not** a historical overlay chart: `investCAGR` (the portfolio's own aggregate CAGR, see the performance table above it) is itself a point-in-time snapshot - current value vs. cost basis, annualized over a cost-basis-weighted average holding duration (`investCAGRWeightedYears`) - not a smooth time series (investment `HistoricalBalance` snapshots are event-driven, created only when holdings change, not on a schedule, so there's no reliable daily series to chart against an index). This feature applies the identical snapshot-to-snapshot methodology to 3 reference indices instead of inventing a different, inconsistent one.

- `fetchYFPriceHistory(symbol)` reuses the exact same unauthenticated Yahoo chart endpoint, headers, and `next: { revalidate: 3600 }` caching as the existing dividend fetch (`fetchYFDividendForSymbol`) - that endpoint already returns OHLC `close`/`timestamp` arrays that the dividend fetch just discards (it only reads `events.dividends`/`meta.regularMarketPrice`); this fetch reads those arrays instead, with `interval=1mo&range=max` (not a fixed window - see `computeIndexCAGR` below for why) and no `events` param.
- `BENCHMARK_SYMBOLS`: `sp500: "^GSPC"`, `cac40: "^FCHI"` (real index tickers), `msciWorld: "URTH"` (the iShares MSCI World ETF - Yahoo has no clean "^" ticker for the real index, so this is a proxy with a small expense-ratio drag, disclosed in the UI footnote).
- `computeIndexCAGR(series, startDate, now)` finds the closest historical close to `startDate` (via `priceAt`, nearest-timestamp match - the fetched series is monthly, not daily) and to `now`, then applies the same `(end/start)^(1/years) - 1` formula as `investCAGR`, over the identical `investCAGRWeightedYears` lookback so the comparison is apples-to-apples. The "years" divisor is derived from the **actual matched data points' dates**, not the requested `startDate` - `investCAGRWeightedYears` can exceed however far back the fetched series reaches (a PEA opened over 10 years ago, URTH's own Feb-2012 inception, etc.), and dividing by the *requested* span while priceAt silently clamps to the *oldest available* point would produce a self-inconsistent (understated) CAGR instead of gracefully reflecting the window actually available.
- Only rendered when `investCAGR !== null` (same gate as the aggregate CAGR itself) and per-index only when that index's fetch actually returned data (Yahoo being unreachable degrades to that one row being omitted, not a crash - same `try/catch` → empty-array fallback as the dividend fetch).

### Full sector-exposure breakdown

`app/analytics/page.tsx`'s "Répartition sectorielle" section (v1.16), right after the allocation-radar section - generalizes `AllocationRadarSection`'s former Tech-only bar (`TECH_WEIGHTS`, a 12-entry hand-verified map, one scalar per ISIN - since **removed**, see the correction at the end of this section) into a full GICS-style breakdown (technology/financial_services/healthcare/consumer_cyclical/consumer_defensive/industrials/energy/utilities/basic_materials/real_estate/communication_services, plus `crypto`/`unclassified` outside the GICS 11) across every holding. `ROADMAP.md` flagged this as needing real scoping before building, since a full per-sector data source is a materially bigger ask than one hand-verified scalar - this section documents that scoping, done live with real evidence during the v1.16 session, not assumed.

**Data sources considered and rejected**, each checked live, not from memory:
- **OpenFIGI** (Bloomberg's free, documented, no-scraping mapping API) - `marketSector` is a broad asset-class label ("Equity"), not a GICS sector. Not usable for this.
- **iShares' own site** (a real primary source, many of this app's real holdings are iShares products) - rebuilt on Astro since this was last relevant, the old known JSON-download pattern no longer works; even fixed, it would only ever cover one issuer (not Amundi/Vanguard/Lyxor/SPDR - the real ETF universe self-hosters actually hold spans several), a materially bigger and more fragile undertaking than the single mechanism this feature actually uses.

**What it actually uses**: Yahoo Finance, the same provider every other Analytics Yahoo integration on this page already depends on, via two different endpoints with two very different trust profiles:
- **`resolveIsinToYahoo(isin)`** (`lib/services/yahoo-finance.ts`) - `/v1/finance/search`, free, no cookie, no crumb, same trust level as `fetchYFPriceHistory` above. Resolves a `Holding.ticker` ISIN to a real Yahoo symbol (confirmed live: 11/12 of `TECH_WEIGHTS`' own ISINs resolve correctly - the one miss is an unlisted private-equity fund, an expected gap). For an `EQUITY` result, `sector`/`industry` come back in this same response - individual stocks need no second call and no crumb at all.
- **`quoteSummary?modules=topHoldings`** - needed for an ETF's full `sectorWeightings` breakdown (search alone doesn't carry it for ETFs). Confirmed live to return a real, complete 11-sector breakdown for every ETF symbol tried (`URTH`, `IWDA.L`, `CSSPX.MI`, `CW8.PA`, `XAID.L`) - but confirmed **requires a session cookie + crumb** (`getYahooCrumb()`: fetch a cookie from `fc.yahoo.com`, then a crumb from `v1/test/getcrumb` - confirmed live that `getcrumb` fails outright with no cookie at all). This is Yahoo's own internal anti-scraping mechanism, not a documented public contract, and this exact endpoint family has already tightened once without notice in this codebase's own lifetime (`v7/finance/quote` is fully dead - see "pnpm overrides"-adjacent history elsewhere in this file for other examples of upstream APIs changing under this project). Accepted as a real, disclosed risk, not glossed over - the crumb is cached module-level for ~50 minutes (`CRUMB_TTL_MS`) rather than re-fetched per holding, both for latency and to look less like scraping traffic.

**Two independent, optional fallback providers** (`lib/services/sector-fallback-providers.ts`), tried in order (`fetchFallbackEtfSectorWeights`: FMP → Alpha Vantage) only when Yahoo's crumb path itself fails - added after this was specifically requested to be "béton" (rock-solid), not just theoretically resilient:
- **`FMP_API_KEY`** / **`ALPHA_VANTAGE_API_KEY`** - optional, deploy-time `.env` variables (`.env.example`), same category as `GOCARDLESS_SECRET_ID`/`GOCARDLESS_SECRET_KEY` - a self-hoster who wants ETF-level resilience against Yahoo breaking configures one or both; the app works fully without either, just without that resilience. Neither is required for setup, matching this project's "`docker compose up` in under 5 minutes" goal.
- Both real, documented, API-key-authenticated REST APIs - the property that makes either "béton" relative to Yahoo's crumb path is that neither is a scraping workaround, it's a supported contract with a ToS. Offered as **two** rather than committing to one specific provider because this session couldn't decisively confirm either one's real-world coverage of European UCITS ETF tickers (the instruments that actually matter for this app's PEA-heavy French user base) without a registered account - Alpha Vantage's public `demo` key *did* confirm `ETF_PROFILE`'s real response shape live (a genuine complete sector-weightings response for its own canned example symbol, `QQQ`), FMP's shape is implemented against documentation only (its docs site itself returned 403 to a direct fetch attempt). **Honesty note, not glossed over**: neither is verified end-to-end against an arbitrary real ISIN with a registered key - whoever configures either key first should sanity-check the Analytics page actually shows data for their own holdings.
- Alpha Vantage's `ETF_PROFILE` uses official GICS sector names in a different casing/wording convention than Yahoo's own (`"INFORMATION TECHNOLOGY"` vs Yahoo's `"Technology"`, `"CONSUMER DISCRETIONARY"` vs `"Consumer Cyclical"`, etc., confirmed live) - `ALPHA_VANTAGE_SECTOR_ALIASES` maps the 4 sectors that actually differ explicitly rather than guessing at a generic transform; the remaining sectors already match Yahoo's wording once normalized.

**`lib/domain/sector-exposure.ts`** (pure, tested) - `normalizeSectorKey(raw)` unifies every source's casing into one canonical key set matching Yahoo's own `topHoldings` keys, including **the one real quirk found live**: `topHoldings`'s real-estate key is the unbroken word `realestate`, while a stock's `search`-returned sector string ("Real Estate") would naturally normalize to `real_estate` - handled as an explicit special case, not silently producing two different buckets for the same sector. `aggregateSectorExposure(holdings)` does the weighted sum across every holding's resolved `SectorWeights`, with an explicit `unclassifiedCents` bucket for any holding no source could resolve.

**Correction (real production feedback, same v1.16 cycle): crypto holdings were originally routed through the Yahoo/fallback resolution chain like any other holding, and always failed it** - BTC/ETH-style tickers aren't ISINs any of the three sources can classify under a GICS sector, so every `CRYPTO`-account holding landed in "Non classé" indistinguishable from a genuine data gap. Confirmed against the demo portfolio: ~40% "unclassified" was reported as an imprecision to fix, and tracing it showed the entire Crypto account's value was the sole contributor. Fixed by bucketing `CRYPTO`-type accounts' holdings directly into a `crypto` key in `app/analytics/page.tsx` (`{ crypto: 1 }`, no network call at all - the account's own `type` is known locally and is a strictly more reliable signal than asking Yahoo to guess) rather than attempting - and always failing - the Yahoo path for them. `crypto` sits outside `SECTOR_KEYS`' 11 GICS entries (same as `unclassified`) since crypto genuinely has no GICS sector; this is accurate classification, not a data-gap workaround. `SECTOR_COLORS.crypto` deliberately reuses `ALLOCATION_CATEGORY_COLORS.crypto`'s exact amber (same "one category, one color app-wide" principle that map's own comment already states) - which surfaced a second real bug caught before shipping: `consumer_cyclical` had independently been assigned that exact same hex, a genuine color collision within the sector palette itself, fixed by moving `consumer_cyclical` to fuchsia (the largest open hue gap between industrials' purple and real_estate's pink).

**Second correction (real production feedback, same v1.16 cycle): the section merged into `AllocationRadarSection`, and gained hover tooltips + a per-sector contribution breakdown.** Real user feedback after the fixes above found the page's own "Radar d'allocation" card (Garantis vs Risqués - a coarser cut of the exact same invested total this section drills into) and this section's own separate card confusing to look at side by side. `SectorExposureSection` stopped rendering its own `bg-[var(--surface)] border ... rounded-xl` card and its `<h2>`; `AllocationRadarSection` (`components/analytics/allocation-radar-section.tsx`) now renders it as a second `<h3>`-titled block inside its own single card, separated by a `border-t` divider - `app/analytics/page.tsx` no longer renders `<SectorExposureSection>` directly, only passes its data through as extra `AllocationRadarSection` props (`sectorBreakdown`/`sectorContributions`/`sectorUnclassifiedCents`/`sectorTotalCents`).

Also real feedback: with up to 13 distinct segment colors (11 GICS + crypto + unclassified) on one bar, the legend dot alone wasn't always enough to place a segment, and "where does this percentage actually come from" wasn't answerable without leaving the page. Both the stacked-bar segments and the legend rows are now real `<button type="button">` elements (not `<div>`s - keyboard-focusable via `group-focus-visible:block`, not just mouse-hoverable via `group-hover:block`) each rendering a shared `Tooltip` sub-component showing the sector's translated name plus its contributing holdings and euro amounts.

**`lib/domain/sector-exposure.ts`'s `aggregateSectorExposure` now also returns `contributions: Record<string, { holdings: SectorContribution[]; truncated: boolean }>`** alongside `breakdown` - built from a new required `name` field on `SectorExposureHolding` (a display label the caller builds once, e.g. `"iShares Core MSCI World (PEA)"` - `app/analytics/page.tsx`'s `holdingLabel()` combines `Holding.name ?? Holding.ticker` with the parent account's own name, so the tooltip can distinguish "the same ETF held in two different accounts" or "two different funds that both happen to be Technology-heavy"). Each sector's contribution list is sorted by contributed cents descending and capped at `MAX_CONTRIBUTIONS_PER_SECTOR = 5` (same "safety cap, not a feature limit" precedent as `MAX_UNCATEGORIZED_GROUPS`/`topAssets`' own top-10 slice) - `truncated: true` when real contributors exist beyond the cap, surfaced in the tooltip as a "+ d'autres positions" line rather than silently presenting a partial list as the whole story. Names wrap (`break-words`) instead of truncating with an ellipsis inside the tooltip - cutting off a fund name mid-word right before its disambiguating account suffix would defeat the entire point of this feature; an early draft with a narrower `max-w-[220px]` + `truncate` did exactly that and was widened to `max-w-[260px]` + `break-words` after a live screenshot caught it.

**Degradation alerting reuses `SyncFailureState`, not a new table.** `UserSettings.sectorDataAlertsEnabled` (`Boolean @default(false)` - unlike the loan/sync-failure toggles nearby, which default `true` to preserve pre-existing always-on behavior, this is a brand-new notification category with no such behavior to preserve, so opt-in is the less presumptuous default) gates `checkSectorDataHealth` in `app/api/alerts/check/route.ts`, called from the same `POST` handler every other alert check already runs from. It calls `probeYahooSectorHealth()` (a live probe against the existing `BENCHMARK_SYMBOLS.msciWorld` symbol, no new symbol dependency) and manages a `SyncFailureState` row under a reserved `source: "yahoo_sector_data"` **directly** rather than through `checkSyncFailures`'s existing loop (which only ever discovers sources by scanning `SyncLog`, a table nothing writes to for this JS-only concern) - same edge-triggered semantics (fire once on transition to broken, one reminder per `REMINDER_INTERVAL_MS`, clear on recovery) reusing `clearSyncFailureState`/`dispatchAlert` directly. Alerts on `!anyPathHealthy`, not `!yahooHealthy` - a self-hoster with a working fallback configured shouldn't get paged just because Yahoo alone hiccupped while the fallback quietly covered for it; the alert exists for "the feature has actually stopped working." **Verified live, not just reasoned through**: a temporary forced-failure flag exercised all three states in sequence against the real running app (fires once on the transition to broken, doesn't re-fire on an immediate second check, clears the moment the probe succeeds again) before being removed from the shipped code.

**Correction: `AllocationRadarSection`'s Tech-only bar was removed, not kept alongside this section as originally planned.** The original design left it untouched (independently hand-verified, its own concentration-warning UX) specifically to avoid "a risky removal nobody asked for" - but real user feedback on the shipped feature asked for exactly that removal: seeing two different "how much tech exposure?" numbers on the same page (the bar's hand-picked `TECH_WEIGHTS` figure vs this section's live Yahoo-sourced `technology` percentage, genuinely different values computed two different ways) read as confusing duplication, not two complementary insights. `TECH_WEIGHTS`, `techPct`/`techValueCents`, the JSX block, its i18n keys (`radar.techExposure`/`highConcentration`/`monitor`/`techFootnote`, `mdTechExposure`), its markdown-export row, and its dedicated `sonar-project.properties` S6819 suppression entry (`e8`, now unused - deliberately left as a gap rather than renumbering `e9`-`e11`) were all removed together, not just hidden - confirmed nothing else referenced any of them before deleting. "Garantis vs Risqués" in the same section is untouched (an orthogonal metric, not a sector concept).

### Portfolio rebalancing

`Holding.targetPct` (0-1 ratio, nullable - same convention as `taxRatePct`) adds a target counterpart to the per-holding "Poids" (current weight) column that already existed on `app/accounts/[id]/page.tsx`'s holdings table (`pct = marketValueCents / accountTotal`). This is scoped **within one account's own holdings** - unrelated to the Analytics allocation chart, which only buckets by account *type* (cash/savings/investments/crypto/realEstate/auto), never per-ticker.

- Set via the existing `components/account-detail/add-holding-dialog.tsx` edit form (one more optional field, not a new dialog), input as a 0-100 percentage and converted to a 0-1 ratio in `upsertHolding` (`lib/actions/holdings.ts`). Same optional-update semantics as `costBasisCents`: leaving it blank on an edit does not clear a previously-set target.
- Targets are **not required to sum to 100%** - a holding with `targetPct: null` is simply excluded from the rebalancing plan (e.g. an untouched legacy position the user doesn't want to manage this way).
- The "Rééquilibrage" section on the account detail page (only shown when at least one holding has a target set) computes, per targeted holding: drift in points (`pct - targetPct*100`) and a suggested trade (`driftValueCents = marketValueCents - accountTotal*targetPct`; positive → suggest selling that amount, negative → suggest buying it), plus an approximate share count from `driftValueCents / lastPriceCents`. The suggested-trade line is only rendered when `driftPts !== 0` (not just `driftValueCents !== 0`) - `driftPts` is two independently-rounded integer percentages, so a holding can sit at e.g. an exact 38.98% weight against a 39% target and show "0 pts" drift while the raw cents-level `driftValueCents` is still technically nonzero; showing a suggested trade next to an "on target" reading would visually contradict it.
- **Informational only** - the suggestion is displayed as text, not wired to pre-fill `AddHoldingDialog`/`SellHoldingDialog` (neither currently accepts external suggested-quantity props, and both are already one scroll up in the same holdings table for the user to act on manually). Keeps this change to one field + one read-only section, no changes to two already-working dialogs' APIs.

### Multi-currency

`Holding` positions can be entered in USD, GBP, or CHF and are converted to EUR **once, at entry time** - `lastPriceCents`/`costBasisCents` stay exactly what they've always been (plain EUR cents), so every existing calculation (net worth, tax, rebalancing, the tax report, the 3 chart components) keeps working completely unmodified. This is deliberately narrower than a "live multi-currency ledger": holdings aren't live-refreshed today either except via sync, so a snapshot-on-entry FX rate matches the app's existing "manually update the price when you check in" paradigm.

- `lib/services/exchange-rate.ts`'s `fetchExchangeRateToEur(currency)` reuses the same unauthenticated Yahoo Finance chart endpoint/headers/`revalidate: 3600` caching convention as the dividend/benchmark fetches in `app/analytics/page.tsx`, via the `EURUSD=X`/`EURGBP=X`/`EURCHF=X` pairs (Yahoo quotes these as "X per 1 EUR", so the raw price is inverted to get "EUR per 1 X"). Extracted to `lib/` rather than kept page-local since it's the first Yahoo fetch called from a Server Action rather than a page.
- `upsertHolding` (`lib/actions/holdings.ts`) reads `currency` from the form (default `"EUR"`, unchanged path - the 3 new fields stay `null`). For a foreign currency, it fetches the rate and **throws if the rate can't be fetched** - no silent fallback to a stale/wrong rate - then stores `nativePriceCents`/`nativeCostBasisCents` (exactly what the user typed) and `fxRateToEur` (the rate captured at entry time) alongside the EUR-converted `lastPriceCents`/`costBasisCents`. Switching a holding's currency back to EUR on an edit nulls out all three native fields.
- `fxRateToEur` is only **re-fetched** when the entered `currency`/native price/native cost basis actually differ from what's already stored (compared against the existing row before deciding) - otherwise the existing rate/EUR values are reused as-is. Without this, editing any unrelated field (renaming the position, setting a rebalancing target) would resubmit the same pre-filled native price and silently re-roll the conversion against whatever the market rate happens to be *today*, shifting the holding's EUR valuation even though nothing about the position's price actually changed - contradicting the "captured at entry time" design above.
- `components/account-detail/add-holding-dialog.tsx`'s price/cost-basis inputs pre-fill from `nativePriceCents`/`nativeCostBasisCents` when set (not `lastPriceCents`) so re-opening the edit dialog on a foreign-currency holding shows back exactly what was typed (e.g. "150.00"), not a lossy back-converted approximation.
- The holdings table (`app/accounts/[id]/page.tsx`) shows a small muted currency-code badge next to the ticker (e.g. "AAPL · USD") when `currency !== "EUR"` - no new table column, to avoid the mobile-width concerns already worked through for this same table (see "Portfolio rebalancing" above).
- **On-demand revaluation (v1.16)** - `RefreshHoldingFxButton` (`components/account-detail/refresh-holding-fx-button.tsx`, next to the row's Sell/Edit buttons, only rendered for `currency !== "EUR"`) calls `refreshHoldingExchangeRate(holdingId)` to re-fetch just the FX rate and recompute `lastPriceCents`/`costBasisCents` from the already-stored `nativePriceCents`/`nativeCostBasisCents` - without this, getting a fresh rate meant reopening the edit dialog and retyping the exact same native price just to trip `upsertHolding`'s own "only re-fetch when the native price actually changed" guard above, a real friction point since that guard exists specifically to *avoid* re-fetching on unrelated edits. Still narrower than a live ledger - nothing re-fetches on its own, still a manual action, still doesn't touch the native price/quantity, only the conversion. `fetchExchangeRateToEur` gained a `bypassCache` param (`cache: "no-store"` instead of `next: { revalidate: 3600 }`) used only by this path - a user who explicitly clicks "refresh" expects a genuinely current rate, not whatever Yahoo response was cached up to an hour ago; `upsertHolding`'s own entry-time fetch keeps the cached, revalidate-based path since there's no "on demand" expectation there.

### Savings goals

Replaces the old single `UserSettings.savingsGoalCents` global figure (v1.14) with a `Goal` model - multiple independently-named goals ("Apport immobilier: 40k/80k", "Fonds d'urgence: 8k/10k"), each with its own progress bar on `/analytics` (`components/analytics/goal-and-passive-income.tsx`'s `GoalProgressBar`, one per goal).

- **`accountId: null` means "track total net worth"** - the exact math the old single global goal always did - not a fallback/error state, a first-class choice equally as normal as linking a real account. **`accountId: <id>`** tracks that one account's own current value instead (its `AssetRow.value`, the same figure the "Mes actifs"/"Répartition détaillée" tables already show - `lib/domain/analytics.ts` exposes the full `assetRows` array, not just the top-10-sliced `topAssets`, specifically so a linked goal's account can be resolved without a second query even when it's outside the top 10).
- **`onDelete: Cascade`** on `Goal.accountId`, same reasoning as `AlertRule.accountId`: a null `accountId` means something different here ("track total net worth"), so silently falling back to that when the linked account is deleted would silently change what the goal measures, not just gracefully degrade it. Deleting the goal with the account is the safer behavior.
- **The account picker excludes `LOAN`** (a liability, not a savings target) - matching `assetRows`' own exclusion of `LOAN` for the same reason, so the picker and the value-lookup source stay in agreement by construction. Unlike `AlertRule`'s narrower per-kind account pickers (fiat-only or investment/crypto-only), a goal can link to any other account type, including `REAL_ESTATE`/`AUTOMOBILE` (e.g. a "down payment" goal). **`lib/actions/goals.ts`'s `assertGoalAccountEligible` enforces this server-side too** (real gap found and fixed in the pre-release code review, not present in the first cut) - the picker only controls what a legitimate UI flow can submit, and a Server Action is directly invocable regardless of what's rendered, same trust boundary as `assertCsvImportEligible`/`assertIncomeEventEligible` elsewhere in this codebase. Without it, a goal silently linked to a LOAN account would always show 0% progress (`assetValueById` never has an entry for it) with no explanation - confirmed live by deliberately injecting a LOAN account id into the picker's DOM and submitting: the Server Action rejected it, no `Goal` row was written.
- **Settings manages, Analytics displays** - `components/settings/goals-section.tsx` + `lib/actions/goals.ts` are CRUD-only (name/target/date/linked account), no live progress shown there, matching how `AlertRule`'s live evaluation lives in `/api/alerts/check`, not in its Settings list.
- **Migration backfill**: `20260823174545_add_goals` carries the pre-v1.14 single global goal forward as the first `Goal` row (`accountId: NULL`, name "Patrimoine", `targetCents` = the old `UserSettings.savingsGoalCents` value) so nothing already configured is lost - the first migration in this repo to do a real cross-table `INSERT ... SELECT`-style backfill, with a `COALESCE` fallback to the old field's own schema default for a fresh install where the `UserSettings` singleton row doesn't exist yet.
- `lib/domain/goals.ts`'s `computeGoalProgress(currentCents, targetCents)` is the shared, unit-tested pure math (`pct` capped at 100, `remaining` floored at 0) - extracted so it's reusable across N goals instead of being computed once inline the way the old single figure was.
- **`prisma/seed-demo.ts` seeds three example goals**, not one - real gap found while checking whether the demo actually showcases this feature: the migration backfill alone only ever produces a single net-worth-tracking goal (whatever `UserSettings.savingsGoalCents` happened to be), which doesn't demonstrate account-linking at all. The seed now creates one net-worth-tracking goal ("Patrimoine") plus two account-linked ones across different account types (a `SAVINGS`-linked "Fonds d'urgence" and an `INVESTMENT`-linked "Objectif CTO"), so a demo visitor sees the actual range of what the feature does. `prisma.goal.deleteMany()` was added to the script's own clearing step too - without it, re-running the seed on an already-migrated-and-seeded database would create a second "Patrimoine" goal alongside the migration-backfilled one instead of replacing it.

### Long-term net worth projection

`components/analytics/projection-chart.tsx` on `/analytics` (v1.14, right after the net-worth-evolution/allocation charts) - a compound-growth "what-if" chart answering "at this pace, where am I in 10/20/30 years", closing the one analytics gap this README already positions against Finary's own "Vision" feature for.

- **The assumed annual return is a live, client-side input, deliberately not a persisted `UserSettings` field.** This is an exploration tool, not a stored preference - the user asked for it this way directly after weighing the tradeoff (a persisted setting would need a schema migration, a Server Action, and Settings-page wiring for a value that's more naturally "try a few numbers" than "set once"). Pre-filled from `investCAGR` (the portfolio's own real CAGR, rounded to 1 decimal and floored at 0% since a real portfolio can have a negative CAGR but the input's own `min="0"` shouldn't be handed an invalid default) when available, else a fixed 5% fallback - always visible, always adjustable, recomputes instantly on every change via `useMemo`, no network round-trip.
- **`lib/domain/projection.ts`'s `projectNetWorth()`** is the pure math, mirroring `lib/domain/loan.ts`'s "params in, computed stats out" shape - a closed-form lump-sum-plus-annuity formula per year (`NW(t) = N0*(1+r)^t + C*(((1+r)^t-1)/r)`, with the `r=0` case handled separately since the annuity term divides by `r`) rather than an iterative simulation, avoiding float drift across 30 loop iterations the same way `loan.ts`'s own closed-form annuity math already does. Takes plain `number` cents, not `bigint` - it's called client-side on every input change, so the `bigint`→`Number` conversion happens once at the component boundary instead of on a server round-trip.
- **The annual contribution is `monthlySavedCents * 12` only when `hasDeclaredSavings` is true - never a fallback to `momDelta`** (the signal `savingsRate` itself falls back to when declared savings is absent). A single month's balance swing is noisy and genuinely inappropriate to extrapolate 30 years forward - the chart still renders with contribution `0` in that case (pure growth of today's net worth), with a visible note explaining why, rather than silently guessing from one volatile data point.
- **Correction (post-release UI/UX pass)**: the original cut of this feature needed zero `AnalyticsResult` changes, but user testing surfaced two real gaps closed in the same pass - the projection didn't account for latent tax on the projected gain (a real question raised against Finary's own simulator as the quality bar), and the horizon was a fixed 30 years with no way to look further or nearer.
  - **Tax-aware mode**: `lib/domain/analytics.ts`'s `computeAnalytics` now also returns `effectiveTaxRate` - a gain-weighted blended latent-tax rate (`getAccountTaxRate(account)` weighted by that account's own unrealized-gain-in-cents, summed across every account with a real gain, mirroring the exact weighting pattern `investCAGRWeightedYears` already uses elsewhere in this same function). EXEMPT/DEFERRED accounts contribute rate `0` and still count toward the gain-weighted denominator, naturally pulling the blended rate down for a mostly tax-advantaged portfolio - the same behavior `totalLatentTax` already has, just expressed as one reusable ratio instead of only ever an absolute cents figure. `projectNetWorth()` (`lib/domain/projection.ts`) takes this as an optional `effectiveTaxRate` param (default `0`, so every pre-existing pre-tax-only caller is unaffected) and computes `gain(t) = NW(t) - N0 - C*t` per year, taxing only a positive `gain(t)` - never the contributions - to produce a second `netWorthAfterTaxCents` figure per point. `ProjectionChart` renders this as a second, dashed, muted reference line (no fill, unlike the solid pre-tax `Area`) plus a small legend and a "≈ X net d'impôt" note under each callout - all gated on `effectiveTaxRate > 0` so a portfolio with no taxable gain (e.g. all-PEA) doesn't draw two overlapping identical lines. `effectiveTaxRate` is in the export-completeness allowlist (`__tests__/export-completeness.test.ts`), same `assetRows` precedent - it's an internal input for this chart's client-side math, not a standalone figure the markdown export needs to show.
  - **Configurable horizon**: the fixed 30-year span became a 10/20/30/40-year segmented pill selector (same visual pattern as `theme-switcher.tsx`/`language-switcher.tsx`, extended to 4 options), client-side state like the return-rate input - not persisted, this is still a "try a few numbers" exploration tool, not a stored preference. The 3 callout stats are now proportional to the selected horizon (`horizon/3`, `horizon*2/3`, `horizon`, rounded) instead of hardcoded 10/20/30, so they stay meaningful at every setting.

### Historical value chart per investment account

A "Trade-Republic-style" smooth value-over-time line for a single `INVESTMENT`/`CRYPTO` account's own detail page (v1.16) - a different, narrower ask than the dashboard-wide allocation chart above. **Scoped deliberately, not assumed** - `ROADMAP.md` flagged this as needing real design work before building, since unlike fiat accounts, investment/crypto `HistoricalBalance` rows are event-driven (only written when a holding actually changes via `refreshAccountBalance()` - see "Multi-currency"/"Portfolio rebalancing" above), not daily.

**Two options were weighed against real evidence, not assumption, before picking one:**

1. **A synthetic daily series** (current quantity × Yahoo Finance historical daily price) was considered and **rejected** after checking what data the app actually has: `ISIN_TO_YF_SYMBOL` (`lib/domain/analytics.ts`) is a **6-entry hand-verified map**, not a general ISIN→Yahoo-symbol resolver - even the demo seed's own PEA ETF ISINs (`IE00B4L5Y983`/`IE00B5BMR087`) aren't in it. Building real coverage would need the same one-by-one manual verification discipline the "Full sector-exposure breakdown" backlog item is *also* blocked on (see `ROADMAP.md`'s v1.16 section) - the same underlying data gap blocks both. Beyond coverage, a synthetic series would also need to assume the current quantity was held for the entire charted period, silently misrepresenting any account where a position was bought/sold/added to - a real correctness risk for a wealth-tracking app, not just a cosmetic one.
2. **The existing event-driven `HistoricalBalance` line** - accurate by construction (real recorded snapshots, no assumptions), zero new data collection, but sparse for a rarely-touched account. Confirmed directly against the dev DB before deciding: a demo PEA left untouched had **0** `HistoricalBalance` rows, Crypto **0**, a CTO edited once that session **1** - not just "coarser" than a fiat chart, often close to empty in practice.

**Chose option 2** - honest and correct beats smooth and sometimes-wrong, matching this codebase's own bar everywhere else real money is displayed. The sparse case is handled, not hidden: `BalanceHistoryChart` already had a `data.length < 2` → `t("charts.notEnoughData")` empty state (built for fiat accounts with little history) - reused as-is rather than building a second one.

- **`lib/domain/account-detail.ts`'s `chartData` needed zero changes** - `computeAccountDetail` already mapped `account.history` into `ChartPoint[]` unconditionally for every account type; only `app/accounts/[id]/page.tsx`'s render gate (`result.isFiat` → `result.isFiat || result.isInvestment`) and prop threading were new. `BalanceChartSection`/`BalanceHistoryChart` both gained an `isInvestment?: boolean` prop (default `false`, so every fiat call site is unaffected) that swaps "Solde"/"Balance" wording for "Valeur"/"Value" (new `valueEvolution`/`value`/`valueAria` keys alongside the existing `balanceEvolution`/`balance`/`balanceAria` ones) - reusing the exact same data-shape-generic `BalancePoint`/chart component rather than building a parallel one, since the only real difference is terminology, not shape or behavior. `canImportCsv` already resolves to `false` for investment accounts (`isFiat && !isSynced && !gocardlessAccountId`), so the CSV-import button correctly never appears on this chart for an investment account without any new gating.
- Positioned in the same spot the fiat balance chart already occupies (right after the account header, before the holdings table) - matches Trade Republic's own layout (the value chart leads a position's detail view, not an afterthought below it).
- Verified live against real `HistoricalBalance` rows (a CTO with 0 then 1 then 4 points, inserted directly to confirm both the empty state and the real rendered line): the sparse-data message renders correctly with only the demo seed's own data, and a 4-point real series renders a correct, correctly-labeled ("Évolution de la valeur") smooth line once enough history exists.
