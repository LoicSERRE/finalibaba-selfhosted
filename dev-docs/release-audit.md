# Pre-commit pipeline & release-boundary audit

Full text, including every per-version audit result. CLAUDE.md carries the short checklist.

## Pre-commit verification pipeline

Run this before proposing or making any commit - it exists so a commit never introduces something CI would have caught anyway (a broken build, a failing test, a new lint/audit finding), and so a SonarQube regression is caught locally before it shows up on the next scan. Order matters: cheapest/fastest checks first, so a trivial mistake (a lint error) fails in seconds instead of after a multi-minute build+test run.

1. **Working tree sanity** - `git status` (nothing unexpected staged/unstaged) and, on any branch that was just merged or rebased, `git diff --check` (flags leftover `<<<<<<<`/`=======`/`>>>>>>>` conflict markers and trailing-whitespace issues that a manual conflict resolution can silently leave behind - this is the "no conflicts" gate).
2. **Lint** - `pnpm run lint` (ESLint, includes `eslint-plugin-sonarjs`'s rules - the same static-analysis family SonarQube's own scan runs, so most Sonar code-smell findings already surface here for free).
3. **Type-check & build** - `NODE_ENV=production pnpm run build` (Next.js's build IS the type-check in this project - there's no separate `tsc --noEmit` script; `NODE_ENV=production` is required, see "Development commands" above). This is the frontend/backend "no conflicts" gate: a broken import, a type mismatch between a Server Action and the component calling it, or a Server/Client boundary violation fails here.
4. **Unit tests** - `pnpm run test:coverage` (not plain `pnpm test` - the coverage run is needed for step 6 anyway, and its `json-summary` report is the one to trust over the terminal table, see "Development commands" above).
5. Steps 2-4 are bundled as **`pnpm run verify`** - run that one command for the common case (JS/TS-only change). Add the Python steps below whenever a commit touches `sync/`:
   - `ruff check sync/` (lint)
   - `cd sync && python -m pytest` (tests). Before a SonarQube scan (step 6), generate the coverage report too - **from the repo root, not from `sync/`**: `python -m pytest sync/tests -c sync/pytest.ini --cov=sync --cov-report=xml:sync/coverage.xml`. Without that report SonarQube's Zero Coverage Sensor counts every `sync/` line as uncovered, which failed the v2.1 gate on a file that was actually at 100%; running it from inside `sync/` produces paths the scanner silently cannot resolve, which looks identical. See `.coveragerc` for the full explanation.
6. **Schema-vs-migrations drift** (only when `prisma/` changed) - `prisma migrate deploy` into an EMPTY database, then `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code`. CI's `python-test` job runs both, since it is the one job with a real Postgres. Replaying the chain from zero is the only thing that catches a migration which changed DATA where it should also have changed the SCHEMA: `20260907191649_update_fr_pfu_rates` moved the French social-levies rate to 18.6% with an `UPDATE` and never altered the column default, so `schema.prisma` said `0.186` while every fresh database said `0.172` - and `UserSettings` rows are created without naming that column, so each new self-hoster was quietly offered the old rate. Invisible on any instance that already had the row, which is why it survived several releases.
7. **SonarQube** - local/on-demand only, not wired into CI (see `sonar-project.properties`'s header comment). After step 4 has produced fresh coverage, run your local `sonar-scanner` from the repo root (it auto-detects `sonar-project.properties`, including the `sonar.javascript.lcov.reportPaths=coverage/lcov.info` it just consumed) against your SonarQube instance, and confirm the quality gate is green with **zero new issues** - not just "no new CRITICAL/BLOCKER", since `sonar-project.properties`'s `sonar.issue.ignore.multicriteria` list already documents every accepted pre-existing exception explicitly; anything new outside that list is a real regression to fix, not to suppress.
8. **Dependency audit** (only when `package.json`/`pnpm-lock.yaml` or `sync/requirements.txt` changed) - `pnpm audit --prod --audit-level=high` and, for Python, `pip-audit -r sync/requirements.txt`. Mirrors the `security`/`python-security` CI jobs; see "pnpm overrides" above before adding a new override in response to a finding here - check whether one already exists or is deliberately not applied.

This pipeline mirrors `ci.yml`'s job list on purpose (`lint` → `typecheck` → `test` → `python-lint`/`python-test` → `security`/`python-security`) plus the SonarQube gate `quality.yml` doesn't cover (SonarQube itself isn't in CI - see "CI quality gates" below) - the goal is that `git push` never surprises CI with something `pnpm run verify` (plus the conditional steps) would already have caught locally.

## Release-boundary health audit

The pipeline above catches regressions in a single diff - it says nothing about whether the codebase as a whole is still healthy, or whether the same bug class is quietly being patched downstream release after release without its root cause ever being touched. Run this broader audit **at each version boundary** - starting a new `vX.Y` (before writing its first feature) or right before tagging one, whichever fits that version's own shape - not on every commit.

**Origin**: prompted directly by a real incident, not built speculatively. `migrateDedicatedSyncToWoob`'s history-depth-loss bug (see "Migrating an existing dedicated integration to Woob" above) was the *third* release in a row (v1.11.2, v1.11.3, and that fix) patching a symptom of the exact same underlying `syncId`-matching gap in `sync/db.py`'s `upsert_account()` - three warning-UI layers were shipped before anyone asked whether the root cause itself was fixable. The first run of this audit (ahead of v1.13) found that root cause in one pass and it turned out to be a ~30-line fix, cheaper than any of the three symptom patches that preceded it.

Seven things to actually check, not just eyeball - each needs real evidence (a command run, a file read), not a guess:

1. **Layering discipline** - grep `components/` for any direct `@/lib/db/prisma` import (there should be none), **and grep `lib/` and `app/api/` for any import from `@/components/`, which is the same violation the other way round**. That second check was missing until v2.10.4 and the repo had carried two instances the whole time: `lib/domain/analytics-export.ts` and `lib/domain/accounts-page.ts` each imported the payload types they produce back out of a client component. Nothing flagged it, because the check only ever looked downhill. **A layering rule has two directions; test both.** **v2.10.6 pre-tag audit**: zero violations in both directions. The three components this version touches (`holdings-table`, `interest-rate-form`, `goal-and-passive-income`) all take their data as props; the two new Server Actions (`addInterestRateChange`, `deleteInterestRateChange`) resolve ownership from the row they were handed, never from the caller. **v2.4 pre-tag audit**: zero violations; the three new components this version adds (`interest-rate-form`, `co-owners-dialog`, `collapsible-section`) all reach data through props or Server Actions. **v2.1 pre-tag audit**: zero violations - `components/` is still clean, and this version's two new components (`configure-trade-republic-dialog.tsx`, `tr-setup-prompt.tsx`) reach the database only through Server Actions, like their Woob counterparts. **v2.0 pre-tag audit: found and fixed one real violation** - `components/layout/sidebar-wrapper.tsx` queried `portfolioGrant` directly (introduced by v2.0's own sharing work).
