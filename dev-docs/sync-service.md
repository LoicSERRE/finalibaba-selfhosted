# Sync service (Woob, Trade Republic, GoCardless bridge)

### App ↔ Sync service communication

The Next.js app calls the Python sync service via HTTP using `SYNC_SERVICE_URL=http://sync:8000` (set automatically in `docker-compose.yml`). In development, the sync service is not started - only the DB runs via `docker-compose.dev.yml`. The reverse direction (sync calling app) also exists now - see "Alerts & webhooks" below.

Every one of `lib/actions/sync.ts`'s blocking calls to the sync service (`triggerSync`, `triggerInstitutionSync`, the LCL/TR/Woob setup start/complete functions) goes through a shared `fetchSync()` helper with a 2-minute `AbortSignal.timeout()` - a real production report: none of these had any timeout, so a genuinely hung sync (no internet reaching the bank from inside the sync container, or a stuck Woob session) left the triggering button spinning forever with zero feedback, no way to tell "still working" from "will never finish". 2 minutes is generous enough for a real bank scrape/2FA round-trip (not a fast local API call) while still bounding the worst case. The UI side of this fix is in `components/settings/sync-status.tsx`'s `syncError` state and `components/settings/institution-sync-button.tsx`'s own `error` state - the "Synchroniser" click was the one path in both components with no `try`/`catch` at all (every setup step already had one), so the new timeout error would otherwise have disappeared into an unhandled rejection instead of ever reaching the user.

### Sync service - optional modules

The `sync/` service has two dedicated sync modules plus two per-institution runners:

| Module | Required credentials | Purpose |
|---|---|---|
| `sync_lcl.py` | `LCL_LOGIN`, `LCL_PASSWORD` | LCL (FR) via Woob hardcoded module |
| `sync_tr.py`'s `run()` | `TR_PHONE`, `TR_PIN` | Trade Republic via pytr, the owner's env-configured connection |
| `sync_woob.py` | `Institution.woobModule`/`woobLogin`/`woobPassword` | Generic Woob runner for any institution configured in Settings |
| `sync_tr.py`'s `run_institution()` | `Institution.trPhone`/`trPin` | Per-user Trade Republic (v2.1) - see "Per-user Trade Republic" below |

Leave credentials blank to disable a module. `sync/main.py` skips gracefully, and `app/settings/page.tsx`'s "Synchronisation automatique" section (the dedicated LCL/TR `SyncStatus` cards, distinct from any Woob-configured institution that happens to also be named "LCL") mirrors that gate: each card - and the section itself, when neither applies - only renders when `LCL_LOGIN`/`TR_PHONE` is actually set. A fresh install with zero `.env` bank credentials used to show both cards permanently stuck on "Jamais synchronisé" regardless, which read as broken and, once a user separately added a Woob-configured "LCL" institution of their own, produced two differently-behaving "LCL" surfaces on the same page. `sync/db.py` contains shared PostgreSQL helpers - do not duplicate inline.

**`infer_account_type()` (`sync/db.py`) guesses an `AccountType` from a raw bank-reported account label** - Woob has no structured "is this a savings account" field of its own, so both `sync_lcl.py` and `sync_woob.py` need this and call the same shared function (`ACCOUNT_TYPE_KEYWORDS`, a case-insensitive substring match, defaulting to `CHECKING` when nothing matches). This is itself a real instance of the "do not duplicate inline" rule stated above being violated and then fixed (v1.15.1): each script used to carry its own local copy, and they had already drifted apart (`sync_woob.py` had gained `"savings"` and the investment-account keywords, `sync_lcl.py` hadn't) before a user report - some of their own real Livret A/LDDS/PEL/CEL/Livret Jeune accounts landing in "Liquidités" instead of "Épargne" on the dashboard - traced the root cause to a missing `"lep"` keyword (a Livret d'Épargne Populaire's raw label is often just "LEP", with no "livret" substring for the older lists to catch). Consolidated into this one function both scripts import, so the two lists can't silently diverge again.

This only affects account-type classification going forward, at sync time when an `Account` row is first created - it does **not** retroactively fix an account already sitting in the database under the wrong type, since nothing re-runs `infer_account_type()` against an existing row. **`scripts/fix-account-types.sh`** is the one-off correction for that: same `.env`-sourced `docker compose exec` convention as `scripts/backup.sh`/`scripts/debug-*.sh`, dry-run by default (prints which accounts it would touch), `--apply` after typed confirmation to actually update. Deliberately scoped to `CHECKING -> SAVINGS` only, using the exact same keyword predicate as `ACCOUNT_TYPE_KEYWORDS`'s SAVINGS-mapped keys (kept in sync manually, noted in the script's own comment) - both types share the same `HistoricalBalance`-based data model (see "Data model" below), so this is a pure metadata correction with no data migration involved. Never touches `INVESTMENT`/`CRYPTO`/`LOAN`/`REAL_ESTATE`/`AUTOMOBILE`/`MEAL_VOUCHER` - those have a genuinely different data model (holdings, computed-at-runtime capital, manual values), and a blind reclassification there could silently misrepresent an account's value rather than just relabel it. There's no UI-based account-type editor yet (only account name, via `renameAccount`) - a real gap this script works around for the accounts affected by this specific bug, not a general-purpose fix.

**A bank this integration structurally cannot drive says so, instead of crashing** (v2.4.1, from issue #51). `setup_woob.py` has classified `CaptchaQuestion`/`BrowserRedirect`/`ActionNeeded` as `unsupported` since it was written; `sync_woob.py` never learned the same lesson, so those exceptions fell into its generic `except Exception` alongside genuine crashes. A user adding Amundi got a raw traceback ending in `RecaptchaV2Question` and a `SyncLog` row whose message was a truncated exception string, with no indication of whether to retry, re-enter credentials, or give up. Reproduced independently on a second Amundi account, so it is the bank rather than one person's setup.

Now a distinct `unsupported` status with a readable message, raised as `UnsupportedBankError`. Deliberately **not** `auth_required`: that status means "reconnect and it will work", which is false here and would send the user round a setup loop that cannot succeed. `checkSyncFailures` treats it as terminal and stops reminding, or a bank that can never work would notify every 24h forever - the same "nothing will ever clear this" dead end `isSourceRetired` exists for, reached from the other direction: not a source that stopped running, but one that was never able to. Settings renders it muted with the message on hover rather than red, since red invites retrying.

**On Amundi specifically, read from the module rather than guessed**: `amundi/browser.py`'s `init_login` raises the captcha unconditionally (`if not captcha_response: raise RecaptchaV2Question(...)`) before credentials are ever assembled. Nothing about the account, the sub-site (`ee`/`tc`/`ca`/`es`) or the configuration avoids it, and the only thing that fills `captcha_response` is one of Woob's three paid third-party solver modules (`anticaptcha`, `deathbycaptcha`, `twocaptcha`) - deliberately not supported here, since it means sending a user's bank login challenge to a third party, against Amundi's own terms. One useful consequence of that ordering: the password is never sent, so a failed attempt cannot count toward the three that temporarily lock an Amundi account.

**Interactive 2FA setup for any Woob-configured bank** (`sync/setup_woob.py`) - a bank added via Settings → "Configurer Woob" that requires strong authentication on first connect used to be a dead end: `sync_woob.py` only recognized the "wait and approve" family of Woob exceptions and, on catching one, told the user to run `sync_woob.py --setup <id>` - a flag that was never actually implemented. A bank whose 2FA is instead an SMS/email/app-generated **code** (`SentOTPQuestion`/`OfflineOTPQuestion`) wasn't even recognized as needing setup at all - it just fell into the generic error handler. Fixed by generalizing the same interactive start/complete pattern `setup_lcl.py`/`setup_tr.py` already use for their one hardcoded bank each, to work for any `institution_id`:

- `start_setup(institution_id)` reads credentials from the `Institution` row (not env vars - this is the generic UI-configured path, see `sync_woob.py` above) and attempts `iter_accounts`, bucketing whatever Woob raises into three UI-facing shapes - confirmed against `woob==3.7`'s actual exception taxonomy (`woob/exceptions.py`) rather than guessed:
  - `pending_approval` - `AppValidation`/`DecoupledValidation` and friends (e.g. LCL's Certicode Plus): nothing to submit, just wait and retry.
  - `code_required` - `SentOTPQuestion`/`OfflineOTPQuestion`: the exception carries `.fields` (`Value` objects whose `.id` is a **backend config key**, not an arbitrary label) and `.medium_type`/`.medium_label` (e.g. "sent by SMS to 06 12..."). The only documented way to resume is `backend.config[field.id].set(code)` then retry - confirmed against Woob's own reference CLI (`woob/tools/application/console.py`'s `bcall_error_handler`), not invented.
  - `captcha_required` - `CaptchaQuestion` (and its `RecaptchaV2Question` subclass): see "Captcha banks" below. Carries `website_key`/`website_url` so the browser can render the real widget.
  - `unsupported` - `ActionNeeded` (+ `BrowserPasswordExpired`/`AuthMethodNotImplemented`), `BrowserRedirect`: genuinely can't be driven from a web form (full OAuth-style browser redirects, an action the bank wants performed on its own site) - surfaces Woob's own message, no retry loop offered.

### Why an interactive setup was never enough (v2.6.1)

v2.5 rendered the captcha and v2.6 fixed the panel that followed it, and a real
Amundi account still could not be connected. Four defects were stacked, each
hidden by the one in front of it, and only a live account surfaced them. Worth
recording in order, because each was invisible until the previous was fixed.

**1. Woob was given no storage, so nothing survived the call.** `Woob()` with no
`storage` keeps neither cookies, nor a bank's session token, nor the 2FA
timestamp. That made an interactive setup structurally pointless for any bank
needing one: the setup authenticated, its session died with the object, and the
sync firing right after opened a fresh browser that was challenged again.
`make_woob()` now gives every path the SAME `StandardStorage`, on the
`woob_session` volume the compose file already mounted. Applied to `sync_lcl.py`
and `setup_lcl.py` too, where the same gap was invisible only because that
account did not enforce Certicode Plus.

**2. A decoupled validation was never resumed.** Woob continues an
`AppValidation` only when the `resume` config key carries a value - its own
reference CLI hardcodes exactly that. Without it `do_login` falls through to
`init_login` and restarts everything, so each "I've approved it" click began a
fresh captcha and a fresh phone prompt. `request_information` was missing for
the same reason: Woob treats `None` as "batch mode, do not trigger 2FA".

**3. A competing sync invalidated the approval.** A scheduled run firing while
the user approved opened a second session and invalidated the `mfa_id` the setup
was polling. Measured from a container log: approval at 08:39, a full sync at
08:41, and `handle_polling` still ran its whole 180-second course without ever
seeing the token. `sync/setup_locks.py` now blocks any sync on an institution
whose setup is in flight - **skipped, not failed**, so no `SyncLog` row and no
failure alert for a bank in the middle of being connected properly. Entries
expire so an abandoned setup cannot freeze a bank for good.

**4. The setup counted the accounts and threw them away.** This is the one that
kept the database empty through every other fix. `_try_connect` did
`accounts = _iter_accounts(...)` and returned `len(accounts)`, leaving a separate
sync to re-fetch them. For an MFA bank that re-fetch is impossible by design -
the Amundi module calls `check_interactive()` from `init_login` as soon as MFA is
on, *"we will not be able to stop the login before the notification is sent"* -
so the follow-up sync could only fail. `persist_accounts` (extracted from
`run()`) now writes them while the approved session is still alive, which is the
only moment they can be written at all.

**The generalisable lesson**: each fix was correct and none of them was
sufficient, because the failure was a *chain*. What finally settled it was
reading what the bank's own module does rather than reasoning about what the
flow should do - and one methodological trap is worth naming: verifying a mounted
file with `docker exec python3 -c` proves nothing, because that starts a NEW
process. `uvicorn` holds its modules in memory, so a volume edit needs a real
restart. Two "the fix does not work" rounds were actually the old code running.

**Amundi cannot ever sync unattended, and the UI now says so by shape.**
`STATE_DURATION = 10` plus the refusal to log in non-interactively means neither
the 4h cron nor a separate "Synchronize" click can refresh it: data arrives when
the human connects, and refreshing means connecting again.
`reconnectOnlyRefreshes` therefore hides the Synchronize button on a
`captcha_required` bank - it could never succeed, and its failure overwrote the
connection that had just worked, showing a warning triangle seconds after a real
success. Deliberately not applied to `auth_required`, where a later run often
does succeed. The setup also returns `synced`, so the UI stops firing the
redundant sync that caused that overwrite.

**Sync messages are now shown, not hovered.** The status was a bare icon with
`title={syncLog.message}`, invisible on mobile and unnoticed everywhere else -
reported as "no error but sync is not ok" (issue #54). The message is printed
under the row whenever the status is not `success`, which also carries the
instruction a captcha bank depends on.

**`BrowserUnavailable` was an empty failure.** La Banque Postale raised a bare
one, so the generic handler wrote a traceback and an EMPTY `SyncLog` message.
Now a `error` status (transient and retryable, unlike `unsupported`) with a
readable message even when the exception carries none, and `ScrapingBlocked` gets
its own wording.

**`ActionNeeded` no longer claims the bank is undriveable.** 35 of 95 modules can
raise it, and it means "accept a notice, complete a form" - the user does it once
and syncing resumes. It keeps the `unsupported` status (alert once rather than
nag every 24h) but says what to do.

### Holdings from the bank, not just a balance (v2.7)

72 of the 96 CapBank modules expose `CapBankWealth` and can report the actual
lines inside an account. This project asked **none** of them: `sync_woob.py`
called `iter_accounts`, stored a balance, and stopped. So every PEA, PEE,
assurance-vie and securities account arrived as a bare figure, and a real PEE
showed up typed as a current account offering an "annual interest rate" - a
field that means nothing for a fund. Reported exactly that way.

`iter_investment` now feeds `Holding` rows. Three decisions worth keeping:

**A line with no share count is stored as one unit at its valuation.** Funds
routinely omit `quantity`. Dropping the line would understate the account;
storing it this way keeps the account **total** exact, and only the per-unit
price becomes the whole line.

**A line that cannot be valued is dropped, never stored at zero.** That is the
"an absent value rendered as a legitimate zero" trap this file already names
under the v2.4 audit - a zero holding would quietly drag the account total down.

**The account retypes itself**, from `CHECKING` only. That is
`infer_account_type`'s "nothing matched" fallback, so this corrects a guess and
never overrides `SAVINGS` or a type a person chose. Holdings are a far better
signal than a label: "PEE SOPRA STERIA GROUP" matches no keyword.

`replace_holdings` builds on the existing `upsert_holding` (Trade Republic
already wrote positions through it) rather than repeating its SQL, and adds the
one thing a full sync needs: **deleting lines that disappeared**, so a sold fund
cannot linger and keep inflating the account.

**The Woob trap that cost the first attempt**: a field the bank did not report
is not `None`, it is the `NotAvailable` singleton, whose `str()` is literally
`"Not available"`. So `inv.unitprice is not None` passes and
`Decimal(str(...))` dies with `ConversionSyntax`. `iter_investment` was working
perfectly and every position was being dropped by the mapping. Every field now
goes through `empty()`, and the test fakes default to `NotAvailable` rather than
`None` so this cannot regress.

### Classifying what a bank login can fail with

`sync/woob_errors.py`. Built after **measuring** the catalogue rather than after
another bug report, and the measurement is the argument:

    BrowserIncorrectPassword   61 of 95 modules   was unclassified
    AssertionError             40                 was unclassified
    BrowserUserBanned          18                 was unclassified
    BrowserPasswordExpired     17                 was unclassified
    AuthMethodNotImplemented   16                 was unclassified

The single most likely failure of all - wrong credentials - fell through to the
generic handler, and `BrowserIncorrectPassword()` carries **no message**, so the
`SyncLog` row was empty and the UI had nothing to say. That is issue #54 reached
from its most probable direction, and it is what "just errors, I don't know why"
looked like from a real Swile attempt.

**Order is meaning, not style.** `BrowserUserBanned` subclasses
`BrowserIncorrectPassword`; `BrowserPasswordExpired` and
`AuthMethodNotImplemented` both subclass `ActionNeeded`. An except-chain gets
this wrong silently - it would tell a locked-out user to check their password,
and retrying is precisely what prolongs the lockout. A table matched top-down
makes the ordering explicit and testable, which is half the reason it exists.

`AssertionError`/`NotImplementedError` are classified too: 40 and 25 modules
raise them for a response they do not recognise, which means *the bank changed
under Woob*, not that the user did anything wrong. Saying so beats a traceback.

### reCAPTCHA v2 and v3 are different mechanisms

v2 is a checkbox a human ticks; v3 is invisible and scored from behaviour, with
nothing to click. Woob models them as separate exception classes and collapsing
them made the UI render a v2 checkbox for a v3 key, which Google answers with
"Invalid input" - a permanently broken box. Of the catalogue: 7 banks use v2, 2
use v3 (`swile`, `cmes`), 1 uses Funcaptcha (`roblox`, unsupported).

`components/settings/recaptcha-v3.tsx` loads the right script (Enterprise has
its own namespace) and calls `execute()`, so the token arrives with no
interaction. **Honest limit: this path has never run against a real v3 bank.**
The one account available to test it (Swile) fails earlier, at the login itself,
so v3 support is written and unit-tested but unproven end to end.

**Swile cannot be connected at all, and it is not this project's bug.** Its
module only does an OAuth `grant_type=password` round-trip and implements no
second factor whatsoever (zero occurrences of `TwoFactorBrowser`, OTP or
`AppValidation` in its source). Measured against the live API: a nonexistent
e-mail returns `invalid_grant`, a real account returns `server_error` - so the
account IS recognised and the server still refuses the token, the signature of
an SSO or 2FA account the module has no way to carry through.

### Auditing what every supported bank actually needs

`scripts/audit-bank-modules.py` answers, without a bank account, which
authentication mechanism each of the 96 CapBank modules requires - the modules
declare it. `sync/bank-capabilities.json` is the committed baseline; `--check`
fails on drift and runs in CI (`.github/workflows/bank-modules-audit.yml`).

It exists because every gap above was found by a user opening an issue. Its
first run showed **24 of 95 banks whose connection broke as soon as their
second factor actually fired** - not niche ones:
`lcl`, `societegenerale`, `creditmutuel`, `caissedepargne`, `banquepopulaire`,
`boursorama`, `bred`, `bp`, `n26`. The fixes above are therefore not "an Amundi
fix" but a whole-family one.

**Scheduled monthly, not only on a Woob bump**: the catalogue lives on
`updates.woob.tech` and changes independently of the pinned version, so a
`requirements.txt` trigger alone would miss most drift.

**Its honest limit, and it matters for how the numbers above are read**: it
reports what a module *can* raise, not what it *will*
for a given account. `lcl` declares a decoupled validation it does not always
enforce, which is exactly why one working LCL account proves nothing about the
next one - and the converse: this repo's own maintainer has synced LCL since
the beginning without ever hitting it, because that account does not have
Certicode Plus switched on. So "24 banks were broken" must always be read as
"broken for the accounts on which that second factor fires", never as "nobody
could use them".

### Captcha banks (Amundi)

Reported as issue #51: adding Amundi produced a raw traceback ending in `RecaptchaV2Question`. The traceback was the real defect and was fixed first (v2.4.1), by classifying captchas as `unsupported` alongside `BrowserRedirect`/`ActionNeeded` - reasoning that a captcha exists precisely to defeat automation.

**That reasoning was wrong, and it is worth recording why**, because it is the kind of wrong that sounds final. A captcha does exist to defeat automation - but the bank is refusing a *robot*, and the answer is to stop being one for one screen rather than to give up. Reading the module settled it in one look: `amundi/browser.py` raises only when `self.config["captcha_response"].get()` is empty, and posts the login normally once it is filled. Woob's exception carries `website_key`/`website_url` for exactly this purpose. The earlier conclusion came from reasoning about what a captcha is *for* instead of reading what the module actually does.

The flow reuses the OTP plumbing verbatim: `captcha_response` is just another config field id, so `setup_woob.py`'s `_pending[...]["field_ids"]` mechanism carries it and `complete_setup` needed **zero changes** - the solved token travels through the same `code` parameter an SMS code does. `components/settings/recaptcha-widget.tsx` renders Google's real checkbox; the token comes back through the existing `completeInstitutionSetup`.

- **The sync path reports a `captcha_required` `SyncLog.status` of its own** (`lib/domain/sync-status.ts`, the companion to `sync-sources.ts` for the other column), because the two existing statuses are each wrong in a *different* direction and neither can be stretched. `unsupported` would hide the Connect button on a bank that in fact works. `auth_required` gets the button right but is level-triggered by `checkSyncFailures`, so a bank the 4h cron can never satisfy would remind the user every 24h **forever** about something they already know - the same "nothing will ever clear this" dead end `isSourceRetired` was written for, reached from a third direction: not a source that stopped running, nor one that never could, but one that only ever runs by hand. The two questions get two predicates (`needsReconnection`, `alertsOnlyOnce`); `__tests__/sync-status.test.ts` pins that `captcha_required` is the only status answering yes to both, which is the entire reason it exists. `BrowserRedirect`/`ActionNeeded` keep `unsupported`, and `sync/tests/test_woob_captcha_and_unsupported.py` pins both halves.
- **The alert fires once and then goes quiet** - worth one notification, since unlike `unsupported` there is something the user can actually do, and its body says both what to do and that the automatic sync will not do it. The `SyncFailureState` row is deliberately *kept* rather than cleared: it is what suppresses every later reminder.
- **A solving service is deliberately not used.** It is the other way to fill the same field, and it means shipping someone else's bank login challenge to a third party. A human clicking a checkbox is the same mechanism without that cost.
- **The honest limit, stated in the UI rather than buried**: a solved token is single-use and expires in ~2 minutes, so this makes **on-demand sync work and can never make the 4h cron work**. Every scheduled run on such a bank lands back on `auth_required`. `woobCaptchaManualOnly` says so on screen before the user connects.
- **CSP**: `script-src` gained `https://www.google.com https://www.gstatic.com` and a new `frame-src 'self' https://www.google.com`. Proportionality checked rather than assumed: `script-src` already carries `'unsafe-inline'`, so anyone who can inject markup can already run arbitrary JS - two host entries do not raise that ceiling. `frame-src` is the one genuinely new capability, narrowed to one host, and `frame-ancestors 'none'` still refuses to let anyone frame *us*. Verified in a real browser against both policies: the old CSP blocks `api.js` outright (widget never renders, 1 violation logged), the new one renders it with zero violations.
- **Verified end to end against the real module**: `start_setup` on a real `amundi` institution returns `captcha_required` with a live key (`6LdBGWYU…`, `https://epargnant.amundi-ee.com/`), and the whole flow renders in a browser - Connect button, real Google checkbox, Confirm disabled until solved, zero CSP violations. Dummy credentials were enough to reach it, which independently confirms the captcha is raised **before** the password is sent (so a retry cannot count toward Amundi's 3-failed-attempt lockout).
- **The blocking limitation, and how nearly it was missed.** Amundi's site key **restricts its allowed domains**, so Google refuses to render it on a self-hosted origin. Measured across three origins with the same key: `localhost` renders the checkbox, `127.0.0.1` is refused, and a realistic `finalibaba.example.com` returns "Domaine non valide pour la clé de site reCAPTCHA". **Since confirmed on a real production instance at a real domain**, which is what turns this from a lab measurement into the documented behaviour: the widget renders and carries Google's own red "Domaine non valide pour la clé de site" inside it, with the explanatory line above it doing its job. So for Amundi this works **only when the app is reached at `localhost`** - which appears to be a leftover in *their* key's allow-list, not something this project can rely on. The earlier note in this file claimed the opposite, because the check scanned for the English "Invalid domain" on a page rendering in French and concluded "no errors". **A negative result from a string match is only as good as the string** - assert on a structural fact instead, which is why `domain_probe` was rewritten to look for the `.recaptcha-checkbox` element rather than for error text.
- **Shipped anyway, deliberately, with the failure explained rather than hidden** (`woobCaptchaDomainNote`): the restriction is per-bank, not universal - another Woob bank with an unrestricted key works fully - and where it cannot work the user now sees Google's own localised error plus a line saying it is the bank's restriction and not their misconfiguration. Forging the `co=` origin parameter to defeat the check (what commercial solving services effectively do) would make it work everywhere and is **deliberately not done**: it is circumventing a control Amundi configured, which is a different thing from clicking a checkbox yourself.
- **Settled on a real Amundi account (v2.5.1): Amundi's backend DOES accept a token solved from `localhost`.** This was the last open question - Google's `siteverify` reports the solving hostname, so a site that checked it would have rejected the token, and nothing short of a real account could tell. It does not check: a captcha solved at `http://localhost:3002`, reached through an SSH/port-forward tunnel to an instance whose app is bound to loopback, was accepted and the login advanced to Amundi's phone approval. So the tunnel is a complete answer for a domain-restricted key, not a half one.
- **The tunnel does not need SSH, and the port matters more than the method.** Any local listener works, because reCAPTCHA only ever looks at the hostname: `localhost` passes, `127.0.0.1` does not (measured), and the port is irrelevant. On an instance published as `127.0.0.1:<port>` for a Cloudflare Tunnel, nothing is reachable from the LAN at all, which is the usual reason this looks impossible at first.
- **`NEXTAUTH_URL` is the real prerequisite when `AUTH_ENABLED=true`, not the tunnel.** NextAuth issues `__Host-`/`__Secure-` prefixed cookies whenever it believes it is on HTTPS, so an instance whose `NEXTAUTH_URL` is `https://<public domain>` hands the browser cookies it will refuse to store over `http://localhost`, and the login silently loops with the captcha nowhere in sight. Diagnosable in one request without touching the UI: `curl -D - .../api/auth/csrf` shows the cookie prefixes. Chrome and Firefox do treat `http://localhost` as a trustworthy origin and often accept them anyway, so try before changing anything.
- **A phone approval after the captcha was fatal until v2.5.1, and it made the bank unconnectable despite the captcha working.** `complete_setup` *raised* for `pending_approval`, which is what Amundi returns once a solved token clears. The UI correctly drops a spent single-use captcha widget on any failure, so a raised approval sent the user back to the Connect button, and every retry began at a fresh captcha and a fresh phone prompt: each step worked, the sequence could never terminate. Fixed by returning the state instead of raising (`_try_connect` already keeps the session alive with empty `field_ids`, so it was always resumable) and by routing it through the same `applyResult` the start path uses. Worth remembering as a class: **a step that hands back another step is not a failure, and modelling it as one can strand a flow that is otherwise entirely working.** `sync/tests/test_woob_captcha_and_unsupported.py` now pins the whole captcha -> approval -> connected loop end to end, precisely because per-step tests all passed while the loop was broken; the test that previously asserted the raise was pinning an incident rather than an invariant (the invariant, empty `field_ids`, never changed).
- `complete_setup(institution_id, code=None)` resumes the same in-memory Woob session (`_pending`, keyed by institution id - unlike `setup_lcl.py`'s single global, several institutions could plausibly be mid-setup at once here).
- `components/settings/woob-setup-prompt.tsx` is the generic UI counterpart to `SyncStatus`'s hardcoded LCL/TR flows (that component is intentionally untouched - it's still the right place for those two specific, already-working integrations) - same two-panel shape (code input / approval-wait), rendered in the institution row only when that institution's latest `SyncLog` is `auth_required`.
- `setup_lcl.py`/`setup_tr.py`/`sync_lcl.py` are deliberately **not** touched or merged into this - they're the dedicated `.env`-configured paths (`LCL_LOGIN`/`TR_PHONE`, see "Sync service - optional modules" above) and keep working exactly as before, entirely independent of any `Institution` DB row. This is purely additive for every other institution.

  `app/settings/page.tsx`'s institution-row Woob controls (sync status icon, `InstitutionSyncButton`, `WoobSetupPrompt`, `ConfigureWoobDialog`) used to be gated behind a `DEDICATED_SYNC_INSTITUTIONS` name-based guard (`new Set(["lcl", "trade republic"])`, skipping any institution whose `name.toLowerCase()` matched) - removed after a real production bug: `Institution.name` is globally unique, and both the seeded reference row (`prisma/seed.ts`) and `AddInstitutionDialog`'s own catalog picker auto-fill this exact name when a user picks "LCL" or "Trade Republic" from the Woob module list - so a user who genuinely configured real Woob credentials on an institution literally named "LCL" had every one of these controls silently disappear, including `ConfigureWoobDialog` itself (no way to even edit or clear the config afterward via UI). The guard's only real justification - not showing Woob management UI on the env-dedicated integrations - was already handled more precisely by `inst.woobModule` being falsy on the seeded reference row; the name check added nothing but this collision.

  **Removing that guard exposed a second, costlier problem** - confirmed the hard way in production, not just reasoned through. `sync_lcl.py`/`sync_tr.py` and `sync_woob.py` write different `syncId` formats for what can be the exact same real bank account (`lcl:<id>` vs `woob:<institutionId>:<id>` - see `upsert_account`'s `WHERE "syncId" = %s` dedup lookup in `sync/db.py`), so configuring Woob credentials on an institution that also has a live `.env`-dedicated sync doesn't update the existing accounts - it silently creates a full second set (same balances, same labels, double-counted in net worth) the next time either sync runs. `dedicatedEnvNames()` in `app/settings/page.tsx` (checks `LCL_LOGIN`/`TR_PHONE` presence, mirroring the dedicated-section gate above) is passed into both `ConfigureWoobDialog` and `AddInstitutionDialog` as `hasDedicatedEnvSync`/`dedicatedEnvNames`, rendering a warning banner (not a hard block - a deliberate, supervised migration off the `.env` path is legitimate, same reasoning as the "Migrating an existing dedicated integration to Woob" note below) whenever the institution being configured matches an active dedicated source. No automatic dedup was attempted (e.g. matching by IBAN across the two `syncId` formats) - out of scope for a warning-first fix, and the two scripts' account-discovery order isn't guaranteed to expose a stable shared identifier without deeper changes to both.

  **Migrating an existing dedicated integration to Woob, if you ever do it anyway**: keep both `.env` credentials and the Woob config live only long enough to confirm the new sync works, then either clear the Woob config (`ConfigureWoobDialog` → "Supprimer la config") to stay on `.env`, or click "Migrer maintenant" in the same dialog's warning banner (`migrateDedicatedSyncToWoob` in `lib/actions/institutions.ts`) to complete the cutover - it deletes the `lcl:`/`tr:`-prefixed `Account` rows (cascades to their `Transaction`/`HistoricalBalance`/`Holding` automatically, every FK pointing at `Account` is `onDelete: Cascade`) once at least one `woob:<institutionId>:`-prefixed account already exists as proof the new sync actually produced something - refuses to run otherwise, so it can never delete the only copy of an account's history. The confirmation step shows both counts (dedicated-sync accounts vs. already-migrated Woob accounts) side by side specifically so a mismatch - Woob discovering fewer accounts than the dedicated integration ever did - is visible before confirming, not after. **This only touches the database** - it cannot edit `.env` from inside a Server Action, so the user still has to remove `LCL_LOGIN`/`LCL_PASSWORD` (or `TR_PHONE`/`TR_PIN`) themselves and restart the containers; the dialog's post-migration message repeats this. Never leave both running - every scheduled sync (every 4h) re-creates the duplicate set if the losing side's `.env` config is still there to re-trigger it.

  **Real production incident (2026-08): matching account counts is not the same as matching history depth.** A user's confirmation step showed "5 accounts vs. 5 accounts" (a clean match) and they clicked "Migrer maintenant" - but the dedicated `.env` sync's accounts held years of real `Transaction`/`HistoricalBalance` rows, while the just-configured Woob accounts had only started accumulating their own days earlier. The cascade delete erased that history permanently; it was recovered by hand from a `pg_dump` backup taken shortly before. Fixed by `getMigrationHistoryDepth` (`lib/actions/institutions.ts`) - fetches the oldest `Transaction`/`HistoricalBalance` date on each side (dedicated-sync accounts vs. Woob accounts for the same institution) - and `historyDepthLossDays`/`HISTORY_DEPTH_WARNING_DAYS` (`lib/domain/institutions.ts`, a pure function so it's unit-testable independent of Prisma) - a fixed 60-day threshold, same "named constant, not user-configurable" convention as `isLoanNearlyPaidOff`'s 5%: a few days' gap (Woob simply started syncing slightly later than the last `.env` sync ran) isn't worth alarming over, but a gap measured in months means real history is about to be destroyed. Only fetched for institutions where the migrate button would actually be offered (both a legacy and a Woob account already exist) - not on every settings page load, since it's a couple of extra queries that are pointless for every other institution. Verified live (Playwright against a seeded worst-case scenario: a legacy account with a 2024 transaction vs. a Woob account with only a 2026 one) that the warning renders with the real interpolated dates and day count, not just that the code compiles.

**The "Configurer Woob" module picker lists real banks, not a hardcoded 17-entry guess.** `GET /woob/modules` (`sync/main.py`) calls `Woob().repositories.get_all_modules_info()` and filters to modules with `CapBank` in their capabilities - ~96 real banks/brokers, fetched from Woob's own repository index. Doesn't force a network refresh itself: `sync/entrypoint.sh` already runs `woob config update` on every container start, so the local index this reads is kept fresh without adding a round-trip to every dialog open. `getWoobBankModules()` (`lib/actions/sync.ts`) fetches this with a 1h Next.js cache (`next: { revalidate: 3600 }`, same convention as the Yahoo Finance fetches in `lib/services/exchange-rate.ts`) and falls back to a small fixed list of major French banks if the sync service can't be reached (e.g. local dev, where only the DB container runs - see "Development commands" above) - so the dialog still works somewhere, just without the full catalog. "Autre" (custom module name) stays as the escape hatch for anything not tagged `CapBank`, or genuinely absent from Woob's catalog entirely (confirmed for Revolut specifically - searched the full module index, no match, not a gap in this list - and re-verified 2026-09-12, along with the index's real size, which is **294 modules** rather than the ~1400 this note claimed for over a year; the 96 `CapBank` figure the bank audit reports is the one that was always right). Same check run again later for the ROADMAP's "more broker integrations" wishlist: Degiro, Boursorama, Binance, and Kraken all carry `CapBank` and are already reachable through this same picker today, no new code needed - only Interactive Brokers came back with no module match, confirmed the same way as Revolut (see `ROADMAP.md`'s v1.12 section). This replaced `sync_woob.py`'s own `--list` CLI flag, which shelled out to `woob config -l` - never valid syntax (the real subcommand is `woob config modules`) - removed rather than fixed, since nothing needs a CLI listing path once the dialog fetches this itself.

`getWoobBankModules()`'s result is passed as a `modules` prop into **both** bank pickers that need it - `ConfigureWoobDialog` (editing an existing institution's Woob config) and `AddInstitutionDialog` (Settings → "Ajouter une institution", the very first bank picker a new self-hosted user sees). Real regression caught in production testing: `AddInstitutionDialog` originally carried its own copy-pasted `WOOB_MODULES` constant (the same old hardcoded 17-bank list) that never got wired to the live catalog when `ConfigureWoobDialog` was switched over - so a brand-new install with zero institutions configured yet only ever saw the short list, in the one dialog that matters most for a first-time setup. Fixed by deleting that dialog's own copy and passing the same `woobModules` prop `app/settings/page.tsx` already fetches once per render - if a third bank-picker call site is ever added, wire it to the same prop rather than reintroducing a local copy.

**The Trade Republic cash account cannot be reconciled against its own transactions, and that is by construction rather than a defect.** Every timeline event is written to the one `CHECKING`-typed "Compte espèces" account, including the ones that belong to other envelopes: on a real instance its 873 transactions sum to **-6 723,42 EUR** against a reported balance of **511,80 EUR**, and 43 of those rows are PEA purchases totalling -16 755,15 EUR that never left that account, while the CTO, PEA and Crypto accounts carry zero transactions each. The balance itself is authoritative - it comes straight from TR - so net worth is unaffected, and budget totals stopped being affected once `isSecuritiesMovement` excluded trades. `scripts/check-balance-reconciliation.sh` is therefore meaningful for a bank account and NOT for this one; do not chase the gap.

**Two events 46 milliseconds apart are one movement; two nine hours apart are two.** Worth writing down because it is the only usable test, and reasoning from the label alone gets it wrong in both directions. Measured across a whole real database, the same-day/same-amount/same-label pairs were: one at 0.046s (Trade Republic emitting two events for a single deposit, the deposit-side twin of the `Kauforder`+`PEA` pair v2.9.4 fixed), and four at 2h, 2h, 9h and 11h - a ferry taken there and back, two rounds at a catering stand, and two genuine transfers. An earlier pass had flagged the 9-hour pair as a probable duplicate on nothing more than its identical label. The near-duplicate window only ever prevents a new insertion, so a pre-fix pair like the 46ms one stays until somebody removes it by hand.

**Trade Republic transaction history**: `sync_tr.py` originally only synced positions and an aggregate cash balance (via `record_balance`) - unlike LCL/Woob, it never wrote individual `Transaction` rows, so the TR cash account had no labels for budget categorization or recurring-transaction detection, only a balance that moved with no explanation. Fixed by fetching TR's own activity-feed API (`timelineTransactions` + `timelineActivityLog`, both cursor-paginated, newest-first - pytr's own `Timeline` class fetches and merges both the same way, since between them they cover everything money-related: card payments, transfers, trades, dividends, interest) and upserting each into `Transaction` via the same `upsert_transaction()` helper LCL/Woob already use, so budgets/recurring-detection work identically for TR's cash account. Deliberately **not filtered to "spending" only** - trades/dividends/interest are imported too, exactly mirroring the real account activity (same reasoning a bank CSV import would show a transfer to a broker as a line item) - the user categorizes what's relevant via the existing budgets UI. `_timeline_item_to_transaction()` builds the label from `title`/`subtitle` (e.g. "Amazon - Kartenzahlung"), skips cancelled items and items with no monetary amount (informational-only timeline entries), and `_fetch_timeline_feed()` stops paginating a feed as soon as an entire page is already-known (`syncId` already in DB) - since the feed is strictly newest-first, everything further back is guaranteed already synced, which is what keeps every sync after the first fast. The very first sync has no known ids, so it paginates the full available history (deliberate - a "recent window only" default would have missed a lot of a long-time user's spending history for a feature specifically meant to make budget tracking finally work for TR).

### Per-user Trade Republic

`v2.1`'s headline item. v2.0 gave every user their own portfolio but left the bank credentials behind - `TR_PHONE`/`TR_PIN` are `.env` values, one per instance, so only the owner could sync Trade Republic and (Woob having no TR module) nobody else could sync it at all. That constraint is documented under "Multi-user architecture" above; this removes it. `Institution` gained `trPhone`/`trPin`, the exact per-institution counterpart to `woobLogin`/`woobPassword`, and `trPin` is plaintext for the same reason `woobPassword` is.

**`Account.syncId` is globally unique, so the shape of these strings is the whole feature.** `sync_tr.py` wrote fixed ids - `tr:cash`, `tr:cto`, `tr:pea`, `tr:crypto` - which are per-*kind*, not per-*user*: two people each with a TR cash account collide on the first insert and the second silently overwrites the first. The per-user path now writes `tr:<institutionId>:<suffix>`, mirroring `woob:<institutionId>:<nativeId>`, while `run()` keeps writing the legacy two-segment id so existing installs are untouched - the same coexistence `lcl:` and `woob:<id>:` already have. `lib/domain/sync-ids.ts` is the single place that shape is built and parsed (`buildTrSyncId`/`parseTrSuffix`/`isTrCashAccount`/`isLegacyEnvSyncId`), with `sync/db.py`'s `_is_trade_republic_sync_id` as its Python mirror; `__tests__/sync-ids.test.ts` pins every case. Two call sites had to stop comparing against the literal `"tr:cash"`: `lib/domain/analytics.ts` (TR's own cash interest rate, which would have silently produced an understated passive-income figure for per-user accounts - no error, just a wrong number) and `migrateDedicatedSyncToWoob`'s legacy-account set, where a per-user TR account being misread as legacy would have offered it up for migration and then cascade-deleted its whole history.

**Namespacing the ids alone did not fix the collision, and only a real database showed it.** With `sync_tr.py` correctly writing `tr:<institutionId>:cash`, a two-user test still produced one shared row. The cause was `upsert_account`'s native-id fallback in `sync/db.py` - the `LIKE '%:<native_id>'` cross-source lookup added after the v1.11 LCL/Woob duplicate-account incident, which matches on the trailing colon segment. That segment is a unique bank-side account id for Woob, which is exactly what makes the fallback correct there, and an account *kind* for Trade Republic, shared by every user on the instance. So the fallback matched two different people's accounts as the same one, with full confidence. Fixed by exempting TR ids from that fallback specifically (`_is_trade_republic_sync_id`), after re-verifying the LCL/Woob dedup it exists for still works. Worth remembering as a class: both writes were individually correct and the bug lived in a third function that read them back, so no unit test on either writer would have found it.

**Session isolation needed no process or working-directory tricks.** Checked against the exact commit `requirements.txt` pins, not a local install: `TradeRepublicApi.__init__` takes a `cookies_file`, and omitting it defaults to `cookies.<phone_no>.txt` rather than one fixed file - so two users never share a session even by accident. `tr_cookies_path()` passes it explicitly anyway (`~/.pytr/cookies.inst-<sanitised id>.txt`) so the file a given institution owns is deterministic and `_drop_session_file()` can delete exactly one.

**Everything else follows patterns already here.** `run_institution(institution_id)` reads credentials from the `Institution` row and reuses `_fetch_and_write_once()` unchanged via a `scope_institution_id` parameter - the batch `run()` is byte-identical to before the split, which the existing `test_sync_tr.py` suite proves. `sync/setup_tr_institution.py` is modelled on `setup_woob.py` (pending state keyed by institution id, not a module-level global, since several family members can plausibly be mid-setup at once) but is much smaller: TR has exactly one second factor, a code pushed to its app, so there is no equivalent of Woob's approval-only/code/unsupported split - just `start_setup` → `complete_setup`. `sync/main.py`'s `_institution_provider()` dispatches the three existing `/sync/institution/{id}/...` routes on whichever credential set is populated, and `_run_all_tr_institutions()` joins the 4h cron.

**The backend is never something the user picks.** Trade Republic is one entry in the same searchable bank list as every Woob bank (`lib/domain/sync-providers.ts`'s `bankPickerEntries`, consumed by `AddInstitutionDialog` and `ConfigureWoobDialog`), and choosing it swaps the credential fields to phone/PIN. `TRADE_REPUBLIC_MODULE` is an underscore-wrapped sentinel so it cannot collide with a real Woob module name, which are plain lowercase identifiers; a Woob module labelled "Trade Republic" would be dropped in favour of the native path, which is a guard against a future catalogue change rather than something that fires today.

This replaced the first cut, a standalone "Configurer Trade Republic" button on every institution row, which the user rejected on sight and for the right reason: it appeared next to institutions that were not Trade Republic and could not become it, and it turned adding an account into "create something generic, then attach TR to it" rather than "pick your bank". One `ConfigureWoobDialog` now covers every backend (its name is historical - see its own header comment).

**One provider per institution, enforced where the choice is made.** `setWoobConfig` and `setTradeRepublicConfig` (`lib/actions/institutions.ts`) each null out the other's fields, and `createInstitution` picks exactly one from its form payload. Without that an institution could hold both, and which backend ran would depend on the order of two `if`s in `_institution_provider()` rather than on anything the user picked - a silent, order-dependent outcome. `__tests__/institutions-actions.test.ts` asserts every one of those write shapes. The status icon, `InstitutionSyncButton` and setup prompt are shared between the two paths - only the `SyncLog` key (`tr:<id>` vs `woob:<id>`) and the prompt component differ.

**`createInstitution` attaches to a credential-less row of the same name rather than failing.** `Institution.name` is unique per user and `prisma/seed.ts` ships reference rows for the common banks - including one literally named "Trade Republic" - so on a seeded install, the documented default, picking that entry is a name collision. It used to throw, and `AddInstitutionDialog` had no `try`/`catch` at all, so the dialog just sat there as if the button had not been clicked. Found by driving the real flow in a browser, not by reading the code: the unit tests mocked the create and the type-checker had nothing to say. An institution that already syncs is refused with a real message instead, since silently repointing a working connection is the one outcome nobody could have meant.

**`TradeRepublicSetupPrompt` is its own component rather than a branch inside `WoobSetupPrompt`** for the same reason: none of Woob's three outcome families apply. What TR has and Woob does not is an expiry - it reports how long the pushed code stays valid - so this one shows a live countdown and swaps Confirm for a "new code" button once it hits zero, instead of letting the user watch a valid-looking code get rejected with no explanation.

**It renders as soon as the institution is configured, not only on `auth_required`** (fixed in v2.1.1). Copying `WoobSetupPrompt`'s gate was wrong for Trade Republic: it *always* needs its pushed-code ceremony before any sync can work, so a freshly configured institution has no `SyncLog` at all and the Connect button was hidden exactly when it was needed. The only way to reveal it was to click "Synchroniser", read the failure, and let that write an `auth_required` row - which is why a user reported being unable to connect a Trade Republic account through the UI at all. The gate is deliberately *not* relaxed for Woob, where a first sync can legitimately succeed from login and password alone.

**Migrating off `TR_PHONE` onto per-user Trade Republic** goes through the same `migrateDedicatedSyncToWoob` flow as LCL, which needed two corrections to be safe for it. Its destination check counted only `woob:<id>:` accounts, so someone moving to their own Trade Republic credentials could never satisfy it and the migration refused forever; it now accepts either backend (`perUserAccountFilter`). More seriously, it selected the accounts to **delete** with `startsWith: "tr:"` - which also matches `tr:<institutionId>:`, so it would have deleted the accounts the migration had just created, the same history loss the v1.11 LCL incident produced. Trade Republic's legacy accounts are now matched by exact id (`legacyTrSyncIds()`), never by prefix; LCL keeps its prefix because nothing else writes `lcl:`. The existing history-depth warning applies unchanged.

**`sync/` did need code changes after all, and missing that cost a release.** v2.0's note that it needs *zero* was true then: only the owner could sync, so `Account.userId`/`SyncLog.userId` taking their DB-level default of the owner was always right. v2.1 made it false and the note was carried forward unchanged. A member who connected their own Trade Republic got accounts owned by the **admin**: Settings showed "4 comptes" against their institution, because `_count.accounts` is unfiltered, and every other page showed nothing, because they all scope to `baseAccountIds(viewer)`. Their `SyncLog` rows landed on the owner too, so `getSyncStatus()` never showed them a status icon.

`upsert_account` and `write_sync_log` now set `userId` explicitly, from the institution's own owner (`institution_owner_id`); `write_sync_log` derives it from the source string (`woob:<id>`/`tr:<id>` name an institution, the bare `lcl`/`trade_republic` ones are the owner's), so all ~10 existing call sites became correct without being touched. `upsert_account` also **realigns an existing row** whose `userId` has drifted from its institution's owner, so an instance already holding stranded accounts repairs itself on the next sync rather than needing a script. `get_institution_id` gained a user scope for the same reason: `Institution` is unique per `(userId, name)`, so a member owning one called "Trade Republic" is legal, and an unscoped name lookup let the owner's env sync write into it.

`sync/tests/test_db_ownership.py` pins all of it **against a real PostgreSQL database**, and CI's `python-test` job now runs a Postgres service and applies the schema with `prisma migrate deploy` so it actually executes there. That is not gold-plating: the defect was an *absent column* silently taking a default, which no mock can express - there is no wrong value to assert on. The tests skip when `DATABASE_URL` is unset, so a plain local `pytest` stays offline.

**Moving off `TR_PHONE` keeps every account and its history - `adoptDedicatedTrAccounts`, not the migrate button.** `migrateDedicatedSyncToWoob` *deletes* the legacy accounts once replacements exist, which for Trade Republic means discarding years of transactions and balances to restart from whatever the API still serves. That is the shape that cost a real user their LCL history in v1.11, and the history-depth warning only announces it.

Nothing needs deleting. The rows are already right; only the string saying which sync owns them is wrong. `tr:cash` becomes `tr:<institutionId>:cash` with an `UPDATE`, the `Account` row is otherwise untouched, and every `Transaction`/`HistoricalBalance`/`Holding` hanging off it stays put. Verified against a real database: same account ids before and after, transactions and balances still attached.

It **refuses while `TR_PHONE` is set**, and that ordering guard is the feature rather than caution: the env sync resolves its accounts by those same legacy ids, so running between the rename and the `.env` edit would simply recreate `tr:cash` - the duplicate set the whole operation exists to avoid. The order is therefore: configure Trade Republic in Settings, remove `TR_PHONE`/`TR_PIN` and restart, take over the accounts, then connect and sync. An account whose per-user id already exists is skipped rather than collided onto `syncId`'s unique constraint - a per-user sync has already made its own copy, and merging two accounts on a guess is not this action's call.

**When every id is already taken it says so rather than reporting "0 adopted".** That is the state of anyone who synced before removing `TR_PHONE`: two full sets side by side, 8 accounts where there should be 4, and a cheerful zero that reads as success. Reported exactly that way from a real instance - "c'est exactement ce que je craignais et c'est arrivé" - and it is a documentation failure, not a user error: the safe ordering was in the release notes rather than enforced anywhere the user was looking. `scripts/fix-duplicate-tr-accounts.sh` is the recovery, and the error message names it. It measures both copies of each account kind (oldest transaction, oldest balance, row counts), **moves everything the doomed copy holds and the survivor does not onto the survivor**, deletes the redundant copy, renames the survivor onto the per-user id, and does all of it in one transaction so a half-applied state cannot become a second set of duplicates.

The move is the part that was nearly missed, and the real instance's dry run is what surfaced it: the per-user copy held **148 transactions the legacy one did not**. `Transaction.syncId` is globally unique and Trade Republic ids are not namespaced per institution, so a transaction sitting on the second copy is one the first never had - the second sync could not have inserted it otherwise. Deleting that copy would have destroyed them outright, recoverable only if a later sync re-fetched them, which is a bet on how far TR's timeline still reaches. Re-pointing them cannot collide, for exactly the same uniqueness reason. `HistoricalBalance` rows are worse still: point-in-time records nothing recomputes, so a deleted one is gone. Only those newer than the survivor's own newest move, which is the gap between the two copies and cannot double up a day. Rehearsed against the reported numbers: 708 + 148 = 856 transactions on the survivor, nothing lost. Dry-run by default. Two copies reaching equally far back are left alone and reported - that is a judgement call, not something to guess; two *empty* copies resolve to the per-user one, since nothing can be lost either way. Rehearsed end to end against a real database seeded with the reported 8-account state.

Offered only for Trade Republic, whose four legacy ids map one-to-one onto the per-user shape. LCL has no per-user path of its own, and Woob's native account ids are not derivable from `lcl:<nativeId>`, so that route keeps the delete-and-resync migration.

**One Trade Republic account cannot be connected twice on the same instance.** Trade Republic allows a single active web session per account, so configuring the *same* phone number both in `.env` and on an institution makes the two log each other out: whichever synced last invalidates the other's session, and the loser fails with an auth error on its next run. The cookie files are already isolated (`cookies.<phone>.txt` vs `cookies.inst-<id>.txt`), so this is Trade Republic's own constraint, not something session handling here can route around. `ConfigureWoobDialog`'s `dedicatedEnvWarning` covers it, and the answer is to pick one path - remove `TR_PHONE`/`TR_PIN` and use the UI, or the reverse.

**A thrown Server Action error is invisible in production**, which cost a release's worth of debugging, and is the single most repeated defect of this whole cycle. It has now been fixed in `sync.ts`, `totp.ts`, `users.ts`'s `changeOwnPassword`, `sharing.ts`, `institutions.ts` and `app-lock.ts` - every flow a user was actually reported hitting. **The rest of `lib/actions/*` still throws** (roughly 60 sites, mostly form validation the UI already prevents): converting them wholesale would touch 27 files and every calling component for cases nobody has hit, so they are left until one is. When converting another, follow the shape used here - a stable key the caller translates, never a sentence - and leave authorization guards throwing, since a caller reaching for someone else's row is not an expected error and must not get a readable explanation. Next replaces it with an opaque digest (React error #441 client-side), so every carefully-worded message in `lib/actions/sync.ts` reached the user in dev and *nothing* in production - a real report was "POST /settings 500" with no explanation anywhere. Next's own guidance (`node_modules/next/dist/docs/01-app/01-getting-started/10-error-handling.md`: "avoid using try/catch blocks and throw errors. Instead, model expected errors as return values") is now followed by `triggerInstitutionSync`/`startInstitutionSetup`/`completeInstitutionSetup`, which return `{ ok: false, error }` (or `status: "failed"`) instead. **Authorization failures still throw** - `assertOwnsInstitution` rejecting someone driving another user's institution is not an expected error and must not come back with a readable explanation. Worth applying to any other action whose message is meant for a human.

**The PWA manifest is a Route Handler at `app/site.webmanifest/route.ts`, not the `app/manifest.ts` convention**, and `app/layout.tsx` renders its `<link>` by hand with `crossOrigin="use-credentials"`. A manifest is fetched *without credentials* by default, so behind an authenticating reverse proxy - Cloudflare Access, Authelia, oauth2-proxy, all recommended in the README - it arrives with no session cookie, gets redirected to the proxy's login host, and the browser refuses the cross-origin result under `default-src 'self'`. Reported exactly that way from a real instance. Next's `metadata.manifest` only accepts a URL and its file convention auto-links a tag that cannot carry `crossorigin`; `manifest: null` does **not** suppress it either (verified - two link tags came out), which is why the route had to move off the convention entirely. `proxy.ts`'s matcher exemption moved with it (`site\.webmanifest$`), or the fetch would redirect to `/login` instead - the same feature broken a different way.

**Deliberately unchanged**: `setup_tr.py`, `sync_tr.py`'s `run()`, and the whole `TR_PHONE`/`TR_PIN` env path, exactly as `setup_lcl.py` was left alone when `setup_woob.py` generalised the Woob path in v1.12. `sync_tr_realtime.py` also still listens only for the env-configured connection - a per-institution real-time listener would mean one persistent websocket per user, which is a real scoping decision rather than a line of plumbing, and is not part of this release. **Corrected in v2.3, after that scoping decision turned out to have a cost nobody priced**: see "Per-user real-time listeners" below.

### Trade Republic real-time tracking

`v1.17`'s headline item - scoped live during the v1.16.1 retrospective, not assumed: checked pytr's actual pinned source (`requirements.txt`'s exact git commit, fetched and read directly), GoCardless's actual docs, and Powens' actual sync cadence before committing to anything. The finding: true instant "just spent 5€" notifications only turn out to be achievable for Trade Republic, because its own API is genuinely websocket/push-capable (`sync_tr.py` already talks to it over a websocket, it just opens the connection, does one request/response round-trip per topic, and closes, throwing that persistent-connection capability away every 4 hours) - LCL/other Woob-scraped banks and GoCardless-synced ones have no equivalent, PSD2 aggregation being batch/rate-limited on the bank's own side, not something this app's own engineering effort can route around. See `ROADMAP.md`'s v1.17 section for the full scoping writeup and the backlog items this same research corrected (GoCardless webhooks downgraded - the webhook docs findable are for its Payments product, not Bank Account Data).

**The goal is not a push notification** - Trade Republic's own app already sends one per purchase, a second one from Finalibaba would be redundant (confirmed directly with the user). The goal is keeping Finalibaba's *own* displayed data current, so opening the dashboard/account page never shows data up to 4h stale, and - since this app has no existing live-refresh mechanism anywhere (`AutoSync` triggers once per page load, nothing polls or pushes into an already-open tab) - an *already-open* tab updates live too, without a manual reload.

**Backend: one new long-lived `asyncio.create_task` in the existing `sync` container - no new Docker service, no new dependency.** `sync/main.py` runs a single uvicorn worker (no `--workers`), so there's no per-worker duplication risk; its existing `lifespan` context manager is the natural startup/shutdown hook for a task that must live for the process's whole lifetime - a genuinely new pattern for this codebase (every other "background work" here is a bounded `ThreadPoolExecutor` job). Gated on `TR_REALTIME_ENABLED` - opt-in, off by default, since this is the first persistent outbound connection this container ever holds open, the same "new/novel capability = opt-in" treatment every other new alert/notification category in this codebase already gets. **It used to also require `TR_PHONE`, which was a real regression as soon as v2.1 shipped** - see "Per-user real-time listeners" below.

- `sync_tr.py` was split to make this possible without duplicating logic: `_fetch_and_write_once(api, cur, *, institution_id, sec_accounts, has_crypto, cash_account_id, known_tx_ids, source="trade_republic")` is the extracted fetch-from-TR-and-write-to-DB cycle (unchanged behavior - the exact same code that used to be inline in `run()`), now callable repeatedly on the same open `api` connection. `run()` itself becomes a thin wrapper: connect, call it once, close - byte-identical behavior to before the split, verified by the full existing `test_sync_tr.py` suite passing unchanged.
- `sync_tr_realtime.py` (new) - `listen_forever()` is the reconnect-with-backoff wrapper (pytr has **no built-in keepalive or auto-reconnect**, confirmed against its own pinned source - `_recv_subscription()` can be awaited repeatedly on the same subscription for successive pushes with no need to resubscribe, but the caller owns reconnection entirely). `_run_one_session()` connects once (same cookie-based `resume_websession()` path `run()` already uses), subscribes to `neonPortfolio`/`cash`(/`cryptoPortfolio` if enabled) - the topics confirmed push-capable, **not** `timelineTransactions` itself, which `sync_tr.py` only ever uses as a one-shot paginated fetch and isn't confirmed to push - then loops `_fetch_and_write_once()` on every push from any of them, treating the push as a "something happened, go re-derive the real delta" trigger rather than trying to diff the pushed payload directly. A real auth error (`_is_auth_error()`) stops the listener (no point retrying against an invalid session) and writes to `SyncLog` under a **separate source, `"trade_republic_realtime"`** - deliberately not sharing the batch cron's own `"trade_republic"` identity, so the listener's own reconnect/failure cycles can't confuse `checkSyncFailures()`'s `SyncFailureState` dedup for the cron path. The existing 90-min HTTP keepalive job (a different concern - server-side session TTL, not the websocket's own liveness) keeps running completely unchanged alongside this.
- After every successful real-time write, the listener POSTs to `/api/realtime/notify` (see below), then `/api/transactions/auto-categorize` and `/api/alerts/check` - the same bearer-token pattern `_auto_categorize()`/`_check_alerts()` in `main.py` already use for the cron path - so a live-detected transaction gets categorized and can trigger a custom alert rule immediately, not up to 4h later.
- Deliberately **not** bundled into this pass: migrating off `pytr`'s Playwright-based WAF bypass to the community `tr-api` successor (ECDSA device-pairing auth, no browser automation) - a real, separate risk noted during scoping (pytr's WAF bypass is reportedly getting rate-limited more often as of mid-2026) but swapping the client would be a materially bigger, riskier change that could destabilize the *already-working* batch sync too. Worth its own follow-up look later.

**Frontend: Server-Sent Events, not WebSocket** - the data only ever flows server→browser ("something changed, go re-fetch"), never the other direction, which is exactly SSE's shape. Confirmed against Next.js 16's own current docs (`node_modules/next/dist/docs/01-app/02-guides/streaming.md`) that a Route Handler returning a `ReadableStream` with `Content-Type: text/event-stream` is an explicitly documented, supported pattern - this codebase already streams a `ReadableStream` response elsewhere (`app/api/backup/route.ts`'s `GET`). The browser's native `EventSource` reconnects on its own after a dropped connection - no client-side reconnect logic to write, unlike the Python listener's own websocket which needs it built by hand.

- **The SSE payload is a bare signal, not real data.** Pushing actual computed dashboard values over SSE would mean duplicating `computeDashboard()`/`computeAnalytics()`'s entire server-rendering pipeline a second time for a "live" path. Instead the signal just tells the open tab to call `router.refresh()` (Next.js's own mechanism to re-run the *current route's* Server Components against the DB's current state) - 100% reuse of the existing render pipeline, zero new data-shape to maintain, and it naturally scopes itself correctly (the dashboard refreshes net worth, an open account page refreshes its own transactions) with no cross-page coordination code.
- `lib/services/realtime-bus.ts` is a module-level singleton (a plain `Set` of subscriber callbacks, not a full `EventEmitter`) fanning the signal out to every open SSE connection - single-process-only by design, correct for this app's single-container/single-user deployment model, the same accepted-scope precedent `sync/setup_tr.py`'s own in-memory `_pending` global already sets. A ~2s in-process debounce coalesces bursts (cash and portfolio both changing from the same trade) into one broadcast.
- `app/api/realtime/stream/route.ts` (browser-facing, `dynamic = "force-dynamic"`) subscribes to the bus for the connection's lifetime and sends a `: heartbeat` comment line every 20s to survive a reverse proxy's own idle timeout - comment lines are ignored by `EventSource`'s `message` dispatch, so they never trigger a spurious refresh. **Goes through the normal NextAuth session gate** (not in `proxy.ts`'s no-auth matcher) since it's opened directly by the browser, unlike every other sync↔app call in this codebase.
- **Real bug found and fixed during live verification**: the very first version enqueued nothing until either a real signal or the first 20s heartbeat - confirmed with a raw TCP socket probe (curl's own buffering under `-v` was misleading) that the underlying HTTP response doesn't flush *any* bytes, including headers, until the first `controller.enqueue()` call, so `EventSource`'s `onopen` silently didn't fire for up to a full heartbeat interval on a fresh connection. Fixed by enqueueing an immediate `: connected` comment line as the very first thing in the stream's `start()` callback - confirmed after the fix that time-to-first-byte drops to ~5ms.
- `app/api/realtime/notify/route.ts` (server-to-server, called by the Python listener) uses the same inline `Authorization: Bearer <NEXTAUTH_SECRET>` check `/api/alerts/check` already has - not `lib/services/api-auth.ts`'s `ApiKey` model, a different trust boundary. Added to `proxy.ts`'s no-auth matcher as `api/realtime/notify` specifically (not a bare `api/realtime` prefix, which would have accidentally also exempted `/stream`).
- `components/layout/realtime-refresh.tsx` (new, mounted once in `app/layout.tsx` alongside `AutoSync`/`ServiceWorkerRegistration`/`OfflineBanner`) opens the `EventSource` and calls `router.refresh()` on every message. Mounted unconditionally, including on `/shared/[token]` - deliberate, not an oversight: it's harmless there (no sync is ever triggered, only a re-render of already-computed data), and the same SSE plumbing stays reusable for a future real-time trigger beyond Trade Republic, not a single-purpose pipe.

### The real-time listener never actually worked (v1.17 to v2.4.1)

Found in production on v2.4.1, and the honest summary is that **real-time tracking connected, said so, and processed nothing, for four releases.**

The receive loop ran `api._recv_subscription()` concurrently, one task per subscribed topic. Every one of those calls `recv()`, which calls `ws.recv()` on the *same* websocket, and the `websockets` library forbids concurrent reads on one connection. So the very first iteration raised `ConcurrencyError`, `listen_forever` caught it as a transient disconnect, backed off, reconnected, and died again. Forever. With two subscriptions minimum (`neonPortfolio` + `cash`), there was no configuration in which it worked.

**Why it survived four releases** is the part worth keeping. `log.info("connected, listening on %s")` fires immediately after subscribing and before the loop, so the logs read exactly like a healthy listener. The failure then appears as a reconnect warning, which is indistinguishable from an ordinary network blip. And `__tests__`-side, `test_sync_tr_realtime.py` faked `_run_one_session` wholesale to test `listen_forever`'s retry logic - so the one function containing the bug was the one function no test ever ran. v2.3's fix (starting a listener per connection) made it *start* for more people without ever making it *work*, and the `/realtime/status` indicator added in the same release reports whether the task is alive, which it is: it is alive and failing.

**The fix is smaller than the bug.** `api.recv()` is already the multiplexer - it owns the socket, dispatches by subscription id, and returns on both the initial answer (`"A"`) and every subsequent delta (`"D"`), deltas being exactly the change pushes this feature exists for. One `await api.recv()` per iteration replaces the whole concurrent-task dance; which topic moved is irrelevant, since any push means "go re-derive the real delta from the API". The initial answers (one per subscription) are drained before the loop, so connecting is not mistaken for a change - without that, every reconnect fired three full Trade Republic fetches back to back.

`test_sync_tr_realtime.py` now drives the real loop against a fake api that enforces the same no-concurrent-recv rule the websocket does. Four of those tests fail against the old loop, which is the check that was missing.

**A second, independent way it was dead, found the moment the first was fixed (v2.4.3).** With the receive loop corrected, the listener reached a real Trade Republic answer for the first time, and that answer was `BAD_SUBSCRIPTION_TYPE: Unknown topic type: neonPortfolio.31`. Two of the three topics it subscribed to - `neonPortfolio` and `cryptoPortfolio` - are not topics at all: neither appears anywhere in pytr's own vocabulary, and at the protocol version pytr connects with (`connect_id = 31`) TR rejects them outright. Only `cash` was ever real.

The rejection arrives **asynchronously**, not from `subscribe()`: TR replies on the socket with an error frame that pytr raises as `TradeRepublicError`. That propagated out of the session, so one bad topic killed the whole listener and it reconnected forever. `sync_tr.py` hits the same rejection on its own `neonPortfolio` fetch but wraps it in a try/except and falls back to ticker prices, which is why the 4h sync kept working and hid this.

Three changes, and the middle one is the durable part: the topic list is now `cash` plus `compactPortfolioByType` per securities account, the pair sync_tr.py's own working fetch path proves TR accepts; `_subscribe_surviving` keeps whichever topics TR actually answers and merely logs the rest, so a future vocabulary change costs coverage rather than the feature; and `MIN_FETCH_INTERVAL_S` puts a 30s floor between fetch cycles, since nothing previously stopped a topic that pushes on every price tick from turning this into a fetch storm.

**The reason to write it down**: TR has now demonstrably changed its topic vocabulary underneath this project. A fixed list of topic strings was a latent bug from the day it was written, and the previous comment in this file claimed those topics were "confirmed against pytr's own pinned source" when two of them appear in that source nowhere. Confirm by grepping, not by recalling.

**The generalisable lesson**, and it is the same one this file keeps recording: *a log line that says "connected" is not evidence of working*. The listener's own success signal was emitted before the code that fails. When something long-running claims to be healthy, the assertion worth writing is that it did its job at least once, not that it started.

### Per-user real-time listeners

`v2.3`. v2.1 deliberately left `sync_tr_realtime.py` on the `.env` connection, reasoning that one websocket per user was a scoping decision rather than plumbing. That was defensible; what was not priced is that the same release invited users to move **off** `.env` - and `main.py` started the listener only `if TR_PHONE and TR_REALTIME_ENABLED`. So completing the migration silently ended real-time updates: no error, no log line, no indicator. The portfolio simply went back to moving once every four hours, which is what a user reported as "ça ne bouge pas".

Worth naming as a class, because it is not the same as the recurring-bug patterns already listed under the release-boundary audit: **a feature can be broken by a migration it does not participate in.** Nothing in `sync_tr_realtime.py` was wrong. The env path it followed was simply no longer the path the data took, and the gate that connected them was in a third file. The audit's item 4 asks whether a bug has been patched more than once; this one asks a different question - when a release moves users from path A to path B, what else was keyed on A?

- **`institution_id` threaded through the module**, `None` keeping the env behaviour byte-identical, exactly the shape `sync_tr.py`'s own `run()`/`run_institution()` split already took in v2.1. Credentials, the account `syncId`, the `SyncLog` source and the notified user all follow from that one argument.
- **`tr-realtime:<institutionId>`, a sibling prefix and not `tr:<id>:realtime`.** `sync/db.py`'s `_sync_log_owner` reads the segment after the prefix as an institution id and refuses anything carrying a further colon, so the nested shape would have filed every listener row under the instance owner instead of the person whose connection it is - silently, since a row still gets written. `lib/domain/sync-sources.ts` is the app-side mirror and the single place these shapes are now parsed.
- **A supervisor, not a task.** Connections are configured, reconnected and deleted while the process runs, so `main.py` reconciles the set of live listeners against the set of configured ones every `REALTIME_RESCAN_S`. Three properties are load-bearing and each has a test: a listener that stopped is **not** restarted on the timer (`listen_forever` only returns after an auth failure, and retrying a dead session every minute is exactly the traffic pattern that gets a Trade Republic account flagged); reconnecting from Settings clears that stop mark, since it is the only signal the process gets that retrying is worth anything; and a failed database read leaves every running listener alone, because an empty result is indistinguishable from "nothing is configured".
- **`GET /realtime/status` and the Settings indicator.** "Is real-time actually on?" had no answer short of reading container logs, and the answer had been silently "no" for anyone who migrated. The endpoint reports **process** state - a connection can be configured and not listening (flag off, session expired, just crashed), and that gap is the whole point. Read once per Settings render with its own 2s timeout, degrading to nothing rather than making the page wait on an indicator.
- **Realtime sources never raise their own sync-failure alert** (`isRealtimeSource`). A listener and its batch sync share one Trade Republic session, so a dead session fails both - and only the batch sync's alert names something the user recognises. The listener's duplicate arrived titled `trade_republic_realtime`, which names nothing. An existing `SyncFailureState` row for such a source is deleted rather than skipped, since nothing would ever clear it otherwise.

**Two other v2.1 gaps of the same shape, found while doing this and fixed in the same pass** - both are the `woob:`-only assumption surviving into a release that added a second per-institution prefix. `friendlySourceLabel` resolved only `woob:<id>`, so a per-user Trade Republic failure was announced by its raw cuid - reintroducing, for a second prefix, the exact unreadable-notification bug that function exists to fix. `isSourceRetired` likewise checked only `woobModule`, so a Trade Republic connection that was removed kept reminding "still broken" every 24h with no way to ever clear itself, the same dead end it was written for when `LCL_LOGIN` was removed from `.env`.

### Reduced sync interval for Woob-synced banks

`v1.17` item 2, the realistic freshness ceiling for LCL and every user-configured Woob institution - screen-scraping with no official push/webhook mechanism at all, unlike Trade Republic (see "Trade Republic real-time tracking" above). `sync/main.py`'s single `_run_all()` (previously misleadingly logged as "Daily sync" despite running every 4h) was split in two:

- **`_run_woob_sources()`** - `_run_lcl()` + `_run_all_woob()`, followed by `_auto_categorize()`/`_check_alerts()` so a freshly-scraped transaction gets categorized and can trigger an alert within this same cadence, not up to 4h later on the next full sync. Scheduled every **30 minutes** (`interval` job, `id="woob_sync"`) - a real, disclosed tradeoff picked after weighing it directly with the user, not a technical ceiling: more frequent scraping raises the risk of a bank's own anti-automation detection flagging the account, and 30 min was chosen as a middle ground (8x fresher than the old 4h cadence) rather than the more aggressive 15 min option also considered.
- **`_run_all()`** - now just Trade Republic's own batch fallback + investment balance snapshots, plus the same categorize/alert follow-up as a safety net (mostly a no-op by the time it runs, since the 30-min job already processed most of what it'd find - harmless, not wasted work, `autoCategorizeTransactions`/`checkAlerts` are both idempotent). Stays on the original 4h cron.
- **Deliberately excludes GoCardless-synced accounts** - GoCardless sync lives entirely in the Next.js app, never in this service, and its own PSD2 rate limit (4-10 requests/day per account per endpoint, see "GoCardless" above) makes anything faster than the existing cadence structurally impossible regardless of what this app does on its own side.
- Global, not per-institution - considered a per-institution configurable interval (some banks plausibly warranting more caution than others) and deliberately scoped it out for this pass as more UI/DB-migration work than the ask justified; revisit if a specific institution's scraping actually gets flagged at 30 min.
- Locking against overlapping runs is unaffected by the split - `_lcl_lock`/APScheduler's own per-job-id `max_instances=1` default already prevented a job from overlapping itself before this change, at whatever cadence it runs.
