# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with this repository.

## What this repo is

`finalibaba-selfhosted` is the **public self-hosted edition** of [Finalibaba](https://github.com/LoicSERRE/Finalibaba), a personal wealth management dashboard. It contains the same core application stripped of personal deployment config, with community-oriented documentation.

**Goal:** anyone should be able to run the app with a single `docker compose up` and a `.env` filled in under 5 minutes.

## Language policy

- **All repo meta** (code comments, README, CLAUDE.md, commit messages, PR descriptions, issue templates) → **English**
- **UI strings** → French by default. English is available via the language switcher (stored in `NEXT_LOCALE` cookie). Add new UI strings to both `messages/fr.json` and `messages/en.json`.
- The private upstream repo (`Finalibaba/`) stays in French - it's personal.

## Relationship with the upstream private repo

The private repo is at `/mnt/c/Projets/Finalibaba` on the same machine (default path baked into `scripts/sync-from-upstream.sh`; override with `./scripts/sync-from-upstream.sh <path>`).

## Development commands

This project uses **pnpm** (not npm/yarn) - the exact version is pinned in `package.json`'s `packageManager` field, and `corepack enable` (already run in the Dockerfile, and standard in Node 22+ environments) makes `pnpm` resolve to that exact version automatically.

```bash
pnpm dev         # Dev server (http://localhost:3000)
NODE_ENV=production pnpm run build    # Prod build + type-check (NODE_ENV=production REQUIRED)
pnpm run lint    # ESLint
pnpm test        # Vitest - see __tests__/
pnpm test __tests__/alerts.test.ts     # Single test file
pnpm test -- -t "name substring"       # Filter by test name across the suite
pnpm run test:coverage  # Vitest with coverage - see "Development commands" note below on the report
```

Docker (local dev - DB only, credentials fixed in `docker-compose.dev.yml`):
```bash
docker compose -f docker-compose.dev.yml up -d
# DATABASE_URL=postgresql://appuser:devpassword@localhost:5432/finalibaba
pnpm exec prisma migrate deploy   # first time only - applies schema to the fresh DB
pnpm run db:seed:demo             # optional - fills it with realistic fictional data to develop against
```

Production (one-shot setup):
```bash
cp .env.example .env   # fill in values
docker compose up -d   # builds and starts everything
```

Prisma:
```bash
pnpm run db:migrate -- --name <name>   # Create + apply migration
pnpm exec prisma generate               # Regenerate client after schema changes (also runs automatically via postinstall on `pnpm install`)
pnpm run db:seed                        # Seed common institutions (reference data, no accounts)
pnpm run db:seed:demo                   # WIPES all data, then seeds realistic fictional accounts/balances/holdings/transactions - for local dev/debugging
pnpm run db:push                        # Sync schema to DB without a migration (dev only)
pnpm run db:studio                      # Open Prisma Studio for DB inspection
```

### pnpm overrides

`pnpm-workspace.yaml`'s `overrides` key forces patched versions of transitive dependencies that can't be resolved by Dependabot alone (upstream packages pin older ranges). Do not remove these entries - they are security fixes. (This lived in `package.json`'s `overrides` field under npm, and briefly under a `package.json` `"pnpm"` key during the pnpm migration - pnpm 11 moved all such settings to `pnpm-workspace.yaml`, silently ignoring the `package.json` location instead of erroring, so double-check here first if an override ever seems to stop applying after a pnpm upgrade.)

CI's `pnpm audit` step runs as `pnpm audit --prod --audit-level=high` - deliberately excluding devDependencies (ESLint, TypeScript, etc.). Those never ship: the Docker `runner` stage installs with `pnpm install --frozen-lockfile --prod --ignore-scripts`, so a devDependency-only advisory (e.g. through `eslint`'s vendored `minimatch`) can't reach production and isn't worth chasing at the cost of breaking the lint toolchain. `prisma` is a runtime `dependencies` entry (not dev) precisely because the `Dockerfile`'s `CMD` runs `pnpm exec prisma migrate deploy` inside the `runner` stage at container start - so `prisma`/`@prisma/dev`-rooted advisories (`find-my-way`, `valibot`, formerly `hono`/`@hono/node-server` before prisma 7.9 dropped that dependency) get installed by that `--prod` install and stay in scope even though the specific vulnerable code path (`@prisma/dev`'s embedded-Postgres `prisma dev` subcommand) is never actually invoked here.

pnpm also blocks a dependency's install/postinstall scripts by default unless explicitly allowed - `pnpm-workspace.yaml`'s `allowBuilds` list covers the packages in this project's tree that legitimately need one (Next's SWC compiler, Prisma's engine binaries, esbuild, file-watching). A `pnpm install` that reports `ERR_PNPM_IGNORED_BUILDS` for a package not already on that list means a new dependency needs the same explicit yes - don't add it blindly; check what the script actually does first.

## Pre-commit verification pipeline

Run this before proposing or making any commit - it exists so a commit never introduces something CI would have caught anyway (a broken build, a failing test, a new lint/audit finding), and so a SonarQube regression is caught locally before it shows up on the next scan. Order matters: cheapest/fastest checks first, so a trivial mistake (a lint error) fails in seconds instead of after a multi-minute build+test run.

1. **Working tree sanity** - `git status` (nothing unexpected staged/unstaged) and, on any branch that was just merged or rebased, `git diff --check` (flags leftover `<<<<<<<`/`=======`/`>>>>>>>` conflict markers and trailing-whitespace issues that a manual conflict resolution can silently leave behind - this is the "no conflicts" gate).
2. **Lint** - `pnpm run lint` (ESLint, includes `eslint-plugin-sonarjs`'s rules - the same static-analysis family SonarQube's own scan runs, so most Sonar code-smell findings already surface here for free).
3. **Type-check & build** - `NODE_ENV=production pnpm run build` (Next.js's build IS the type-check in this project - there's no separate `tsc --noEmit` script; `NODE_ENV=production` is required, see "Development commands" above). This is the frontend/backend "no conflicts" gate: a broken import, a type mismatch between a Server Action and the component calling it, or a Server/Client boundary violation fails here.
4. **Unit tests** - `pnpm run test:coverage` (not plain `pnpm test` - the coverage run is needed for step 6 anyway, and its `json-summary` report is the one to trust over the terminal table, see "Development commands" above).
5. Steps 2-4 are bundled as **`pnpm run verify`** - run that one command for the common case (JS/TS-only change). Add the Python steps below whenever a commit touches `sync/`:
   - `ruff check sync/` (lint)
   - `cd sync && python -m pytest` (tests). Before a SonarQube scan (step 6), generate the coverage report too - **from the repo root, not from `sync/`**: `python -m pytest sync/tests -c sync/pytest.ini --cov=sync --cov-report=xml:sync/coverage.xml`. Without that report SonarQube's Zero Coverage Sensor counts every `sync/` line as uncovered, which failed the v2.1 gate on a file that was actually at 100%; running it from inside `sync/` produces paths the scanner silently cannot resolve, which looks identical. See `.coveragerc` for the full explanation.
6. **SonarQube** - local/on-demand only, not wired into CI (see `sonar-project.properties`'s header comment). After step 4 has produced fresh coverage, run your local `sonar-scanner` from the repo root (it auto-detects `sonar-project.properties`, including the `sonar.javascript.lcov.reportPaths=coverage/lcov.info` it just consumed) against your SonarQube instance, and confirm the quality gate is green with **zero new issues** - not just "no new CRITICAL/BLOCKER", since `sonar-project.properties`'s `sonar.issue.ignore.multicriteria` list already documents every accepted pre-existing exception explicitly; anything new outside that list is a real regression to fix, not to suppress.
7. **Dependency audit** (only when `package.json`/`pnpm-lock.yaml` or `sync/requirements.txt` changed) - `pnpm audit --prod --audit-level=high` and, for Python, `pip-audit -r sync/requirements.txt`. Mirrors the `security`/`python-security` CI jobs; see "pnpm overrides" above before adding a new override in response to a finding here - check whether one already exists or is deliberately not applied.

This pipeline mirrors `ci.yml`'s job list on purpose (`lint` → `typecheck` → `test` → `python-lint`/`python-test` → `security`/`python-security`) plus the SonarQube gate `quality.yml` doesn't cover (SonarQube itself isn't in CI - see "CI quality gates" below) - the goal is that `git push` never surprises CI with something `pnpm run verify` (plus the conditional steps) would already have caught locally.

## Release-boundary health audit

The pipeline above catches regressions in a single diff - it says nothing about whether the codebase as a whole is still healthy, or whether the same bug class is quietly being patched downstream release after release without its root cause ever being touched. Run this broader audit **at each version boundary** - starting a new `vX.Y` (before writing its first feature) or right before tagging one, whichever fits that version's own shape - not on every commit.

**Origin**: prompted directly by a real incident, not built speculatively. `migrateDedicatedSyncToWoob`'s history-depth-loss bug (see "Migrating an existing dedicated integration to Woob" above) was the *third* release in a row (v1.11.2, v1.11.3, and that fix) patching a symptom of the exact same underlying `syncId`-matching gap in `sync/db.py`'s `upsert_account()` - three warning-UI layers were shipped before anyone asked whether the root cause itself was fixable. ### Multi-user architecture (v2.0)

The app was single-user by design until v2.0. Everything below exists so that stays true for anyone who wants it - **an instance with `AUTH_ENABLED` unset behaves exactly as it did before**, no login, no user management UI, no per-user anything visible.

**One always-present owner, never a nullable user.** The v2 migration creates a fixed-id row (`OWNER_USER_ID = "user-owner"`, `lib/domain/users.ts`) with no credentials and backfills every pre-existing row to it. `getViewer()` (`lib/auth-context.ts`) resolves to that row without a session in mono mode. This is the single decision the whole design rests on: there is no `userId | null` branching anywhere, no "is multi-user enabled" check inside a query, and switching an existing instance to multi-user later attaches its history to the admin **by construction** - the bootstrap screen only sets credentials on a row that already owns everything. `lib/domain/users.ts` exists as its own module solely to break the `lib/auth.ts` ↔ `lib/auth-context.ts` import cycle.

**Two account sets, deliberately distinct** - the distinction that prevents privilege escalation, not a convenience:

- `baseAccountIds(userId)` = own ∪ co-owned. The **only** set allowed to back a derived artifact: share-link content, API-key responses, alert evaluation, internal-transfer detection, exports, net worth. Never includes a portfolio merely granted for reading, so a read-only guest can't mint a public link or an API key over the grantor's data - one that would keep working after the grant was revoked, since those tokens carry no grant check of their own.
- `viewAccountIds(userId, viewedGrantorId?)` = the above, or the grantor's set when a real `PortfolioGrant` exists. Request-scoped page reads only. A stale/revoked grant falls back to "own" silently rather than erroring - the switcher's selection is caller-supplied state, not a claim.

**A deleted account must never resolve to another one.** `getViewer()`'s owner fallback is only reachable with **no** live session. It used to be reachable with a session too: a member's account deleted while they had a tab open failed the id lookup, fell through, and came back as the owner with `role: "ADMIN"`. Reported from a real instance ("quand l'admin supprime ce compte, au refresh je suis connecté au compte admin"), and reproduced live before fixing - the deleted member's cookie rendered the owner's Settings page including the admin-only backup section, which dumps and restores the whole database. A session naming a user who no longer exists now raises `DeletedSessionUserError`; `app/layout.tsx` is the only caller allowed to catch it, and renders `SessionEnded`, which signs the browser out. Deliberately not a redirect: the layout renders on `/login` too, so redirecting there would loop. `__tests__/auth-context.test.ts` pins it, including that the owner row is never even looked up - that second query was the escalation.

The bug class is worth naming, because it is not "we forgot a check": **a failed identity lookup that falls through to a more privileged identity.** A sweep for the same shape across every other resolution path found none - `resolveUser` (no username means the owner, but a password still has to match, and a non-owner with no hash is rejected outright), `getTotpEnabled` (returns a bare boolean, grants nothing), `authenticateApiKey` and the share-link lookup (both deny on a miss), `viewAccountIds`/`getViewContext` (a stale grant falls back to the viewer's *own* set, which is narrower), and `removeAccountCoOwner`, the one remaining `"use server"` export taking a `userId`, which is gated on `assertAccountOwner` and only ever removes access. Every one of those falls in the safe direction. The rule to apply when adding another: **a lookup that fails must deny or narrow, never widen** - and if a fallback exists at all, it must be unreachable from the authenticated path.

**Guards, not hidden buttons.** `assertAccountWritable` / `assertOwned` / `assertTransactionsWritable` (`lib/auth-context.ts`) mirror the pre-existing `assert*Eligible` family and exist for the same stated reason: a Server Action is directly invocable regardless of what the UI renders. `assertOwned` throws an identical `"Not found."` for a missing row and for someone else's row - a distinguishing error would confirm the existence of another user's data to anyone enumerating ids. `assertTransactionsWritable` compares against the **distinct** id count, so a duplicated id can't pad a forged batch up to passing.

**A userId parameter on a `"use server"` export is an impersonation primitive.** Every export of such a module is directly invocable from the browser with attacker-chosen arguments. Two real instances were found and fixed while doing this:

- `getUserSettingsFor(userId)` was exported and returns the row holding `smtpPassword`/`ntfyAuthToken` in **plaintext** - it would have handed any authenticated user every other user's alert credentials. Now un-exported.
- `autoCategorizeTransactions` needed a userId to work per user, so the engine moved to `lib/services/auto-categorize-runner.ts` (a plain module) and the action file kept only a thin session-resolving wrapper. The two internal cron routes import the engine directly and loop over users themselves.

A scripted check for this shape is worth re-running whenever an action file gains a parameter - it's an easy mistake to make and an invisible one to review.

**Cron routes loop per user.** `/api/alerts/check` and `/api/transactions/auto-categorize` each iterate `prisma.user.findMany()`; in mono mode that's exactly one iteration over the owner. Alerts must be per-user or a notification would quote a net worth its recipient can't see anywhere in their own app. `/api/investments/snapshot-balances` deliberately stays one instance-wide pass - it recomputes each account's balance from that account's own holdings, reads no per-user config, and addresses no notification to anyone, so a per-user loop would be the same work split into more queries.

**Internal-transfer detection had to stop being global.** `lib/domain/internal-transfers.ts`'s header states the assumption it was built on: every account in the database belongs to the same person, so any same-amount cross-account pair is safe to treat as a transfer. That's false in multi-user, and a global pass becomes a cross-user false-positive generator - user A's €500 debit and user B's unrelated €500 credit two days apart would be paired and both silently excluded from their owners' budgets and income. The pass now pools `baseAccountIds(runner)`. Safe to run from several users' passes over a co-owned account: the write only ever sets the flag to `true` (monotonic), so two passes can't thrash a row.

**Per-browser stores are namespaced too**, since neither is reachable by a server-side check: the service worker's runtime cache (`public/sw.js`, keyed by a `u=` registration param - a different value is a different worker URL, so it installs and its `activate` handler evicts every other bucket) and the app-lock unlock flag in `sessionStorage`.

**Same physical bank account, two users** (`app/api/gocardless/callback/route.ts`): `Account.gocardlessAccountId` is globally unique, so the upsert would silently rewrite the first user's row and append a balance snapshot to it. The callback now skips a conflicting account and redirects with `?gc=already-connected`, pointing the user at co-ownership instead. Attribution comes from `institution.userId`, never the session - this is a redirect back from the bank and can legitimately arrive without a cookie, which is also why the ownership check for starting a connection lives in `app/api/gocardless/connect/route.ts` instead.

**Two sharing mechanisms, deliberately not one** (`lib/actions/sharing.ts`):

- **Co-ownership** (`AccountCoOwner`) is per **account** and grants **write**. A joint Livret A appears in both portfolios pointing at the same rows - either person can categorize a transaction on it. It works by putting the account inside `baseAccountIds`, so every existing guard admits it with no special case. Managed from the account's own detail page (`components/account-detail/co-owners-section.tsx`), offered only to the account's **direct** owner: a co-owner cannot add further co-owners, which keeps `Account.userId` the single answer to "who decides who sees this" (`assertAccountOwner`, deliberately *not* `assertAccountWritable`, which also passes for co-owners).
- **A portfolio grant** (`PortfolioGrant`) is per **person** and grants **read** over everything the grantor owns - the "my partner sees my accounts but touches nothing" case. Managed in Settings, and never consulted by a mutation.

**H4 - removing a co-owner needs an explicit cleanup, because no FK cascade will ever fire.** The account survives, so the removed person's `AlertRule`s and `Goal`s pointing at it would simply keep existing against something they can no longer see - and an alert rule in that state is worse than dead: `checkCustomAlertRules` would still evaluate it and push them a notification quoting a balance they have no way to look at. `removeAccountCoOwner` deletes exactly their own rows for that account, in one transaction with the co-owner row itself; the account owner's own rules and the removed person's unrelated goals are untouched.

**The portfolio switcher (H6) changes what pages READ, never what actions may WRITE.** `getViewContext()` (`lib/auth-context.ts`) is the single entry point for a read surface and returns `{ viewer, ownerId, accountIds, readOnly }`. `ownerId` is the part that makes it correct rather than half-working: `accountIds` covers everything hanging off an account, but a page also reads entities owned by a *person* - categories, goals, the `UserSettings` row feeding analytics - and rendering the grantor's transactions against the viewer's own categories would show every row uncategorized, which reads as broken data rather than a permission boundary. Mutations never call this; they resolve their writable set from `getWritableContext`/`baseAccountIds`, which know nothing about the cookie.

The selection lives in a `viewing_portfolio` cookie, re-validated against a real `PortfolioGrant` on **every** read. A revoked or forged value falls back to the viewer's own portfolio in full read-write mode rather than erroring - a stale cookie is an everyday state (revoked while a tab sat open), not an attack to shout about. Verified live: with the grant deleted and the cookie still present, all of the grantor's data disappears on the very next request.

**Scope of the switcher, chosen rather than drifted into**: it covers `/` , `/accounts` (list + detail), `/analytics` and `/transactions` - the "see my partner's finances" surfaces. `/budgets`, `/income`, `/recurring` and `/settings` always show your own data; they're personal management surfaces, and a guest browsing someone's budget envelopes isn't the use case this was built for.

`readOnly` is threaded into the components that render mutation affordances (`RealEstateTab`/`LoanTab`/`AutomobileTab`, `AccountHeader`, `HoldingsTable`, `InvestmentFormsSection`, `TransactionsTable`, `TransactionCategoryCell`, and `canImportCsv` at the page level). This is **not** the access control - every one of those Server Actions guards ownership itself - it exists so a guest is never shown a button whose only possible outcome is an error. `TransactionCategoryCell` degrades to a static category chip, the same treatment `/budgets/[categoryId]` already gives split rows. The Settings backup section is likewise hidden for non-admins, matching the admin check the route itself gained in Lot B.

**Testing note**: probing rendered HTML for UI strings gives false positives - `NextIntlClientProvider` ships the entire messages JSON inside a `<script>` tag, so *every* label "appears" on *every* page. Assertions about what a guest can see must strip `<script>` blocks first and compare against markers that exist only in real data (an account name, a transaction label), never against a translated string.

**Local multi-user dev setup**: `SEED_MULTIUSER_PASSWORD=<8+ chars> pnpm run db:seed:multiuser`, on top of `db:seed:demo`. Additive (wipes nothing, idempotent) - creates a `member` account with its own two accounts, co-owns one of the owner's savings accounts, and grants the member read access to the owner's portfolio, so the switcher/co-owner panel/read-only mode can be exercised without hand-writing SQL. Deliberately **not** folded into `seed-demo.ts`: `docker-compose.demo.yml` runs the public demo with `AUTH_ENABLED=false`, where a second user has no login, no switcher and no user list - their accounts would be correctly invisible everywhere, which is confusing to seed and worse to debug. The demo stays single-user on purpose. The script refuses to run without the env var rather than shipping a default password.

**Accepted, documented constraints**: `.env` sync credentials (`LCL_LOGIN`/`TR_PHONE`) stay the owner's, so a second user cannot env-sync LCL or Trade Republic. **Corrected in v2.1 for Trade Republic specifically** - the "and since Woob has no Trade Republic module, a second user cannot sync Trade Republic at all" that used to follow here is no longer true: any user can now add their own from Settings, see "Per-user Trade Republic" below. LCL still has no per-user path of its own, but is reachable per-user through the generic Woob picker, so the remaining constraint is a redundant special case rather than a block on anyone. The *data* is unaffected either way: an env-synced account is co-ownable and grant-viewable exactly like a manual one. `sync/` needs **zero code changes** - `Account.userId` and `SyncLog.userId` carry a permanent DB-level default of the owner precisely because `sync/db.py` INSERTs those two tables via raw SQL with explicit column lists that know nothing about the column. That default is scaffolding for the sidecar only: every app-side `create` passes `userId` explicitly, and `__tests__/institutions-actions.test.ts` asserts it does.

#### Security audit (post-v2.0)

Ran as its own phase after the multi-user build, per `ROADMAP.md`'s sequencing. Findings below are split into what it **fixed** and what remains **open with a stated reason**. Everything was verified against a running instance, not read-only reasoning.

**Fixed by the audit:**

1. **The invitation flow was completely unreachable** (`proxy.ts`). `/invite/[token]` was not in the middleware's auth-exempt list, so on an `AUTH_ENABLED=true` instance every invitee was redirected to `/login` - a page they cannot get past, since not having an account is the entire premise. The multi-user build's own tests never caught it because they created users directly in the database. Fixed by exempting `invite(?:\/.*)?$` with the same anchoring as `api/v1` (verified: a valid token renders the form, a bogus one is a uniform `notFound()`, and `/invite999` still goes through auth). The redemption path itself was then confirmed end-to-end: single-use enforced, role `MEMBER`, empty portfolio, token consumed.

2. **Username enumeration by timing** (`lib/auth.ts`). `resolveUser` returned immediately for an unknown username but paid for a bcrypt comparison on a real one - **measured at a 64ms gap** over localhost, far above the noise floor. The rate limiter bounds how fast that can be probed but doesn't close it: a timing probe only needs a response, not a success. Fixed by comparing against `UNMATCHED_USER_HASH` (hashed from fresh random bytes at module load) on every non-matching path. Re-measured after the fix: −5ms, i.e. noise.

3. **Upstream error bodies forwarded to the client** (`app/api/gocardless/institutions/route.ts`). `String(e)` returned whatever GoCardless said - and `lib/services/gocardless.ts` builds its messages from that API's raw response body, including the auth-failure path. This repo already decided against that pattern for `pg_dump`/`psql` stderr (commit `1ae43c0`); this route was the one place it wasn't applied. Now logs server-side and returns a generic message.

**Verified sound, recorded so the next pass doesn't re-derive it:**

- **Role is never taken from the token.** `getViewer()` re-reads it from the database on every request, so `token.role` is decorative and a forged or stale one cannot escalate. `role` is written in exactly two places, both hardcoded (`bootstrapOwner` → ADMIN on the owner row only, `acceptInvitation` → MEMBER).
- **Cross-origin Server Actions are rejected by the framework** (confirmed live: same-origin resolves the action, cross-origin aborts with "Invalid Server Actions request" before it runs).
- **No raw SQL anywhere** in `lib/`/`app/` (no `$queryRawUnsafe`/`$executeRaw*`); `pg_dump`/`psql` are spawned with an argument array, never a shell string, and their connection string comes from `DATABASE_URL`, not user input.
- **No XSS sinks** (`dangerouslySetInnerHTML`/`innerHTML` appear nowhere).
- **Nothing logs a credential**; the backup route's own rule (swallow stderr, return a generic message) is upheld.
- **Every bearer-token route rejects an absent or wrong secret** (401 on all four), `/api/realtime/stream` correctly stays behind the session, and the H5 separation holds through **both** derived-artifact paths - a guest holding a live portfolio grant gets an empty response from their own API key *and* from a share link they minted.

**Still open, with reasons** - these are deliberate, not oversights:

1. **GoCardless callback has no CSRF/state binding.** `app/api/gocardless/callback/route.ts` recovers the institution from a `?ref=` query param the caller controls. Attribution comes from `institution.userId` rather than the session (the redirect legitimately arrives without a cookie), so it cannot mis-assign accounts to the wrong user - the H7 conflict check also refuses an account already connected by someone else. What remains unproven is whether a crafted callback can drive an *unwanted* import against an institution whose requisition id is already set. Starting a connection is now ownership-checked (`connect/route.ts`), which is the practical mitigation; a real `state` nonce round-tripped through the requisition would be the proper fix.

2. **Backup/restore is a full-instance takeover primitive.** `GET` dumps every user's data, `POST` replaces the entire database *including the `User` table* - so a restore can silently install arbitrary credentials. It is admin-gated (`requireAdmin`) and hidden from non-admins in Settings, which is proportionate for this app's model (admin ≈ shell access). **Confirmed by the audit**: hitting either verb directly as a MEMBER returns `403 {"error":"Admin access required."}`, and unauthenticated requests are redirected by the middleware before reaching the handler. Left open only in the sense that the primitive itself remains instance-wide by design.

3. **Plaintext credential inventory** - deliberate, per this repo's stated threat model (network exposure, not a compromised host), but it should be a conscious audit finding rather than a discovery: `UserSettings.smtpPassword`, `UserSettings.ntfyAuthToken`, `User.totpSecret`, `Institution.woobPassword`, `ShareLink.token`, `ApiKey.token`, `Invitation.token`. The multi-user change raises the stakes on the first two specifically, since one user reading another's row now means reading *someone else's* mail credentials - which is exactly why `getUserSettingsFor` was un-exported (see above). Re-run a check that no `"use server"` export takes a `userId` parameter.

4. **Rate limiting is per (IP, username), still in-memory.** `lib/auth.ts` was keyed by IP alone before v2.0; keying it by username too stops one account's failed attempts from locking out everyone behind the same NAT. It remains a single-process in-memory map (lost on restart, not shared across replicas) and there is no rate limit at all on invitation redemption or on the username-resolution path in `lib/actions/sharing.ts` - the latter returns a distinct "no such user" error, which is a deliberate usability call for an invitation-driven flow but is a username oracle.

5. **App-lock derives its WebAuthn user handle from the real user id** (`webAuthnUserId(viewer.id)`), replacing the pre-v2 hardcoded constant, and every ceremony plus `AppLockCredential` row is scoped by `userId`. **Confirmed by the audit**: the handle is a plain `TextEncoder` encoding of the user id, so it is deterministic and stable for a given user - a re-registration can't silently orphan an existing authenticator. Nothing open; recorded so the next pass doesn't re-derive it.

6. **`refreshAccountBalance` is an unguarded `"use server"` export.** Called server-to-server by the snapshot cron, which has no session. It is a pure recompute (derives an account's balance from that account's own holdings, writes nothing caller-controlled), so invoking it against another user's account can neither disclose nor corrupt anything - but it is directly invocable and worth a second opinion.

7. **Not verified under concurrency.** All isolation testing was sequential. Two simultaneous requests racing on co-ownership removal vs. an alert-rule write, or on invitation redemption, were not exercised. `acceptInvitation` consumes its token inside the same transaction as the user creation specifically to survive a double-open, which is the one race that was reasoned about.

### Authentication

**Disabled by default** (`AUTH_ENABLED` unset or anything other than `"true"`). Self-hosted = private network, network-level trust is sufficient.

Enabled via `AUTH_ENABLED=true` + `AUTH_PASSWORD` (plaintext) or `AUTH_PASSWORD_HASH` (bcrypt). When enabled: NextAuth Credentials provider, JWT session 30d, rate-limit 5 attempts/15min/IP. Display name via `AUTH_USER_NAME` (defaults to `"owner"`).

**Optional TOTP 2FA** on top of the password, toggled from Settings (`components/settings/two-factor-section.tsx` + `lib/actions/totp.ts`), never via env var - state lives on the `UserSettings` singleton (`totpEnabled`, `totpSecret`, `totpBackupCodes`). `lib/domain/totp.ts` holds the pure crypto (secret/URI generation via `otplib`, `verifyTotpCode` with 30s clock-drift tolerance, bcrypt-hashed one-time backup codes). `lib/auth.ts`'s `authorize()` checks `totpEnabled` after the password succeeds and accepts either a live 6-digit code or a backup code (consuming it from `totpBackupCodes` on use) - `components/auth/login-form.tsx` only renders the extra code field when a server-fetched `totpEnabled` prop says to. `regenerateBackupCodes`/`disableTotp` require a **live** TOTP code, never a backup code, so a single backup code can't mint itself replacements or turn off 2FA outright.

`proxy.ts` is the Next.js middleware (at the repo root). It reads `process.env.AUTH_ENABLED` in the `authorized` callback and bypasses NextAuth when it isn't `"true"`. If the upstream `proxy.ts` ever diverges, do **not** blindly overwrite this file.

`components/layout/sidebar-wrapper.tsx` is a **server component** (no `"use client"`) - reads `AUTH_ENABLED`, passes `showLogout` prop to `sidebar-dynamic.tsx`.
`components/layout/sidebar-dynamic.tsx` is a **client component** (`"use client"`) - handles `dynamic({ ssr: false })` (required to be in a client component in Next.js 16). This file does not exist in the upstream repo.
Both files are selfhosted-specific and must never be overwritten by the sync script.

For users who want security without built-in auth: document Nginx Proxy Manager, Caddy basicauth, Traefik + Authelia, Cloudflare Access, or VPN (Tailscale).

### App-lock (WebAuthn)

Settings → "Verrouillage de l'appli" (`components/settings/app-lock-section.tsx` + `lib/actions/app-lock.ts`, `@simplewebauthn/server`/`@simplewebauthn/browser`) - a fast local unlock for an already-installed, already-trusted PWA via the device's own biometric/PIN authenticator, matching what Finary/Trade Republic's native apps offer. **Deliberately independent of `AUTH_ENABLED`** (same precedent as read-only share links below) - the primary use case is a private-network instance with `AUTH_ENABLED` off, where a quick device-local unlock is still wanted without standing up a full password login.

**Not a network/security boundary the way `AUTH_ENABLED`'s server-side NextAuth session is.** `components/layout/app-lock-gate.tsx` (mounted in `app/layout.tsx`, wrapping the sidebar + `<main>`) is a client-side overlay: Next has no server-side concept of "this browser tab is currently locked", so the real page content is still server-rendered and sent in the initial RSC payload regardless of lock state - the gate only hides it behind a full-screen overlay until a WebAuthn ceremony succeeds. This is an intentional, proportionate match to what was actually asked for, not an oversight - Trade Republic's own app-lock works identically (a local UI gate in front of data the app already has cached, not a re-fetch-behind-auth boundary). It protects against "someone picks up my unlocked phone and opens the installed PWA", not network interception (the reverse proxy/TLS's job, see "Security headers" above) or local devtools access (which could clear the unlock state directly, the same way it could defeat a native app's lock screen only with more effort). Unlock state lives in `sessionStorage` (re-locks when the browser/PWA is fully closed and reopened), not a cookie - the point is a per-open unlock, not a second login session.

**Data model**: `AppLockCredential` - one row per registered authenticator (a device's Touch ID/Windows Hello/Android biometric gets its own key pair), so a user with the PWA installed on both a phone and a laptop registers two independently-revocable rows. `credentialId`/`publicKey`/`counter` are the standard WebAuthn verification triple (COSE public key + signature counter for replay detection) - `publicKey` is never a secret to protect the way `totpSecret` is, it can't authenticate on its own without the matching private key that never leaves the device's secure hardware. `UserSettings.appLockEnabled` gates whether the gate ever shows the lock screen at all; `appLockChallenge` is transient per-ceremony state (registration or authentication, never both at once for a single-user app) - same single-reusable-slot, safe-to-overwrite-an-abandoned-attempt trust model `totpSecret` already has during TOTP setup. Removing the last registered credential (`removeAppLockCredential`) auto-disables app-lock in the same transaction - a device-less "enabled" state would leave the lock screen with nothing to authenticate against, an unrecoverable dead end short of shell access to the DB (the same recovery story `totpSecret`/`AUTH_PASSWORD` already document).

**RP ID/origin derivation** (`getRpConfig()` in `lib/actions/app-lock.ts`) - WebAuthn requires the `rpID`/origin passed to `generateRegistrationOptions`/`verifyRegistrationResponse` etc. to exactly match the domain the browser actually used, or every ceremony fails. Reuses `APP_URL` when set (same "the app's public URL when behind a reverse proxy" config GoCardless's OAuth callback already reads), otherwise derives it from the incoming request's `host`/`x-forwarded-proto` headers - same fallback shape as `app/api/gocardless/connect/route.ts`'s own `process.env.APP_URL ?? \`${req.nextUrl.protocol}//${req.nextUrl.host}\`` , just read via `next/headers`' `headers()` since a Server Action has no `req` object to read directly. This is also why app-lock only actually works over HTTPS or `localhost` specifically - WebAuthn requires a secure context by spec, and a bare LAN IP over plain HTTP (this app's own documented default access pattern, see "Security headers" above) is not one; `components/settings/app-lock-section.tsx` and the lock screen itself both feature-detect via `@simplewebauthn/browser`'s `browserSupportsWebAuthn()` and show a clear "not available" message rather than a silent failure when it isn't.

`USER_ID` (`lib/actions/app-lock.ts`) is a fixed, hardcoded byte string, not derived from any real per-account identifier - this is a single-user app (see the Data model section's v2.0 multi-user note), so there's no real user id to use it for; WebAuthn only needs it to namespace resident keys and dedupe registrations for "the same user" on one authenticator, which a fixed constant satisfies exactly.

### Read-only share links

Settings → "Liens de partage" (`components/settings/share-links-section.tsx` +
`lib/actions/share-links.ts`) generates a `/shared/[token]` URL that renders
the net-worth dashboard read-only, to hand to an advisor or family member
without giving them write access - or the app password at all. This is
**deliberately independent of `AUTH_ENABLED`**: the primary use case is
exposing one view externally (e.g. via a reverse proxy) while `AUTH_ENABLED`
stays off for the trusted private network, matching "Authentication" above's
default trust model. `ShareLink` (`prisma/schema.prisma`) stores the token in
**plaintext** - same trust model as `UserSettings.totpSecret`/
`Institution.woobPassword` (the DB isn't hardened against server compromise,
so hashing this one field buys little), and unlike TOTP backup codes it needs
to be re-copyable later, not shown once. Unguessability comes from entropy
instead: `lib/domain/share-links.ts`'s `generateShareToken()` is 256 random
bits (`randomBytes(32).toString("base64url")`) - no rate limiting needed,
unlike the login password (low-entropy, human-memorable, why that path has
one).

**Bare routes** (`lib/domain/bare-routes.ts`) - `/login`, `/invite/*` and
`/shared/*` render without the app shell, and the predicate is shared by the
three client components that need it: the sidebar's null return, `MainContent`'s
padding (both the mobile-nav clearance and the page gutter, neither of which
means anything with no nav rendered), and `AutoSync`'s own guard. The last is
the one that matters beyond looks: `AutoSync` already skipped `/shared/*` so an
anonymous visitor could not trigger a real bank sync by opening a page, and the
login screen needed exactly the same treatment for exactly the same reason - it
was firing a sync, and showing the "Synchronisation en cours" badge, to someone
who had not authenticated. Found by screenshotting the page rather than reading
it. The sidebar is `dynamic({ ssr: false })`, so its absence cannot be checked
in server HTML at all; a curl-based assertion passes whether or not the fix
works.

`proxy.ts`'s middleware `matcher` excludes `shared` from ever reaching
`withAuth`, the same category as `api/auth`/`api/health` - the token lookup
inside `app/shared/[token]/page.tsx` is the page's own, independent gate
(`notFound()` uniformly for "doesn't exist" and "expired", no signal to an
anonymous visitor about which). That page sets `robots: { index: false,
follow: false }` since the URL may be reachable from the public internet.

The dashboard's JSX was extracted into `components/dashboard/dashboard-view.tsx`
(a pure presentational component, `interactive` prop) so `app/page.tsx` and
`app/shared/[token]/page.tsx` can't drift out of sync while rendering the same
data two different ways - the only interactive element either page has is the
per-account `Link` into `/accounts/[id]`, which the shared route must never
expose. Beyond that, isolating a share-link visitor from the real app is
handled inside the two client components that already call `usePathname()`
for their own reasons, rather than a route-group restructure: `sidebar.tsx`
returns `null` on `/shared/*` (no nav back into the editable app), and
`auto-sync.tsx` skips calling `autoTriggerSync()` there (an anonymous visitor
must never trigger a real bank sync just by opening the page - the one actual
correctness bug a naive version of this feature would have shipped with).

### Security headers

Set via `next.config.ts`'s `headers()` - CSP, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, and `poweredByHeader: false`. The CSP's `img-src` allows `google.com` **and** `*.gstatic.com` - `lib/domain/institutions.ts`'s favicon URLs are requested from `google.com/s2/favicons` but that endpoint actually serves the image via a redirect to `*.gstatic.com`, which only showed up testing with a real browser (Playwright), not by reading the URL. `script-src`/`style-src` need `'unsafe-inline'` for Next's own RSC hydration payload and CSS-in-JS - a nonce-based CSP would remove that but needs a per-request nonce threaded from `proxy.ts` through the root layout, not done here.

**No `Strict-Transport-Security` header, deliberately.** This app is routinely reached over plain HTTP on a private LAN/VPN (see "Authentication" above - `AUTH_ENABLED` defaults to off because network-level trust is the expected setup). HSTS is browser-cached and self-reinforcing: a browser that ever received it over plain HTTP would refuse all future plain-HTTP connections to that host until manually cleared. Reverse proxies that terminate real TLS (Nginx Proxy Manager, Caddy, Traefik) should set HSTS themselves at that layer, where "this connection is actually HTTPS" is actually true.

### PWA / offline support

Installable (`app/manifest.ts`, auto-detected and linked by Next the same way `app/icon.tsx`/`app/apple-icon.tsx` already are - no explicit `metadata.manifest` entry needed) - replaced an earlier static `public/manifest.json` that pointed both its "any" and "maskable" icon entries at the same unpadded `icon.svg`, which is wrong for maskable specifically (Android's circular/rounded-square mask would crop it). `app/icon-512/route.tsx` and `app/icon-512-maskable/route.tsx` are plain Route Handlers (not the `icon.tsx` file-convention - those are for the browser tab/iOS home screen, already covered separately) returning a 512×512 `ImageResponse` each, `force-static` since neither has any request-time data. Both render `components/shared/pwa-logo-512.tsx`'s `Logo512`, which computes every coordinate from `icon.svg`'s own 100×100 viewBox via real arithmetic (a `VIEWBOX_TO_CANVAS` scale factor, plus a `MASKABLE_SAFE_ZONE` shrink-and-recenter for the maskable variant) rather than hand-copied decimals, so the two variants (and any future logo edit) can't visually drift apart. `appleWebApp` (`app/layout.tsx`'s `metadata`) and the `env(safe-area-inset-bottom)` padding on `<main>` predate this - already handled iOS home-screen install and notch/home-indicator spacing.

**Service worker (`public/sw.js`)** also handles Web Push (v1.15) - `push`/`notificationclick` listeners, unrelated to the caching logic below (see "Alerts & webhooks" for the full design). Runtime caching only, no precache list: every route in this app is dynamic/server-rendered (see the route table under "File layout" above - almost nothing is `○` static), so there's no build-time HTML to precache against. Instead it caches whatever the browser actually requests as it browses - "cache what you've seen", the same model as the browser's own disk cache, just surviving offline too. Registered by `components/layout/service-worker-registration.tsx` (mounted once in the root layout) as `/sw.js?offlinePages=0|1`.

- Deliberately excludes every non-`GET` request (Server Actions POST to the same URL as the page that calls them - a mutation must never be served from or silently absorbed into the cache) and everything under `/api/` (session-sensitive or mutating either way).
- `_next/static/*` (content-hashed, genuinely immutable per build) always gets cache-first, regardless of `offlinePages`.
- **With `offlinePages=0` it does not intercept navigations at all** (v2.1.1). It used to fetch and return the response, caching successes "so a repeat visit loads faster" - which was simply false: only `cacheFirst` and `networkFirstWithFallback` ever read the cache, and neither runs on that path, so it wrote entries nobody read. It also broke real page loads. Once `respondWith` has been called the worker owns the response, and a rejected `fetch()` becomes an unrecoverable network error - which is what a user hit behind Cloudflare Access: an expired Access session answers a navigation with a cross-origin redirect to its login host, `public/sw.js` is served with the app's own `connect-src 'self'` CSP, so following that redirect from inside the worker is blocked and the page fails with "the promise was rejected" until a manual refresh. Not intercepting lets the browser follow the redirect at the top level, where it is allowed. Worth remembering as a class: **a service worker should only call `respondWith` when it can both add value and handle failure**, because after that call there is no way to hand the request back.
- Everything else (page navigations) is `offlinePages`-dependent: `1` does network-first-with-cache-fallback (a real offline experience - the point of this feature); `0` still caches successful responses for faster repeat loads, but never reads from the cache to answer a request that *failed* - a network error surfaces as a normal connection error, exactly what would happen without a service worker at all.
- **Why it's conditional on `AUTH_ENABLED` at all** (the query param is the only way this static file can know a server-only env var, short of a network round-trip on every install - `app/layout.tsx` reads `process.env.AUTH_ENABLED` server-side and passes the resolved boolean down as a prop): falling back to a cached authenticated page on network failure would bypass the server-side session check that page normally goes through on every load. A session can expire (30d JWT, see "Authentication" below) or be revoked without this service worker ever finding out, if it's just replaying a stale cached response instead of hitting the network. `AUTH_ENABLED` is not `"true"` (the documented default - private-network trust model, see "Authentication" below) is the one case genuinely safe to give the fuller offline experience to.
- **Cache cleared on logout** (`components/layout/sidebar.tsx`'s only `signOut()` call site, gated the same as that button - `showLogout`, i.e. `AUTH_ENABLED=true`) - `offlinePages=0` already stops a network failure from ever serving stale cached data, but successful responses are still cached along the way for the speed benefit; without this, that cached (real, once-authenticated) data would keep sitting in Cache Storage on a shared/public device after an explicit logout.
- `components/layout/offline-banner.tsx` is a `navigator.onLine` indicator, deliberately independent of the service worker's own cache-hit/miss logic - simpler and more robust than threading a custom "served from cache" signal back from the SW, and honesty matters here specifically: a stale cached balance shown with no indication it might be out of date would be actively misleading for a wealth-tracking app, not just a missing nice-to-have. Built on `useSyncExternalStore` (not `useEffect`+`useState`, which the lint config's `react-hooks/set-state-in-effect` rule rejects for exactly this "subscribe to a browser API" shape) - `getServerSnapshot` always returns `false` since `navigator` doesn't exist during SSR, so the banner never flashes on the server-rendered HTML, only after real client-side hydration confirms the browser is actually offline.
- `next.config.ts`'s CSP gained an explicit `worker-src 'self'` - would fall back to `script-src` without it (already `'self'`-scoped, so functionally the same), added anyway rather than relying on every browser's CSP3 fallback behavior being implemented identically.

**App-icon badging (v2.0)** - `public/sw.js`'s `push` handler calls `navigator.setAppBadge()` alongside `showNotification`, and `service-worker-registration.tsx` calls `clearAppBadge()` on mount **and on every `visibilitychange` to visible**. The second listener is the one that matters: an installed PWA is resumed far more often than cold-started, so a badge cleared only on a fresh load would sit there for days. Called with **no count** on purpose - this app dispatches alerts but stores no read/unread state anywhere, so any number would be invented; a bare dot is the honest signal, and opening the app is the only read receipt that exists. Supported on iOS 16.4+ for home-screen web apps (the same gate Web Push already requires) and on desktop Chrome/Edge; Android shows its own badge for unread notifications and ignores the call; feature-detected because it is absent in Firefox and in a plain browser tab. Added by v2.0's native-mobile-app scoping pass (see `ROADMAP.md`), which found it had been available all along and unused - it closes most of the "a native app feels more present" gap that scoping pass was weighing, for a few lines.

**"Swipe-friendly views for phones"** (the other half of this ROADMAP item's original wording) was dropped rather than built - no concrete gap was found (no tab/carousel UI that would clearly benefit from a swipe gesture), and inventing one to fill the wording would have been scope creep, not a real fix. The mobile-responsiveness half of "PWA/mobile-optimised" was already substantially done incrementally by earlier real-usage-driven releases (44×44 touch targets, `overflow-x-auto` on every table, the searchable Woob bank picker, etc.) before this feature was ever scoped - confirmed by grep, not assumed, before writing any of the above.

**`proxy.ts`'s matcher gained real gaps from this feature, found and fixed in the same pass.** `app/icon.tsx`/`app/apple-icon.tsx` (pre-existing) and the four new routes above (`icon-512`, `icon-512-maskable`, `manifest.webmanifest`, `sw.js`) have no literal file extension in their URL for the matcher's pre-existing `.(?:png|jpg|ico|webp)` branch to catch - on an `AUTH_ENABLED=true` instance, every one of them would have been silently redirected to `/login` instead of serving the real content, breaking browser-tab favicons, iOS home-screen install, and the PWA install prompt alike (the icon fetches never carry a session cookie a human hasn't logged in with yet). Every alternative added for this is `$`-anchored (added to the pre-existing `icon\.svg` too, while touching this line anyway) - confirmed live against a real `AUTH_ENABLED=true` dev server that an unanchored `icon-512` alternative matches as a bare *prefix*, not an exact path: a nonexistent `/icon-512999` was bypassing auth entirely (harmless here since it 404s either way, but the wrong reason - not a path this matcher was ever meant to exempt). Deliberately **not** extending this same anchoring pass to the pre-existing, unrelated `api/*`/`shared`/`_next/*` alternatives in the same matcher - `shared`/`_next/*` are meant to match subpaths (`/shared/<token>`, `/_next/static/...`), so naively `$`-anchoring them the same way would break them outright; `api/*` likely has the identical latent prefix-match quirk but is pre-existing and untouched here, out of scope for this fix.

Implemented via `next-intl`. Locale detection order: `NEXT_LOCALE` cookie → `Accept-Language` header → `DEFAULT_LOCALE` env var (defaults to `"fr"`). Supported locales: `fr` (default) and `en`. No URL prefix per locale.

### Light theme

Explicit opt-in only (Settings → Apparence), same cookie-based pattern as locale above rather than an automatic `prefers-color-scheme` switch for an unset/new preference - deliberately. This app has always been dark-only; silently switching a user to light on their very first visit (or an existing user with no stored preference) just because their OS happens to be set that way for reasons unrelated to this app would be a surprising regression, not a feature. Dark stays the bare `:root` default in `globals.css` for that case; `:root[data-theme="light"]` is the explicit-light override, applied server-side on `<html>` in `app/layout.tsx` from a `THEME` cookie so there's no flash-of-wrong-theme on load. `lib/actions/theme.ts` (`setTheme`) and `app/api/set-theme/route.ts` mirror `lib/actions/locale.ts`/`app/api/set-locale/route.ts` exactly - same cookie name shape, same 1-year `maxAge`, same reason both a Server Action and a GET route exist side by side (the client `ThemeSwitcher` calls the route via `fetch` + `router.refresh()`, not the action directly). `lib/domain/theme.ts`'s `resolveThemePreference()` is the single shared cookie-parsing function every one of the three read sites (`app/layout.tsx`'s `generateViewport()` and `RootLayout`, `app/settings/page.tsx`) calls, so "dark" being the safe default for an unset/invalid cookie is only ever asserted in one place.

**"Auto" (v1.15)** - a 3rd explicit choice alongside Sombre/Clair, additive to the opt-in-only decision above, not a reversal of it: it only ever applies when the user themselves picks it (`THEME=auto`), never as the default for someone who hasn't chosen anything. Live-follows the OS scheme while the tab stays open (e.g. a phone's own scheduled day/night switch) with **zero JavaScript** - `app/globals.css`'s `@media (prefers-color-scheme: light) { :root:not([data-theme]) {...} }` block handles both the initial paint (resolved at CSS-parse time, before hydration - no flash) and every live OS change automatically, since media queries re-evaluate on their own. `app/layout.tsx` renders **no** `data-theme` attribute at all for `THEME=auto`, letting that rule decide; it renders an explicit `data-theme="dark"` for an explicit "Sombre" choice (even though the value duplicates the bare `:root` default's own colors) specifically so the media query's `:not([data-theme])` condition excludes it - without that, an explicit dark choice could get silently overridden the moment the OS happened to prefer light, exactly the kind of surprise this feature's own opt-in philosophy exists to prevent. `generateViewport()`'s `colorScheme` becomes `"light dark"` (not a fixed value) in auto mode, so native browser chrome (scrollbars, form controls) follows the OS live too, not just this app's own CSS tokens. **Verified live with Playwright** (`page.emulate_media(color_scheme=...)`, changed mid-session with no reload): auto mode's background genuinely swaps in the same page load when the emulated OS scheme flips, an explicit dark/light choice each correctly resists the opposite OS preference, and a brand-new visitor with no cookie at all and an OS set to light still renders dark - confirming the core "never silently switch a user who hasn't chosen" property survived adding this feature, not just asserting it.

`--accent`/`--accent-strong` are deliberately **not** overridden for light - the brand indigo works as a button/highlight background regardless of overall theme (a white-text button's own contrast requirement doesn't depend on what's around it). Only `--background`/`--foreground`/`--surface`/`--surface-elevated`/`--border`/`--muted`/`--accent-text`/`--positive`/`--negative`/`--warning` get light-specific values - the semantic-status colors (`--positive`/`--negative`/`--warning`) in particular need darker shades than dark mode's bright versions, since the same hue at dark-mode brightness reads as washed out on a light background and fails WCAG AA as text. Every light-mode pairing was verified against the real WCAG relative-luminance contrast formula (a Python script, not eyeballed) before being written into `globals.css` - values are commented inline with their measured ratio.

`app/layout.tsx`'s `viewport` export became `generateViewport()` (async, reading the same `THEME` cookie) specifically so `colorScheme` can follow the resolved theme - Next only allows one or the other per segment, not a static object for some fields and a dynamic one for others. Leaving `colorScheme: "dark"` hardcoded while a user had explicitly switched to light would misstyle every native browser control (scrollbars, `<select>` popups, checkboxes) with the wrong-theme defaults, a real regression this specifically avoids. `themeColor` (the browser chrome/status-bar tint) stays a constant brand indigo across both themes, not made theme-conditional - out of scope for a UI toggle, not part of the installable app's identity the way the manifest's own `theme_color` isn't either.

Verified the codebase was actually ready for this before writing any palette: grepped for raw Tailwind gray/black/white color classes and stray hex literals across `app/`/`components/` first - zero found outside expected data-color files (`lib/utils/palette.ts`, `mcc-categories.ts`, `merchant-categories.ts` - allocation/category swatch colors, intentionally independent of the UI theme) and `app/layout.tsx`'s own `themeColor`. The existing "never use raw Tailwind colour classes for brand colours" discipline (see "Design tokens" below) meant this was close to a pure CSS-variable-table addition, not a per-component audit.

### Public REST API

Read-only, versioned under `app/api/v1/` (`GET /net-worth`, `/net-worth/history`, `/accounts`, `/transactions`) - for external tools (Home Assistant, a custom dashboard/widget) that want programmatic access without giving them the app password or a NextAuth session. Every route reuses `computeDashboard()` (or, for transactions, the exact same `isInternalTransfer: false` query the read-only share view's transactions section already uses) rather than a separate derivation - the API must never disagree with what the dashboard/share view themselves show for the same data. `DashboardHistoryPoint` gained an `isoDate` field (`lib/domain/dashboard.ts`) specifically for the history endpoint - the existing `date` field is locale-formatted for UI display ("20 août"), not something a JSON API consumer can parse; `isoDate` is computed from the exact same `historyRaw` entry as `date`, not a second lookup, so the two can never disagree on which day a point belongs to.

**Scope deliberately stops at these four endpoints** - transactions/budgets/holdings/analytics were considered and rejected for v1 after weighing it directly: the stated use cases (a Home Assistant sensor, a dashboard widget) are all "glanceable summary" consumers, and the marginal usefulness of exposing full budget/holdings/analytics detail for that use case is small next to the marginal *risk* - a leaked API key exposing "net worth + accounts + recent transaction labels" is bad, but a leaked key additionally exposing full spending-category breakdowns, dividend income, and investment performance is a materially bigger blast radius for a use case that doesn't actually need it (nobody puts their full transaction ledger in a home-dashboard tile). Same "demand-driven" reasoning already applied to Interactive Brokers/Plaid in `ROADMAP.md` - more endpoints are additive and can follow the same pattern if real usage asks for them, not built speculatively now.

**Auth**: a dedicated `ApiKey` model (Settings → API - `components/settings/api-keys-section.tsx`, mirroring `share-links-section.tsx`'s create/list/revoke shape closely), never the shared `NEXTAUTH_SECRET` bearer token `app/api/alerts/check/route.ts` uses for the sync→app call - that secret must stay strictly internal (leaking it is session-forgery-level), whereas an API key is meant to be handed to a third-party tool and individually revocable without killing every logged-in session. `lib/services/api-auth.ts`'s `authenticateApiKey()` is the shared gate every `app/api/v1/*` route calls itself (`Authorization: Bearer <token>` looked up against `ApiKey.token`) - `token` is plaintext, same trust model as `ShareLink.token`/`UserSettings.totpSecret`/`Institution.woobPassword` (see "Read-only share links" above for why hashing this one field buys little against this app's actual threat model), and stays re-copyable in the UI rather than a GitHub-style "shown once" ceremony, again matching `ShareLink`'s own precedent exactly. `generateApiKeyToken()` (`lib/domain/api-keys.ts`) prefixes the 256-bit random token with `fnlb_` - purely cosmetic recognizability, plays no role in validation.

`proxy.ts`'s matcher excludes `api/v1` from the NextAuth check (same category as `api/alerts`/`api/transactions` - an external tool has no browser session to present) using `api\/v1(?:\/.*)?$`, not a bare `api/v1` alternative - the `(?:\/.*)?$` shape matches `/api/v1` and every real subpath (`/api/v1/net-worth`) while still rejecting a bare-prefix collision like `/api/v1999`, applying the same anchoring lesson the PWA routes above already needed (confirmed live the same way: an unanchored version let a nonexistent path bypass auth).

### Demo mode

Set `DEMO_MODE=true` to enable a read-only public demo. `proxy.ts` intercepts all non-GET requests and returns 403. The `<AutoSync />` component on the dashboard is also disabled. Use `docker-compose.demo.yml` for a pre-seeded demo environment.

### GoCardless (Open Banking PSD2)

Optional. EU + UK bank connections via the official PSD2 API (free tier: 50 connections, 90-day history).

Credentials: `GOCARDLESS_SECRET_ID` + `GOCARDLESS_SECRET_KEY`. Set `APP_URL` to the app's public URL when behind a reverse proxy - it's used as the OAuth callback after bank authentication. Leave `APP_URL` blank for localhost use.

GoCardless logic lives in the Next.js app (not the `sync/` service).

**Transactions, not just balances.** `syncGocardlessBalances` (writes a `HistoricalBalance` row) originally had no counterpart at all for individual transactions - GoCardless-linked accounts got a moving balance with no explanation, the same gap Trade Republic's cash account had before its own timeline sync was added (see "Sync service - optional modules" below). Fixed by `syncGocardlessTransactions` (`lib/actions/gocardless.ts`), which fetches `GET /accounts/{id}/transactions/` (`getTransactions` in `lib/services/gocardless.ts`) and writes `Transaction` rows via `createMany({ skipDuplicates: true })` keyed on `syncId: gocardless_${transactionId}` - transactions are immutable once synced here, so there's never a reason to update an already-known row, only insert new ones. Both syncs are combined behind the same "Sync" button (`syncGocardlessAccount`, called from `SyncOpenBankingButton`) rather than adding a second button, since the transactions and balances endpoints have independent rate-limit quotas (GoCardless: up to 4-10 requests/day per account per endpoint) - calling both on every click doesn't cost either one anything.

- Only `booked` transactions are processed, never `pending` - the Berlin Group/PSD2 schema's `pending` array routinely lacks a stable `transactionId`, which the `syncId`-based dedup above needs; a transaction becomes syncable once the bank moves it to `booked` on a later sync, same as it would show up late in the bank's own app.
- The label is built from `remittanceInformationUnstructured`, falling back to `creditorName`/`debtorName` when that's blank - mirrors Trade Republic's own title/subtitle fallback chain in spirit, just against PSD2's field names instead.
- `merchantCategoryCode` (when the account's bank actually populates it - it's optional per the spec) is captured into `Transaction.merchantCategoryCode` and feeds the MCC-based categorization signal - see "Automatic categorization" below.
- `autoCategorizeTransactions` runs immediately after a transaction sync completes, same reasoning as every other trigger point for it - a freshly-synced transaction with a populated MCC gets a chance to land in a category in the same sync, not a cycle behind.

### App ↔ Sync service communication

The Next.js app calls the Python sync service via HTTP using `SYNC_SERVICE_URL=http://sync:8000` (set automatically in `docker-compose.yml`). In development, the sync service is not started - only the DB runs via `docker-compose.dev.yml`. The reverse direction (sync calling app) also exists now - see "Alerts & webhooks" below.

Every one of `lib/actions/sync.ts`'s blocking calls to the sync service (`triggerSync`, `triggerInstitutionSync`, the LCL/TR/Woob setup start/complete functions) goes through a shared `fetchSync()` helper with a 2-minute `AbortSignal.timeout()` - a real production report: none of these had any timeout, so a genuinely hung sync (no internet reaching the bank from inside the sync container, or a stuck Woob session) left the triggering button spinning forever with zero feedback, no way to tell "still working" from "will never finish". 2 minutes is generous enough for a real bank scrape/2FA round-trip (not a fast local API call) while still bounding the worst case. The UI side of this fix is in `components/settings/sync-status.tsx`'s `syncError` state and `components/settings/institution-sync-button.tsx`'s own `error` state - the "Synchroniser" click was the one path in both components with no `try`/`catch` at all (every setup step already had one), so the new timeout error would otherwise have disappeared into an unhandled rejection instead of ever reaching the user.

### Alerts & webhooks

Settings → "Alertes" (`components/settings/alert-channels-section.tsx` + `alert-triggers-section.tsx` + `lib/actions/alerts.ts` - see "Settings UI split" below for why it's two files) configures notifications for three triggers, all evaluated in one place: `POST /api/alerts/check` (`app/api/alerts/check/route.ts`). Three channels - **not Telegram** (the user didn't want it) and **not SMS** (no free/open-source sending path exists - every real carrier-SMS option is a paid aggregator; a GSM modem + SIM card is the only free route and doesn't fit a `docker compose up` app):

- **ntfy** - `ntfyTopicUrl`, a single POST per alert (`lib/services/notifications.ts`'s `sendNtfyMessage`), using ntfy's **JSON publish API** (POST to the server root with `topic`/`title`/`message` as body fields) rather than the simple API (POST straight to the topic URL, title as a `Title` header). The header approach doesn't work here: HTTP header values must be Latin-1 and alert titles are French/user-entered (accents), so a raw fetch() throws a ByteString conversion error - confirmed while first building this, titles used to get folded into the body instead with ntfy showing its own fallback title. JSON string fields are UTF-8-safe with no such limitation, so this is the actual fix, not a workaround. `icon`/`click` (the Finalibaba icon + tap-to-open link) are only added when `APP_URL` is set - both need a URL ntfy's own servers/client can fetch, so they're skipped for LAN/VPN-only instances the same way GoCardless's OAuth callback already treats a blank `APP_URL`. `icon` points at `/icon` (Next's own file-route, `app/icon.tsx` - a generated PNG) rather than `public/icon.svg`, since ntfy only accepts JPEG/PNG icons. `tags: ["bar_chart"]` (ntfy maps GitHub-style emoji shortcodes, this one renders 📊) - a user found every alert visually indistinguishable from any other app's notifications in their phone's list. One fixed tag for every alert rather than a different emoji per kind - `dispatchAlert` only ever receives a plain title/body pair from all ~8 call sites in `app/api/alerts/check/route.ts`, so per-kind tagging would mean threading a new parameter through every one of them for a cosmetic nice-to-have.
- **Email** - `alertEmailTo` + `smtpHost`/`smtpPort`/`smtpUser`/`smtpPassword`/`smtpFrom`, sent via `nodemailer` (`sendEmail`). `smtpPassword` is the one field with different blank-handling than every other field in this form: blank means "leave unchanged", not "clear it" - it's never pre-filled with the real stored value (a plaintext password shouldn't round-trip back into the browser on every page load), so a blank submit almost always means "didn't touch this field". Verified against a throwaway local `smtp4dev` container during development, not just unit-tested - a real send/receive round-trip without needing a live mail account.
- **Web Push** (v1.15, `components/settings/web-push-section.tsx` + `lib/actions/push.ts` + `lib/services/notifications.ts`'s `sendWebPush`/`getOrCreateVapidKeys`) - broader device support (iOS 16.4+, Android, desktop) without depending on a third-party relay the way ntfy does. Its own section, separate from ntfy/email's shared form - "configuring" it is a browser `pushManager.subscribe()` action on the device itself, not a text field to type into and Save, so it doesn't fit that form's shape. One `PushSubscription` row per subscribed browser/device (a phone and a laptop each get their own independently-revocable row, same multi-device shape as `AppLockCredential`). VAPID keys (`UserSettings.vapidPublicKey`/`vapidPrivateKey`) are generated once by the app itself on first subscribe attempt (`getOrCreateVapidKeys`), never something a self-hoster configures - same "app generates it, not the user" precedent as `totpSecret` - and must stay stable forever after, regenerating them would silently invalidate every already-registered subscription. `sendWebPush` reads `prisma.pushSubscription` directly rather than taking a subscriber list as a parameter - same "a service reads what it needs from the DB itself" precedent as `lib/services/api-auth.ts`'s `authenticateApiKey()`, which is what keeps `dispatchAlert`'s own signature (and every one of the ~10 alert-check functions in `app/api/alerts/check/route.ts` that call it) unchanged from before Web Push existed: `UserSettings` just grew 3 real columns that flow through automatically via the existing `settings: UserSettingsModel` parameter every one of them already had. Also prunes any subscription the push service reports as gone (HTTP 404/410) inline in the same function, since it already has DB access for the read - a dead subscription would otherwise fail silently forever with no way for the user to notice short of it just never working. `public/sw.js` gained `push`/`notificationclick` listeners - `notificationclick` focuses an already-open tab instead of always opening a new one, since this app's own auto-sync/offline-banner already run continuously in whatever tab is open. **Verified live with Playwright, working around a real environment limitation, not glossed over**: vanilla open-source Chromium (what Playwright bundles) lacks the Google API keys real Google Chrome ships with, so it can't complete actual FCM push registration in this sandbox (confirmed directly - a real subscribe attempt fails with a genuine browser-level `AbortError: push service not available`, not a bug in this app's code). Worked around by mocking only `PushManager.prototype.subscribe` to return a well-formed fake subscription, letting everything else - the permission check, the dialog flow, the Server Action call, the `PushSubscription` row actually landing in the database, the UI refresh - run for real and be confirmed end-to-end.

**Each channel has its own independent on/off toggle** (`UserSettings.ntfyEnabled`/`emailAlertsEnabled`/`webPushEnabled`, all `Boolean @default(true)`) - layered on top of "is it configured" above, not a replacement for it. Before this, a user with both ntfy and email filled in had no way to receive through only one of them: `dispatchAlert` (`lib/services/notifications.ts`) fanned out to every channel with non-blank config unconditionally. Requested directly by the user rather than found as a bug - the config-presence check alone was working exactly as designed, it just didn't cover "I have both set up but only want one right now." Default `true` so an already-configured channel on an existing install keeps firing exactly as before upgrading; the ntfy/email checkboxes live at the top of their shared section in `alert-channels-section.tsx` (`updateAlertChannels` in `lib/actions/alerts.ts` saves them via the same plain-checkbox convention as `loanAlertsEnabled`/`syncFailureAlertsEnabled` in `updateAlertTriggers`), so toggling one channel off never touches the other's stored config - re-enabling later doesn't require re-typing the topic URL or SMTP settings. `webPushEnabled` follows the same independent-toggle shape but lives in its own section's UI (a "Désactiver" button, not a form checkbox - see the Web Push bullet above for why), and flips back to `true` automatically the moment a device subscribes, rather than needing a separate re-enable step after adding the first device on a fresh install.

**ntfy topics are generated, never user-invented.** First version of this feature asked users to pick their own topic name - a real mistake, not a hypothetical one: ntfy.sh's free tier has no access control, an easily-guessed name is the only thing standing between a public server and someone else reading real net worth figures, and asking a human to invent an unguessable string is exactly what password-strength meters exist to prevent. Fixed the same way `ShareLink.token` already solved the identical problem (`lib/domain/share-links.ts`'s `generateShareToken()`): unguessability from entropy, not from a human-chosen secret. `alert-channels-section.tsx`'s "Générer" button builds `https://ntfy.sh/finalibaba-<192 random bits>` **client-side** via the Web Crypto API (`crypto.getRandomValues()`) - no server round-trip, it's a pure "fill the field" convenience persisted only when the user hits the form's own Save button, same as every other field here. The field stays freely editable for self-hosted-ntfy-server users (genuine privacy independent of trusting ntfy.sh at all - see below), backed by `ntfyAuthToken` (`UserSettings`, blank/unused with the public server) sent as `Authorization: Bearer <token>` in `sendNtfyMessage()` - fine as a header unlike the human-entered alert text, a token is always ASCII.

### Self-hosted alerts infrastructure (optional `ntfy`/`mail` Compose services)

Both entirely optional, Compose-profile-gated (`profiles: ["ntfy"]`/`["mail"]` in `docker-compose.yml`) so a plain `docker compose up -d` is unaffected - confirmed empirically that a required (`:?`) variable on a profile-gated service breaks `docker compose config` even when that profile is never requested (Compose evaluates required-variable interpolation for every service in the file before profile filtering runs), which is why `MAIL_DOMAIN` uses a `:-` empty default instead and docker-mailserver's own startup fails loudly if it's blank when the `mail` profile is actually used.

- **`ntfy`** (`binwiederhier/ntfy`) - `NTFY_AUTH_DEFAULT_ACCESS=deny-all` so nobody reads or writes without a token created via `ntfy user add`/`ntfy token add` (README has the exact commands). Verified live: unauthenticated publish → 403, correct Bearer token → message delivered and readable, wrong token → rejected.
- **`mail`** (`ghcr.io/docker-mailserver/docker-mailserver`) - chosen over hand-rolling Postfix+OpenDKIM (a `mail/Dockerfile` matching `sync/`'s own-Dockerfile pattern was considered) because correctly wiring the milter socket and DKIM key lifecycle by hand is genuine, easy-to-get-subtly-wrong sysadmin work, and this image is exactly built for it. `SMTP_ONLY=1` disables IMAP/POP/mailboxes (this project only ever sends, never receives), `ENABLE_OPENDKIM=1` signs outgoing mail.
  - **`SMTP_ONLY=1` disables SASL entirely**, not just IMAP - confirmed empirically (`postconf -n | grep sasl` showed `smtpd_sasl_auth_enable=no` on the submission port regardless of any user created via `setup email add`, because `SMTP_ONLY` also disables Dovecot, which is where Postfix's SASL backend normally comes from). Authenticated submission on port 587 genuinely does not work in this mode - not a config oversight, a deliberate trade-off of this mode. Fixed by relaying on trust instead: `PERMIT_DOCKER=connected-networks` adds the container's own Docker network to Postfix's `mynetworks`, and Finalibaba's SMTP fields point at port 25 with no user/password - same "same Docker network = trusted, no credentials" model already used for `app`↔`sync`, not a new pattern.
  - **OpenDKIM has its own `TrustedHosts`**, separate from Postfix's `mynetworks` - a `PERMIT_DOCKER`-trusted relay still won't get signed ("not internal"/"not authenticated" → "no signature data" in the log) unless the sending host is also in this file. Confirmed it does **not** need the same manual treatment - docker-mailserver auto-detects and adds the container's own Docker network to `TrustedHosts` on its own at startup.
  - **`docker restart`/`docker compose restart` does not reliably reload DKIM config** after running `setup email add`/`setup config dkim` on an already-running container - confirmed empirically (`/etc/opendkim/{SigningTable,KeyTable}` stayed stale/empty, or picked up the new signing table but with root-owned key files the `opendkim` user can't read, `can't load key ... Permission denied`). A full recreate (`docker compose up -d --force-recreate mail`, matching a `down`+`up`) reliably re-runs the complete first-boot setup (correct file ownership included) - README documents recreate, not restart, for this reason.
  - **`MAIL_DOMAIN` must be the root domain, never a subdomain** - `docker-compose.yml` sets `hostname: mail` + `domainname: ${MAIL_DOMAIN}`, so Docker concatenates them into the container's real FQDN/HELO as `mail.<MAIL_DOMAIN>`. Setting `MAIL_DOMAIN=mail.yourdomain.com` yourself (an easy mistake - it reads like the intended sending hostname, and is literally what `.env.example`'s own old comment example implied before this was caught and fixed) produces the broken `mail.mail.yourdomain.com` - confirmed the hard way via mail-tester.com flagging "no A record behind your hostname" and a `RDNS`/SPF `HELO` mismatch, at a real cost (0/10 deliverability score) before the `.env` value was corrected to the bare root domain.
  - No published port at all - Postfix only makes *outbound* connections to recipient mail servers, nothing needs to reach it from the internet (unlike `ntfy`, which the phone does).
  - `mail_config` (mounted at `/tmp/docker-mailserver`) is the volume that must never be lost - it holds the generated OpenDKIM keypair; losing it means a new key that no longer matches the already-published DNS record.

**Email provider presets, not raw SMTP fields.** A "Fournisseur" `<select>` (Gmail / Outlook / self-hosted / Personnalisé) pre-fills `smtpHost`/`smtpPort` on change - `smtp.gmail.com:587`, `smtp.office365.com:587` (STARTTLS, no change needed to `sendEmail()`'s existing `secure: config.port === 465` logic), `mail:25` for this project's own optional `mail` service (see below - port 25, not 587, and deliberately no user/password for that one). Fields stay editable, presets are a convenience fill only. Hint text calls out that Gmail/Outlook both require an app password (not the real account password) for third-party SMTP access, and that `smtpFrom` has to match the authenticated account or they reject/rewrite it - asked the user directly about the email UX (raw SMTP vs. presets vs. a third-party API key vs. dropping email) since there's a real constraint underneath: no self-hosted app can make email actually land in an inbox without an authenticated relay somewhere (no SPF/DKIM/reputation from a residential IP), so "simpler" can only mean "less to type", not "no relay needed".

**Per-trigger opt-out.** Net worth already had one (blank threshold = disabled); loan-nearly-paid-off and sync-failure didn't, until the user asked for it - `UserSettings.loanAlertsEnabled`/`syncFailureAlertsEnabled` (`Boolean @default(true)`, so existing installs keep today's always-on behavior), two checkboxes in the form, checked in `checkLoanAlerts()`/`checkSyncFailures()` before doing anything else. Scoped to on/off per trigger, not full per-trigger-per-channel routing (e.g. "loan alerts to ntfy only, net worth to email only") - a real possible future refinement, but broader than what was asked.

**All config lives in `UserSettings` (DB/Settings UI), not `.env`** - unlike GoCardless/LCL/TR (deploy-time secrets), this follows the more recent precedent in this codebase (TOTP, share links, tax rates): no redeploy/restart needed to add or change a topic URL or SMTP relay. `smtpPassword` is plaintext, same trust model as `totpSecret`/`Institution.woobPassword`.

**Threshold-crossing logic stays in TypeScript**, reusing `computeDashboard()` and `calcCurrentCapital()`/`hasLoanParams()` rather than re-implementing net worth or loan math in Python - the sync service already has full DB access and could theoretically compute its own approximation, but that would risk an alert firing at a different number than what the dashboard shows, and duplicate the single source of truth described under "Net worth calculation" below.

**One new route, called once per existing 4h sync cron - not a new schedule.** `sync/main.py`'s `_run_all()` already runs every 4h via APScheduler and already runs every sync source sequentially before returning; `_check_alerts()` is one more step at the end of it, calling the route via `requests` (already a direct import in `sync_tr.py`, not a new Python dependency). The three checks, each its own function in the route file for readability (and because a single combined function tripped the `sonarjs/cognitive-complexity` lint gate):

- **Net worth threshold** (`checkNetWorthAlert`) - `netWorthAlertThresholdCents` (blank = disabled). Dedup via `netWorthAlertLastAbove: Boolean?` (null = never evaluated) - `lib/domain/alerts.ts`'s `evaluateNetWorthAlert()` never fires on the first-ever check for a freshly-set threshold, it only establishes the baseline; only a real flip after that fires. `updateAlertSettings` resets this to `null` whenever the threshold value itself changes, so moving it doesn't misread the new number against a stale baseline.
- **Loan nearly paid off** (`checkLoanAlerts`) - fixed at 5% of the original `loanAmountCents` remaining (`isLoanNearlyPaidOff`, a named constant, not user-configurable - keeps the UI lean). Dedup via `Account.loanPaidOffAlertSent` (one-way flag, a loan only crosses this once). Short-circuits to `[]` when `UserSettings.loanAlertsEnabled` is false.
- **Sync failures** (`checkSyncFailures`) - edge-triggered via `SyncFailureState` (one row per currently-broken source): alerts once when a source's latest `SyncLog` row transitions from success/unknown into `error`/`auth_required`, then at most one reminder per 24h while it stays broken, clearing the moment it succeeds again. Deliberately scoped to the *automatic* 4h cron only, not on-demand "Sync now" clicks in Settings - a manual sync's failure is already visible right there in the UI to whoever just clicked it; a push notification adds value specifically for the unattended background job. Short-circuits to `[]` when `UserSettings.syncFailureAlertsEnabled` is false. `formatSyncFailureBody` deliberately does **not** surface `SyncLog.message` (raw Python exception text like "Session web absente - lance --setup", aimed at someone running the sync container's CLI) - a user flagged the raw text as unreadable in a push notification, so the body is now one of two fixed, translated sentences keyed on `status` (`auth_required` vs a plain error) instead; the technical detail is still visible in Settings' sync status / `SyncLog` directly for anyone troubleshooting. `friendlySourceLabel` resolves `SyncLog.source` (a machine key - `"trade_republic"`/`"lcl"`/`"woob:<institutionId>"`, the last a raw cuid) to a human-readable name only at notification time, looking up the `Institution` for the `woob:` case - `source` itself stays unchanged since it's also `SyncFailureState`'s dedup key. Falls back to a generic "une banque configurée via Woob" (never the raw id) when that lookup finds nothing - a real production case, see `isSourceRetired` below for why.

  **`isSourceRetired`** - a real gap found in production: a source (`"lcl"`, `"trade_republic"`, or a `woob:<id>`) that will never write another `SyncLog` row again - because `LCL_LOGIN`/`TR_PHONE` was removed from `.env`, or a Woob institution's config was cleared/the institution deleted - has no way to ever clear its `SyncFailureState` (only a fresh `status: "success"` row does that), so it kept re-alerting "still broken" every 24h forever for a source that wasn't broken, just retired. Confirmed against the exact incident that surfaced this: `LCL_LOGIN` was removed from prod `.env` earlier (see "Migrating an existing dedicated integration to Woob" above) specifically to stop the LCL/Woob duplicate-account bug, and the dedicated `lcl` source's last-ever `SyncLog` row (`auth_required`, from before removal) then kept reminding indefinitely with no way to self-heal. Checked once per source per `checkSyncFailures` run (env var reads and a single `Institution` lookup are cheap) - a source retired *after* it already had an active `SyncFailureState` still gets detected and its state deleted, not just skipped for new alerts, so the reminder stops on the very next check rather than needing a manual DB cleanup.

**Auth for the sync→app call**: unlike `app→sync` (port 8000, never published, Docker-network-only per `SECURITY.md`), `app`'s port is published to the host and potentially reverse-proxied to the internet, so `/api/alerts/check` can't assume "reachable = internal" the way sync's endpoints do. It's excluded from `proxy.ts`'s NextAuth matcher (same category as `api/auth` - no browser session exists on this call path) and gates itself instead: `NEXTAUTH_SECRET`, passed into the `sync`/`sync-demo` containers' environment in `docker-compose.yml`/`docker-compose.demo.yml`, doubles as the shared bearer token (`Authorization: Bearer <secret>`). Reusing it avoids a new required env var - it's already mandatory, and its leak is already maximally severe (session forgery), so reusing it here doesn't meaningfully raise the blast radius. `APP_SERVICE_URL` (`http://app:3000` / `http://app-demo:3000`) is the fixed-hostname counterpart to `SYNC_SERVICE_URL` above, same pattern.

**Custom alert rules** (`AlertRule` model, Settings → "Règles d'alerte personnalisées") - a parallel, user-defined mechanism alongside the 3 fixed triggers above, which stay untouched. One polymorphic table, `kind: ACCOUNT_BALANCE | BUDGET_OVERRUN | ACCOUNT_OVERDRAFT | INVESTMENT_VALUE | HOLDING_PRICE | UNREALIZED_GAIN | REBALANCING_DRIFT | NEW_TRANSACTION`, mirroring the same type-conditional-nullable-fields convention `Account` already uses for its LOAN/INVESTMENT-only fields, rather than one table per kind - every kind shares the same on/off toggle, optional custom message, and Settings UI list shape. `checkCustomAlertRules` (`app/api/alerts/check/route.ts`) is a fourth check called from the same `POST` handler, after the other 3, dispatching each rule to its own per-kind checker via `dispatchAlertRuleCheck`.

Four of the eight kinds - `ACCOUNT_BALANCE`, `ACCOUNT_OVERDRAFT`, `INVESTMENT_VALUE`, and `HOLDING_PRICE` (plus `UNREALIZED_GAIN` when `gainUnit = AMOUNT`) - are mathematically the exact same "current cents value crosses `balanceThresholdCents`" edge-triggered comparison (`evaluateAccountBalanceAlert`), just with a different source for "current" and a different eligible-account/holding scope in the UI. Rather than one pair of threshold/dedup columns per kind, they all share `AlertRule.accountId`/`balanceThresholdCents`/`balanceLastAbove` - see the schema comment for why (and why those columns kept their original "balance"-flavored names instead of being renamed when this was added, to avoid a risky column-rename migration against already-deployed installs' real rule data).

- `ACCOUNT_BALANCE` rules are scoped to fiat accounts (CHECKING/SAVINGS/MEAL_VOUCHER, the ones with a meaningful `HistoricalBalance`-derived current balance) - a separate evaluator from, not a shared call with, `evaluateNetWorthAlert`, even though the edge-triggered logic is identical, so the built-in net-worth trigger's own code path stays untouched by this feature. Dedup state (`AlertRule.balanceLastAbove`) is per-rule, same null-means-never-evaluated convention as `UserSettings.netWorthAlertLastAbove`; changing the threshold on an existing rule resets it to `null`, same as `updateAlertTriggers` already does for net worth.
- `ACCOUNT_OVERDRAFT` rules are the same fiat-account scope and checker as `ACCOUNT_BALANCE` (`checkAccountBalanceRule` handles both, branching only on `rule.kind` for the dispatched message text) - the only difference is `balanceThresholdCents` is fixed at `0` and set once at creation (`createAlertRule`), never a user-entered field, so "alert me if this account goes negative" doesn't require the user to type a number that's always going to be zero anyway.
- `INVESTMENT_VALUE` rules are scoped to INVESTMENT/CRYPTO accounts and use their holdings' market value (`holdingMarketValueCents`, summed across the account) instead of a `HistoricalBalance` row, since investment/crypto accounts don't have one.
- `HOLDING_PRICE` rules reference a specific `Holding` (`AlertRule.holdingId`, `onDelete: Cascade`) rather than an account, comparing its `lastPriceCents` directly - already EUR-converted at entry time for foreign-currency holdings (see "Multi-currency" below), so no extra FX handling is needed at check time. The Settings UI's holding picker is a flattened list built from `investmentAccounts` (fetched once in `app/settings/page.tsx`, passed down alongside the account list `AccountBalanceFields`/`AccountThresholdFields` already needed).
- `UNREALIZED_GAIN` rules are the one kind where `accountId` being `null` is valid input, not a malformed-row guard failure - it means "aggregate across every investment/crypto account" rather than one specific account (`checkUnrealizedGainRule` runs a second, broader `prisma.holding.findMany` query only in that case, since `findActiveAlertRules`'s own include only preloads the rule's *own* account's holdings). `gainUnit: PERCENT | AMOUNT` picks whether the rule's threshold is `gainThresholdPct` (a plain float percentage, evaluated by `evaluatePercentAlert` - kept as its own function rather than coercing percent into cents, so a stored threshold's unit is never ambiguous) or the shared `balanceThresholdCents` in euros - a rule stores exactly one, the other stays `null`, and which one is editable later is fixed at creation same as everywhere else in this dialog. `computeUnrealizedGain` (`lib/domain/alerts.ts`) sums market value minus cost basis across the relevant holdings, skipping any with unknown `costBasisCents` (same convention `accounts-page.ts`'s own per-account gain sum already uses) - `gainPct` is `null` when every considered holding had a zero or unknown cost basis, since a percentage isn't meaningful without a real denominator, and the rule simply doesn't evaluate that check until it is.
- `BUDGET_OVERRUN` rules key off `Category.budgetCents` directly (no separate threshold field) and re-arm every calendar month instead of being edge-triggered - a category that overran its budget in July should be able to alert again in August even though spend never "un-overran" in between, it just resets at the month boundary. `AlertRule.budgetOverrunLastFiredPeriod` stores the last `"YYYY-MM"` (UTC) period the rule fired for; `evaluateBudgetOverrunAlert` fires once per period the moment current-month spend (computed the same way `/budgets` does, `Transaction` rows with `amountCents < 0` in `[startOfMonth, startOfNextMonth)`) exceeds the budget.
- `REBALANCING_DRIFT` rules (v1.16) reference a specific `Holding` like `HOLDING_PRICE` does, but compare `|driftPts|` (`computeHoldingDriftPts`, how far the position's actual weight has drifted from `Holding.targetPct`) against `gainThresholdPct` via `evaluatePercentAlert`, reusing the same columns `UNREALIZED_GAIN`'s `PERCENT` mode uses rather than `balanceThresholdCents` - a points comparison, not a cents one. Only holdings with a `targetPct` already set are eligible, enforced both in the Settings picker and server-side (`assertHoldingHasTarget` in `lib/actions/alert-rules.ts`, since a Server Action is directly invocable regardless of what the UI offers).
- `NEW_TRANSACTION` rules (v1.17) are the one kind that isn't a threshold-crossing comparison at all - "a new transaction exists" has no value to cross a line, so it can't reuse `balanceLastAbove`'s edge-trigger dedup. Uses its own cursor instead, `AlertRule.lastNotifiedTransactionAt` (`null` = never evaluated - the first check establishes the baseline from the latest already-matching transaction's `createdAt` **without firing**, same never-fire-on-first-check convention as `netWorthAlertLastAbove`, so creating the rule doesn't dump an account's entire history into one notification). `accountId` reused as scope (`null` = every account, same "null is valid input" precedent as `UNREALIZED_GAIN`); `balanceThresholdCents` reused as a **minimum absolute amount** to alert on, not a crossing value; a new `transactionDirection: DEBIT | CREDIT | null` enum (`null` = both) is the one genuinely new customization axis this kind needed. Internal transfers are unconditionally excluded (`excludeInternalTransfers`), not a rule option, matching every other transaction query in this app. Deliberately **not** reset on a later threshold/direction edit, unlike every other kind's own dedup flag (`lib/actions/alert-rules.ts`'s `applyNewTransactionUpdate`) - this cursor means "already told the user about this transaction," which stays true regardless of a later filter change; verified live (edited a rule's minimum amount via Settings, confirmed `lastNotifiedTransactionAt` in the DB was untouched). Confirmed live end-to-end otherwise too: a fresh rule's first check set the baseline without notifying despite existing history, a real new matching transaction fired the alert and advanced the cursor, a repeat check didn't re-fire, and both the minimum-amount and direction filters correctly excluded transactions that shouldn't match.
- No per-rule channel routing - every kind calls the same `dispatchAlert` every built-in trigger uses, same reasoning as the loan/sync-failure toggles' own "broader than what was asked" note above.
- `accountId`/`holdingId`/`categoryId` are all `onDelete: Cascade` (not `Transaction`'s `SetNull`-on-`Category` convention) - a rule whose account/holding/category was deleted has no purpose left, and a nulled-out rule would sit dead in the Settings list instead of just disappearing with it.

**Settings UI split** (`components/settings/alert-channels-section.tsx` + `alert-triggers-section.tsx`, replacing a single earlier `alerts-section.tsx`) - the original one-form design mixed "how you're notified" (ntfy/email config) with "what triggers a notification" (net worth threshold, loan/sync-failure toggles) in one long scrolling form, which read as cluttered once custom alert rules were added below it. Split into two cards, each with its own Server Action (`updateAlertChannels`/`updateAlertTriggers` in `lib/actions/alerts.ts`, replacing the old combined `updateAlertSettings`) and its own Save button, so updating a channel doesn't require re-submitting trigger config and vice versa. `AlertChannelsSection` stays `"use client"` (the email-preset dropdown and ntfy generate/copy buttons need interactivity); `AlertTriggersSection` is a plain server component - nothing in it needs local state, just native form elements posting straight to a Server Action.

### Sync service - optional modules

The `sync/` service has two dedicated sync modules plus two per-institution runners:

| Module | Required credentials | Purpose |
|---|---|---|
| `sync_lcl.py` | `LCL_LOGIN`, `LCL_PASSWORD` | LCL (FR) via Woob hardcoded module |
| `sync_tr.py`'s `run()` | `TR_PHONE`, `TR_PIN` | Trade Republic via pytr, the owner's env-configured connection |
| `sync_woob.py` | `Institution.woobModule`/`woobLogin`/`woobPassword` | Generic Woob runner for any institution configured in Settings |
| `sync_tr.py`'s `run_institution()` | `Institution.trPhone`/`trPin` | Per-user Trade Republic (v2.1) - see "Per-user Trade Republic" below |

Leave credentials blank to disable a module. `sync/main.py` skips gracefully, and `app/settings/page.tsx`'s "Synchronisation automatique" section (the dedicated LCL/TR `SyncStatus` cards, distinct from any Woob-configured institution that happens to also be named "LCL") mirrors that gate: each card - and the section itself, when neither applies - only renders when `LCL_LOGIN`/`TR_PHONE` is actually set. A fresh install with zero `.env` bank credentials used to show both cards permanently stuck on "Jamais synchronisé" regardless, which read as broken and, once a user separately added a Woob-configured "LCL" institution of their own, produced two differently-behaving "LCL" surfaces on the same page. `sync/db.py` contains shared PostgreSQL helpers - do not duplicate inline.

**`infer_account_type()` (`sync/db.py`) guesses an `AccountType` from a raw bank-reported account label** - Woob has no structured "is this a savings account" field of its own, so both `sync_lcl.py` and `sync_woob.py` need this and call the same shared function (`ACCOUNT_TYPE_KEYWORDS`, a case-insensitive substring match, defaulting to `CHECKING` when nothing matches). This is itself a real instance of the "do not duplicate inline" rule stated above being violated and then fixed (v1.15.1): each script used to carry its own local copy, and they had already drifted apart (`sync_woob.py` had gained `"savings"` and the investment-account keywords, `sync_lcl.py` hadn't) before a user report - some of their own real Livret A/LDDS/PEL/CEL/Livret Jeune accounts landing in "Liquidités" instead of "Épargne" on the dashboard - traced the root cause to a missing `"lep"` keyword (a Livret d'Épargne Populaire's raw label is often just "LEP", with no "livret" substring for the older lists to catch). Consolidated into this one function both scripts import, so the two lists can't silently diverge again.

This only affects account-type classification going forward, at sync time when an `Account` row is first created - it does **not** retroactively fix an account already sitting in the database under the wrong type, since nothing re-runs `infer_account_type()` against an existing row. **`scripts/fix-account-types.sh`** is the one-off correction for that: same `.env`-sourced `docker compose exec` convention as `scripts/backup.sh`/`scripts/debug-*.sh`, dry-run by default (prints which accounts it would touch), `--apply` after typed confirmation to actually update. Deliberately scoped to `CHECKING -> SAVINGS` only, using the exact same keyword predicate as `ACCOUNT_TYPE_KEYWORDS`'s SAVINGS-mapped keys (kept in sync manually, noted in the script's own comment) - both types share the same `HistoricalBalance`-based data model (see "Data model" below), so this is a pure metadata correction with no data migration involved. Never touches `INVESTMENT`/`CRYPTO`/`LOAN`/`REAL_ESTATE`/`AUTOMOBILE`/`MEAL_VOUCHER` - those have a genuinely different data model (holdings, computed-at-runtime capital, manual values), and a blind reclassification there could silently misrepresent an account's value rather than just relabel it. There's no UI-based account-type editor yet (only account name, via `renameAccount`) - a real gap this script works around for the accounts affected by this specific bug, not a general-purpose fix.

**Interactive 2FA setup for any Woob-configured bank** (`sync/setup_woob.py`) - a bank added via Settings → "Configurer Woob" that requires strong authentication on first connect used to be a dead end: `sync_woob.py` only recognized the "wait and approve" family of Woob exceptions and, on catching one, told the user to run `sync_woob.py --setup <id>` - a flag that was never actually implemented. A bank whose 2FA is instead an SMS/email/app-generated **code** (`SentOTPQuestion`/`OfflineOTPQuestion`) wasn't even recognized as needing setup at all - it just fell into the generic error handler. Fixed by generalizing the same interactive start/complete pattern `setup_lcl.py`/`setup_tr.py` already use for their one hardcoded bank each, to work for any `institution_id`:

- `start_setup(institution_id)` reads credentials from the `Institution` row (not env vars - this is the generic UI-configured path, see `sync_woob.py` above) and attempts `iter_accounts`, bucketing whatever Woob raises into three UI-facing shapes - confirmed against `woob==3.7`'s actual exception taxonomy (`woob/exceptions.py`) rather than guessed:
  - `pending_approval` - `AppValidation`/`DecoupledValidation` and friends (e.g. LCL's Certicode Plus): nothing to submit, just wait and retry.
  - `code_required` - `SentOTPQuestion`/`OfflineOTPQuestion`: the exception carries `.fields` (`Value` objects whose `.id` is a **backend config key**, not an arbitrary label) and `.medium_type`/`.medium_label` (e.g. "sent by SMS to 06 12..."). The only documented way to resume is `backend.config[field.id].set(code)` then retry - confirmed against Woob's own reference CLI (`woob/tools/application/console.py`'s `bcall_error_handler`), not invented.
  - `unsupported` - `ActionNeeded` (+ `BrowserPasswordExpired`/`AuthMethodNotImplemented`), `CaptchaQuestion`, `BrowserRedirect`: genuinely can't be driven from a web form (captcha widgets, full OAuth-style browser redirects) - surfaces Woob's own message, no retry loop offered.
- `complete_setup(institution_id, code=None)` resumes the same in-memory Woob session (`_pending`, keyed by institution id - unlike `setup_lcl.py`'s single global, several institutions could plausibly be mid-setup at once here).
- `components/settings/woob-setup-prompt.tsx` is the generic UI counterpart to `SyncStatus`'s hardcoded LCL/TR flows (that component is intentionally untouched - it's still the right place for those two specific, already-working integrations) - same two-panel shape (code input / approval-wait), rendered in the institution row only when that institution's latest `SyncLog` is `auth_required`.
- `setup_lcl.py`/`setup_tr.py`/`sync_lcl.py` are deliberately **not** touched or merged into this - they're the dedicated `.env`-configured paths (`LCL_LOGIN`/`TR_PHONE`, see "Sync service - optional modules" above) and keep working exactly as before, entirely independent of any `Institution` DB row. This is purely additive for every other institution.

  `app/settings/page.tsx`'s institution-row Woob controls (sync status icon, `InstitutionSyncButton`, `WoobSetupPrompt`, `ConfigureWoobDialog`) used to be gated behind a `DEDICATED_SYNC_INSTITUTIONS` name-based guard (`new Set(["lcl", "trade republic"])`, skipping any institution whose `name.toLowerCase()` matched) - removed after a real production bug: `Institution.name` is globally unique, and both the seeded reference row (`prisma/seed.ts`) and `AddInstitutionDialog`'s own catalog picker auto-fill this exact name when a user picks "LCL" or "Trade Republic" from the Woob module list - so a user who genuinely configured real Woob credentials on an institution literally named "LCL" had every one of these controls silently disappear, including `ConfigureWoobDialog` itself (no way to even edit or clear the config afterward via UI). The guard's only real justification - not showing Woob management UI on the env-dedicated integrations - was already handled more precisely by `inst.woobModule` being falsy on the seeded reference row; the name check added nothing but this collision.

  **Removing that guard exposed a second, costlier problem** - confirmed the hard way in production, not just reasoned through. `sync_lcl.py`/`sync_tr.py` and `sync_woob.py` write different `syncId` formats for what can be the exact same real bank account (`lcl:<id>` vs `woob:<institutionId>:<id>` - see `upsert_account`'s `WHERE "syncId" = %s` dedup lookup in `sync/db.py`), so configuring Woob credentials on an institution that also has a live `.env`-dedicated sync doesn't update the existing accounts - it silently creates a full second set (same balances, same labels, double-counted in net worth) the next time either sync runs. `dedicatedEnvNames()` in `app/settings/page.tsx` (checks `LCL_LOGIN`/`TR_PHONE` presence, mirroring the dedicated-section gate above) is passed into both `ConfigureWoobDialog` and `AddInstitutionDialog` as `hasDedicatedEnvSync`/`dedicatedEnvNames`, rendering a warning banner (not a hard block - a deliberate, supervised migration off the `.env` path is legitimate, same reasoning as the "Migrating an existing dedicated integration to Woob" note below) whenever the institution being configured matches an active dedicated source. No automatic dedup was attempted (e.g. matching by IBAN across the two `syncId` formats) - out of scope for a warning-first fix, and the two scripts' account-discovery order isn't guaranteed to expose a stable shared identifier without deeper changes to both.

  **Migrating an existing dedicated integration to Woob, if you ever do it anyway**: keep both `.env` credentials and the Woob config live only long enough to confirm the new sync works, then either clear the Woob config (`ConfigureWoobDialog` → "Supprimer la config") to stay on `.env`, or click "Migrer maintenant" in the same dialog's warning banner (`migrateDedicatedSyncToWoob` in `lib/actions/institutions.ts`) to complete the cutover - it deletes the `lcl:`/`tr:`-prefixed `Account` rows (cascades to their `Transaction`/`HistoricalBalance`/`Holding` automatically, every FK pointing at `Account` is `onDelete: Cascade`) once at least one `woob:<institutionId>:`-prefixed account already exists as proof the new sync actually produced something - refuses to run otherwise, so it can never delete the only copy of an account's history. The confirmation step shows both counts (dedicated-sync accounts vs. already-migrated Woob accounts) side by side specifically so a mismatch - Woob discovering fewer accounts than the dedicated integration ever did - is visible before confirming, not after. **This only touches the database** - it cannot edit `.env` from inside a Server Action, so the user still has to remove `LCL_LOGIN`/`LCL_PASSWORD` (or `TR_PHONE`/`TR_PIN`) themselves and restart the containers; the dialog's post-migration message repeats this. Never leave both running - every scheduled sync (every 4h) re-creates the duplicate set if the losing side's `.env` config is still there to re-trigger it.

  **Real production incident (2026-08): matching account counts is not the same as matching history depth.** A user's confirmation step showed "5 accounts vs. 5 accounts" (a clean match) and they clicked "Migrer maintenant" - but the dedicated `.env` sync's accounts held years of real `Transaction`/`HistoricalBalance` rows, while the just-configured Woob accounts had only started accumulating their own days earlier. The cascade delete erased that history permanently; it was recovered by hand from a `pg_dump` backup taken shortly before. Fixed by `getMigrationHistoryDepth` (`lib/actions/institutions.ts`) - fetches the oldest `Transaction`/`HistoricalBalance` date on each side (dedicated-sync accounts vs. Woob accounts for the same institution) - and `historyDepthLossDays`/`HISTORY_DEPTH_WARNING_DAYS` (`lib/domain/institutions.ts`, a pure function so it's unit-testable independent of Prisma) - a fixed 60-day threshold, same "named constant, not user-configurable" convention as `isLoanNearlyPaidOff`'s 5%: a few days' gap (Woob simply started syncing slightly later than the last `.env` sync ran) isn't worth alarming over, but a gap measured in months means real history is about to be destroyed. Only fetched for institutions where the migrate button would actually be offered (both a legacy and a Woob account already exist) - not on every settings page load, since it's a couple of extra queries that are pointless for every other institution. Verified live (Playwright against a seeded worst-case scenario: a legacy account with a 2024 transaction vs. a Woob account with only a 2026 one) that the warning renders with the real interpolated dates and day count, not just that the code compiles.

**The "Configurer Woob" module picker lists real banks, not a hardcoded 17-entry guess.** `GET /woob/modules` (`sync/main.py`) calls `Woob().repositories.get_all_modules_info()` and filters to modules with `CapBank` in their capabilities - ~96 real banks/brokers, fetched from Woob's own repository index. Doesn't force a network refresh itself: `sync/entrypoint.sh` already runs `woob config update` on every container start, so the local index this reads is kept fresh without adding a round-trip to every dialog open. `getWoobBankModules()` (`lib/actions/sync.ts`) fetches this with a 1h Next.js cache (`next: { revalidate: 3600 }`, same convention as the Yahoo Finance fetches in `lib/services/exchange-rate.ts`) and falls back to a small fixed list of major French banks if the sync service can't be reached (e.g. local dev, where only the DB container runs - see "Development commands" above) - so the dialog still works somewhere, just without the full catalog. "Autre" (custom module name) stays as the escape hatch for anything not tagged `CapBank`, or genuinely absent from Woob's catalog entirely (confirmed for Revolut specifically - searched the full ~1400-module index, no match, not a gap in this list). Same check run again later for the ROADMAP's "more broker integrations" wishlist: Degiro, Boursorama, Binance, and Kraken all carry `CapBank` and are already reachable through this same picker today, no new code needed - only Interactive Brokers came back with no module match, confirmed the same way as Revolut (see `ROADMAP.md`'s v1.12 section). This replaced `sync_woob.py`'s own `--list` CLI flag, which shelled out to `woob config -l` - never valid syntax (the real subcommand is `woob config modules`) - removed rather than fixed, since nothing needs a CLI listing path once the dialog fetches this itself.

`getWoobBankModules()`'s result is passed as a `modules` prop into **both** bank pickers that need it - `ConfigureWoobDialog` (editing an existing institution's Woob config) and `AddInstitutionDialog` (Settings → "Ajouter une institution", the very first bank picker a new self-hosted user sees). Real regression caught in production testing: `AddInstitutionDialog` originally carried its own copy-pasted `WOOB_MODULES` constant (the same old hardcoded 17-bank list) that never got wired to the live catalog when `ConfigureWoobDialog` was switched over - so a brand-new install with zero institutions configured yet only ever saw the short list, in the one dialog that matters most for a first-time setup. Fixed by deleting that dialog's own copy and passing the same `woobModules` prop `app/settings/page.tsx` already fetches once per render - if a third bank-picker call site is ever added, wire it to the same prop rather than reintroducing a local copy.

**Trade Republic transaction history**: `sync_tr.py` originally only synced positions and an aggregate cash balance (via `record_balance`) - unlike LCL/Woob, it never wrote individual `Transaction` rows, so the TR cash account had no labels for budget categorization or recurring-transaction detection, only a balance that moved with no explanation. Fixed by fetching TR's own activity-feed API (`timelineTransactions` + `timelineActivityLog`, both cursor-paginated, newest-first - pytr's own `Timeline` class fetches and merges both the same way, since between them they cover everything money-related: card payments, transfers, trades, dividends, interest) and upserting each into `Transaction` via the same `upsert_transaction()` helper LCL/Woob already use, so budgets/recurring-detection work identically for TR's cash account. Deliberately **not filtered to "spending" only** - trades/dividends/interest are imported too, exactly mirroring the real account activity (same reasoning a bank CSV import would show a transfer to a broker as a line item) - the user categorizes what's relevant via the existing budgets UI. `_timeline_item_to_transaction()` builds the label from `title`/`subtitle` (e.g. "Amazon - Kartenzahlung"), skips cancelled items and items with no monetary amount (informational-only timeline entries), and `_fetch_timeline_feed()` stops paginating a feed as soon as an entire page is already-known (`syncId` already in DB) - since the feed is strictly newest-first, everything further back is guaranteed already synced, which is what keeps every sync after the first fast. The very first sync has no known ids, so it paginates the full available history (deliberate - a "recent window only" default would have missed a lot of a long-time user's spending history for a feature specifically meant to make budget tracking finally work for TR).

### Per-user Trade Republic

`v2.1`'s headline item. v2.0 gave every user their own portfolio but left the bank credentials behind - `TR_PHONE`/`TR_PIN` are `.env` values, one per instance, so only the owner could sync Trade Republic and (Woob having no TR module) nobody else could sync it at all. That constraint is documented under "Multi-user architecture" above; this removes it. `Institution` gained `trPhone`/`trPin`, the exact per-institution counterpart to `woobLogin`/`woobPassword`, and `trPin` is plaintext for the same reason `woobPassword` is.

**`Account.syncId` is globally unique, so the shape of these strings is the whole feature.** `sync_tr.py` wrote fixed ids - `tr:cash`, `tr:cto`, `tr:pea`, `tr:crypto` - which are per-*kind*, not per-*user*: two people each with a TR cash account collide on the first insert and the second silently overwrites the first. The per-user path now writes `tr:<institutionId>:<suffix>`, mirroring `woob:<institutionId>:<nativeId>`, while `run()` keeps writing the legacy two-segment id so existing installs are untouched - the same coexistence `lcl:` and `woob:<id>:` already have. `lib/domain/sync-ids.ts` is the single place that shape is built and parsed (`buildTrSyncId`/`parseTrSuffix`/`isTrCashAccount`/`isLegacyEnvSyncId`), with `sync/db.py`'s `_is_trade_republic_sync_id` as its Python mirror; `__tests__/sync-ids.test.ts` pins every case. Two call sites had to stop comparing against the literal `"tr:cash"`: `lib/domain/analytics.ts` (TR's own cash interest rate, which would have silently produced an understated passive-income figure for per-user accounts - no error, just a wrong number) and `migrateDedicatedSyncToWoob`'s legacy-account set, where a per-user TR account being misread as legacy would have offered it up for migration and then cascade-deleted its whole history.

**Namespacing the ids alone did not fix the collision, and only a real database showed it.** With `sync_tr.py` correctly writing `tr:<institutionId>:cash`, a two-user test still produced one shared row. The cause was `upsert_account`'s native-id fallback in `sync/db.py` - the `LIKE '%:<native_id>'` cross-source lookup added after the v1.11 LCL/Woob duplicate-account incident, which matches on the trailing colon segment. That segment is a unique bank-side account id for Woob, which is exactly what makes the fallback correct there, and an account *kind* for Trade Republic, shared by every user on the instance. So the fallback matched two different people's accounts as the same one, with full confidence. Fixed by exempting TR ids from that fallback specifically (`_is_trade_republic_sync_id`), after re-verifying the LCL/Woob dedup it exists for still works. Worth remembering as a class: both writes were individually correct and the bug lived in a third function that read them back, so no unit test on either writer would have found it.

**Session isolation needed no process or working-directory tricks.** Checked against the exact commit `requirements.txt` pins, not a local install: `TradeRepublicApi.__init__` takes a `cookies_file`, and omitting it defaults to `cookies.<phone_no>.txt` rather than one fixed file - so two users never share a session even by accident. `tr_cookies_path()` passes it explicitly anyway (`~/.pytr/cookies.inst-<sanitised id>.txt`) so the file a given institution owns is deterministic and `_drop_session_file()` can delete exactly one.

**Everything else follows patterns already here.** `run_institution(institution_id)` reads credentials from the `Institution` row and reuses `_fetch_and_write_once()` unchanged via a `scope_institution_id` parameter - the batch `run()` is byte-identical to before the split, which the existing `test_sync_tr.py` suite proves. `sync/setup_tr_institution.py` is modelled on `setup_woob.py` (pending state keyed by institution id, not a module-level global, since several family members can plausibly be mid-setup at once) but is much smaller: TR has exactly one second factor, a code pushed to its app, so there is no equivalent of Woob's approval-only/code/unsupported split - just `start_setup` → `complete_setup`. `sync/main.py`'s `_institution_provider()` dispatches the three existing `/sync/institution/{id}/...` routes on whichever credential set is populated, and `_run_all_tr_institutions()` joins the 4h cron.

**The backend is never something the user picks.** Trade Republic is one entry in the same searchable bank list as every Woob bank (`lib/domain/sync-providers.ts`'s `bankPickerEntries`, consumed by `AddInstitutionDialog` and `ConfigureWoobDialog`), and choosing it swaps the credential fields to phone/PIN. `TRADE_REPUBLIC_MODULE` is an underscore-wrapped sentinel so it cannot collide with a real Woob module name, which are plain lowercase identifiers; a Woob module labelled "Trade Republic" would be dropped in favour of the native path, which is a guard against a future catalogue change rather than something that fires today.

This replaced the first cut, a standalone "Configurer Trade Republic" button on every institution row, which the user rejected on sight and for the right reason: it appeared next to institutions that were not Trade Republic and could not become it, and it turned adding an account into "create something generic, then attach TR to it" rather than "pick your bank". One `ConfigureWoobDialog` now covers every backend (its name is historical - see its own header comment).

**One provider per institution, enforced where the choice is made.** `setWoobConfig` and `setTradeRepublicConfig` (`lib/actions/institutions.ts`) each null out the other's fields, and `createInstitution` picks exactly one from its form payload. Without that an institution could hold both, and which backend ran would depend on the order of two `if`s in `_institution_provider()` rather than on anything the user picked - a silent, order-dependent outcome. `__tests__/institutions-actions.test.ts` asserts every one of those write shapes. The status icon, `InstitutionSyncButton` and setup prompt are shared between the two paths - only the `SyncLog` key (`tr:<id>` vs `woob:<id>`) and the prompt component differ.

**`createInstitution` attaches to a credential-less row of the same name rather than failing.** `Institution.name` is unique per user and `prisma/seed.ts` ships reference rows for the common banks - including one literally named "Trade Republic" - so on a seeded install, the documented default, picking that entry is a name collision. It used to throw, and `AddInstitutionDialog` had no `try`/`catch` at all, so the dialog just sat there as if the button had not been clicked. Found by driving the real flow in a browser, not by reading the code: the unit tests mocked the create and the type-checker had nothing to say. An institution that already syncs is refused with a real message instead, since silently repointing a working connection is the one outcome nobody could have meant.

**`TradeRepublicSetupPrompt` is its own component rather than a branch inside `WoobSetupPrompt`** for the same reason: none of Woob's three outcome families apply. What TR has and Woob does not is an expiry - it reports how long the pushed code stays valid - so this one shows a live countdown and swaps Confirm for a "new code" button once it hits zero, instead of letting the user watch a valid-looking code get rejected with no explanation.

**It renders as soon as the institution is configured, not only on `auth_required`** (fixed in v2.1.1). Copying `WoobSetupPrompt`'s gate was wrong for Trade Republic: it *always* needs its pushed-code ceremony before any sync can work, so a freshly configured institution has no `SyncLog` at all and the Connect button was hidden exactly when it was needed. The only way to reveal it was to click "Synchroniser", read the failure, and let that write an `auth_required` row - which is why a user reported being unable to connect a Trade Republic account through the UI at all. The gate is deliberately *not* relaxed for Woob, where a first sync can legitimately succeed from login and password alone.

**Migrating off `TR_PHONE` onto per-user Trade Republic** goes through the same `migrateDedicatedSyncToWoob` flow as LCL, which needed two corrections to be safe for it. Its destination check counted only `woob:<id>:` accounts, so someone moving to their own Trade Republic credentials could never satisfy it and the migration refused forever; it now accepts either backend (`perUserAccountFilter`). More seriously, it selected the accounts to **delete** with `startsWith: "tr:"` - which also matches `tr:<institutionId>:`, so it would have deleted the accounts the migration had just created, the same history loss the v1.11 LCL incident produced. Trade Republic's legacy accounts are now matched by exact id (`legacyTrSyncIds()`), never by prefix; LCL keeps its prefix because nothing else writes `lcl:`. The existing history-depth warning applies unchanged.

**Deliberately unchanged**: `setup_tr.py`, `sync_tr.py`'s `run()`, and the whole `TR_PHONE`/`TR_PIN` env path, exactly as `setup_lcl.py` was left alone when `setup_woob.py` generalised the Woob path in v1.12. `sync_tr_realtime.py` also still listens only for the env-configured connection - a per-institution real-time listener would mean one persistent websocket per user, which is a real scoping decision rather than a line of plumbing, and is not part of this release.

### Trade Republic real-time tracking

`v1.17`'s headline item - scoped live during the v1.16.1 retrospective, not assumed: checked pytr's actual pinned source (`requirements.txt`'s exact git commit, fetched and read directly), GoCardless's actual docs, and Powens' actual sync cadence before committing to anything. The finding: true instant "just spent 5€" notifications only turn out to be achievable for Trade Republic, because its own API is genuinely websocket/push-capable (`sync_tr.py` already talks to it over a websocket, it just opens the connection, does one request/response round-trip per topic, and closes, throwing that persistent-connection capability away every 4 hours) - LCL/other Woob-scraped banks and GoCardless-synced ones have no equivalent, PSD2 aggregation being batch/rate-limited on the bank's own side, not something this app's own engineering effort can route around. See `ROADMAP.md`'s v1.17 section for the full scoping writeup and the backlog items this same research corrected (GoCardless webhooks downgraded - the webhook docs findable are for its Payments product, not Bank Account Data).

**The goal is not a push notification** - Trade Republic's own app already sends one per purchase, a second one from Finalibaba would be redundant (confirmed directly with the user). The goal is keeping Finalibaba's *own* displayed data current, so opening the dashboard/account page never shows data up to 4h stale, and - since this app has no existing live-refresh mechanism anywhere (`AutoSync` triggers once per page load, nothing polls or pushes into an already-open tab) - an *already-open* tab updates live too, without a manual reload.

**Backend: one new long-lived `asyncio.create_task` in the existing `sync` container - no new Docker service, no new dependency.** `sync/main.py` runs a single uvicorn worker (no `--workers`), so there's no per-worker duplication risk; its existing `lifespan` context manager is the natural startup/shutdown hook for a task that must live for the process's whole lifetime - a genuinely new pattern for this codebase (every other "background work" here is a bounded `ThreadPoolExecutor` job). Gated on `TR_PHONE` (same as the existing cron) **and** a new `TR_REALTIME_ENABLED` env var - opt-in, off by default, since this is the first persistent outbound connection this container ever holds open, the same "new/novel capability = opt-in" treatment every other new alert/notification category in this codebase already gets.

- `sync_tr.py` was split to make this possible without duplicating logic: `_fetch_and_write_once(api, cur, *, institution_id, sec_accounts, has_crypto, cash_account_id, known_tx_ids, source="trade_republic")` is the extracted fetch-from-TR-and-write-to-DB cycle (unchanged behavior - the exact same code that used to be inline in `run()`), now callable repeatedly on the same open `api` connection. `run()` itself becomes a thin wrapper: connect, call it once, close - byte-identical behavior to before the split, verified by the full existing `test_sync_tr.py` suite passing unchanged.
- `sync_tr_realtime.py` (new) - `listen_forever()` is the reconnect-with-backoff wrapper (pytr has **no built-in keepalive or auto-reconnect**, confirmed against its own pinned source - `_recv_subscription()` can be awaited repeatedly on the same subscription for successive pushes with no need to resubscribe, but the caller owns reconnection entirely). `_run_one_session()` connects once (same cookie-based `resume_websession()` path `run()` already uses), subscribes to `neonPortfolio`/`cash`(/`cryptoPortfolio` if enabled) - the topics confirmed push-capable, **not** `timelineTransactions` itself, which `sync_tr.py` only ever uses as a one-shot paginated fetch and isn't confirmed to push - then loops `_fetch_and_write_once()` on every push from any of them, treating the push as a "something happened, go re-derive the real delta" trigger rather than trying to diff the pushed payload directly. A real auth error (`_is_auth_error()`) stops the listener (no point retrying against an invalid session) and writes to `SyncLog` under a **separate source, `"trade_republic_realtime"`** - deliberately not sharing the batch cron's own `"trade_republic"` identity, so the listener's own reconnect/failure cycles can't confuse `checkSyncFailures()`'s `SyncFailureState` dedup for the cron path. The existing 90-min HTTP keepalive job (a different concern - server-side session TTL, not the websocket's own liveness) keeps running completely unchanged alongside this.
- After every successful real-time write, the listener POSTs to `/api/realtime/notify` (see below), then `/api/transactions/auto-categorize` and `/api/alerts/check` - the same bearer-token pattern `_auto_categorize()`/`_check_alerts()` in `main.py` already use for the cron path - so a live-detected transaction gets categorized and can trigger a custom alert rule immediately, not up to 4h later.
- Deliberately **not** bundled into this pass: migrating off `pytr`'s Playwright-based WAF bypass to the community `tr-api` successor (ECDSA device-pairing auth, no browser automation) - a real, separate risk noted during scoping (pytr's WAF bypass is reportedly getting rate-limited more often as of mid-2026) but swapping the client would be a materially bigger, riskier change that could destabilize the *already-working* batch sync too. Worth its own follow-up look later.

**Frontend: Server-Sent Events, not WebSocket** - the data only ever flows server→browser ("something changed, go re-fetch"), never the other direction, which is exactly SSE's shape. Confirmed against Next.js 16's own current docs (`node_modules/next/dist/docs/01-app/02-guides/streaming.md`) that a Route Handler returning a `ReadableStream` with `Content-Type: text/event-stream` is an explicitly documented, supported pattern - this codebase already streams a `ReadableStream` response elsewhere (`app/api/backup/route.ts`'s `GET`). The browser's native `EventSource` reconnects on its own after a dropped connection - no client-side reconnect logic to write, unlike the Python listener's own websocket which needs it built by hand.

- **The SSE payload is a bare signal, not real data.** Pushing actual computed dashboard values over SSE would mean duplicating `computeDashboard()`/`computeAnalytics()`'s entire server-rendering pipeline a second time for a "live" path. Instead the signal just tells the open tab to call `router.refresh()` (Next.js's own mechanism to re-run the *current route's* Server Components against the DB's current state) - 100% reuse of the existing render pipeline, zero new data-shape to maintain, and it naturally scopes itself correctly (the dashboard refreshes net worth, an open account page refreshes its own transactions) with no cross-page coordination code.
- `lib/services/realtime-bus.ts` is a module-level singleton (a plain `Set` of subscriber callbacks, not a full `EventEmitter`) fanning the signal out to every open SSE connection - single-process-only by design, correct for this app's single-container/single-user deployment model, the same accepted-scope precedent `sync/setup_tr.py`'s own in-memory `_pending` global already sets. A ~2s in-process debounce coalesces bursts (cash and portfolio both changing from the same trade) into one broadcast.
- `app/api/realtime/stream/route.ts` (browser-facing, `dynamic = "force-dynamic"`) subscribes to the bus for the connection's lifetime and sends a `: heartbeat` comment line every 20s to survive a reverse proxy's own idle timeout - comment lines are ignored by `EventSource`'s `message` dispatch, so they never trigger a spurious refresh. **Goes through the normal NextAuth session gate** (not in `proxy.ts`'s no-auth matcher) since it's opened directly by the browser, unlike every other sync↔app call in this codebase.
- **Real bug found and fixed during live verification**: the very first version enqueued nothing until either a real signal or the first 20s heartbeat - confirmed with a raw TCP socket probe (curl's own buffering under `-v` was misleading) that the underlying HTTP response doesn't flush *any* bytes, including headers, until the first `controller.enqueue()` call, so `EventSource`'s `onopen` silently didn't fire for up to a full heartbeat interval on a fresh connection. Fixed by enqueueing an immediate `: connected` comment line as the very first thing in the stream's `start()` callback - confirmed after the fix that time-to-first-byte drops to ~5ms.
- `app/api/realtime/notify/route.ts` (server-to-server, called by the Python listener) uses the same inline `Authorization: Bearer <NEXTAUTH_SECRET>` check `/api/alerts/check` already has - not `lib/services/api-auth.ts`'s `ApiKey` model, a different trust boundary. Added to `proxy.ts`'s no-auth matcher as `api/realtime/notify` specifically (not a bare `api/realtime` prefix, which would have accidentally also exempted `/stream`).
- `components/layout/realtime-refresh.tsx` (new, mounted once in `app/layout.tsx` alongside `AutoSync`/`ServiceWorkerRegistration`/`OfflineBanner`) opens the `EventSource` and calls `router.refresh()` on every message. Mounted unconditionally, including on `/shared/[token]` - deliberate, not an oversight: it's harmless there (no sync is ever triggered, only a re-render of already-computed data), and the same SSE plumbing stays reusable for a future real-time trigger beyond Trade Republic, not a single-purpose pipe.

### Reduced sync interval for Woob-synced banks

`v1.17` item 2, the realistic freshness ceiling for LCL and every user-configured Woob institution - screen-scraping with no official push/webhook mechanism at all, unlike Trade Republic (see "Trade Republic real-time tracking" above). `sync/main.py`'s single `_run_all()` (previously misleadingly logged as "Daily sync" despite running every 4h) was split in two:

- **`_run_woob_sources()`** - `_run_lcl()` + `_run_all_woob()`, followed by `_auto_categorize()`/`_check_alerts()` so a freshly-scraped transaction gets categorized and can trigger an alert within this same cadence, not up to 4h later on the next full sync. Scheduled every **30 minutes** (`interval` job, `id="woob_sync"`) - a real, disclosed tradeoff picked after weighing it directly with the user, not a technical ceiling: more frequent scraping raises the risk of a bank's own anti-automation detection flagging the account, and 30 min was chosen as a middle ground (8x fresher than the old 4h cadence) rather than the more aggressive 15 min option also considered.
- **`_run_all()`** - now just Trade Republic's own batch fallback + investment balance snapshots, plus the same categorize/alert follow-up as a safety net (mostly a no-op by the time it runs, since the 30-min job already processed most of what it'd find - harmless, not wasted work, `autoCategorizeTransactions`/`checkAlerts` are both idempotent). Stays on the original 4h cron.
- **Deliberately excludes GoCardless-synced accounts** - GoCardless sync lives entirely in the Next.js app, never in this service, and its own PSD2 rate limit (4-10 requests/day per account per endpoint, see "GoCardless" above) makes anything faster than the existing cadence structurally impossible regardless of what this app does on its own side.
- Global, not per-institution - considered a per-institution configurable interval (some banks plausibly warranting more caution than others) and deliberately scoped it out for this pass as more UI/DB-migration work than the ask justified; revisit if a specific institution's scraping actually gets flagged at 30 min.
- Locking against overlapping runs is unaffected by the split - `_lcl_lock`/APScheduler's own per-job-id `max_instances=1` default already prevented a job from overlapping itself before this change, at whatever cadence it runs.

### Backup & restore

Two paths, both wrap `pg_dump`/`psql` (full DB dump - schema + data, never a hand-rolled Prisma export, to avoid drift and BigInt/Decimal serialization issues):

- **CLI**: `scripts/backup.sh` / `scripts/restore.sh` - call `docker compose exec db pg_dump|psql`. `restore.sh` pauses `app`/`sync` if present and requires typed confirmation.
- **UI**: Settings → Backup & restore (`components/settings/backup-restore-section.tsx`), backed by `app/api/backup/route.ts` (`GET` streams a gzip dump, `POST` restores from an uploaded file, auto-detecting gzip vs plain `.sql`). This runs `pg_dump`/`psql` from inside the `app` container itself - that's why the `runner` stage in `Dockerfile` installs `postgresql16-client` (must track the `postgres:16-alpine` server version; a client older than the server can't dump it). Hidden entirely in `DEMO_MODE` (matches the auto-sync section's pattern).

Both directions use `pg_dump --clean --if-exists` (so restore drops/recreates objects first) and `psql --single-transaction` (restore is all-or-nothing, no partial state on error). Never echo raw `pg_dump`/`psql` stderr to the client - log it server-side and return a generic error message, per the exception-exposure fix in commit `1ae43c0`.

Implementation notes (post-v1.2.0 audit fixes):

- `buildConnectionString()` passes the *whole* `DATABASE_URL` (password stripped, everything else - including query params like `?sslmode=require` - intact) as a single positional arg to `pg_dump`/`psql`, with the password supplied separately via `PGPASSWORD`. Don't go back to manually extracting `host`/`port`/`user`/`database` into separate `-h`/`-p`/`-U`/`-d` flags - that approach silently drops any connection query params.
- The `GET` handler's `ReadableStream` only closes successfully once **both** `gzip`'s `"end"` (all bytes flushed) and `pg_dump`'s `"close"` (exit code known) have fired, and only if the exit code was `0`. A pg_dump that dies mid-dump after already writing valid-looking output must **error**, not silently succeed - a truncated "successful" backup is far worse than a visibly failed download, since the corruption would otherwise only surface during an actual restore. The `settled` flag guards every controller call this can race with (`enqueue`, `close`, `error`) - including `cancel()`, which must also set it (a client aborting mid-download must not let a still-queued `gzip.on("data")` callback call `enqueue()` on an already-cancelled stream and crash the process).
- After a successful restore, the process calls `process.exit(0)` (gated to `NODE_ENV === "production"`, so local `pnpm dev` isn't killed) so the container's `restart: unless-stopped` policy hands the app a fresh Prisma connection pool - the restore just dropped and recreated the whole schema out from under any pooled connections' cached query plans, the same reason `scripts/restore.sh` stops the `app` container before restoring. `components/settings/backup-restore-section.tsx` polls the current page with a `HEAD` request (never `/api/backup` - that would trigger another full `pg_dump`) until the app responds again before reloading.

### CSV import (transactions & balance history)

For fiat accounts (`CHECKING`/`SAVINGS`/`MEAL_VOUCHER`) not covered by auto-sync - gated by `canImportCsv = isFiat && !isSynced && !account.gocardlessAccountId` in `app/accounts/[id]/page.tsx`. Two independent entry points, both rendered wherever that condition holds:

- **Transactions** - `components/account-detail/import-transactions-dialog.tsx` + `lib/actions/transactions.ts`'s `importTransactions(accountId, rows)`. Writes `Transaction` rows.
- **Balance history** - `components/account-detail/import-balance-history-dialog.tsx` + `lib/actions/balances.ts`'s `importBalanceHistory(accountId, rows)`. Writes `HistoricalBalance` rows at noon UTC (`${date}T12:00:00.000Z`, same convention as `prisma/seed-demo.ts` - avoids a midnight-UTC day shift in negative-offset timezones). Because the dashboard's net-worth-over-time chart (`app/page.tsx`) is built by aggregating `HistoricalBalance` across every account grouped by day, backfilling this way also backfills that chart - no separate "net worth snapshot" model exists or is needed.
  - Deliberately **not** offered for `LOAN` (its balance is computed at runtime via `calcCurrentCapital()`, never stored - importing a raw balance would double as a false asset in the dashboard aggregation, which doesn't know to treat it as a liability) or for `INVESTMENT`/`CRYPTO`/`REAL_ESTATE`/`AUTOMOBILE` (their current-value source of truth is holdings+live price or `manualValueCents`, not the latest `HistoricalBalance` row - importing snapshots there would create a chart whose last point silently disagrees with the value shown in the account header). Fiat accounts are the one type where `HistoricalBalance` is already the authoritative source for both current value and chart history, so there's no such discontinuity risk.

Shared design across both importers:

- CSV parsing, date parsing, header aliasing, and validation live in `lib/domain/csv-import.ts` (`parseCsvDate`, `isFutureDate`, `looksNumeric`, `makeHeaderNormalizer`) - shared by both dialog components so a fix in one place reaches both importers. Parsing and duplicate detection happen **entirely client-side** - no server round-trip until the user confirms. Header aliases (French: `libellé`/`montant`/`solde`/`valeur`) and both `YYYY-MM-DD`/`DD/MM/YYYY` date formats are accepted.
- `looksNumeric()` rejects non-numeric-but-non-empty values (`"N/A"`, `"#REF!"`, `"3.5abc"`) before they reach `parseCents()` - `parseCents()` itself falls back to `0` on `NaN` (a deliberate leniency other callers, like the settings tax-rate inputs, rely on), so without this guard a garbage CSV cell would silently import as a real €0.00 row instead of being flagged.
- `isFutureDate()` rejects balance-history rows dated after today (UTC) - without it, a typo'd date (e.g. `2062` instead of `2026`) would become the account's displayed "current balance" everywhere (`app/page.tsx`, `app/accounts/[id]/page.tsx` both take `history[0]` ordered by `recordedAt desc`), with no delete UI to undo it. Transactions don't get this check - nothing reads "the most recent transaction" as a current-value source, so a future-dated transaction isn't a correctness bug the way a future-dated balance is.
- Both `importTransactions` and `importBalanceHistory` call `lib/actions/csv-import-guard.ts`'s `assertCsvImportEligible(accountId)` before writing anything - it re-derives the same eligibility rule as the page's `canImportCsv` (fiat type, not synced, no `gocardlessAccountId`). **Do not remove this** even though the UI already hides the import buttons for ineligible accounts: Server Actions are directly invocable regardless of what's rendered, and this is the only thing stopping a stale page or a future call site from writing CSV data onto a `LOAN`/`INVESTMENT`/synced account.
- "Duplicate" is advisory, not a hard constraint - flagged rows are unchecked by default but the user can still import them. Transactions: flagged when `date|label|amountCents` matches an existing `Transaction` for that account. Balance history: flagged when a `HistoricalBalance` already exists for that exact date. There is no hash-based auto-merge for transactions specifically, because two legitimately different transactions can share a fingerprint (e.g. two identical recurring debits on the same day) - auto-merging on content hash would silently drop one.
- Existing-row fingerprints/dates are computed server-side in the page and passed down as plain `string[]` props - never pass `BigInt` values to a Client Component, following the same "no BigInt across the RSC boundary" rule as `components/shared/export-accounts-button.tsx`.
- Every imported `Transaction`/`HistoricalBalance` row is stored at **noon UTC** (`${date}T12:00:00.000Z`), not midnight - both importers must agree on this (they didn't originally: `importTransactions` used midnight, causing a one-day shift on negative-UTC-offset deployments that `importBalanceHistory` didn't have). Midnight UTC is one keystroke away from reintroducing that bug - don't "simplify" it back to `new Date(r.date)`.
- Every imported `Transaction` gets a fresh `syncId` (`csv_` + `randomUUID()`); neither importer attempts idempotent re-import matching like the Woob/GoCardless sync paths do with their own bank-provided IDs. Re-importing the same file twice creates duplicates - that's what the client-side duplicate flagging is for.

### Recurring transactions

`/recurring` - subscriptions, bills, and regular income, with auto-detection, cash-flow projection, and missed-payment flagging. All the math lives in `lib/domain/recurring.ts` (pure functions, no DB calls, mirrors `lib/domain/loan.ts`'s "params in, computed stats out, `asOf`-dated" shape) so it stays testable in isolation from the page that calls it.

- **Detection** (`detectCandidates`) groups the last 25 months of `Transaction` rows by `(accountId, normalizeLabel(label))` - **per-account, not cross-account**, because `label` is raw bank-feed text specific to one institution's formatting; matching similar-looking labels across two different accounts risks a false merge in a way `Category` (a deliberately account-independent concept) doesn't. A group needs `MIN_OCCURRENCES = 3+`, at least 70% of its amounts within a median±tolerance band (`10%` of the median or a `5€` floor, whichever is larger - a flat 10% would be too tight for small subscriptions and a unanimous match would false-negative on one bonus month or one price change), and a median day-gap (not average - a single skipped/duplicated occurrence skews an average) landing in a frequency band (weekly 6–8d, monthly 27–33d, yearly 350–380d). The 25-month window is deliberate: a yearly pattern needs ~2 years of history before 3 occurrences exist to detect from, so anything shorter silently kills yearly detection. Detection only ever proposes `intervalCount = 1` - inferring "every 2 months" cadences from noisy gaps is out of scope; fix it via the manual edit dialog instead.
- Confirmed/paused/dismissed all live in the same `RecurringTransaction` row via `active`+`autoDetected` - dismissing a suggestion creates a row with `active: false, autoDetected: true` (`dismissSuggestion` in `lib/actions/recurring.ts`) purely so its `(accountId, normalizeLabel(label))` key is excluded from future detection passes; there's no way to distinguish "paused after being active" from "never-confirmed dismissal" in storage, and the UI doesn't try to - both just show a "Paused" badge with a Resume action.
- **Missed-payment check** (`isMissed`) only ever looks at the single most recent expected occurrence, not every occurrence since `anchorDate` - walking full history would flag a subscription cancelled 2 years ago as "missed" every month forever. `DEFAULT_GRACE_DAYS = 5` window, same amount-tolerance formula as detection.
- **Cash-flow projection** (`projectDailyCumulative`) is a *relative* running total starting at 0 over the next 90 days - deliberately not tied to actual account balances or the real net-worth calculation, to avoid conflating this with `UserSettings.salaryNetCents`/`monthlyExpensesCents` (the Analytics page's Runway/Savings-Rate cards have their own manual-entry semantics that this feature must not silently overwrite or duplicate). `components/recurring/cashflow-chart.tsx` renders this with Recharts `Area type="stepAfter"` (not `"monotone"`, copied from `components/shared/net-worth-chart.tsx`'s scaffold otherwise) - the cumulative total is a step function that jumps on occurrence days, and smooth interpolation between 90 daily points would draw a misleading ramp.
- Month-stepping (`addMonthsClamped` in `lib/domain/recurring.ts`) clamps to the last day of shorter months (anchor on the 31st → lands on Feb 28/29) - `lib/domain/loan.ts`'s `endDate.setMonth(...)` pattern does NOT do this (native `Date` overflows instead of clamping, e.g. Jan 31 + 1 month rolls to Mar 3) and must not be copied here.
- Dates use the noon-UTC convention (`${dateStr}T12:00:00.000Z`) throughout, same as CSV import - `anchorDate` must line up day-for-day against real `Transaction.date` values for missed-payment matching to work.

### Global transaction ledger

`/transactions` - search and filter every transaction across every account by label, account, category, date range, and amount, instead of only per-account or via the `/budgets/[categoryId]` drill-down. No schema change - reads the existing `Transaction` table. `lib/domain/transactions-ledger.ts` holds the pure `searchParams` parsing (`parseTransactionLedgerFilters`) so invalid-input handling is testable without a request; the actual Prisma `where` construction stays in `app/transactions/page.tsx` per this project's lib/domain-has-no-DB-calls convention. Not linked from the sidebar/mobile nav - same "off nav, reached contextually" precedent as `/tax-report` (see "Public REST API" above, and the mobile bottom nav's own "already-7-item" crowding note under "PWA / offline support"); reached instead via a "View all transactions" link on each account's own transactions table (`components/account-detail/transactions-table.tsx`), which deep-links with `?accountId=`.

- **`isInternalTransfer: false` is mandatory here too**, same as `/budgets` and `/api/v1/transactions` - easy to forget building a *new* transaction query from scratch, since it's not a schema-enforced default. A first draft of this page's `where` clause omitted it (caught before release, not in production) - the ledger would otherwise have doubled as a second, undocumented way to browse transactions the rest of the app deliberately hides.
- **Amount filter is a magnitude range, not a signed one** - `amountMin`/`amountMax` (both optional, entered in euros) filter on `|amountCents|`, not on the signed value. A user filtering "at least 50€" means either a big debit or a big credit, not "credits ≥ 50€" - matching how every other magnitude-based threshold in this app already works (`AlertRule.balanceThresholdCents`, the `/budgets` uncategorized-groups sort by absolute spend). Prisma has no `abs()` in a `WHERE` filter, so this is expressed as one or two ranges combined with a top-level `OR`: `amountMagnitudeRanges()` in `lib/domain/transactions-ledger.ts`.
  - **Real bug caught before release**: the max-only case (`amountMin` blank, `amountMax` set) was first built the same way as the two-bound case - two disjoint ranges `(x ≥ -max) OR (x ≤ max)` OR'd together - which is a **tautology**, always true for any `x`, since every number is on at least one side of zero. This silently disabled the filter entirely (every transaction "matched") rather than throwing or erroring, so it wasn't obvious from the type-checker or a build - only found by comparing actual filtered row counts against the raw dataset in manual testing. A min-set bound genuinely needs two disjoint half-lines/bands (there's a real gap around zero to exclude), but a max-only bound is one contiguous interval `[-max, max]` and must be a single range - `amountMagnitudeRanges()` now branches on `min === null` specifically to return that single range instead. `__tests__/transactions-ledger.test.ts` asserts the exact shape returned for the max-only case, not just that filtering "works", so this specific regression can't silently come back.
- The min/max amount fields are debounced together in one `useEffect` (`components/transactions/transaction-filters.tsx`), not two independent ones per field - firing `updateParams` separately per field would race, since the second call's `searchParams` closure can still be stale from before the first call's navigation has landed and re-rendered the component. The existing `from`/`to` date inputs don't share this risk in practice (a native date-picker interaction is `onChange`-immediate, not debounced, and two separate date picks are far enough apart in real usage for the first navigation to settle) but the same failure mode is theoretically present there too - not fixed here, out of scope for this feature.

### Budget rollover

Opt-in per category (`Category.budgetRolloverEnabled`, off by default so every existing budget keeps today's behavior) - unused envelope carries into next month instead of resetting to zero, matching YNAB's "give every dollar a job" model. `lib/domain/budgets.ts` holds the pure math (`monthsBetween`, `computeRolloverCarryInCents`); the actual `Transaction` query and per-month bucketing stay in `app/budgets/page.tsx`, same lib/domain-has-no-DB-calls split as `lib/domain/transactions-ledger.ts`.

- **Computed live from `Transaction` history on every render, not a maintained running balance** - no cron/scheduled job walks month boundaries updating a stored figure (unlike `sync/main.py`'s 4h APScheduler loop for alerts). Consistent with how this codebase already computes everything else that could theoretically be cached (`computeDashboard()`, `calcCurrentCapital()`) - a personal self-hosted instance's transaction volume makes re-deriving it on each `/budgets` load cheap, and it can never drift out of sync with the real ledger the way a maintained counter could.
- **Only a positive leftover compounds forward, floored at 0 each month** - a deliberately simpler, safer variant of YNAB's own model, which does carry a negative balance forward as visible debt. An overspent month never creates a deficit the next month has to pay down first, matching the roadmap wording's own "carries into next month instead of resetting to zero" framing, which only ever talks about surplus, never deficit. `computeRolloverCarryInCents(budgetCents, priorMonthsSpentCents)` walks the months oldest-to-newest, each month's available envelope being that month's budget plus whatever carried in, clamped at 0 before becoming the next month's carry-in.
- **`Category.budgetRolloverEnabledAt`** anchors the walk-forward computation to when rollover was actually turned on - bounds `monthsBetween()`'s query to real elapsed months since enabling rather than the category's entire lifetime (further capped at `MAX_ROLLOVER_MONTHS = 60`, same "safety cap, not a feature limit" reasoning as `/budgets`' own `MAX_UNCATEGORIZED_ROWS`), and means re-enabling after a pause starts a fresh carry rather than resurrecting a stale one from months the category might have sat disabled. `lib/actions/categories.ts`'s `updateCategory` only moves this timestamp to `now()` on the actual off→on transition (checked against the category's existing row before writing) - re-saving the form while rollover is already on (e.g. only changing the budget amount) leaves it untouched via Prisma's own "`undefined` in the update payload means don't touch this field" convention, so an unrelated edit can never silently reset an accumulated carry back to zero. **Verified live, not just reasoned through**: backdated a category's anchor and injected known prior-month spend directly in a dev database, confirmed `/budgets` rendered the exact hand-computed carry-in figure, then confirmed a same-form re-save with only the budget amount changed left the anchor timestamp untouched in the database.
- Every month in the walk needs a spend figure even when it had zero matching transactions (a month with no spend still means the full budget carries forward) - `monthsBetween()` enumerates every calendar month in the range up front, and the page looks up each one in a map built from a single bucketed `Transaction` query, defaulting to `0` for a month absent from the map, rather than only ever seeing months that happen to have a row.
- `CategoryCard` (`components/budgets/category-card.tsx`) receives the already-computed `rolloverCarryInCents` as a prop and only ever adds it to `budgetCents` to get the effective cap - both the progress bar percentage and the "sur {amount}" text use this effective figure, not the raw stored budget, so a category with a carry doesn't show a misleadingly tight bar. The card's text switches to "sur {amount} (dont {carry} reporté)" only when the carry is non-zero, so a category with rollover on but nothing accumulated yet still reads identically to one without rollover at all.

### Split transactions

A single transaction across 2+ categories (e.g. one supermarket trip: groceries + household goods), each split summing to the transaction's own `amountCents` - `TransactionSplit` (`transactionId`, nullable `categoryId` with `onDelete: SetNull` same as `Transaction.categoryId` itself, signed `amountCents`). `lib/domain/transaction-splits.ts`'s `validateSplitLines` (pure, ≥2 lines, no zero-amount line, sum must equal the total exactly) is the only place the sum invariant is checked; `lib/actions/transaction-splits.ts`'s `setTransactionSplits` is the sole write path (delete-then-recreate in one `$transaction`, so a partial write is never visible).

- **A split transaction's own `categoryId` goes `null`** - the category breakdown lives entirely in its `TransactionSplit` rows from that point on. This is the one design decision every other change here exists to support correctly: `Transaction.categoryId: null` had exactly one meaning before this feature ("genuinely uncategorized, please suggest one") and now has two, so every place that queried on that assumption needed an explicit `splits: { none: {} } }` (or the reverse, a `splits: { some: {...} } }` match) alongside it.
- **The auto-categorization guard is the correctness-critical one.** `autoCategorizeTransactions`'s uncategorized-pool query (`lib/actions/auto-categorize.ts`) now requires `splits: { none: {} } }` alongside `categoryId: null` - without it, self-learning/MCC/dictionary would treat every split transaction as genuinely uncategorized and silently overwrite the user's manual split on the very next sync cycle or CSV import. **Verified live, not just reasoned through**: split a real transaction in a dev database, ran "Auto-catégoriser," confirmed both the `categoryId: null` and the two `TransactionSplit` rows were untouched afterward.
- **Picking a single category always supersedes an existing split** - `setTransactionCategory`, `applyCategoryToSimilarTransactions`, and `bulkAssignCategory` (`lib/actions/transactions.ts`) all now delete any existing `TransactionSplit` rows for the affected transaction(s) in the same `$transaction` as the categoryId write. Without this, a transaction caught by one of these (a bulk "apply to similar" propagation, in particular - its candidate set isn't scoped to "uncategorized" the way the other two are, so it can realistically hit an already-split transaction) would end up with both a non-null `categoryId` *and* stale split rows - breaking the "categoryId is null iff split" invariant everything else here relies on.
- **Every category-total consumer that groups `Transaction` by `categoryId` needed a matching `TransactionSplit` groupBy, merged in** - `app/budgets/page.tsx` (`spendByCategory`/`incomeByCategory`, the rollover per-month walk above, and the uncategorized-groups query), `app/budgets/[categoryId]/page.tsx` (the drill-down), `app/api/alerts/check/route.ts`'s `checkBudgetOverrunRule`, and `app/income/page.tsx`'s "Autres revenus" year-to-date totals. `mergeCentsMaps` (`lib/domain/budgets.ts`) combines a plain-Transaction sum map with a TransactionSplit sum map for the same period, summing overlapping keys - reused across all of these rather than each rewriting the same merge. Every split query filters on the *parent* transaction's `date`/`isInternalTransfer` via the relation (`transaction: { date: {...}, isInternalTransfer: false } }`), never `TransactionSplit.createdAt` - a split represents a portion of a real transaction that happened on that transaction's own date. **Verified live, not just reasoned through**: split a real €149 transaction into €100/€49 across two categories in a dev database, confirmed both categories' `/budgets` cards changed by exactly the right amount (cross-checked against a raw SQL aggregation independent of the app code), and confirmed the drill-down page showed the split's own €100 portion on its row, not the transaction's full €149.
  - **Found and fixed a real, unrelated pre-existing gap while touching `checkBudgetOverrunRule` for this**: it never filtered `isInternalTransfer: false` at all, unlike every other category-spend query in the app - a manually-categorized internal transfer would have counted toward a `BUDGET_OVERRUN` alert but never toward the `/budgets` card for the same category, silently disagreeing with the page the alert's own message points the user at.
  - **`isInternalTransfer: false` got forgotten twice in this same version** (the global ledger's first draft, caught before release; the `BUDGET_OVERRUN` gap just above, found after release) - a real recurring-bug-pattern flagged by the release-boundary health audit below, not a one-off. Root-caused to every call site having to remember a bare boolean by convention, with nothing structural making it hard to omit. Fixed by `lib/domain/transaction-filters.ts`'s `excludeInternalTransfers`/`excludeInternalTransfersOnSplit` - every one of the queries above, plus `autoCategorizeTransactions`'s uncategorized-pool query, now builds its `where` by wrapping the rest of the clause in one of these two rather than spreading the boolean in by hand. Both are generic over `const T extends object` (not just `T extends object`) specifically so a literal like `category: { kind: "INCOME" }` passed through doesn't widen to `category: { kind: string }` and fail Prisma's exact enum-typed `WhereInput` check - confirmed the hard way, the first version without `const` type parameters compiled the helpers fine but broke every call site that passed a literal-typed filter through them. This doesn't make the omission *impossible* (nothing stops a future query from skipping the helper entirely), but it does make the correct pattern the obviously-easiest thing to reach for.
- **The `/budgets/[categoryId]` drill-down renders split-derived rows differently from plain ones** - a static "Divisée" badge (no `<select>`) instead of `TransactionCategorySelect`, since editing one split line's category in isolation isn't supported inline there (picking a value from a plain `<select>` would delete the whole split, same as it does from every other entry point). The page's own plain-transaction query also gained `splits: { none: {} } }` so a split transaction's *parent* row never appears there a second time alongside its split-derived rows.
- **`TransactionCategoryCell`** (`components/shared/transaction-category-cell.tsx`) is the one integration point used everywhere a transaction row needs to show/edit a category outside the drill-down above - the account's own transactions table and the global `/transactions` ledger. Branches on whether `splits.length > 0`: a "Divisée (N)" badge opening `SplitTransactionDialog` in edit mode, or the plain `TransactionCategorySelect` plus a small split-trigger button opening the same dialog in create mode (2 empty starter lines).
- **`SplitTransactionDialog`** (`components/shared/split-transaction-dialog.tsx`) only ever asks for a magnitude per line (never a sign) - the sign is inferred server-side in `setTransactionSplits` from the parent transaction's own sign, so a debit always splits into negative line amounts and a credit into positive ones without the UI needing to reason about it. A live "remaining to allocate" figure gates the Save button (disabled until it hits exactly 0), computed from the same euro-string parsing the Server Action itself uses.
- **The global ledger's category filter matches a split line too, not just the transaction's own `categoryId`** (`app/transactions/page.tsx`) - `OR: [{ categoryId: filters.categoryId }, { splits: { some: { categoryId: filters.categoryId } } } ]`, so filtering by a category doesn't silently miss every transaction where that category is only one line of a split. Filtering by "Sans catégorie" matches the same two cases `uncategorizedSpentCents` does on `/budgets` - a genuinely uncategorized plain transaction, or a split transaction with at least one uncategorized line. This pushed the `where` clause from a flat spread-in object to an explicit `AND: [...]` of conditions - the category filter and the amount filter (see "Global transaction ledger" above) each need their own top-level `OR`, and a plain object can only ever hold one `OR` key before the second one silently overwrites the first.
- **Deliberately out of scope for this pass**: exports (CSV/markdown) don't reflect a transaction's split breakdown - a split transaction still exports as one row with no category context, a real but lower-stakes gap than the money-total correctness issues above, left for a follow-up. Self-learning also never trains from a split transaction (its `categoryId` is always null, so it's invisible to the history query that builds the label→category model) - same "manual correction, not automatic training signal" precedent as `GENERIC_TRANSFER_LABELS` under "Automatic categorization" below. Recurring-transaction detection's own category guess (`lib/domain/recurring.ts`'s `mode()` of matched transactions' `categoryId`) also isn't split-aware - a low-stakes best-guess default for a new recurring template, not a real financial total, so a split transaction just doesn't contribute a vote either way rather than being specially handled.

### Automatic categorization

Three complementary sources, composed in strict priority order by `autoCategorizeTransactions` (`lib/actions/auto-categorize.ts`), against currently-uncategorized `Transaction` rows - manual categorization stops being a per-transaction chore once a merchant (or a salary/dividend/interest deposit label, see below) has been categorized a couple of times, is well-known enough to ship a default for, or carries an official MCC code.

- **1. Self-learned history** (`lib/domain/auto-categorize.ts`'s `suggestCategoryAssignments`) - learns a `(accountId, normalizeLabelForCategorization(label)) -> categoryId` mapping from the user's own already-categorized history. This always takes priority over the other two sources when it has an answer, since it reflects this specific user's actual, confirmed intent, even when that intent disagrees with what MCC or the dictionary would have guessed - same per-account scoping as `detectCandidates` (recurring transactions, above) and the `/budgets` uncategorized-groups UI, for the identical reason (`label` is raw bank-feed text specific to one institution's formatting). Two confidence thresholds: `MIN_HISTORY_OCCURRENCES = 2` (a label needs at least 2 prior categorized occurrences before its majority category is trusted - a single manually-corrected mistake shouldn't immediately start auto-propagating) and `MIN_CONSISTENCY_RATIO = 0.7` (the majority category must clear 70% of that label's history, not just be the plurality winner of a scattered mix). Below either threshold, the transaction is simply absent from the suggestion map - never mapped to a guessed-but-unconfident category.
  - **`normalizeLabelForCategorization`** (also `lib/domain/auto-categorize.ts`) is a looser variant of `recurring.ts`'s own `normalizeLabel`, used only here and by "Correcting a categorization everywhere at once" below - recurring-transaction detection keeps its own separately-tuned `normalizeLabel` untouched. On top of the usual trim+lowercase, it strips a trailing year-like suffix (` 2025`/` 26` - a literal space then 2 or 4 digits, anchored at the end) - a real gap a user hit in production: French Livret interest is credited once a year with a label like "INTERETS 2025"/"INTERETS 26" (banks vary between 4-digit and 2-digit year suffixes), so under plain `normalizeLabel` two occurrences of the *exact same* label could never accumulate (the label itself changes every year, and interest lands only once a year) - `MIN_HISTORY_OCCURRENCES` could never be reached, so self-learning could never fire for this pattern at all. Only a *trailing* token is stripped, not any 2-digit number anywhere in the label - a bare `\d{2}` match with no anchoring would also eat a real arrondissement/store-number suffix like "MCDONALD'S PARIS 15" (a real but low-consequence tradeoff, documented in the function's own comment). The strip anchors on a literal space, not `\s+`, specifically because `\s+` immediately before a quantified group is exactly the shape ESLint's `sonarjs/super-linear-regex` rule flags as backtracking risk - whitespace is collapsed to single spaces *before* the strip runs so the anchor can be a plain space.
  - **`isGenericTransferLabel`/`GENERIC_TRANSFER_LABELS`** (same file) - a small denylist (currently just `"virement sepa"`/`"virement instantane"`) of bank transfer boilerplate that must never be treated as a trustworthy self-learning group, checked in `groupKey` before a label is ever allowed to accumulate history. Found investigating a real production incident: on a real LCL account, "VIREMENT SEPA" appeared on both a same-day, same-amount internal transfer between two of the user's own accounts *and* on unrelated salary-sized credits with no counterparty name attached (the bank doesn't consistently attach one - it does for some transfers, "VIREMENT SOPRA STERIA GROUP"/"VIREMENT M LOIC SERRE", not others, no reliable pattern to detect which). One transaction correctly categorized as salary had propagated (via "apply to similar", below) onto every other "VIREMENT SEPA" transaction in the account, internal transfers included. The same check gates `applyCategoryToSimilarTransactions` (`lib/actions/transactions.ts`) and `createIncomeEventFromTransaction`/`markSimilarTransactionsAsIncome` (`lib/actions/income.ts`) - a generic label never offers or accepts bulk propagation, only ever a one-off manual categorization. This list only prevents self-learning from repeating the mistake for whichever *other* real thing a generic label happens to also mean - it does nothing for the transfer half of the problem itself; see "Internal transfer detection" below for that.

### Internal transfer detection

`lib/domain/internal-transfers.ts`'s `detectInternalTransferPairs` - a pure function finding pairs of transactions that are almost certainly the two sides of one internal transfer (money moving between two of the user's own accounts), independent of label text entirely. Motivated directly by the `GENERIC_TRANSFER_LABELS` incident above: once it was clear a bank's own label text can't reliably distinguish an internal transfer from a real external payment, the fix had to come from somewhere else - the transaction data itself. A transfer between two of the user's own accounts always produces a matching debit on one account and credit on the other, for the exact same amount, within a day or two. This is a single-user app (see the Data model section's v2.0 multi-user note) - every account in the database belongs to the same person, so any such matching pair is safe to treat as an internal transfer without needing a counterparty name at all.

- **Matching**: groups debits by absolute amount, builds every (credit, debit) candidate pair within a configurable tolerance (`3` days by default) on *different* accounts - a same-account "pair" is never considered a transfer no matter how well the amounts happen to cancel out - then assigns pairs globally, closest date-diff first, before looser pairs get a chance to compete for an already-claimed debit. **Not the original design**: v1.9 shipped a simpler per-credit greedy version (iterate credits in whatever order they're listed, each grabs its own closest still-unclaimed debit) that turned out to have a real failure mode found in production - an unrelated same-amount credit processed earlier could permanently claim the one debit that was actually the true same-day match for a credit processed later, since claims were never revisited. Global-priority ordering fixes that specific case (the exact-date pair always outranks a looser one and gets assigned first) without needing a full min-cost matching algorithm - still not provably optimal for every conceivable case, but a personal account rarely has more than a couple of same-amount candidates to disambiguate between.
- **`Transaction.isInternalTransfer`** (`Boolean @default(false)`) is where the result gets persisted - `flagInternalTransfers` (`lib/actions/auto-categorize.ts`) runs this pass first, unconditionally and **never scoped to a single account** (unlike the rest of `autoCategorizeTransactions` - transfers are inherently cross-account), against every not-yet-flagged transaction in the whole table. Once flagged, a transaction is permanently excluded from the `isInternalTransfer: false` candidate pool on every future run, keeping each pass bounded to genuinely new transactions rather than rescanning history every time.
- Flagged transactions are excluded from the uncategorized pool all three categorization sources draw from (self-learning/MCC/dictionary never assign them a category), from `/budgets`' monthly spend total and its uncategorized-groups nagging list, but **not** from being manually categorized via the transaction row's own dropdown - the flag only suppresses the automatic sources, exactly the same "flag doesn't block manual, only automatic" shape as `GENERIC_TRANSFER_LABELS` above.
- **Retroactive cleanup, deliberately narrow**: the same `flagInternalTransfers` pass also clears `categoryId` for any newly-flagged transaction whose *current* category is named exactly `"Revenus"` - undoing the specific damage the reported incident caused. It does **not** clear any other category a newly-flagged transaction might already have - a different category could reflect a deliberate manual choice (some users may want to track internal transfers under their own category), which this pass has no business overriding.
- **2. Merchant Category Code** (`lib/domain/mcc-categories.ts`'s `matchMccCategory`, `MCC_CATEGORIES`) - the card network's own 4-digit merchant classification (ISO 18245), when the account's bank actually populated `Transaction.merchantCategoryCode` - see "GoCardless" above for where that field comes from (GoCardless/PSD2-synced accounts only; Woob, Trade Republic, and CSV import have no equivalent concept). Ranks above the text dictionary because it's assigned by the card network at merchant registration time, not guessed from a label substring - a genuinely more authoritative signal, when present. Every code/description in `MCC_CATEGORIES` was checked against [github.com/greggles/mcc-codes](https://github.com/greggles/mcc-codes), not written from memory - MCC numbers are easy to misremember and a wrong mapping here would mis-categorize real transactions silently. Deliberately excludes 6011 (ATM cash disbursement) and 4829 (wire transfer/money order) - a withdrawal or transfer isn't "spent" on a category, so leaving those unmapped (uncategorized) is the honest behavior, not a gap to fill.
- **3. Merchant dictionary** (`lib/domain/merchant-categories.ts`'s `matchMerchantCategory`, `MERCHANT_PATTERNS`) - a flat `pattern -> categoryName` map of well-known brand-name substrings (Carrefour, Netflix, SNCF, Uber, EDF, etc.), consulted last, only for transactions neither of the above had an opinion on - the same flat-map shape as `mcc-categories.ts`'s `MCC_CATEGORIES`, not an array of per-category objects (an earlier draft used that shape; SonarQube's copy-paste detector flagged it as duplicated code, since the same `{ categoryName, color, patterns: [...] }` object structure repeating 7 times is indistinguishable from real duplication once literals are normalized for comparison). This exists for the cold-start case self-learning alone can't help with: a brand new user, or any user's first-ever transaction from a well-known merchant, has no history yet to learn from - and unlike MCC, it works for every sync source, not just GoCardless. Deliberately small and not attempting global/every-country coverage (unlike everywhere else in this app - see "Tax treatment" below - this one piece is intentionally opinionated/French-leaning by design, extend the list as real gaps show up rather than guessing every merchant up front); a plain substring match against the lowercased label, not fuzzy matching, since real bank labels are typically boilerplate wrapped around one clear merchant name.
  - **Real production bug, found post-release**: Trade Republic's own transaction labels are German and built from the traded instrument's name ("Kauf"/"Verkauf"/"Sparplan ausgeführt"). `"spar"` (matched for the Spar supermarket chain) is a substring of "Sparplan" (savings plan) - TR's standard wording for every recurring investment purchase, crypto or stock - so every Sparplan execution was silently landing in Alimentation. Removed. The broader class this exposed is still only partially addressed: several other patterns (`totalenergies`, `orange`, `engie`, `veolia`, `axa`, `allianz`, `shell`, `esso`, `"bp "`, `"air france"`) are simultaneously a real French merchant/utility/insurer *and* a stock a French investor might hold via TR - "TotalEnergies - Kauf" and a real fuel purchase are indistinguishable by text alone. Not yet fixed pending confirmed real-world examples (`scripts/debug-categorization.sh` is the tool for that) - see the comment above `MERCHANT_PATTERNS` before touching this list further.
- **Both default-category sources share the same taxonomy** (Alimentation, Transport, Abonnements, Logement, Santé, Shopping, Loisirs, Revenus - 8 broad categories, not one per merchant type) and the same creation path: `resolveDefaultCategoryIds` (`lib/actions/auto-categorize.ts`) takes an explicit name->color map from whichever source matched, so it's reusable for both MCC and the text dictionary without needing to know which one called it. This is the one place auto-categorization creates a `Category` rather than only assigning an existing one - exactly so a brand new user with zero categories still gets somewhere useful for a well-known merchant or MCC to land. The first 7 are deliberately consolidated by **payment nature, not life domain**: restaurants/fast food fold into Alimentation rather than a separate "Restaurants" category, and gym memberships, telecom bills, insurance premiums, and streaming subscriptions all fold into Abonnements even though they're unrelated domains - the shared trait is "recurring, subscription-style payment", per an explicit user design call ("réunie par exemple streaming et salle de sport ça va dans abonnement") made after an earlier, more granular draft. **Revenus** is the one category that isn't spending - currently seeded by exactly one pattern, `"zinsen"` (German for "interest"), Trade Republic's own literal title for interest payouts on uninvested cash, confirmed from a real captured API response in `sync/tests/test_sync_tr.py` rather than guessed.
- **Salary and dividends are still not detected as a special case** - they're just another label the user categorizes once (into "Salaire"/"Dividendes"/whatever they call it) and the self-learning engine recognizes on every future occurrence, exactly like any merchant; there's no reliable universal *brand name* or MCC for a salary (every employer's label is different) the way there is for Carrefour or Netflix, and no confirmed real label text for dividends yet (see `scripts/debug-categorization.sh`'s query 2). **Interest is the one exception**, added to the dictionary directly (see `"zinsen"` above) precisely because it isn't a guess at an employer/brand name - it's Trade Republic's own structural vocabulary for what kind of event the transaction is, which is a safe signal in a way a company name isn't. This was also a deliberate scope decision for `IncomeEvent` specifically: `sync_tr.py`'s timeline items carry no ISIN/ticker in what reaches `Transaction.label`. *Silently auto-creating* `IncomeEvent` rows from a guessed keyword match against label text was considered and rejected for that reason - `autoCategorizeTransactions` itself only ever writes to `Transaction.categoryId`. A *manual, per-transaction-confirmed* path was added later though - see "Mark as income" under "Interest & dividend income tracking" below - which sidesteps the rejected idea entirely: the user picks the specific transaction each time, the system never decides on its own.
  - **Correction**: an earlier version of this comment claimed TR's raw timeline items have no structured event-type field at all ("grepped - it doesn't exist") - that was wrong, found later while investigating a real inter-account-transfer mis-categorization report. The raw item dict *does* carry a top-level `eventType` string (`"ACCOUNT_TRANSFER_INCOMING"`, `"INTEREST_PAYOUT"`, `"CARD_SUCCESSFUL_TRANSACTION"`, etc. - confirmed against `pytr`'s own `event.py`/`tests/all_events_test.json` fixtures on GitHub, not guessed) - `sync_tr.py`'s `_timeline_item_to_transaction()` just never reads it, only `title`/`subtitle`/`amount`/`status`/`timestamp`. Capturing it would be a materially more reliable signal than text matching for telling a transfer apart from a card payment or a dividend - a real, not-yet-implemented improvement opportunity, tracked as a follow-up rather than done here since it needs a real account's data to confirm which raw `eventType` strings actually distinguish an inter-account transfer from external incoming money (pytr's own mapping collapses several distinct raw strings - `ACCOUNT_TRANSFER_INCOMING`/`BANK_TRANSACTION_INCOMING`/`INCOMING_TRANSFER`/`PAYMENT_INBOUND` - into the same coarser `DEPOSIT` bucket for its own purposes, which doesn't by itself prove TR's backend distinguishes "from one of your own accounts" from "from an external payer" at the raw-string level).
- **Four trigger points**, all funnelling through the same `autoCategorizeTransactions(accountId?)`: CSV import (`importTransactions` in `lib/actions/transactions.ts`, scoped to the imported account, right after the rows are inserted), the sync-triggered `POST /api/transactions/auto-categorize` route (every account, called from `sync/main.py`'s `_run_all()` right before `_check_alerts()` - same NEXTAUTH_SECRET bearer-token pattern as that call, and ordered first so a category assignment made this cycle can make a `BUDGET_OVERRUN` custom alert rule fire in the same run instead of lagging a cycle behind), `syncGocardlessTransactions` (right after new GoCardless transactions land, so a populated MCC gets a chance to match in the same sync), and the manual "Auto-catégoriser" button on `/budgets` (`components/budgets/auto-categorize-button.tsx`, calls `runAutoCategorizeNow` across every account - useful for a first backfill, or to seed default categories on a fresh install with no categorization history at all). Same `proxy.ts` matcher exclusion as `api/alerts` (no browser session on that call path). All four only ever touch currently-uncategorized (`categoryId: null`) transactions - a transaction that was auto-categorized *wrong* (like the Sparplan bug above) is never revisited automatically, since re-running these sources can't tell "already correctly categorized" from "already wrongly categorized" apart. See "Correcting a categorization everywhere at once" below for how a wrong batch actually gets fixed.
- Applies suggestions from all three sources via one `updateMany` per distinct target category (grouping the merged suggestion map by `categoryId` first), not one write per transaction.

**Correcting a categorization everywhere at once.** Fixing `setTransactionCategory` (`lib/actions/transactions.ts`) one `<select>` at a time doesn't scale when a dictionary/MCC/self-learning miss hit every occurrence of a label at once (the Sparplan bug above being the motivating real case) - the user explicitly asked for this after finding it painful in practice. `setTransactionCategory` now also counts how many *other* transactions in the same account share the same `normalizeLabelForCategorization(label)` but currently sit in a different category (including uncategorized), returning `{ siblingCount }`. `TransactionCategorySelect` (`components/shared/transaction-category-select.tsx`) only opens a confirmation dialog when that count is `> 0` - a label with no siblings never interrupts the user with an empty prompt. Confirming calls `applyCategoryToSimilarTransactions(transactionId, categoryId)`, which re-derives the label match server-side from the source transaction (not client-supplied ids, same trust boundary as `bulkAssignCategory`) and `updateMany`s every match in that account, unconditionally overwriting whatever category (or none) they currently have - this is the one categorization path in the app that *does* touch already-categorized transactions, by design, since it's always a direct, explicit user correction rather than an automatic guess. Scoped per-account, same reasoning as every other label-based grouping in this codebase (label is raw bank-feed text specific to one institution's formatting). Using the year-stripping `normalizeLabelForCategorization` here too (not just for self-learning) matters for the same Livret-interest case: correcting one year's "INTERETS 2025" now offers to also fix "INTERETS 2026" and any other year already sitting in the account, not just other transactions from the exact same year.

**`scripts/debug-categorization.sh`** - read-only diagnostic queries (investment/crypto transactions and their assigned category, uncategorized dividend/interest-looking labels, per-account-type breakdown of a given category) for troubleshooting categorization issues directly against a running instance's database, same `.env`-sourcing/`docker compose exec` convention as `scripts/backup.sh`.

**`scripts/debug-sync-history.sh`** - same read-only, `.env`-sourced `docker compose exec` convention, for a different question: prints the last 30 `SyncLog` rows per source plus current `SyncFailureState` rows, to tell whether a sync-failure alert (see "Alerts & webhooks" above) was a real, since-resolved transient issue or something still stuck.

### Interest & dividend income tracking

`/income` - `IncomeEvent` rows (`DIVIDEND` or `INTEREST`, optional `ticker`, gross `amountCents`, optional `taxWithheldCents` for foreign withholding tax, `date`), created either by typing the form on `/income` from scratch or via "Mark as income" from a real `Transaction` (see below). Either way this is a real, user-confirmed record, distinct from the estimate described below - nothing here is auto-synced or silently auto-detected without the user confirming a specific transaction.

- Net amount is always computed as `amountCents - (taxWithheldCents ?? 0)`, never stored. `ticker` is free text (not a FK to `Holding`) so a sold position's dividend history survives the holding being deleted.
- The Analytics page's "Passive income" card shows real year-to-date `IncomeEvent` totals (dividends/interest, net of withholding) with a link to `/income` - **this replaced an estimate** that used a hardcoded `DIVIDEND_YIELDS` map and unauthenticated Yahoo Finance dividend-history fetches, plus French regulated-savings rates matched by account **name substring** (`"livret a"`, `"ldds"`, etc.). Being a **year-to-date** figure, it's legitimately €0 for most of the year for an account whose interest is credited only once, in December - a real UX complaint, not a bug, and not something "Mark as income" below changes (it makes recording the event easier, not the YTD framing different).
- That estimate machinery (`DIVIDEND_YIELDS`, `ISIN_TO_YF_SYMBOL`, `fetchYFDividendForSymbol`, the name-matched savings rates in `app/analytics/page.tsx`) is **not removed** - it still feeds the separate "Dividend calendar" section (upcoming per-holding ex-dividend dates), a genuinely different, forward-looking concept that this feature doesn't replace. Don't confuse the two `taxRate` variables in that file: `dividendEffectiveTaxRate()` is dividend withholding tax (ISIN country + `investmentSubtype`-based), unrelated to the latent capital-gains tax described below.
- `createIncomeEvent`/`updateIncomeEvent`/`createIncomeEventFromTransaction` (`lib/actions/income.ts`) all call `assertIncomeEventEligible(accountId, type)` before writing anything - `DIVIDEND` on `INVESTMENT`/`CRYPTO`/`CHECKING` accounts, `INTEREST` on `CHECKING`/`SAVINGS`. This mirrors `components/income/add-income-dialog.tsx`'s client-side account filter and `assertCsvImportEligible`'s rationale: Server Actions are directly invocable regardless of what's rendered, so the eligibility rule has to be enforced server-side too, not just via which accounts populate the dialog's dropdown. `DIVIDEND` allowing `CHECKING` (not just `INVESTMENT`/`CRYPTO`) is a real, later addition - see "Trade Republic transaction history" above: every TR timeline event (trades, dividends, interest, card payments) lands on one shared `CHECKING`-typed "Compte espèces" account, so a real dividend payout can legitimately need recording against a `CHECKING` account.

**"Mark as income"** (`components/account-detail/mark-as-income-button.tsx`, on eligible rows in the account's transactions table) creates an `IncomeEvent` directly from a real `Transaction` instead of the user retyping amount/date by hand - a real gap the user hit in production: typing "the right title" and finding the right transaction manually for every dividend/interest payment was, in their words, too tedious to be worth using. Only shown for a transaction that's a credit (`amountCents > 0`), on an eligible account type, with no `IncomeEvent` linked yet (`Transaction.incomeEvent`, the reverse side of `IncomeEvent.transactionId` below). Amount and date are pre-filled from the transaction and **not editable** in the dialog - editing them would desync the record from the transaction it's supposed to represent, defeating the point of linking it; only `ticker` and `taxWithheldCents` are user input. The type toggle (Dividende/Intérêts) only appears when the account is genuinely ambiguous (`CHECKING`, per the TR case above) - a `SAVINGS` account locks to `INTEREST`, since `DIVIDEND` isn't even eligible there.

- `IncomeEvent.transactionId` (`String? @unique`) is the link - nullable for every pre-existing row and for anyone who still prefers the manual form, `@unique` so the same real payment can't be marked twice, `onDelete: SetNull` (not `Cascade`) since deleting the source transaction shouldn't destroy an already fiscally-relevant income record, only its provenance link.
- **Propagation, same shape as "Correcting a categorization everywhere at once" above**: after marking one transaction, `createIncomeEventFromTransaction` returns how many *other*, not-yet-linked, credit transactions in the account share the same `normalizeLabelForCategorization(label)` (the auto-categorization module's own year-stripping normalization, reused here for the identical reason - a once-a-year interest credit's label changes every year). When that count is `> 0`, a confirmation dialog offers `markSimilarTransactionsAsIncome`, which creates an `IncomeEvent` for each match in one `createMany`. Unlike the categorization version, this one **skips** already-linked transactions rather than overwriting them - marking as income always creates a new fiscal record, it never corrects an existing one, so a sibling that's already recorded is left untouched instead of being double-recorded.
- This is deliberately still a **manual, per-transaction-confirmed** action, not automatic creation from a guessed keyword match - the "Automatic categorization" section above explains why that specific idea (auto-creating `IncomeEvent` from unverified label text) was considered and rejected for `sync_tr.py`'s timeline items. The difference here is that the user is the one selecting/confirming the specific transaction each time (even in bulk, they chose the source transaction and reviewed the resulting count before confirming) - the system never silently decides a transaction is income on its own.

**"Autres revenus"** (also `/income`) - a second, separate section listing every `CategoryKind.INCOME` category (see "Data model" below) with its year-to-date total, linking each into its own `/budgets/[categoryId]` drill-down. This is where salary lives - typed as its own `Category` (e.g. "Salaire") rather than an `IncomeEvent`, and deliberately **not merged into the `IncomeEvent` list above**, for a concrete reason: `/tax-report` queries `prisma.incomeEvent.findMany` directly to build the annual dividend/interest tax summary, and French salary income has nothing to do with that report (it's taxed via an entirely different mechanism, PAYE/prélèvement à la source) - adding a `SALARY` `IncomeType` would have silently polluted a report that's specifically about investment income. Keeping salary as a `Category` instead means it naturally reuses everything already built for categorization (self-learning, "apply to similar", the drill-down page) with zero risk to the tax report's scope. The resulting overlap - Trade Republic's "Zinsen" interest can show up on *both* this section (via the auto-created "Revenus" category) and the `IncomeEvent` list above (if the user also used "Mark as income" on the same transaction) - is accepted, not a bug: the two mechanisms serve different purposes (broad/automatic vs precise/tax-reportable) and a user is free to use either, both, or neither for a given payment.

### Tax treatment

Latent (unrealized capital-gains) tax is a **per-account** setting, not a global one: `Account.taxTreatment` (`TaxTreatment` enum: `EXEMPT` | `DEFERRED` | `TAXABLE`) + `Account.taxRatePct` (0-1 ratio, meaningful only when `TAXABLE`). `lib/domain/tax.ts`'s `getAccountTaxRate(account)` is the single shared resolver - `EXEMPT`/`DEFERRED` both return `0`, `TAXABLE` returns `taxRatePct` - used by all four pages that compute latent tax (`app/page.tsx`, `app/accounts/page.tsx`, `app/accounts/[id]/page.tsx`, `app/analytics/page.tsx`), replacing 4 previously-duplicated `account.type`/`investmentSubtype` branching helpers.

- This exists so non-French wrappers have somewhere to go: a UK ISA or US Roth IRA is `EXEMPT`, a PER/401k is `DEFERRED` (not taxed until withdrawal - not taxed for latent/net-worth purposes today either), anything else is `TAXABLE` at whatever rate the user enters. `investmentSubtype` (`"PEA"`/`"CTO"`, cosmetic label only) is fully decoupled from this - an ISA doesn't need to pretend to be a "CTO" to get taxed correctly.
- Set at account creation (`components/accounts/add-account-dialog.tsx` + `createAccount`, rate pre-filled with a hardcoded 17.2%/31.4% suggestion based on the PEA/CTO/Crypto choice, always editable) or afterward via an inline form in the account detail page's fiscal summary (`updateAccountTaxTreatment` in `lib/actions/accounts.ts`, same `<form action={...}>` pattern as `updateInvestmentStartDate`) - there was no prior UI to edit `investmentSubtype` post-creation either, so this is the first edit surface for either field.
- `UserSettings.taxRatePea`/`taxRateCto`/`taxRateCrypto` (Settings → Fiscalité) still exist, but only as **defaults offered when creating a new account** - they are no longer read per-render for existing accounts. Migration `20260727141819_add_account_tax_treatment` backfilled every pre-existing account's `taxRatePct` from these same global rates at the time it ran, so upgrading never changes a displayed number: CRYPTO → `taxRateCrypto`, PEA → `taxRatePea`, CTO → `taxRateCto`, INVESTMENT with no subtype set → `EXEMPT` (reproducing the old chain's `null` = "no tax computed" outcome exactly, not a claim that the account is a real tax-exempt wrapper).

### Realized gains & annual tax report

Before this feature, selling a holding meant retyping a smaller `quantity`/`costBasisCents` on the existing `Holding` row (`upsertHolding` in `lib/actions/holdings.ts`) - a blind overwrite with no history, no gain ever computed. `Sale` (`ticker`, `quantity` sold, `proceedsCents`, `costBasisCents` of the *sold portion*, `date`) now records disposals as discrete events, the same shape as `IncomeEvent`. Realized gain is always `proceedsCents - costBasisCents`, never stored.

- **Recording a sale** (`components/account-detail/sell-holding-dialog.tsx`, "Sell" button next to each holding row in `app/accounts/[id]/page.tsx`) uses the **average-cost method**, not per-lot FIFO/LIFO: the sold portion's cost basis defaults to `holding.costBasisCents * (soldQty / holding.quantity)`, always user-editable. `recordSale` (`lib/actions/sales.ts`) wraps creating the `Sale` row and adjusting the `Holding` in one `prisma.$transaction` - full disposal (`quantitySold >= holding.quantity`) deletes the `Holding`, partial disposal reduces `quantity` and `costBasisCents` proportionally, then calls the same `refreshAccountBalance` helper `upsertHolding`/`deleteHolding` already use (exported from `lib/actions/holdings.ts` for this reason). `recordSale` also rejects a sold-portion `costBasisCents` that's negative or exceeds the holding's own remaining `costBasisCents` - without that guard the remaining `Holding.costBasisCents` can go negative, which then inflates the displayed gain (and latent tax) beyond the position's actual market value indefinitely.
- **No backfill and no `updateSale`**: past sales already lost to the old overwrite behavior can't be reconstructed, and editing a past `Sale`'s quantity/proceeds after the fact would need the same retroactive-holding-adjustment problem `deleteSale` already punts on (**record-only deletion** - it does not reverse the `Holding` change, since the holding may have had further buys/sells/price updates since; correcting a mistake means deleting the `Sale` row *and* manually fixing the `Holding` via the existing edit dialog).
- **`/tax-report`** aggregates `Sale` + `IncomeEvent` for a given calendar year (`?year=` search param). Estimated tax on gains reuses `getAccountTaxRate()` from "Tax treatment" above (`EXEMPT`/`DEFERRED` sales show €0 tax, same semantics as latent tax elsewhere) - it does not attempt to model additional income tax on dividends/interest beyond what `IncomeEvent.taxWithheldCents` already nets out, by design (country-agnostic scope, not a French PFU/social-charges calculator). No sidebar nav item - linked instead from the Analytics "Passive income" card and the account detail page's fiscal summary, to avoid further crowding the already-7-item mobile bottom nav.
- The estimated tax figure **nets gains and losses per account for the year** before taxing (grouping `Sale` rows by `accountId`, only taxing a positive net) - same convention as the account-detail page's aggregate tax figure. The per-row "Tax" column in the sales table is a per-sale reference figure only (as if that were the year's only sale) and intentionally won't sum to the displayed total whenever an account had both a gain and a loss sale that year - disclosed in the page's footnote.
- Markdown export (`components/shared/export-tax-report-button.tsx`) reuses `lib/utils/markdown-export.ts`'s `fmt`/`sign`/`downloadFile`, same convention as `components/shared/export-analytics-button.tsx`/`components/shared/export-accounts-button.tsx` - this is the "country-agnostic, exportable" part of the roadmap wording; the report itself is presented as an estimate for informational purposes, not an official tax document or a literal French IFU form mapping. Unlike those other two exports, every per-row figure here (sale proceeds/cost basis/gain/tax, each dividend/interest line) is passed `fmt(x, 2)` explicitly rather than `fmt`'s own 0-decimal default - matching the page's own `formatCurrency(x)` calls for these same rows (2 decimals, no override), which the export originally didn't. Found in production: a real dividend of 0,46€ was rounding to "0 €" in the downloaded file while the page correctly showed "0,46 €" right next to it - real money silently disappearing from a document whose whole purpose is being accurate enough to declare. The summary card figures stay at the export's 0-decimal default, matching the page's own `formatCurrency(x, 0)` summary cards.

### Benchmark comparison

`app/analytics/page.tsx`'s "Comparaison aux indices" section, right after the investment performance table. Deliberately **not** a historical overlay chart: `investCAGR` (the portfolio's own aggregate CAGR, see the performance table above it) is itself a point-in-time snapshot - current value vs. cost basis, annualized over a cost-basis-weighted average holding duration (`investCAGRWeightedYears`) - not a smooth time series (investment `HistoricalBalance` snapshots are event-driven, created only when holdings change, not on a schedule, so there's no reliable daily series to chart against an index). This feature applies the identical snapshot-to-snapshot methodology to 3 reference indices instead of inventing a different, inconsistent one.

- `fetchYFPriceHistory(symbol)` reuses the exact same unauthenticated Yahoo chart endpoint, headers, and `next: { revalidate: 3600 }` caching as the existing dividend fetch (`fetchYFDividendForSymbol`) - that endpoint already returns OHLC `close`/`timestamp` arrays that the dividend fetch just discards (it only reads `events.dividends`/`meta.regularMarketPrice`); this fetch reads those arrays instead, with `interval=1mo&range=max` (not a fixed window - see `computeIndexCAGR` below for why) and no `events` param.
- `BENCHMARK_SYMBOLS`: `sp500: "^GSPC"`, `cac40: "^FCHI"` (real index tickers), `msciWorld: "URTH"` (the iShares MSCI World ETF - Yahoo has no clean "^" ticker for the real index, so this is a proxy with a small expense-ratio drag, disclosed in the UI footnote).
- `computeIndexCAGR(series, startDate, now)` finds the closest historical close to `startDate` (via `priceAt`, nearest-timestamp match - the fetched series is monthly, not daily) and to `now`, then applies the same `(end/start)^(1/years) - 1` formula as `investCAGR`, over the identical `investCAGRWeightedYears` lookback so the comparison is apples-to-apples. The "years" divisor is derived from the **actual matched data points' dates**, not the requested `startDate` - `investCAGRWeightedYears` can exceed however far back the fetched series reaches (a PEA opened over 10 years ago, URTH's own Feb-2012 inception, etc.), and dividing by the *requested* span while priceAt silently clamps to the *oldest available* point would produce a self-inconsistent (understated) CAGR instead of gracefully reflecting the window actually available.
- Only rendered when `investCAGR !== null` (same gate as the aggregate CAGR itself) and per-index only when that index's fetch actually returned data (Yahoo being unreachable degrades to that one row being omitted, not a crash - same `try/catch` → empty-array fallback as the dividend fetch).

### Full sector-exposure breakdown

`app/analytics/page.tsx`'s "Répartition sectorielle" section (v1.16), right after the allocation-radar section - generalizes `AllocationRadarSection`'s former Tech-only bar (`TECH_WEIGHTS`, a 12-entry hand-verified map, one scalar per ISIN - since **removed**, see the correction at the end of this section) into a full GICS-style breakdown (technology/financial_services/healthcare/consumer_cyclical/consumer_defensive/industrials/energy/utilities/basic_materials/real_estate/communication_services, plus `crypto`/`unclassified` outside the GICS 11) across every holding. `ROADMAP.md` flagged this as needing real scoping before building, since a full per-sector data source is a materially bigger ask than one hand-verified scalar - this section documents that scoping, done live with real evidence during the v1.16 session, not assumed.

**Data sources considered and rejected**, each checked live, not from memory:
- **OpenFIGI** (Bloomberg's free, documented, no-scraping mapping API) - `marketSector` is a broad asset-class label ("Equity"), not a GICS sector. Not usable for this.
- **iShares' own site** (a real primary source, many of this app's real holdings are iShares products) - rebuilt on Astro since this was last relevant, the old known JSON-download pattern no longer works; even fixed, it would only ever cover one issuer (not Amundi/Vanguard/Lyxor/SPDR - the real ETF universe self-hosters actually hold spans several), a materially bigger and more fragile undertaking than the single mechanism this feature actually uses.

**What it actually uses**: Yahoo Finance, the same provider every other Analytics Yahoo integration on this page already depends on, via two different endpoints with two very different trust profiles:
- **`resolveIsinToYahoo(isin)`** (`lib/services/yahoo-finance.ts`) - `/v1/finance/search`, free, no cookie, no crumb, same trust level as `fetchYFPriceHistory` above. Resolves a `Holding.ticker` ISIN to a real Yahoo symbol (confirmed live: 11/12 of `TECH_WEIGHTS`' own ISINs resolve correctly - the one miss is an unlisted private-equity fund, an expected gap). For an `EQUITY` result, `sector`/`industry` come back in this same response - individual stocks need no second call and no crumb at all.
- **`quoteSummary?modules=topHoldings`** - needed for an ETF's full `sectorWeightings` breakdown (search alone doesn't carry it for ETFs). Confirmed live to return a real, complete 11-sector breakdown for every ETF symbol tried (`URTH`, `IWDA.L`, `CSSPX.MI`, `CW8.PA`, `XAID.L`) - but confirmed **requires a session cookie + crumb** (`getYahooCrumb()`: fetch a cookie from `fc.yahoo.com`, then a crumb from `v1/test/getcrumb` - confirmed live that `getcrumb` fails outright with no cookie at all). This is Yahoo's own internal anti-scraping mechanism, not a documented public contract, and this exact endpoint family has already tightened once without notice in this codebase's own lifetime (`v7/finance/quote` is fully dead - see "pnpm overrides"-adjacent history elsewhere in this file for other examples of upstream APIs changing under this project). Accepted as a real, disclosed risk, not glossed over - the crumb is cached module-level for ~50 minutes (`CRUMB_TTL_MS`) rather than re-fetched per holding, both for latency and to look less like scraping traffic.

**Two independent, optional fallback providers** (`lib/services/sector-fallback-providers.ts`), tried in order (`fetchFallbackEtfSectorWeights`: FMP → Alpha Vantage) only when Yahoo's crumb path itself fails - added after this was specifically requested to be "béton" (rock-solid), not just theoretically resilient:
- **`FMP_API_KEY`** / **`ALPHA_VANTAGE_API_KEY`** - optional, deploy-time `.env` variables (`.env.example`), same category as `GOCARDLESS_SECRET_ID`/`GOCARDLESS_SECRET_KEY` - a self-hoster who wants ETF-level resilience against Yahoo breaking configures one or both; the app works fully without either, just without that resilience. Neither is required for setup, matching this project's "`docker compose up` in under 5 minutes" goal.
- Both real, documented, API-key-authenticated REST APIs - the property that makes either "béton" relative to Yahoo's crumb path is that neither is a scraping workaround, it's a supported contract with a ToS. Offered as **two** rather than committing to one specific provider because this session couldn't decisively confirm either one's real-world coverage of European UCITS ETF tickers (the instruments that actually matter for this app's PEA-heavy French user base) without a registered account - Alpha Vantage's public `demo` key *did* confirm `ETF_PROFILE`'s real response shape live (a genuine complete sector-weightings response for its own canned example symbol, `QQQ`), FMP's shape is implemented against documentation only (its docs site itself returned 403 to a direct fetch attempt). **Honesty note, not glossed over**: neither is verified end-to-end against an arbitrary real ISIN with a registered key - whoever configures either key first should sanity-check the Analytics page actually shows data for their own holdings.
- Alpha Vantage's `ETF_PROFILE` uses official GICS sector names in a different casing/wording convention than Yahoo's own (`"INFORMATION TECHNOLOGY"` vs Yahoo's `"Technology"`, `"CONSUMER DISCRETIONARY"` vs `"Consumer Cyclical"`, etc., confirmed live) - `ALPHA_VANTAGE_SECTOR_ALIASES` maps the 4 sectors that actually differ explicitly rather than guessing at a generic transform; the remaining sectors already match Yahoo's wording once normalized.

**`lib/domain/sector-exposure.ts`** (pure, tested) - `normalizeSectorKey(raw)` unifies every source's casing into one canonical key set matching Yahoo's own `topHoldings` keys, including **the one real quirk found live**: `topHoldings`'s real-estate key is the unbroken word `realestate`, while a stock's `search`-returned sector string ("Real Estate") would naturally normalize to `real_estate` - handled as an explicit special case, not silently producing two different buckets for the same sector. `aggregateSectorExposure(holdings)` does the weighted sum across every holding's resolved `SectorWeights`, with an explicit `unclassifiedCents` bucket for any holding no source could resolve.

**Correction (real production feedback, same v1.16 cycle): crypto holdings were originally routed through the Yahoo/fallback resolution chain like any other holding, and always failed it** - BTC/ETH-style tickers aren't ISINs any of the three sources can classify under a GICS sector, so every `CRYPTO`-account holding landed in "Non classé" indistinguishable from a genuine data gap. Confirmed against the demo portfolio: ~40% "unclassified" was reported as an imprecision to fix, and tracing it showed the entire Crypto account's value was the sole contributor. Fixed by bucketing `CRYPTO`-type accounts' holdings directly into a `crypto` key in `app/analytics/page.tsx` (`{ crypto: 1 }`, no network call at all - the account's own `type` is known locally and is a strictly more reliable signal than asking Yahoo to guess) rather than attempting - and always failing - the Yahoo path for them. `crypto` sits outside `SECTOR_KEYS`' 11 GICS entries (same as `unclassified`) since crypto genuinely has no GICS sector; this is accurate classification, not a data-gap workaround. `SECTOR_COLORS.crypto` deliberately reuses `ALLOCATION_CATEGORY_COLORS.crypto`'s exact amber (same "one category, one color app-wide" principle that map's own comment already states) - which surfaced a second real bug caught before shipping: `consumer_cyclical` had independently been assigned that exact same hex, a genuine color collision within the sector palette itself, fixed by moving `consumer_cyclical` to fuchsia (the largest open hue gap between industrials' purple and real_estate's pink).

**Second correction (real production feedback, same v1.16 cycle): the section merged into `AllocationRadarSection`, and gained hover tooltips + a per-sector contribution breakdown.** Real user feedback after the fixes above found the page's own "Radar d'allocation" card (Garantis vs Risqués - a coarser cut of the exact same invested total this section drills into) and this section's own separate card confusing to look at side by side. `SectorExposureSection` stopped rendering its own `bg-[var(--surface)] border ... rounded-xl` card and its `<h2>`; `AllocationRadarSection` (`components/analytics/allocation-radar-section.tsx`) now renders it as a second `<h3>`-titled block inside its own single card, separated by a `border-t` divider - `app/analytics/page.tsx` no longer renders `<SectorExposureSection>` directly, only passes its data through as extra `AllocationRadarSection` props (`sectorBreakdown`/`sectorContributions`/`sectorUnclassifiedCents`/`sectorTotalCents`).

Also real feedback: with up to 13 distinct segment colors (11 GICS + crypto + unclassified) on one bar, the legend dot alone wasn't always enough to place a segment, and "where does this percentage actually come from" wasn't answerable without leaving the page. Both the stacked-bar segments and the legend rows are now real `<button type="button">` elements (not `<div>`s - keyboard-focusable via `group-focus-visible:block`, not just mouse-hoverable via `group-hover:block`) each rendering a shared `Tooltip` sub-component showing the sector's translated name plus its contributing holdings and euro amounts.

**`lib/domain/sector-exposure.ts`'s `aggregateSectorExposure` now also returns `contributions: Record<string, { holdings: SectorContribution[]; truncated: boolean }>`** alongside `breakdown` - built from a new required `name` field on `SectorExposureHolding` (a display label the caller builds once, e.g. `"iShares Core MSCI World (PEA)"` - `app/analytics/page.tsx`'s `holdingLabel()` combines `Holding.name ?? Holding.ticker` with the parent account's own name, so the tooltip can distinguish "the same ETF held in two different accounts" or "two different funds that both happen to be Technology-heavy"). Each sector's contribution list is sorted by contributed cents descending and capped at `MAX_CONTRIBUTIONS_PER_SECTOR = 5` (same "safety cap, not a feature limit" precedent as `MAX_UNCATEGORIZED_GROUPS`/`topAssets`' own top-10 slice) - `truncated: true` when real contributors exist beyond the cap, surfaced in the tooltip as a "+ d'autres positions" line rather than silently presenting a partial list as the whole story. Names wrap (`break-words`) instead of truncating with an ellipsis inside the tooltip - cutting off a fund name mid-word right before its disambiguating account suffix would defeat the entire point of this feature; an early draft with a narrower `max-w-[220px]` + `truncate` did exactly that and was widened to `max-w-[260px]` + `break-words` after a live screenshot caught it.

**Degradation alerting reuses `SyncFailureState`, not a new table.** `UserSettings.sectorDataAlertsEnabled` (`Boolean @default(false)` - unlike the loan/sync-failure toggles nearby, which default `true` to preserve pre-existing always-on behavior, this is a brand-new notification category with no such behavior to preserve, so opt-in is the less presumptuous default) gates `checkSectorDataHealth` in `app/api/alerts/check/route.ts`, called from the same `POST` handler every other alert check already runs from. It calls `probeYahooSectorHealth()` (a live probe against the existing `BENCHMARK_SYMBOLS.msciWorld` symbol, no new symbol dependency) and manages a `SyncFailureState` row under a reserved `source: "yahoo_sector_data"` **directly** rather than through `checkSyncFailures`'s existing loop (which only ever discovers sources by scanning `SyncLog`, a table nothing writes to for this JS-only concern) - same edge-triggered semantics (fire once on transition to broken, one reminder per `REMINDER_INTERVAL_MS`, clear on recovery) reusing `clearSyncFailureState`/`dispatchAlert` directly. Alerts on `!anyPathHealthy`, not `!yahooHealthy` - a self-hoster with a working fallback configured shouldn't get paged just because Yahoo alone hiccupped while the fallback quietly covered for it; the alert exists for "the feature has actually stopped working." **Verified live, not just reasoned through**: a temporary forced-failure flag exercised all three states in sequence against the real running app (fires once on the transition to broken, doesn't re-fire on an immediate second check, clears the moment the probe succeeds again) before being removed from the shipped code.

**Correction: `AllocationRadarSection`'s Tech-only bar was removed, not kept alongside this section as originally planned.** The original design left it untouched (independently hand-verified, its own concentration-warning UX) specifically to avoid "a risky removal nobody asked for" - but real user feedback on the shipped feature asked for exactly that removal: seeing two different "how much tech exposure?" numbers on the same page (the bar's hand-picked `TECH_WEIGHTS` figure vs this section's live Yahoo-sourced `technology` percentage, genuinely different values computed two different ways) read as confusing duplication, not two complementary insights. `TECH_WEIGHTS`, `techPct`/`techValueCents`, the JSX block, its i18n keys (`radar.techExposure`/`highConcentration`/`monitor`/`techFootnote`, `mdTechExposure`), its markdown-export row, and its dedicated `sonar-project.properties` S6819 suppression entry (`e8`, now unused - deliberately left as a gap rather than renumbering `e9`-`e11`) were all removed together, not just hidden - confirmed nothing else referenced any of them before deleting. "Garantis vs Risqués" in the same section is untouched (an orthogonal metric, not a sector concept).

### Portfolio rebalancing

`Holding.targetPct` (0-1 ratio, nullable - same convention as `taxRatePct`) adds a target counterpart to the per-holding "Poids" (current weight) column that already existed on `app/accounts/[id]/page.tsx`'s holdings table (`pct = marketValueCents / accountTotal`). This is scoped **within one account's own holdings** - unrelated to the Analytics allocation chart, which only buckets by account *type* (cash/savings/investments/crypto/realEstate/auto), never per-ticker.

- Set via the existing `components/account-detail/add-holding-dialog.tsx` edit form (one more optional field, not a new dialog), input as a 0-100 percentage and converted to a 0-1 ratio in `upsertHolding` (`lib/actions/holdings.ts`). Same optional-update semantics as `costBasisCents`: leaving it blank on an edit does not clear a previously-set target.
- Targets are **not required to sum to 100%** - a holding with `targetPct: null` is simply excluded from the rebalancing plan (e.g. an untouched legacy position the user doesn't want to manage this way).
- The "Rééquilibrage" section on the account detail page (only shown when at least one holding has a target set) computes, per targeted holding: drift in points (`pct - targetPct*100`) and a suggested trade (`driftValueCents = marketValueCents - accountTotal*targetPct`; positive → suggest selling that amount, negative → suggest buying it), plus an approximate share count from `driftValueCents / lastPriceCents`. The suggested-trade line is only rendered when `driftPts !== 0` (not just `driftValueCents !== 0`) - `driftPts` is two independently-rounded integer percentages, so a holding can sit at e.g. an exact 38.98% weight against a 39% target and show "0 pts" drift while the raw cents-level `driftValueCents` is still technically nonzero; showing a suggested trade next to an "on target" reading would visually contradict it.
- **Informational only** - the suggestion is displayed as text, not wired to pre-fill `AddHoldingDialog`/`SellHoldingDialog` (neither currently accepts external suggested-quantity props, and both are already one scroll up in the same holdings table for the user to act on manually). Keeps this change to one field + one read-only section, no changes to two already-working dialogs' APIs.

### Multi-currency

`Holding` positions can be entered in USD, GBP, or CHF and are converted to EUR **once, at entry time** - `lastPriceCents`/`costBasisCents` stay exactly what they've always been (plain EUR cents), so every existing calculation (net worth, tax, rebalancing, the tax report, the 3 chart components) keeps working completely unmodified. This is deliberately narrower than a "live multi-currency ledger": holdings aren't live-refreshed today either except via sync, so a snapshot-on-entry FX rate matches the app's existing "manually update the price when you check in" paradigm.

- `lib/services/exchange-rate.ts`'s `fetchExchangeRateToEur(currency)` reuses the same unauthenticated Yahoo Finance chart endpoint/headers/`revalidate: 3600` caching convention as the dividend/benchmark fetches in `app/analytics/page.tsx`, via the `EURUSD=X`/`EURGBP=X`/`EURCHF=X` pairs (Yahoo quotes these as "X per 1 EUR", so the raw price is inverted to get "EUR per 1 X"). Extracted to `lib/` rather than kept page-local since it's the first Yahoo fetch called from a Server Action rather than a page.
- `upsertHolding` (`lib/actions/holdings.ts`) reads `currency` from the form (default `"EUR"`, unchanged path - the 3 new fields stay `null`). For a foreign currency, it fetches the rate and **throws if the rate can't be fetched** - no silent fallback to a stale/wrong rate - then stores `nativePriceCents`/`nativeCostBasisCents` (exactly what the user typed) and `fxRateToEur` (the rate captured at entry time) alongside the EUR-converted `lastPriceCents`/`costBasisCents`. Switching a holding's currency back to EUR on an edit nulls out all three native fields.
- `fxRateToEur` is only **re-fetched** when the entered `currency`/native price/native cost basis actually differ from what's already stored (compared against the existing row before deciding) - otherwise the existing rate/EUR values are reused as-is. Without this, editing any unrelated field (renaming the position, setting a rebalancing target) would resubmit the same pre-filled native price and silently re-roll the conversion against whatever the market rate happens to be *today*, shifting the holding's EUR valuation even though nothing about the position's price actually changed - contradicting the "captured at entry time" design above.
- `components/account-detail/add-holding-dialog.tsx`'s price/cost-basis inputs pre-fill from `nativePriceCents`/`nativeCostBasisCents` when set (not `lastPriceCents`) so re-opening the edit dialog on a foreign-currency holding shows back exactly what was typed (e.g. "150.00"), not a lossy back-converted approximation.
- The holdings table (`app/accounts/[id]/page.tsx`) shows a small muted currency-code badge next to the ticker (e.g. "AAPL · USD") when `currency !== "EUR"` - no new table column, to avoid the mobile-width concerns already worked through for this same table (see "Portfolio rebalancing" above).
- **On-demand revaluation (v1.16)** - `RefreshHoldingFxButton` (`components/account-detail/refresh-holding-fx-button.tsx`, next to the row's Sell/Edit buttons, only rendered for `currency !== "EUR"`) calls `refreshHoldingExchangeRate(holdingId)` to re-fetch just the FX rate and recompute `lastPriceCents`/`costBasisCents` from the already-stored `nativePriceCents`/`nativeCostBasisCents` - without this, getting a fresh rate meant reopening the edit dialog and retyping the exact same native price just to trip `upsertHolding`'s own "only re-fetch when the native price actually changed" guard above, a real friction point since that guard exists specifically to *avoid* re-fetching on unrelated edits. Still narrower than a live ledger - nothing re-fetches on its own, still a manual action, still doesn't touch the native price/quantity, only the conversion. `fetchExchangeRateToEur` gained a `bypassCache` param (`cache: "no-store"` instead of `next: { revalidate: 3600 }`) used only by this path - a user who explicitly clicks "refresh" expects a genuinely current rate, not whatever Yahoo response was cached up to an hour ago; `upsertHolding`'s own entry-time fetch keeps the cached, revalidate-based path since there's no "on demand" expectation there.

### Data model

- `Institution` → many `Account`. Carries at most one per-user sync provider's credentials: `woobModule`/`woobLogin`/`woobPassword`, or (v2.1) `trPhone`/`trPin` - never both, enforced by each config action clearing the other's fields. See "Per-user Trade Republic" below
- `Account` (`AccountType`: `CHECKING | SAVINGS | INVESTMENT | REAL_ESTATE | MEAL_VOUCHER | CRYPTO | AUTOMOBILE | LOAN`)
  - Fiat (CHECKING, SAVINGS, MEAL_VOUCHER): `HistoricalBalance` (balance in cents as `BigInt`)
  - Investment/Crypto: `Holding` (ticker + `Decimal` quantity) + live price at runtime. `investmentSubtype` = `"PEA"` or `"CTO"` (cosmetic label only). `taxTreatment` (`TaxTreatment` enum) + `taxRatePct` drive the actual latent-tax rate - see "Tax treatment" below
  - Real Estate & Automobile: `manualValueCents` + optional `liabilityCents`
  - LOAN: capital computed at runtime via `calcCurrentCapital()` from `lib/domain/loan.ts`. `loanPaidOffAlertSent` is a one-way dedup flag for the "nearly paid off" alert - see "Alerts & webhooks" above.
- `Holding` - unique on `(accountId, ticker)`. `costBasisCents` for P&L. `targetPct` (0-1 ratio, nullable) drives the "Portfolio rebalancing" feature below - independent of any other field. `currency` (`HoldingCurrency` enum, default `EUR`) + `nativePriceCents`/`nativeCostBasisCents`/`fxRateToEur` (all null when `currency = EUR`) drive "Multi-currency" below - `lastPriceCents`/`costBasisCents` are always EUR regardless of `currency`
- `HistoricalBalance` - daily balance snapshots
- `Transaction` - bank movements. `amountCents`: positive = credit, negative = debit. Deduplicated via `syncId`. Optional `categoryId` → `Category` (`onDelete: SetNull` - deleting a category un-categorizes its transactions instead of deleting them) - `null` here means either "genuinely uncategorized" or "split across multiple categories", disambiguated by whether any `TransactionSplit` rows exist for it - see "Split transactions" below. Optional `merchantCategoryCode` - GoCardless-only (PSD2's Berlin Group schema), null for every other sync source - see "Automatic categorization" below. Reverse-linked from at most one `IncomeEvent` (`incomeEvent`) when "Mark as income" created one from it - see "Interest & dividend income tracking" below. `isInternalTransfer` (`Boolean @default(false)`) - set when this transaction is matched as one half of a same-amount, cross-account transfer pair - see "Internal transfer detection" below.
- `TransactionSplit` - one category's portion of a transaction split across 2+ categories (`transactionId`, nullable `categoryId` with `onDelete: SetNull`, signed `amountCents`) - every split row for one transaction must sum exactly to that transaction's own `amountCents`. See "Split transactions" below.
- `Category` - user-defined category (name, hex `color`, `kind: CategoryKind` (`EXPENSE` default | `INCOME`), optional `budgetCents`). `budgetCents` is a single ongoing monthly envelope, not a per-month history - editing it takes effect immediately, including retroactively on the current month's progress bar (no historical record of past amounts), and is meaningless (never stored) for an `INCOME` category - a spending cap has no equivalent for money coming in. `budgetRolloverEnabled` (off by default) + `budgetRolloverEnabledAt` drive "Budget rollover" below - unused envelope carries forward instead of resetting to zero each month, meaningless for an `INCOME` category the same way `budgetCents` itself is. `/budgets` only ever lists `EXPENSE` categories and computes each one's current-calendar-month spend via `prisma.transaction.groupBy({ by: ["categoryId"] })` filtered to `amountCents < 0` (debits only) - a `categoryId: null` bucket in that same query is the "uncategorized spend" figure. `INCOME` categories (default-seeded "Revenus", or a user-created one like "Salaire") instead get their own section on `/income` - see below. Clicking a category name links to `/budgets/[categoryId]`, a drill-down page listing every transaction (across all accounts) tagged with it regardless of kind, reusing `TransactionCategorySelect` so a mis-tagged row can be recategorized in place.
  - **Why `kind` exists, and why it's explicit, not inferred**: an earlier version tried to make a single category's `/budgets` card automatically switch between "spent" and "received" framing based on which dominated that specific month's transactions - rejected after direct user pushback before shipping: the same category's card would silently flip behavior month to month (no spending this month → "received" framing; some spending next month → back to normal), which is a genuinely worse UX than a stable, explicit choice made once at creation, and doesn't match how any real budgeting app (YNAB, Bankin', Firefly III) separates income from expenses - they use a fixed type, not monthly inference. `kind` is chosen via a toggle at creation/edit time (`components/budgets/add-category-dialog.tsx`), defaults to `EXPENSE` (`Category`'s own schema default) for every existing call site that doesn't pass one.
  - **"Reste à vivre"** (`app/budgets/page.tsx`) - a summary card showing every credit minus every debit for the current month, deliberately computed across *all* transactions regardless of category or `categoryId: null`, not scoped to `INCOME`-kind categories specifically - it's meant to answer "how much came in vs went out this month", which shouldn't require perfect categorization to be true. Internal transfers (`isInternalTransfer`) are excluded from both sides, same as everywhere else.
  - **Bulk categorization**: `/budgets` also lists the top `MAX_UNCATEGORIZED_GROUPS` (8) uncategorized-transaction label groups by total absolute spend (`components/budgets/uncategorized-group-card.tsx`, grouped in-memory by `normalizeLabel()` from `lib/domain/recurring.ts` - same normalization the recurring-detection heuristic uses, since it's the same "same real-world thing, different bank-feed casing" problem). `bulkAssignCategory(transactionIds, categoryId)` in `lib/actions/transactions.ts` sets one category on an arbitrary batch of transaction ids in one `updateMany` - the ids come from a server-computed group, never from client-supplied label matching, so there's no risk of a stale/forged id list touching the wrong rows.
  - Recurring-suggestion candidates (`detectCandidates` in `lib/domain/recurring.ts`) carry a `categoryId` guess: the majority (mode) category already assigned among the matched transactions, if any. This is why confirming a long-standing subscription's suggestion often needs no manual category pick - it's inherited from however you'd already tagged that label's past transactions, not re-guessed from scratch.
- `RecurringTransaction` - a subscription/bill/regular-income template (`label`, signed `amountCents`, `frequency` enum `WEEKLY|MONTHLY|YEARLY`, `intervalCount`, `anchorDate`, optional `categoryId`). `active: false` means either user-paused or a dismissed auto-detection suggestion - both states are excluded from projections and from resurfacing as a suggestion (see below), there's no separate "dismissed" table
- `IncomeEvent` - a real, user-confirmed dividend or interest payment (`type` enum `DIVIDEND|INTEREST`, optional `ticker`, gross `amountCents`, optional `taxWithheldCents`, `date`, optional `transactionId` linking back to the source `Transaction` when created via "Mark as income" rather than typed from scratch). See "Interest & dividend income tracking" below - distinct from the Analytics page's separate Yahoo-Finance-based dividend/interest *estimate*.
- `Sale` - a recorded disposal of part or all of a `Holding` position (`ticker`, `quantity` sold, `proceedsCents`, `costBasisCents` of the sold portion, `date`). See "Realized gains & annual tax report" below - realized gain is `proceedsCents - costBasisCents`, never stored.
- `SyncLog` - per-run log entries: `source` ("lcl" | "trade_republic"), `status` ("success" | "error" | "auth_required"), optional `message`
- `UserSettings` - singleton (`id = "singleton"`): salary, expenses, monthly saved, `taxRatePea`/`taxRateCto`/`taxRateCrypto` (Float, defaults 0.172/0.314/0.314) - now only defaults suggested when creating a new account, see "Tax treatment" below. `savingsGoalCents` is VESTIGIAL as of v1.14 - superseded by the `Goal` model below, kept (not dropped) per this repo's non-destructive-migration convention, no longer read or written anywhere. Also holds the alert channel config, per-channel toggles, dedup state, and per-trigger toggles (`ntfyTopicUrl`/`ntfyEnabled`, `alertEmailTo`/`smtp*`/`emailAlertsEnabled`, `webPushEnabled`, `vapidPublicKey`/`vapidPrivateKey`, `netWorthAlertThresholdCents`/`netWorthAlertLastAbove`, `lastSyncFailureAlertCheckedAt`, `loanAlertsEnabled`/`syncFailureAlertsEnabled`/`sectorDataAlertsEnabled`) - see "Alerts & webhooks" above and "Full sector-exposure breakdown" for the last one. `appLockEnabled`/`appLockChallenge` - see "App-lock (WebAuthn)" above.
- `ShareLink` - a token-gated read-only dashboard link (`token` unique, plaintext, optional `label`, optional `expiresAt`, `lastAccessedAt`). See "Read-only share links" above.
- `ApiKey` - a token-gated read-only REST API credential (`token` unique, plaintext, optional `label`, `lastUsedAt`). See "Public REST API" above.
- `AlertRule` - a user-defined alert (`kind: ACCOUNT_BALANCE | BUDGET_OVERRUN | ACCOUNT_OVERDRAFT | INVESTMENT_VALUE | HOLDING_PRICE | UNREALIZED_GAIN | REBALANCING_DRIFT | NEW_TRANSACTION`, `active`, optional `message`), parallel to the 3 fixed triggers on `UserSettings`. See "Custom alert rules" above.
- `Goal` (v1.14) - a user-defined savings goal (`name`, `targetCents`, optional `targetDate`, optional `accountId`). See "Savings goals" below.
- `AppLockCredential` (v1.15) - one registered WebAuthn authenticator (`credentialId` unique, `publicKey` bytes, `counter`, `deviceLabel`, `lastUsedAt`). See "App-lock (WebAuthn)" above.
- `PushSubscription` (v1.15) - one Web Push-subscribed browser/device (`endpoint` unique, `p256dh`, `auth`, optional `deviceLabel`, `lastUsedAt`). See "Alerts & webhooks" above.

### Savings goals

Replaces the old single `UserSettings.savingsGoalCents` global figure (v1.14) with a `Goal` model - multiple independently-named goals ("Apport immobilier: 40k/80k", "Fonds d'urgence: 8k/10k"), each with its own progress bar on `/analytics` (`components/analytics/goal-and-passive-income.tsx`'s `GoalProgressBar`, one per goal).

- **`accountId: null` means "track total net worth"** - the exact math the old single global goal always did - not a fallback/error state, a first-class choice equally as normal as linking a real account. **`accountId: <id>`** tracks that one account's own current value instead (its `AssetRow.value`, the same figure the "Mes actifs"/"Répartition détaillée" tables already show - `lib/domain/analytics.ts` exposes the full `assetRows` array, not just the top-10-sliced `topAssets`, specifically so a linked goal's account can be resolved without a second query even when it's outside the top 10).
- **`onDelete: Cascade`** on `Goal.accountId`, same reasoning as `AlertRule.accountId`: a null `accountId` means something different here ("track total net worth"), so silently falling back to that when the linked account is deleted would silently change what the goal measures, not just gracefully degrade it. Deleting the goal with the account is the safer behavior.
- **The account picker excludes `LOAN`** (a liability, not a savings target) - matching `assetRows`' own exclusion of `LOAN` for the same reason, so the picker and the value-lookup source stay in agreement by construction. Unlike `AlertRule`'s narrower per-kind account pickers (fiat-only or investment/crypto-only), a goal can link to any other account type, including `REAL_ESTATE`/`AUTOMOBILE` (e.g. a "down payment" goal). **`lib/actions/goals.ts`'s `assertGoalAccountEligible` enforces this server-side too** (real gap found and fixed in the pre-release code review, not present in the first cut) - the picker only controls what a legitimate UI flow can submit, and a Server Action is directly invocable regardless of what's rendered, same trust boundary as `assertCsvImportEligible`/`assertIncomeEventEligible` elsewhere in this codebase. Without it, a goal silently linked to a LOAN account would always show 0% progress (`assetValueById` never has an entry for it) with no explanation - confirmed live by deliberately injecting a LOAN account id into the picker's DOM and submitting: the Server Action rejected it, no `Goal` row was written.
- **Settings manages, Analytics displays** - `components/settings/goals-section.tsx` + `lib/actions/goals.ts` are CRUD-only (name/target/date/linked account), no live progress shown there, matching how `AlertRule`'s live evaluation lives in `/api/alerts/check`, not in its Settings list.
- **Migration backfill**: `20260823174545_add_goals` carries the pre-v1.14 single global goal forward as the first `Goal` row (`accountId: NULL`, name "Patrimoine", `targetCents` = the old `UserSettings.savingsGoalCents` value) so nothing already configured is lost - the first migration in this repo to do a real cross-table `INSERT ... SELECT`-style backfill, with a `COALESCE` fallback to the old field's own schema default for a fresh install where the `UserSettings` singleton row doesn't exist yet.
- `lib/domain/goals.ts`'s `computeGoalProgress(currentCents, targetCents)` is the shared, unit-tested pure math (`pct` capped at 100, `remaining` floored at 0) - extracted so it's reusable across N goals instead of being computed once inline the way the old single figure was.
- **`prisma/seed-demo.ts` seeds three example goals**, not one - real gap found while checking whether the demo actually showcases this feature: the migration backfill alone only ever produces a single net-worth-tracking goal (whatever `UserSettings.savingsGoalCents` happened to be), which doesn't demonstrate account-linking at all. The seed now creates one net-worth-tracking goal ("Patrimoine") plus two account-linked ones across different account types (a `SAVINGS`-linked "Fonds d'urgence" and an `INVESTMENT`-linked "Objectif CTO"), so a demo visitor sees the actual range of what the feature does. `prisma.goal.deleteMany()` was added to the script's own clearing step too - without it, re-running the seed on an already-migrated-and-seeded database would create a second "Patrimoine" goal alongside the migration-backfilled one instead of replacing it.

### Long-term net worth projection

`components/analytics/projection-chart.tsx` on `/analytics` (v1.14, right after the net-worth-evolution/allocation charts) - a compound-growth "what-if" chart answering "at this pace, where am I in 10/20/30 years", closing the one analytics gap this README already positions against Finary's own "Vision" feature for.

- **The assumed annual return is a live, client-side input, deliberately not a persisted `UserSettings` field.** This is an exploration tool, not a stored preference - the user asked for it this way directly after weighing the tradeoff (a persisted setting would need a schema migration, a Server Action, and Settings-page wiring for a value that's more naturally "try a few numbers" than "set once"). Pre-filled from `investCAGR` (the portfolio's own real CAGR, rounded to 1 decimal and floored at 0% since a real portfolio can have a negative CAGR but the input's own `min="0"` shouldn't be handed an invalid default) when available, else a fixed 5% fallback - always visible, always adjustable, recomputes instantly on every change via `useMemo`, no network round-trip.
- **`lib/domain/projection.ts`'s `projectNetWorth()`** is the pure math, mirroring `lib/domain/loan.ts`'s "params in, computed stats out" shape - a closed-form lump-sum-plus-annuity formula per year (`NW(t) = N0*(1+r)^t + C*(((1+r)^t-1)/r)`, with the `r=0` case handled separately since the annuity term divides by `r`) rather than an iterative simulation, avoiding float drift across 30 loop iterations the same way `loan.ts`'s own closed-form annuity math already does. Takes plain `number` cents, not `bigint` - it's called client-side on every input change, so the `bigint`→`Number` conversion happens once at the component boundary instead of on a server round-trip.
- **The annual contribution is `monthlySavedCents * 12` only when `hasDeclaredSavings` is true - never a fallback to `momDelta`** (the signal `savingsRate` itself falls back to when declared savings is absent). A single month's balance swing is noisy and genuinely inappropriate to extrapolate 30 years forward - the chart still renders with contribution `0` in that case (pure growth of today's net worth), with a visible note explaining why, rather than silently guessing from one volatile data point.
- **Correction (post-release UI/UX pass)**: the original cut of this feature needed zero `AnalyticsResult` changes, but user testing surfaced two real gaps closed in the same pass - the projection didn't account for latent tax on the projected gain (a real question raised against Finary's own simulator as the quality bar), and the horizon was a fixed 30 years with no way to look further or nearer.
  - **Tax-aware mode**: `lib/domain/analytics.ts`'s `computeAnalytics` now also returns `effectiveTaxRate` - a gain-weighted blended latent-tax rate (`getAccountTaxRate(account)` weighted by that account's own unrealized-gain-in-cents, summed across every account with a real gain, mirroring the exact weighting pattern `investCAGRWeightedYears` already uses elsewhere in this same function). EXEMPT/DEFERRED accounts contribute rate `0` and still count toward the gain-weighted denominator, naturally pulling the blended rate down for a mostly tax-advantaged portfolio - the same behavior `totalLatentTax` already has, just expressed as one reusable ratio instead of only ever an absolute cents figure. `projectNetWorth()` (`lib/domain/projection.ts`) takes this as an optional `effectiveTaxRate` param (default `0`, so every pre-existing pre-tax-only caller is unaffected) and computes `gain(t) = NW(t) - N0 - C*t` per year, taxing only a positive `gain(t)` - never the contributions - to produce a second `netWorthAfterTaxCents` figure per point. `ProjectionChart` renders this as a second, dashed, muted reference line (no fill, unlike the solid pre-tax `Area`) plus a small legend and a "≈ X net d'impôt" note under each callout - all gated on `effectiveTaxRate > 0` so a portfolio with no taxable gain (e.g. all-PEA) doesn't draw two overlapping identical lines. `effectiveTaxRate` is in the export-completeness allowlist (`__tests__/export-completeness.test.ts`), same `assetRows` precedent - it's an internal input for this chart's client-side math, not a standalone figure the markdown export needs to show.
  - **Configurable horizon**: the fixed 30-year span became a 10/20/30/40-year segmented pill selector (same visual pattern as `theme-switcher.tsx`/`language-switcher.tsx`, extended to 4 options), client-side state like the return-rate input - not persisted, this is still a "try a few numbers" exploration tool, not a stored preference. The 3 callout stats are now proportional to the selected horizon (`horizon/3`, `horizon*2/3`, `horizon`, rounded) instead of hardcoded 10/20/30, so they stay meaningful at every setting.

### Net worth calculation

**Gross = fiat balances + holdings market value + real estate/automobile manualValueCents**
**Net = Gross − liabilityCents − loan remaining capital − latent taxes**

Latent tax rate: per-account via `getAccountTaxRate()` - see "Tax treatment" above. `UserSettings`'s PEA/CTO/Crypto rates (Settings → Fiscalité) are only the defaults suggested when creating a new account.

### Historical asset-allocation chart

Extends the dashboard's current-moment allocation pie (`AssetAllocationChart`) into a stacked-area view over time (`AllocationHistoryChart`, `components/shared/allocation-history-chart.tsx`) - "Répartition dans le temps" (v1.16), right below the existing net-worth-chart/allocation-pie row on `/` and the read-only `/shared/[token]` view. Built entirely from the same per-account `HistoricalBalance` rows `computeDashboard()`'s existing `history` (net worth) series already reads - no new data collection, no new Prisma query on the dashboard page.

- `lib/domain/dashboard.ts`'s `computeDashboard()` gained a `typeMap` (account id → `AccountType`, built alongside the existing `liabMap`) and a parallel `allocationHistoryRaw`/`allocationHistory` computation inside the exact same day-by-day `running`-balance loop that already produces `historyRaw`/`history` - not a second pass over `allBalances`. Each day, `running`'s per-account values are bucketed into the same 6 categories `allocationRaw` already uses (`cash`/`savings`/`investments`/`crypto`/`realEstate`/`auto`), keyed off `typeMap`. `LOAN` accounts are skipped entirely, matching `allocationRaw`'s own exclusion (pure liability, no asset counterpart in either view).

### Historical value chart per investment account

A "Trade-Republic-style" smooth value-over-time line for a single `INVESTMENT`/`CRYPTO` account's own detail page (v1.16) - a different, narrower ask than the dashboard-wide allocation chart above. **Scoped deliberately, not assumed** - `ROADMAP.md` flagged this as needing real design work before building, since unlike fiat accounts, investment/crypto `HistoricalBalance` rows are event-driven (only written when a holding actually changes via `refreshAccountBalance()` - see "Multi-currency"/"Portfolio rebalancing" above), not daily.

**Two options were weighed against real evidence, not assumption, before picking one:**

1. **A synthetic daily series** (current quantity × Yahoo Finance historical daily price) was considered and **rejected** after checking what data the app actually has: `ISIN_TO_YF_SYMBOL` (`lib/domain/analytics.ts`) is a **6-entry hand-verified map**, not a general ISIN→Yahoo-symbol resolver - even the demo seed's own PEA ETF ISINs (`IE00B4L5Y983`/`IE00B5BMR087`) aren't in it. Building real coverage would need the same one-by-one manual verification discipline the "Full sector-exposure breakdown" backlog item is *also* blocked on (see `ROADMAP.md`'s v1.16 section) - the same underlying data gap blocks both. Beyond coverage, a synthetic series would also need to assume the current quantity was held for the entire charted period, silently misrepresenting any account where a position was bought/sold/added to - a real correctness risk for a wealth-tracking app, not just a cosmetic one.
2. **The existing event-driven `HistoricalBalance` line** - accurate by construction (real recorded snapshots, no assumptions), zero new data collection, but sparse for a rarely-touched account. Confirmed directly against the dev DB before deciding: a demo PEA left untouched had **0** `HistoricalBalance` rows, Crypto **0**, a CTO edited once that session **1** - not just "coarser" than a fiat chart, often close to empty in practice.

**Chose option 2** - honest and correct beats smooth and sometimes-wrong, matching this codebase's own bar everywhere else real money is displayed. The sparse case is handled, not hidden: `BalanceHistoryChart` already had a `data.length < 2` → `t("charts.notEnoughData")` empty state (built for fiat accounts with little history) - reused as-is rather than building a second one.

- **`lib/domain/account-detail.ts`'s `chartData` needed zero changes** - `computeAccountDetail` already mapped `account.history` into `ChartPoint[]` unconditionally for every account type; only `app/accounts/[id]/page.tsx`'s render gate (`result.isFiat` → `result.isFiat || result.isInvestment`) and prop threading were new. `BalanceChartSection`/`BalanceHistoryChart` both gained an `isInvestment?: boolean` prop (default `false`, so every fiat call site is unaffected) that swaps "Solde"/"Balance" wording for "Valeur"/"Value" (new `valueEvolution`/`value`/`valueAria` keys alongside the existing `balanceEvolution`/`balance`/`balanceAria` ones) - reusing the exact same data-shape-generic `BalancePoint`/chart component rather than building a parallel one, since the only real difference is terminology, not shape or behavior. `canImportCsv` already resolves to `false` for investment accounts (`isFiat && !isSynced && !gocardlessAccountId`), so the CSV-import button correctly never appears on this chart for an investment account without any new gating.
- Positioned in the same spot the fiat balance chart already occupies (right after the account header, before the holdings table) - matches Trade Republic's own layout (the value chart leads a position's detail view, not an afterthought below it).
- Verified live against real `HistoricalBalance` rows (a CTO with 0 then 1 then 4 points, inserted directly to confirm both the empty state and the real rendered line): the sparse-data message renders correctly with only the demo seed's own data, and a 4-point real series renders a correct, correctly-labeled ("Évolution de la valeur") smooth line once enough history exists.

**Follow-up, same v1.16 cycle: real user feedback on the shipped chart** - correctly noted that relying only on manual edits (or `RefreshHoldingFxButton`'s own incidental `refreshAccountBalance()` call, foreign-currency holdings only) to populate this chart's data points meant a long-held, rarely-touched position would stay sparse indefinitely, and asked for automatic periodic capture while explicitly keeping the manual button as a "capture right now" option, not replacing it with the automatic path.

- New route `app/api/investments/snapshot-balances/route.ts` - same call shape, same `NEXTAUTH_SECRET` bearer-token auth, as `/api/alerts/check`/`/api/transactions/auto-categorize`. Calls the already-existing `refreshAccountBalance()` (`lib/actions/holdings.ts`) for every `INVESTMENT`/`CRYPTO` account, unconditionally - this does **not** fetch new market prices for holdings (still a manual "update the price when you check in" action, completely unchanged); it only records *today's already-known valuation* (quantity × `lastPriceCents`, exactly what `refreshAccountBalance` already computes on a manual edit) more regularly, the same way a synced fiat account already gets a fresh balance snapshot on every sync cycle regardless of whether the balance actually moved.
- `sync/main.py`'s `_run_all()` gained `_snapshot_investment_balances()`, called on the same existing 4h cron alongside `_auto_categorize()`/`_check_alerts()` - no new schedule, same "one more step on the cron that's already running" precedent those two already established. `proxy.ts`'s middleware matcher gained `api/investments` to the same no-browser-session exclusion list as `api/alerts`/`api/transactions`, same bare-prefix (not `$`-anchored) style as those two existing entries.
- `RefreshHoldingFxButton` stays exactly as it was, unreplaced - clicking it still does its own thing (re-fetch the FX rate) and still incidentally adds a chart data point via the same `refreshAccountBalance()` call it already made, now just one of two ways a point gets recorded instead of the only way for a foreign-currency holding.
- Between two automatic snapshots with no real edit in between, the recorded value is identical (no live price-fetching was added) - the chart shows a flat line for that stretch, which is honest (nothing changed) rather than misleadingly smooth-looking; a genuine step change still shows clearly the moment a price is actually updated.

**A different, unrelated question raised while testing this**: whether the Sell/Edit buttons visible on the demo CTO account's holdings table were intended at all. They are - pre-existing, unrelated to this feature - manually-managed (non-`isSynced`) investment accounts are meant to support recording purchases/sales by hand for cost-basis and tax-report tracking (see "Realized gains & annual tax report" above); `holdings-table.tsx` already gates the entire actions cell (Sell, Edit, and `RefreshHoldingFxButton`) behind `!isSynced`, so a real broker-synced account never shows them. Confirmed this gating is intact and `RefreshHoldingFxButton` sits inside the same `!isSynced` block as the pre-existing two, not a separate, differently-scoped check.

### Container image hardening

`docker.yml`'s `trivy-scan` job scans the published `app`/`sync` images for OS-package-level CVEs (npm audit/pip-audit only ever see `package.json`/`requirements.txt`, never what's baked into the base image layer). Two things have already been removed from the runtime images because they were pure dead weight *and* a real CVE surface, not just untested risk:

- **`Dockerfile` (app)**: `node:22-alpine` bundles `npm` (and its own vendored `node_modules`) even though this project only ever uses `pnpm` via `corepack` - `npm`/`npx` are never invoked anywhere in this Dockerfile or its `CMD`. Removed via `rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/npm /usr/local/bin/npx` at the end of the `runner` stage. Verified `pnpm`/`node`/`prisma` still work with it gone; confirmed 0 CRITICAL/HIGH findings afterward (previously 6, including one CRITICAL in a vendored `tar`).
- **`sync/Dockerfile`**: `gcc`/`g++` (and the headers/`libc6-dev`/`linux-libc-dev` they pull in via `apt-get autoremove`) are only needed to compile `requirements.txt`'s native extensions (woob's `lxml`, `cryptography`, `psycopg2`) - the compiler itself is dead weight once the `.so` files exist. Removed right after `pip install` in the same `RUN` layer. Verified all sync modules (`woob`, `pytr`, `playwright`, `psycopg2`) still import fine afterward; this alone accounted for 47 of 117 CRITICAL/HIGH findings.
- **`sync/Dockerfile`, round two**: `git` is only needed for `pip install` to clone `pytr`'s pinned git commit (no PyPI release) - never used again afterward, and removing it cascades (via `apt-get autoremove`) to `perl`/`liberror-perl`/`libcurl3t64-gnutls`, which nothing else needs either. `xvfb`/`xserver-common` come bundled with `playwright install --with-deps chromium`'s headed-**and**-headless dependency union, but this project only ever launches Chromium headless (`setup_tr.py`) and never starts an X server (grep confirms `Xvfb`/`DISPLAY` are never referenced in `sync/`) - removing them cascades to the Mesa GL/Vulkan/X11-window-manager stack they alone pulled in (Chromium's own `ldd` output has no `libGL`/`libEGL` dependency - it ships its own software renderer for headless use). Verified together, not just individually: after removing all of it, headless Chromium still launches, executes JS, renders a canvas element, and produces a correct screenshot (byte-identical across two independent test runs) - cut CRITICAL/HIGH findings on this image roughly in half (66 → 33; see #22 for the full investigation, including why `perl-base` specifically is *not* touched - it's a Debian-essential package apt itself refuses to remove without `--allow-remove-essential`).

**Known accepted risk**: the sync image's CRITICAL/HIGH count is not a fixed number - it drifts upward over time purely from newly-disclosed CVEs against packages that were already there, with no code or Dockerfile change on this project's side. It was ~33 right after the hardening pass above; the v1.14 audit measured it at **66** (60 HIGH + 6 CRITICAL across 27 distinct CVEs, via `gh api .../code-scanning/alerts?ref=refs/tags/v1.13.1`) against the same trimmed Dockerfile - `libglib2.0`, `perl-base`, the `util-linux`/`ncurses` family, `libcups2t64`, `libxml2`, and a handful of single-count Debian base packages, either genuine Chromium runtime dependencies (`libglib2.0`, `libblkid1`, `libmount1` are all in its own `ldd` output) or Debian-essential base packages nothing here installed on purpose. **Don't treat a re-measured count higher than the last note as a regression to chase** - re-verify the Dockerfile still has the same trimming (`git`/`gcc`/`g++`/`xvfb` still absent) before concluding anything changed on this project's end; if it does, the growth is upstream Debian/Chromium CVE disclosure, not a fix that got un-done. `trivy-scan` therefore runs **non-blocking** (`exit-code: 0`) for the `sync` matrix entry specifically, while staying fully blocking (`exit-code: 1`) for `app`, which is clean as of v1.13.1 (see the pnpm/tar note below - it was briefly not clean at the v1.13.0 tag). This is deliberately narrower than the `find-my-way`/`valibot` exemptions under "pnpm overrides" below (those are unreachable *code paths* in an otherwise-used dependency; this is Chromium's own real runtime footprint) - it's accepted because `sync/`'s HTTP API is Docker-network-only per `SECURITY.md`, never internet-exposed, not because the CVEs don't matter. Findings still upload to the Security tab either way (`if: always()` on the SARIF upload), so they stay visible.

**Recurring pattern, not a one-off**: the app image's own blocking gate has now been tripped twice by the exact same root cause - a `tar` version vendored *inside* corepack's cached pnpm single-executable build (`home/node/.cache/node/corepack/v1/pnpm/<version>/...`), never this project's own dependency tree. First occurrence (v1.4.4-v1.4.11, GHSA-r292-9mhp-454m, MEDIUM) never actually blocked anything - `limit-severities-for-sarif: true` fixed a *different* bug that happened to also reveal this finding in a debug dump, and it sat below the CRITICAL/HIGH gate. Second occurrence (v1.13.0, CVE-2026-73566, HIGH) did block the release. Root cause both times: the pinned `packageManager` version in `package.json` was simply old enough that corepack's cached pnpm build still bundled a vulnerable `tar`. Fixed in v1.13.1 by bumping `pnpm@11.17.0` → `pnpm@11.22.0` (bundles `tar@7.5.22`, verified via `npm pack pnpm@11.22.0` and reading the bundled `tar/package.json` directly, not just trusting a changelog). There is no deeper structural fix available short of not caching corepack at all (which would break the Dockerfile `CMD`'s `pnpm exec prisma migrate deploy` at every container start) - this is accepted, expected maintenance: when it recurs again, re-check whether the currently-pinned pnpm version's bundled `tar` is still ahead of the latest disclosed CVE, and bump if not, the same way the "pnpm overrides" table below gets bumped for transitive-dependency CVEs.

**Three real, distinct bugs made `trivy-scan(app)` look broken across v1.4.4-v1.4.10, in order**: (1) `aquasecurity/trivy-action` pinned as `@0.36.0` instead of the real tag `@v0.36.0`, failing before any scan ran; (2) a raw `${{ github.repository }}`-built `image-ref` scanning `ghcr.io/LoicSERRE/...` (capitalized, matching this repo's real GitHub owner) instead of the required-lowercase GHCR path, also failing before any scan ran - fixed by lowercasing it explicitly, then hardened further by scanning `build-app`/`build-sync`'s own `digest` output instead of the mutable `:latest` tag (immune to any registry tag-propagation lag, a real but secondary bug this surfaced); (3) `/root/.cache/pnpm` (410MB of npm-registry metadata left over from `pnpm install --prod`, never read at runtime) made Trivy's secret scanner slow enough to occasionally exceed its 5-minute default timeout mid-scan - reproduced locally with the exact same timeout, fixed by removing that cache (keep `/root/.cache/node/corepack` though, that one **is** needed at runtime - see the `Dockerfile` comment). After all three were fixed, one real (if minor) finding was still failing the gate: a MEDIUM-severity `tar` DoS (`GHSA-r292-9mhp-454m`) vendored *inside* corepack's own cached pnpm single-executable build, not this project's dependency tree. It was slipping through a `severity: CRITICAL,HIGH` filter that should have excluded it, because `aquasecurity/trivy-action`'s `format: sarif` mode builds its report **"with all severities" regardless of the `severity` input** unless `limit-severities-for-sarif: true` is also set - a real trivy-action gotcha, not a workflow logic bug, and the actual root cause of most of this saga's apparent flakiness. All fixed; see the commit history around v1.4.4-v1.4.11 for the full trail if this class of "images build and push fine, but the gate after them behaves unpredictably" resurfaces.

**A third, different root-cause class tripped the same gate at the v1.16.0 tag: a floating base-image tag, not a vendored dependency.** `Trivy` failed on `CVE-2026-14456` (Alpine's `libssl3` 3.5.7-r0, a HIGH-severity unbounded-memory-growth DoS in OpenSSL's QUIC server) even though the patched `3.5.8-r0` was already available in Alpine's own package repo at build time (confirmed live: `apk upgrade --no-cache` against the same `node:26-alpine` tag pulled it immediately) - nothing in this `Dockerfile` ever installs `libssl3` directly, it only arrives transitively via the base image. Unlike the `pnpm`/`tar` saga above, there was no pinned version to bump - `node:26-alpine` is an unpinned floating tag by design (tracking Node 26's latest Alpine build), so its baked-in package snapshot can simply be stale relative to Alpine's live repo on any given day. Fixed by adding `apk upgrade --no-cache` as the first command in the `runner` stage, before installing anything else - this makes every build pull current Alpine packages regardless of how stale the pulled base-image layer happens to be, rather than trusting whatever snapshot the tag last baked in. Same category of fix as `sync/Dockerfile`'s existing `apt-get update` pattern before its own package installs, just not previously applied to this Dockerfile's `runner` stage.

### CI quality gates

`quality.yml` is a second, separate scanning workflow from `docker.yml`'s `trivy-scan` above - lightweight, stateless scanners (actionlint, zizmor, SonarQube, a duplication/complexity ratchet) adapted from an internal template workflow set. Tool versions are pinned inline in `run:` lines rather than via `uses:`, so Dependabot's `github-actions` ecosystem entry won't auto-bump them - bump manually on a new CVE class or rule-pack update. `zizmor` (workflow security posture) runs non-blocking by design: this repo pins actions by tag, not SHA, and that's its dominant finding class - informational until that's revisited.

The duplication/complexity ratchet job compares each run against a baseline artifact from a prior run via `gh api`; a transient GitHub API error on that lookup used to hard-fail the whole job instead of just skipping the comparison. Both the "list artifacts" and "download artifact zip" calls now fail open (treated as "no baseline yet") - don't re-tighten this to fail closed, a flaky `gh api` call isn't a real quality regression.

### Prisma client

This project uses **Prisma 7** with the `@prisma/adapter-pg` driver adapter (not the legacy built-in engine). `lib/db/prisma.ts` creates the client via a `pg.Pool` → `PrismaPg` adapter. Always import `prisma` from `@/lib/db/prisma` - never instantiate `PrismaClient` directly. The client is a module-level singleton (cached on `globalThis` in dev to survive HMR).

The client is generated to `app/generated/prisma` (gitignored, never committed). `pnpm install` runs it automatically via the `postinstall` script; re-run `pnpm exec prisma generate` manually after editing `schema.prisma` without reinstalling. In `Dockerfile`, the `deps` and `runner` stages run `pnpm install --frozen-lockfile` with `--ignore-scripts` because `prisma/schema.prisma` isn't copied into those stages yet - the `builder` stage generates the client explicitly once the full source is present.
