# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with this repository.

## What this repo is

`finalibaba-selfhosted` is the **public self-hosted edition** of [Finalibaba](https://github.com/LoicSERRE/Finalibaba), a personal wealth management dashboard. It contains the same core application stripped of personal deployment config, with community-oriented documentation.

**Goal:** anyone should be able to run the app with a single `docker compose up` and a `.env` filled in under 5 minutes.

## Language policy

- **All repo meta** (code comments, README, CLAUDE.md, commit messages, PR descriptions, issue templates) → **English**
- **UI strings** → French by default. English is available via the language switcher (stored in `NEXT_LOCALE` cookie). Add new UI strings to both `messages/fr.json` and `messages/en.json`.
- The private upstream repo (`Finalibaba/`) stays in French - it's personal.

## Relationship with the upstream private repo

The private repo is at `/mnt/c/Projets/Finalibaba` on the same machine (default path baked into `scripts/sync-from-upstream.sh`; override with `./scripts/sync-from-upstream.sh <path>`).

**Porting rule:** app-layer changes (features, bug fixes, schema changes) made in `Finalibaba/` should be ported here via `scripts/sync-from-upstream.sh`. Infra-layer changes (deploy pipeline, VPS config, personal credentials) are **never** ported.

The script's `rsync --exclude` list is the source of truth for what never gets synced - it covers infra files (`.github/`, all `docker-compose*.yml`, `env.server.example`, `.env*`), selfhosted-only docs (`CLAUDE.md`, `README.md`, `ROADMAP.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `LICENSE`), demo/mock seed files (`prisma/seed-demo.ts`, `prisma/seed-tr-mock.ts`), and `scripts/`, `.claude/` themselves. The files below additionally need protection because they *do* exist upstream but must keep selfhosted-specific content:

Files that must **never** be overwritten by the sync script:

| File | Reason |
|---|---|
| `proxy.ts` | Selfhosted version has conditional auth - may diverge from upstream |
| `components/layout/sidebar-wrapper.tsx` | Server component reading `AUTH_ENABLED` - selfhosted-specific |
| `components/layout/sidebar-dynamic.tsx` | Selfhosted-only file, does not exist in upstream |
| `docker-compose.yml` / `docker-compose.dev.yml` | Different from upstream (build from source, generic credentials) |

## Tech stack

Same as upstream.

- **Framework:** Next.js 16+ (App Router, Server Actions for mutations), React 19+
- **Styling & UI:** Tailwind CSS v4 with CSS custom properties (no config file - tokens in `globals.css`)
- **Database:** PostgreSQL via Prisma ORM - client generated to `app/generated/prisma`
- **Charts:** Recharts
- **Icons:** `lucide-react`
- **Sync service:** Python FastAPI + APScheduler (optional - runs without bank credentials)

> Always append `@latest` when installing packages.

## Development commands

This project uses **pnpm** (not npm/yarn) - the exact version is pinned in `package.json`'s `packageManager` field, and `corepack enable` (already run in the Dockerfile, and standard in Node 22+ environments) makes `pnpm` resolve to that exact version automatically.

```bash
pnpm dev         # Dev server (http://localhost:3000)
NODE_ENV=production pnpm run build    # Prod build + type-check (NODE_ENV=production REQUIRED)
pnpm run lint    # ESLint
pnpm test        # Vitest - see __tests__/
pnpm test __tests__/alerts.test.ts     # Single test file
pnpm test -- -t "name substring"       # Filter by test name across the suite
pnpm run test:coverage  # Vitest with coverage - see "Development commands" note below on the report
```

Docker (local dev - DB only, credentials fixed in `docker-compose.dev.yml`):
```bash
docker compose -f docker-compose.dev.yml up -d
# DATABASE_URL=postgresql://appuser:devpassword@localhost:5432/finalibaba
pnpm exec prisma migrate deploy   # first time only - applies schema to the fresh DB
pnpm run db:seed:demo             # optional - fills it with realistic fictional data to develop against
```

Production (one-shot setup):
```bash
cp .env.example .env   # fill in values
docker compose up -d   # builds and starts everything
```

Prisma:
```bash
pnpm run db:migrate -- --name <name>   # Create + apply migration
pnpm exec prisma generate               # Regenerate client after schema changes (also runs automatically via postinstall on `pnpm install`)
pnpm run db:seed                        # Seed common institutions (reference data, no accounts)
pnpm run db:seed:demo                   # WIPES all data, then seeds realistic fictional accounts/balances/holdings/transactions - for local dev/debugging
pnpm run db:push                        # Sync schema to DB without a migration (dev only)
pnpm run db:studio                      # Open Prisma Studio for DB inspection
```

Vitest for unit tests - `pnpm test` runs everything under `__tests__/**`, covering `lib/domain/`, `lib/utils/`, `lib/services/` (all pure functions: money math, tax, loans, recurring-transaction detection, CSV import, analytics/dashboard aggregation, export completeness) and `lib/auth.ts` (rate limiter + the real `authorize()` credentials/bcrypt flow - see the comment on `provider.options.authorize` in `__tests__/auth.test.ts` for a real next-auth v4 footgun: `CredentialsProvider()`'s top-level `.authorize` is a hardcoded `() => null` stub, the real function only lives at `.options.authorize` until NextAuth's own request pipeline merges it). `pnpm run test:coverage` runs the same suite with a `text`+`json-summary` report - trust the JSON output over the terminal table, which has a rendering bug in this vitest version that silently drops some 100%-covered files from the printed table (their numbers are still folded into the overall summary).

**Known, accepted coverage gaps**: `lib/actions/*` (19 Server Action files - every DB mutation in the app) and `lib/services/gocardless.ts` are excluded from the SonarQube coverage gate wholesale (`sonar-project.properties`'s `sonar.coverage.exclusions`) even though one file now has partial Vitest coverage - `__tests__/totp-actions.test.ts` mocks `@/lib/db/prisma` directly and exercises `lib/actions/totp.ts`'s error paths and success data shape (not `startTotpSetup`'s QR generation), proving Prisma mocking is viable here. It stays "light coverage only" per that test file's own comment, and the other 18 action files remain untested - a real test DB or broader Prisma mocking convention would still be needed to close the gap for good. `sync/` only tests the pure functions extracted from `sync_tr.py` - `sync_lcl.py`/`sync_woob.py`/`db.py`/`main.py`/`setup_lcl.py`/`setup_tr.py`/`setup_woob.py` are untested. No component-rendering tests (no jest-dom/RTL/Playwright as committed dependencies) - components stay thin wrappers around the tested `lib/` functions by design, e.g. the dashboard's JSX extraction into `components/dashboard/dashboard-view.tsx` described under "Read-only share links" below.

### pnpm overrides

`pnpm-workspace.yaml`'s `overrides` key forces patched versions of transitive dependencies that can't be resolved by Dependabot alone (upstream packages pin older ranges). Do not remove these entries - they are security fixes. (This lived in `package.json`'s `overrides` field under npm, and briefly under a `package.json` `"pnpm"` key during the pnpm migration - pnpm 11 moved all such settings to `pnpm-workspace.yaml`, silently ignoring the `package.json` location instead of erroring, so double-check here first if an override ever seems to stop applying after a pnpm upgrade.)

CI's `pnpm audit` step runs as `pnpm audit --prod --audit-level=high` - deliberately excluding devDependencies (ESLint, TypeScript, etc.). Those never ship: the Docker `runner` stage installs with `pnpm install --frozen-lockfile --prod --ignore-scripts`, so a devDependency-only advisory (e.g. through `eslint`'s vendored `minimatch`) can't reach production and isn't worth chasing at the cost of breaking the lint toolchain. `prisma` is a runtime `dependencies` entry (not dev) precisely because the `Dockerfile`'s `CMD` runs `pnpm exec prisma migrate deploy` inside the `runner` stage at container start - so `prisma`/`@prisma/dev`-rooted advisories (`find-my-way`, `valibot`, formerly `hono`/`@hono/node-server` before prisma 7.9 dropped that dependency) get installed by that `--prod` install and stay in scope even though the specific vulnerable code path (`@prisma/dev`'s embedded-Postgres `prisma dev` subcommand) is never actually invoked here.

pnpm also blocks a dependency's install/postinstall scripts by default unless explicitly allowed - `pnpm-workspace.yaml`'s `allowBuilds` list covers the packages in this project's tree that legitimately need one (Next's SWC compiler, Prisma's engine binaries, esbuild, file-watching). A `pnpm install` that reports `ERR_PNPM_IGNORED_BUILDS` for a package not already on that list means a new dependency needs the same explicit yes - don't add it blindly; check what the script actually does first.

## Pre-commit verification pipeline

Run this before proposing or making any commit - it exists so a commit never introduces something CI would have caught anyway (a broken build, a failing test, a new lint/audit finding), and so a SonarQube regression is caught locally before it shows up on the next scan. Order matters: cheapest/fastest checks first, so a trivial mistake (a lint error) fails in seconds instead of after a multi-minute build+test run.

1. **Working tree sanity** - `git status` (nothing unexpected staged/unstaged) and, on any branch that was just merged or rebased, `git diff --check` (flags leftover `<<<<<<<`/`=======`/`>>>>>>>` conflict markers and trailing-whitespace issues that a manual conflict resolution can silently leave behind - this is the "no conflicts" gate).
2. **Lint** - `pnpm run lint` (ESLint, includes `eslint-plugin-sonarjs`'s rules - the same static-analysis family SonarQube's own scan runs, so most Sonar code-smell findings already surface here for free).
3. **Type-check & build** - `NODE_ENV=production pnpm run build` (Next.js's build IS the type-check in this project - there's no separate `tsc --noEmit` script; `NODE_ENV=production` is required, see "Development commands" above). This is the frontend/backend "no conflicts" gate: a broken import, a type mismatch between a Server Action and the component calling it, or a Server/Client boundary violation fails here.
4. **Unit tests** - `pnpm run test:coverage` (not plain `pnpm test` - the coverage run is needed for step 6 anyway, and its `json-summary` report is the one to trust over the terminal table, see "Development commands" above).
5. Steps 2-4 are bundled as **`pnpm run verify`** - run that one command for the common case (JS/TS-only change). Add the Python steps below whenever a commit touches `sync/`:
   - `ruff check sync/` (lint)
   - `cd sync && python -m pytest` (tests)
6. **SonarQube** - local/on-demand only, not wired into CI (see `sonar-project.properties`'s header comment). After step 4 has produced fresh coverage, run your local `sonar-scanner` from the repo root (it auto-detects `sonar-project.properties`, including the `sonar.javascript.lcov.reportPaths=coverage/lcov.info` it just consumed) against your SonarQube instance, and confirm the quality gate is green with **zero new issues** - not just "no new CRITICAL/BLOCKER", since `sonar-project.properties`'s `sonar.issue.ignore.multicriteria` list already documents every accepted pre-existing exception explicitly; anything new outside that list is a real regression to fix, not to suppress.
7. **Dependency audit** (only when `package.json`/`pnpm-lock.yaml` or `sync/requirements.txt` changed) - `pnpm audit --prod --audit-level=high` and, for Python, `pip-audit -r sync/requirements.txt`. Mirrors the `security`/`python-security` CI jobs; see "pnpm overrides" above before adding a new override in response to a finding here - check whether one already exists or is deliberately not applied.

This pipeline mirrors `ci.yml`'s job list on purpose (`lint` → `typecheck` → `test` → `python-lint`/`python-test` → `security`/`python-security`) plus the SonarQube gate `quality.yml` doesn't cover (SonarQube itself isn't in CI - see "CI quality gates" below) - the goal is that `git push` never surprises CI with something `pnpm run verify` (plus the conditional steps) would already have caught locally.

Selfhosted-specific points below.

### Authentication

**Disabled by default** (`AUTH_ENABLED` unset or anything other than `"true"`). Self-hosted = private network, network-level trust is sufficient.

Enabled via `AUTH_ENABLED=true` + `AUTH_PASSWORD` (plaintext) or `AUTH_PASSWORD_HASH` (bcrypt). When enabled: NextAuth Credentials provider, JWT session 30d, rate-limit 5 attempts/15min/IP. Display name via `AUTH_USER_NAME` (defaults to `"owner"`).

**Optional TOTP 2FA** on top of the password, toggled from Settings (`components/settings/two-factor-section.tsx` + `lib/actions/totp.ts`), never via env var - state lives on the `UserSettings` singleton (`totpEnabled`, `totpSecret`, `totpBackupCodes`). `lib/domain/totp.ts` holds the pure crypto (secret/URI generation via `otplib`, `verifyTotpCode` with 30s clock-drift tolerance, bcrypt-hashed one-time backup codes). `lib/auth.ts`'s `authorize()` checks `totpEnabled` after the password succeeds and accepts either a live 6-digit code or a backup code (consuming it from `totpBackupCodes` on use) - `components/auth/login-form.tsx` only renders the extra code field when a server-fetched `totpEnabled` prop says to. `regenerateBackupCodes`/`disableTotp` require a **live** TOTP code, never a backup code, so a single backup code can't mint itself replacements or turn off 2FA outright.

`proxy.ts` is the Next.js middleware (at the repo root). It reads `process.env.AUTH_ENABLED` in the `authorized` callback and bypasses NextAuth when it isn't `"true"`. If the upstream `proxy.ts` ever diverges, do **not** blindly overwrite this file.

`components/layout/sidebar-wrapper.tsx` is a **server component** (no `"use client"`) - reads `AUTH_ENABLED`, passes `showLogout` prop to `sidebar-dynamic.tsx`.
`components/layout/sidebar-dynamic.tsx` is a **client component** (`"use client"`) - handles `dynamic({ ssr: false })` (required to be in a client component in Next.js 16). This file does not exist in the upstream repo.
Both files are selfhosted-specific and must never be overwritten by the sync script.

For users who want security without built-in auth: document Nginx Proxy Manager, Caddy basicauth, Traefik + Authelia, Cloudflare Access, or VPN (Tailscale).

### Read-only share links

Settings → "Liens de partage" (`components/settings/share-links-section.tsx` +
`lib/actions/share-links.ts`) generates a `/shared/[token]` URL that renders
the net-worth dashboard read-only, to hand to an advisor or family member
without giving them write access - or the app password at all. This is
**deliberately independent of `AUTH_ENABLED`**: the primary use case is
exposing one view externally (e.g. via a reverse proxy) while `AUTH_ENABLED`
stays off for the trusted private network, matching "Authentication" above's
default trust model. `ShareLink` (`prisma/schema.prisma`) stores the token in
**plaintext** - same trust model as `UserSettings.totpSecret`/
`Institution.woobPassword` (the DB isn't hardened against server compromise,
so hashing this one field buys little), and unlike TOTP backup codes it needs
to be re-copyable later, not shown once. Unguessability comes from entropy
instead: `lib/domain/share-links.ts`'s `generateShareToken()` is 256 random
bits (`randomBytes(32).toString("base64url")`) - no rate limiting needed,
unlike the login password (low-entropy, human-memorable, why that path has
one).

`proxy.ts`'s middleware `matcher` excludes `shared` from ever reaching
`withAuth`, the same category as `api/auth`/`api/health` - the token lookup
inside `app/shared/[token]/page.tsx` is the page's own, independent gate
(`notFound()` uniformly for "doesn't exist" and "expired", no signal to an
anonymous visitor about which). That page sets `robots: { index: false,
follow: false }` since the URL may be reachable from the public internet.

The dashboard's JSX was extracted into `components/dashboard/dashboard-view.tsx`
(a pure presentational component, `interactive` prop) so `app/page.tsx` and
`app/shared/[token]/page.tsx` can't drift out of sync while rendering the same
data two different ways - the only interactive element either page has is the
per-account `Link` into `/accounts/[id]`, which the shared route must never
expose. Beyond that, isolating a share-link visitor from the real app is
handled inside the two client components that already call `usePathname()`
for their own reasons, rather than a route-group restructure: `sidebar.tsx`
returns `null` on `/shared/*` (no nav back into the editable app), and
`auto-sync.tsx` skips calling `autoTriggerSync()` there (an anonymous visitor
must never trigger a real bank sync just by opening the page - the one actual
correctness bug a naive version of this feature would have shipped with).

### Security headers

Set via `next.config.ts`'s `headers()` - CSP, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, and `poweredByHeader: false`. The CSP's `img-src` allows `google.com` **and** `*.gstatic.com` - `lib/domain/institutions.ts`'s favicon URLs are requested from `google.com/s2/favicons` but that endpoint actually serves the image via a redirect to `*.gstatic.com`, which only showed up testing with a real browser (Playwright), not by reading the URL. `script-src`/`style-src` need `'unsafe-inline'` for Next's own RSC hydration payload and CSS-in-JS - a nonce-based CSP would remove that but needs a per-request nonce threaded from `proxy.ts` through the root layout, not done here.

**No `Strict-Transport-Security` header, deliberately.** This app is routinely reached over plain HTTP on a private LAN/VPN (see "Authentication" above - `AUTH_ENABLED` defaults to off because network-level trust is the expected setup). HSTS is browser-cached and self-reinforcing: a browser that ever received it over plain HTTP would refuse all future plain-HTTP connections to that host until manually cleared. Reverse proxies that terminate real TLS (Nginx Proxy Manager, Caddy, Traefik) should set HSTS themselves at that layer, where "this connection is actually HTTPS" is actually true.

### i18n

Implemented via `next-intl`. Locale detection order: `NEXT_LOCALE` cookie → `Accept-Language` header → `DEFAULT_LOCALE` env var (defaults to `"fr"`). Supported locales: `fr` (default) and `en`. No URL prefix per locale.

UI strings live in `messages/fr.json` and `messages/en.json`. When adding new strings, update both files. Institution logos are fetched from Google Favicons using domain mappings in `lib/domain/institutions.ts`.

### Demo mode

Set `DEMO_MODE=true` to enable a read-only public demo. `proxy.ts` intercepts all non-GET requests and returns 403. The `<AutoSync />` component on the dashboard is also disabled. Use `docker-compose.demo.yml` for a pre-seeded demo environment.

### GoCardless (Open Banking PSD2)

Optional. EU + UK bank connections via the official PSD2 API (free tier: 50 connections, 90-day history).

Credentials: `GOCARDLESS_SECRET_ID` + `GOCARDLESS_SECRET_KEY`. Set `APP_URL` to the app's public URL when behind a reverse proxy - it's used as the OAuth callback after bank authentication. Leave `APP_URL` blank for localhost use.

GoCardless logic lives in the Next.js app (not the `sync/` service).

**Transactions, not just balances.** `syncGocardlessBalances` (writes a `HistoricalBalance` row) originally had no counterpart at all for individual transactions - GoCardless-linked accounts got a moving balance with no explanation, the same gap Trade Republic's cash account had before its own timeline sync was added (see "Sync service - optional modules" below). Fixed by `syncGocardlessTransactions` (`lib/actions/gocardless.ts`), which fetches `GET /accounts/{id}/transactions/` (`getTransactions` in `lib/services/gocardless.ts`) and writes `Transaction` rows via `createMany({ skipDuplicates: true })` keyed on `syncId: gocardless_${transactionId}` - transactions are immutable once synced here, so there's never a reason to update an already-known row, only insert new ones. Both syncs are combined behind the same "Sync" button (`syncGocardlessAccount`, called from `SyncOpenBankingButton`) rather than adding a second button, since the transactions and balances endpoints have independent rate-limit quotas (GoCardless: up to 4-10 requests/day per account per endpoint) - calling both on every click doesn't cost either one anything.

- Only `booked` transactions are processed, never `pending` - the Berlin Group/PSD2 schema's `pending` array routinely lacks a stable `transactionId`, which the `syncId`-based dedup above needs; a transaction becomes syncable once the bank moves it to `booked` on a later sync, same as it would show up late in the bank's own app.
- The label is built from `remittanceInformationUnstructured`, falling back to `creditorName`/`debtorName` when that's blank - mirrors Trade Republic's own title/subtitle fallback chain in spirit, just against PSD2's field names instead.
- `merchantCategoryCode` (when the account's bank actually populates it - it's optional per the spec) is captured into `Transaction.merchantCategoryCode` and feeds the MCC-based categorization signal - see "Automatic categorization" below.
- `autoCategorizeTransactions` runs immediately after a transaction sync completes, same reasoning as every other trigger point for it - a freshly-synced transaction with a populated MCC gets a chance to land in a category in the same sync, not a cycle behind.

### App ↔ Sync service communication

The Next.js app calls the Python sync service via HTTP using `SYNC_SERVICE_URL=http://sync:8000` (set automatically in `docker-compose.yml`). In development, the sync service is not started - only the DB runs via `docker-compose.dev.yml`. The reverse direction (sync calling app) also exists now - see "Alerts & webhooks" below.

### Alerts & webhooks

Settings → "Alertes" (`components/settings/alert-channels-section.tsx` + `alert-triggers-section.tsx` + `lib/actions/alerts.ts` - see "Settings UI split" below for why it's two files) configures notifications for three triggers, all evaluated in one place: `POST /api/alerts/check` (`app/api/alerts/check/route.ts`). Two channels, both asked about explicitly and scoped this way on purpose - **not Telegram** (the user didn't want it) and **not SMS** (no free/open-source sending path exists - every real carrier-SMS option is a paid aggregator; a GSM modem + SIM card is the only free route and doesn't fit a `docker compose up` app):

- **ntfy** - `ntfyTopicUrl`, a single POST per alert (`lib/services/notifications.ts`'s `sendNtfyMessage`), using ntfy's **JSON publish API** (POST to the server root with `topic`/`title`/`message` as body fields) rather than the simple API (POST straight to the topic URL, title as a `Title` header). The header approach doesn't work here: HTTP header values must be Latin-1 and alert titles are French/user-entered (accents), so a raw fetch() throws a ByteString conversion error - confirmed while first building this, titles used to get folded into the body instead with ntfy showing its own fallback title. JSON string fields are UTF-8-safe with no such limitation, so this is the actual fix, not a workaround. `icon`/`click` (the Finalibaba icon + tap-to-open link) are only added when `APP_URL` is set - both need a URL ntfy's own servers/client can fetch, so they're skipped for LAN/VPN-only instances the same way GoCardless's OAuth callback already treats a blank `APP_URL`. `icon` points at `/icon` (Next's own file-route, `app/icon.tsx` - a generated PNG) rather than `public/icon.svg`, since ntfy only accepts JPEG/PNG icons.
- **Email** - `alertEmailTo` + `smtpHost`/`smtpPort`/`smtpUser`/`smtpPassword`/`smtpFrom`, sent via `nodemailer` (`sendEmail`). `smtpPassword` is the one field with different blank-handling than every other field in this form: blank means "leave unchanged", not "clear it" - it's never pre-filled with the real stored value (a plaintext password shouldn't round-trip back into the browser on every page load), so a blank submit almost always means "didn't touch this field". Verified against a throwaway local `smtp4dev` container during development, not just unit-tested - a real send/receive round-trip without needing a live mail account.

**ntfy topics are generated, never user-invented.** First version of this feature asked users to pick their own topic name - a real mistake, not a hypothetical one: ntfy.sh's free tier has no access control, an easily-guessed name is the only thing standing between a public server and someone else reading real net worth figures, and asking a human to invent an unguessable string is exactly what password-strength meters exist to prevent. Fixed the same way `ShareLink.token` already solved the identical problem (`lib/domain/share-links.ts`'s `generateShareToken()`): unguessability from entropy, not from a human-chosen secret. `alert-channels-section.tsx`'s "Générer" button builds `https://ntfy.sh/finalibaba-<192 random bits>` **client-side** via the Web Crypto API (`crypto.getRandomValues()`) - no server round-trip, it's a pure "fill the field" convenience persisted only when the user hits the form's own Save button, same as every other field here. The field stays freely editable for self-hosted-ntfy-server users (genuine privacy independent of trusting ntfy.sh at all - see below), backed by `ntfyAuthToken` (`UserSettings`, blank/unused with the public server) sent as `Authorization: Bearer <token>` in `sendNtfyMessage()` - fine as a header unlike the human-entered alert text, a token is always ASCII.

### Self-hosted alerts infrastructure (optional `ntfy`/`mail` Compose services)

Both entirely optional, Compose-profile-gated (`profiles: ["ntfy"]`/`["mail"]` in `docker-compose.yml`) so a plain `docker compose up -d` is unaffected - confirmed empirically that a required (`:?`) variable on a profile-gated service breaks `docker compose config` even when that profile is never requested (Compose evaluates required-variable interpolation for every service in the file before profile filtering runs), which is why `MAIL_DOMAIN` uses a `:-` empty default instead and docker-mailserver's own startup fails loudly if it's blank when the `mail` profile is actually used.

- **`ntfy`** (`binwiederhier/ntfy`) - `NTFY_AUTH_DEFAULT_ACCESS=deny-all` so nobody reads or writes without a token created via `ntfy user add`/`ntfy token add` (README has the exact commands). Verified live: unauthenticated publish → 403, correct Bearer token → message delivered and readable, wrong token → rejected.
- **`mail`** (`ghcr.io/docker-mailserver/docker-mailserver`) - chosen over hand-rolling Postfix+OpenDKIM (a `mail/Dockerfile` matching `sync/`'s own-Dockerfile pattern was considered) because correctly wiring the milter socket and DKIM key lifecycle by hand is genuine, easy-to-get-subtly-wrong sysadmin work, and this image is exactly built for it. `SMTP_ONLY=1` disables IMAP/POP/mailboxes (this project only ever sends, never receives), `ENABLE_OPENDKIM=1` signs outgoing mail.
  - **`SMTP_ONLY=1` disables SASL entirely**, not just IMAP - confirmed empirically (`postconf -n | grep sasl` showed `smtpd_sasl_auth_enable=no` on the submission port regardless of any user created via `setup email add`, because `SMTP_ONLY` also disables Dovecot, which is where Postfix's SASL backend normally comes from). Authenticated submission on port 587 genuinely does not work in this mode - not a config oversight, a deliberate trade-off of this mode. Fixed by relaying on trust instead: `PERMIT_DOCKER=connected-networks` adds the container's own Docker network to Postfix's `mynetworks`, and Finalibaba's SMTP fields point at port 25 with no user/password - same "same Docker network = trusted, no credentials" model already used for `app`↔`sync`, not a new pattern.
  - **OpenDKIM has its own `TrustedHosts`**, separate from Postfix's `mynetworks` - a `PERMIT_DOCKER`-trusted relay still won't get signed ("not internal"/"not authenticated" → "no signature data" in the log) unless the sending host is also in this file. Confirmed it does **not** need the same manual treatment - docker-mailserver auto-detects and adds the container's own Docker network to `TrustedHosts` on its own at startup.
  - **`docker restart`/`docker compose restart` does not reliably reload DKIM config** after running `setup email add`/`setup config dkim` on an already-running container - confirmed empirically (`/etc/opendkim/{SigningTable,KeyTable}` stayed stale/empty, or picked up the new signing table but with root-owned key files the `opendkim` user can't read, `can't load key ... Permission denied`). A full recreate (`docker compose up -d --force-recreate mail`, matching a `down`+`up`) reliably re-runs the complete first-boot setup (correct file ownership included) - README documents recreate, not restart, for this reason.
  - **`MAIL_DOMAIN` must be the root domain, never a subdomain** - `docker-compose.yml` sets `hostname: mail` + `domainname: ${MAIL_DOMAIN}`, so Docker concatenates them into the container's real FQDN/HELO as `mail.<MAIL_DOMAIN>`. Setting `MAIL_DOMAIN=mail.yourdomain.com` yourself (an easy mistake - it reads like the intended sending hostname, and is literally what `.env.example`'s own old comment example implied before this was caught and fixed) produces the broken `mail.mail.yourdomain.com` - confirmed the hard way via mail-tester.com flagging "no A record behind your hostname" and a `RDNS`/SPF `HELO` mismatch, at a real cost (0/10 deliverability score) before the `.env` value was corrected to the bare root domain.
  - No published port at all - Postfix only makes *outbound* connections to recipient mail servers, nothing needs to reach it from the internet (unlike `ntfy`, which the phone does).
  - `mail_config` (mounted at `/tmp/docker-mailserver`) is the volume that must never be lost - it holds the generated OpenDKIM keypair; losing it means a new key that no longer matches the already-published DNS record.

**Email provider presets, not raw SMTP fields.** A "Fournisseur" `<select>` (Gmail / Outlook / self-hosted / Personnalisé) pre-fills `smtpHost`/`smtpPort` on change - `smtp.gmail.com:587`, `smtp.office365.com:587` (STARTTLS, no change needed to `sendEmail()`'s existing `secure: config.port === 465` logic), `mail:25` for this project's own optional `mail` service (see below - port 25, not 587, and deliberately no user/password for that one). Fields stay editable, presets are a convenience fill only. Hint text calls out that Gmail/Outlook both require an app password (not the real account password) for third-party SMTP access, and that `smtpFrom` has to match the authenticated account or they reject/rewrite it - asked the user directly about the email UX (raw SMTP vs. presets vs. a third-party API key vs. dropping email) since there's a real constraint underneath: no self-hosted app can make email actually land in an inbox without an authenticated relay somewhere (no SPF/DKIM/reputation from a residential IP), so "simpler" can only mean "less to type", not "no relay needed".

**Per-trigger opt-out.** Net worth already had one (blank threshold = disabled); loan-nearly-paid-off and sync-failure didn't, until the user asked for it - `UserSettings.loanAlertsEnabled`/`syncFailureAlertsEnabled` (`Boolean @default(true)`, so existing installs keep today's always-on behavior), two checkboxes in the form, checked in `checkLoanAlerts()`/`checkSyncFailures()` before doing anything else. Scoped to on/off per trigger, not full per-trigger-per-channel routing (e.g. "loan alerts to ntfy only, net worth to email only") - a real possible future refinement, but broader than what was asked.

**All config lives in `UserSettings` (DB/Settings UI), not `.env`** - unlike GoCardless/LCL/TR (deploy-time secrets), this follows the more recent precedent in this codebase (TOTP, share links, tax rates): no redeploy/restart needed to add or change a topic URL or SMTP relay. `smtpPassword` is plaintext, same trust model as `totpSecret`/`Institution.woobPassword`.

**Threshold-crossing logic stays in TypeScript**, reusing `computeDashboard()` and `calcCurrentCapital()`/`hasLoanParams()` rather than re-implementing net worth or loan math in Python - the sync service already has full DB access and could theoretically compute its own approximation, but that would risk an alert firing at a different number than what the dashboard shows, and duplicate the single source of truth described under "Net worth calculation" below.

**One new route, called once per existing 4h sync cron - not a new schedule.** `sync/main.py`'s `_run_all()` already runs every 4h via APScheduler and already runs every sync source sequentially before returning; `_check_alerts()` is one more step at the end of it, calling the route via `requests` (already a direct import in `sync_tr.py`, not a new Python dependency). The three checks, each its own function in the route file for readability (and because a single combined function tripped the `sonarjs/cognitive-complexity` lint gate):

- **Net worth threshold** (`checkNetWorthAlert`) - `netWorthAlertThresholdCents` (blank = disabled). Dedup via `netWorthAlertLastAbove: Boolean?` (null = never evaluated) - `lib/domain/alerts.ts`'s `evaluateNetWorthAlert()` never fires on the first-ever check for a freshly-set threshold, it only establishes the baseline; only a real flip after that fires. `updateAlertSettings` resets this to `null` whenever the threshold value itself changes, so moving it doesn't misread the new number against a stale baseline.
- **Loan nearly paid off** (`checkLoanAlerts`) - fixed at 5% of the original `loanAmountCents` remaining (`isLoanNearlyPaidOff`, a named constant, not user-configurable - keeps the UI lean). Dedup via `Account.loanPaidOffAlertSent` (one-way flag, a loan only crosses this once). Short-circuits to `[]` when `UserSettings.loanAlertsEnabled` is false.
- **Sync failures** (`checkSyncFailures`) - edge-triggered via `SyncFailureState` (one row per currently-broken source): alerts once when a source's latest `SyncLog` row transitions from success/unknown into `error`/`auth_required`, then at most one reminder per 24h while it stays broken, clearing the moment it succeeds again. Deliberately scoped to the *automatic* 4h cron only, not on-demand "Sync now" clicks in Settings - a manual sync's failure is already visible right there in the UI to whoever just clicked it; a push notification adds value specifically for the unattended background job. Short-circuits to `[]` when `UserSettings.syncFailureAlertsEnabled` is false. `formatSyncFailureBody` deliberately does **not** surface `SyncLog.message` (raw Python exception text like "Session web absente - lance --setup", aimed at someone running the sync container's CLI) - a user flagged the raw text as unreadable in a push notification, so the body is now one of two fixed, translated sentences keyed on `status` (`auth_required` vs a plain error) instead; the technical detail is still visible in Settings' sync status / `SyncLog` directly for anyone troubleshooting. `friendlySourceLabel` resolves `SyncLog.source` (a machine key - `"trade_republic"`/`"lcl"`/`"woob:<institutionId>"`, the last a raw cuid) to a human-readable name only at notification time, looking up the `Institution` for the `woob:` case - `source` itself stays unchanged since it's also `SyncFailureState`'s dedup key.

**Auth for the sync→app call**: unlike `app→sync` (port 8000, never published, Docker-network-only per `SECURITY.md`), `app`'s port is published to the host and potentially reverse-proxied to the internet, so `/api/alerts/check` can't assume "reachable = internal" the way sync's endpoints do. It's excluded from `proxy.ts`'s NextAuth matcher (same category as `api/auth` - no browser session exists on this call path) and gates itself instead: `NEXTAUTH_SECRET`, passed into the `sync`/`sync-demo` containers' environment in `docker-compose.yml`/`docker-compose.demo.yml`, doubles as the shared bearer token (`Authorization: Bearer <secret>`). Reusing it avoids a new required env var - it's already mandatory, and its leak is already maximally severe (session forgery), so reusing it here doesn't meaningfully raise the blast radius. `APP_SERVICE_URL` (`http://app:3000` / `http://app-demo:3000`) is the fixed-hostname counterpart to `SYNC_SERVICE_URL` above, same pattern.

**Custom alert rules** (`AlertRule` model, Settings → "Règles d'alerte personnalisées") - a parallel, user-defined mechanism alongside the 3 fixed triggers above, which stay untouched. One polymorphic table, `kind: ACCOUNT_BALANCE | BUDGET_OVERRUN | ACCOUNT_OVERDRAFT | INVESTMENT_VALUE | HOLDING_PRICE | UNREALIZED_GAIN`, mirroring the same type-conditional-nullable-fields convention `Account` already uses for its LOAN/INVESTMENT-only fields, rather than one table per kind - every kind shares the same on/off toggle, optional custom message, and Settings UI list shape. `checkCustomAlertRules` (`app/api/alerts/check/route.ts`) is a fourth check called from the same `POST` handler, after the other 3, dispatching each rule to its own per-kind checker via `dispatchAlertRuleCheck`.

Four of the six kinds - `ACCOUNT_BALANCE`, `ACCOUNT_OVERDRAFT`, `INVESTMENT_VALUE`, and `HOLDING_PRICE` (plus `UNREALIZED_GAIN` when `gainUnit = AMOUNT`) - are mathematically the exact same "current cents value crosses `balanceThresholdCents`" edge-triggered comparison (`evaluateAccountBalanceAlert`), just with a different source for "current" and a different eligible-account/holding scope in the UI. Rather than one pair of threshold/dedup columns per kind, they all share `AlertRule.accountId`/`balanceThresholdCents`/`balanceLastAbove` - see the schema comment for why (and why those columns kept their original "balance"-flavored names instead of being renamed when this was added, to avoid a risky column-rename migration against already-deployed installs' real rule data).

- `ACCOUNT_BALANCE` rules are scoped to fiat accounts (CHECKING/SAVINGS/MEAL_VOUCHER, the ones with a meaningful `HistoricalBalance`-derived current balance) - a separate evaluator from, not a shared call with, `evaluateNetWorthAlert`, even though the edge-triggered logic is identical, so the built-in net-worth trigger's own code path stays untouched by this feature. Dedup state (`AlertRule.balanceLastAbove`) is per-rule, same null-means-never-evaluated convention as `UserSettings.netWorthAlertLastAbove`; changing the threshold on an existing rule resets it to `null`, same as `updateAlertTriggers` already does for net worth.
- `ACCOUNT_OVERDRAFT` rules are the same fiat-account scope and checker as `ACCOUNT_BALANCE` (`checkAccountBalanceRule` handles both, branching only on `rule.kind` for the dispatched message text) - the only difference is `balanceThresholdCents` is fixed at `0` and set once at creation (`createAlertRule`), never a user-entered field, so "alert me if this account goes negative" doesn't require the user to type a number that's always going to be zero anyway.
- `INVESTMENT_VALUE` rules are scoped to INVESTMENT/CRYPTO accounts and use their holdings' market value (`holdingMarketValueCents`, summed across the account) instead of a `HistoricalBalance` row, since investment/crypto accounts don't have one.
- `HOLDING_PRICE` rules reference a specific `Holding` (`AlertRule.holdingId`, `onDelete: Cascade`) rather than an account, comparing its `lastPriceCents` directly - already EUR-converted at entry time for foreign-currency holdings (see "Multi-currency" below), so no extra FX handling is needed at check time. The Settings UI's holding picker is a flattened list built from `investmentAccounts` (fetched once in `app/settings/page.tsx`, passed down alongside the account list `AccountBalanceFields`/`AccountThresholdFields` already needed).
- `UNREALIZED_GAIN` rules are the one kind where `accountId` being `null` is valid input, not a malformed-row guard failure - it means "aggregate across every investment/crypto account" rather than one specific account (`checkUnrealizedGainRule` runs a second, broader `prisma.holding.findMany` query only in that case, since `findActiveAlertRules`'s own include only preloads the rule's *own* account's holdings). `gainUnit: PERCENT | AMOUNT` picks whether the rule's threshold is `gainThresholdPct` (a plain float percentage, evaluated by `evaluatePercentAlert` - kept as its own function rather than coercing percent into cents, so a stored threshold's unit is never ambiguous) or the shared `balanceThresholdCents` in euros - a rule stores exactly one, the other stays `null`, and which one is editable later is fixed at creation same as everywhere else in this dialog. `computeUnrealizedGain` (`lib/domain/alerts.ts`) sums market value minus cost basis across the relevant holdings, skipping any with unknown `costBasisCents` (same convention `accounts-page.ts`'s own per-account gain sum already uses) - `gainPct` is `null` when every considered holding had a zero or unknown cost basis, since a percentage isn't meaningful without a real denominator, and the rule simply doesn't evaluate that check until it is.
- `BUDGET_OVERRUN` rules key off `Category.budgetCents` directly (no separate threshold field) and re-arm every calendar month instead of being edge-triggered - a category that overran its budget in July should be able to alert again in August even though spend never "un-overran" in between, it just resets at the month boundary. `AlertRule.budgetOverrunLastFiredPeriod` stores the last `"YYYY-MM"` (UTC) period the rule fired for; `evaluateBudgetOverrunAlert` fires once per period the moment current-month spend (computed the same way `/budgets` does, `Transaction` rows with `amountCents < 0` in `[startOfMonth, startOfNextMonth)`) exceeds the budget.
- No per-rule channel routing - every kind calls the same `dispatchAlert` every built-in trigger uses, same reasoning as the loan/sync-failure toggles' own "broader than what was asked" note above.
- `accountId`/`holdingId`/`categoryId` are all `onDelete: Cascade` (not `Transaction`'s `SetNull`-on-`Category` convention) - a rule whose account/holding/category was deleted has no purpose left, and a nulled-out rule would sit dead in the Settings list instead of just disappearing with it.

**Settings UI split** (`components/settings/alert-channels-section.tsx` + `alert-triggers-section.tsx`, replacing a single earlier `alerts-section.tsx`) - the original one-form design mixed "how you're notified" (ntfy/email config) with "what triggers a notification" (net worth threshold, loan/sync-failure toggles) in one long scrolling form, which read as cluttered once custom alert rules were added below it. Split into two cards, each with its own Server Action (`updateAlertChannels`/`updateAlertTriggers` in `lib/actions/alerts.ts`, replacing the old combined `updateAlertSettings`) and its own Save button, so updating a channel doesn't require re-submitting trigger config and vice versa. `AlertChannelsSection` stays `"use client"` (the email-preset dropdown and ntfy generate/copy buttons need interactivity); `AlertTriggersSection` is a plain server component - nothing in it needs local state, just native form elements posting straight to a Server Action.

### Sync service - optional modules

The `sync/` service has two dedicated sync modules plus a generic Woob runner:

| Module | Required credentials | Purpose |
|---|---|---|
| `sync_lcl.py` | `LCL_LOGIN`, `LCL_PASSWORD` | LCL (FR) via Woob hardcoded module |
| `sync_tr.py` | `TR_PHONE`, `TR_PIN` | Trade Republic via pytr |
| `sync_woob.py` | Set per-institution in UI | Generic Woob runner for any institution configured in Settings |

Leave credentials blank to disable a module. `sync/main.py` skips gracefully, and `app/settings/page.tsx`'s "Synchronisation automatique" section (the dedicated LCL/TR `SyncStatus` cards, distinct from any Woob-configured institution that happens to also be named "LCL") mirrors that gate: each card - and the section itself, when neither applies - only renders when `LCL_LOGIN`/`TR_PHONE` is actually set. A fresh install with zero `.env` bank credentials used to show both cards permanently stuck on "Jamais synchronisé" regardless, which read as broken and, once a user separately added a Woob-configured "LCL" institution of their own, produced two differently-behaving "LCL" surfaces on the same page. `sync/db.py` contains shared PostgreSQL helpers - do not duplicate inline.

**Interactive 2FA setup for any Woob-configured bank** (`sync/setup_woob.py`) - a bank added via Settings → "Configurer Woob" that requires strong authentication on first connect used to be a dead end: `sync_woob.py` only recognized the "wait and approve" family of Woob exceptions and, on catching one, told the user to run `sync_woob.py --setup <id>` - a flag that was never actually implemented. A bank whose 2FA is instead an SMS/email/app-generated **code** (`SentOTPQuestion`/`OfflineOTPQuestion`) wasn't even recognized as needing setup at all - it just fell into the generic error handler. Fixed by generalizing the same interactive start/complete pattern `setup_lcl.py`/`setup_tr.py` already use for their one hardcoded bank each, to work for any `institution_id`:

- `start_setup(institution_id)` reads credentials from the `Institution` row (not env vars - this is the generic UI-configured path, see `sync_woob.py` above) and attempts `iter_accounts`, bucketing whatever Woob raises into three UI-facing shapes - confirmed against `woob==3.7`'s actual exception taxonomy (`woob/exceptions.py`) rather than guessed:
  - `pending_approval` - `AppValidation`/`DecoupledValidation` and friends (e.g. LCL's Certicode Plus): nothing to submit, just wait and retry.
  - `code_required` - `SentOTPQuestion`/`OfflineOTPQuestion`: the exception carries `.fields` (`Value` objects whose `.id` is a **backend config key**, not an arbitrary label) and `.medium_type`/`.medium_label` (e.g. "sent by SMS to 06 12..."). The only documented way to resume is `backend.config[field.id].set(code)` then retry - confirmed against Woob's own reference CLI (`woob/tools/application/console.py`'s `bcall_error_handler`), not invented.
  - `unsupported` - `ActionNeeded` (+ `BrowserPasswordExpired`/`AuthMethodNotImplemented`), `CaptchaQuestion`, `BrowserRedirect`: genuinely can't be driven from a web form (captcha widgets, full OAuth-style browser redirects) - surfaces Woob's own message, no retry loop offered.
- `complete_setup(institution_id, code=None)` resumes the same in-memory Woob session (`_pending`, keyed by institution id - unlike `setup_lcl.py`'s single global, several institutions could plausibly be mid-setup at once here).
- `components/settings/woob-setup-prompt.tsx` is the generic UI counterpart to `SyncStatus`'s hardcoded LCL/TR flows (that component is intentionally untouched - it's still the right place for those two specific, already-working integrations) - same two-panel shape (code input / approval-wait), rendered in the institution row only when that institution's latest `SyncLog` is `auth_required`.
- `setup_lcl.py`/`setup_tr.py`/`sync_lcl.py` are deliberately **not** touched or merged into this - they're the dedicated `.env`-configured paths (`LCL_LOGIN`/`TR_PHONE`, see "Sync service - optional modules" above) and keep working exactly as before, entirely independent of any `Institution` DB row. This is purely additive for every other institution.

  `app/settings/page.tsx`'s institution-row Woob controls (sync status icon, `InstitutionSyncButton`, `WoobSetupPrompt`, `ConfigureWoobDialog`) used to be gated behind a `DEDICATED_SYNC_INSTITUTIONS` name-based guard (`new Set(["lcl", "trade republic"])`, skipping any institution whose `name.toLowerCase()` matched) - removed after a real production bug: `Institution.name` is globally unique, and both the seeded reference row (`prisma/seed.ts`) and `AddInstitutionDialog`'s own catalog picker auto-fill this exact name when a user picks "LCL" or "Trade Republic" from the Woob module list - so a user who genuinely configured real Woob credentials on an institution literally named "LCL" had every one of these controls silently disappear, including `ConfigureWoobDialog` itself (no way to even edit or clear the config afterward via UI). The guard's only real justification - not showing Woob management UI on the env-dedicated integrations - was already handled more precisely by `inst.woobModule` being falsy on the seeded reference row; the name check added nothing but this collision.

  **Removing that guard exposed a second, costlier problem** - confirmed the hard way in production, not just reasoned through. `sync_lcl.py`/`sync_tr.py` and `sync_woob.py` write different `syncId` formats for what can be the exact same real bank account (`lcl:<id>` vs `woob:<institutionId>:<id>` - see `upsert_account`'s `WHERE "syncId" = %s` dedup lookup in `sync/db.py`), so configuring Woob credentials on an institution that also has a live `.env`-dedicated sync doesn't update the existing accounts - it silently creates a full second set (same balances, same labels, double-counted in net worth) the next time either sync runs. `dedicatedEnvNames()` in `app/settings/page.tsx` (checks `LCL_LOGIN`/`TR_PHONE` presence, mirroring the dedicated-section gate above) is passed into both `ConfigureWoobDialog` and `AddInstitutionDialog` as `hasDedicatedEnvSync`/`dedicatedEnvNames`, rendering a warning banner (not a hard block - a deliberate, supervised migration off the `.env` path is legitimate, same reasoning as the "Migrating an existing dedicated integration to Woob" note below) whenever the institution being configured matches an active dedicated source. No automatic dedup was attempted (e.g. matching by IBAN across the two `syncId` formats) - out of scope for a warning-first fix, and the two scripts' account-discovery order isn't guaranteed to expose a stable shared identifier without deeper changes to both.

  **Migrating an existing dedicated integration to Woob, if you ever do it anyway**: keep both `.env` credentials and the Woob config live only long enough to confirm the new sync works, then either clear the Woob config (`ConfigureWoobDialog` → "Supprimer la config") to stay on `.env`, or click "Migrer maintenant" in the same dialog's warning banner (`migrateDedicatedSyncToWoob` in `lib/actions/institutions.ts`) to complete the cutover - it deletes the `lcl:`/`tr:`-prefixed `Account` rows (cascades to their `Transaction`/`HistoricalBalance`/`Holding` automatically, every FK pointing at `Account` is `onDelete: Cascade`) once at least one `woob:<institutionId>:`-prefixed account already exists as proof the new sync actually produced something - refuses to run otherwise, so it can never delete the only copy of an account's history. The confirmation step shows both counts (dedicated-sync accounts vs. already-migrated Woob accounts) side by side specifically so a mismatch - Woob discovering fewer accounts than the dedicated integration ever did - is visible before confirming, not after. **This only touches the database** - it cannot edit `.env` from inside a Server Action, so the user still has to remove `LCL_LOGIN`/`LCL_PASSWORD` (or `TR_PHONE`/`TR_PIN`) themselves and restart the containers; the dialog's post-migration message repeats this. Never leave both running - every scheduled sync (every 4h) re-creates the duplicate set if the losing side's `.env` config is still there to re-trigger it.

**The "Configurer Woob" module picker lists real banks, not a hardcoded 17-entry guess.** `GET /woob/modules` (`sync/main.py`) calls `Woob().repositories.get_all_modules_info()` and filters to modules with `CapBank` in their capabilities - ~96 real banks/brokers, fetched from Woob's own repository index. Doesn't force a network refresh itself: `sync/entrypoint.sh` already runs `woob config update` on every container start, so the local index this reads is kept fresh without adding a round-trip to every dialog open. `getWoobBankModules()` (`lib/actions/sync.ts`) fetches this with a 1h Next.js cache (`next: { revalidate: 3600 }`, same convention as the Yahoo Finance fetches in `lib/services/exchange-rate.ts`) and falls back to a small fixed list of major French banks if the sync service can't be reached (e.g. local dev, where only the DB container runs - see "Development commands" above) - so the dialog still works somewhere, just without the full catalog. "Autre" (custom module name) stays as the escape hatch for anything not tagged `CapBank`, or genuinely absent from Woob's catalog entirely (confirmed for Revolut specifically - searched the full ~1400-module index, no match, not a gap in this list). Same check run again later for the ROADMAP's "more broker integrations" wishlist: Degiro, Boursorama, Binance, and Kraken all carry `CapBank` and are already reachable through this same picker today, no new code needed - only Interactive Brokers came back with no module match, confirmed the same way as Revolut (see `ROADMAP.md`'s v1.12 section). This replaced `sync_woob.py`'s own `--list` CLI flag, which shelled out to `woob config -l` - never valid syntax (the real subcommand is `woob config modules`) - removed rather than fixed, since nothing needs a CLI listing path once the dialog fetches this itself.

`getWoobBankModules()`'s result is passed as a `modules` prop into **both** bank pickers that need it - `ConfigureWoobDialog` (editing an existing institution's Woob config) and `AddInstitutionDialog` (Settings → "Ajouter une institution", the very first bank picker a new self-hosted user sees). Real regression caught in production testing: `AddInstitutionDialog` originally carried its own copy-pasted `WOOB_MODULES` constant (the same old hardcoded 17-bank list) that never got wired to the live catalog when `ConfigureWoobDialog` was switched over - so a brand-new install with zero institutions configured yet only ever saw the short list, in the one dialog that matters most for a first-time setup. Fixed by deleting that dialog's own copy and passing the same `woobModules` prop `app/settings/page.tsx` already fetches once per render - if a third bank-picker call site is ever added, wire it to the same prop rather than reintroducing a local copy.

**Trade Republic transaction history**: `sync_tr.py` originally only synced positions and an aggregate cash balance (via `record_balance`) - unlike LCL/Woob, it never wrote individual `Transaction` rows, so the TR cash account had no labels for budget categorization or recurring-transaction detection, only a balance that moved with no explanation. Fixed by fetching TR's own activity-feed API (`timelineTransactions` + `timelineActivityLog`, both cursor-paginated, newest-first - pytr's own `Timeline` class fetches and merges both the same way, since between them they cover everything money-related: card payments, transfers, trades, dividends, interest) and upserting each into `Transaction` via the same `upsert_transaction()` helper LCL/Woob already use, so budgets/recurring-detection work identically for TR's cash account. Deliberately **not filtered to "spending" only** - trades/dividends/interest are imported too, exactly mirroring the real account activity (same reasoning a bank CSV import would show a transfer to a broker as a line item) - the user categorizes what's relevant via the existing budgets UI. `_timeline_item_to_transaction()` builds the label from `title`/`subtitle` (e.g. "Amazon - Kartenzahlung"), skips cancelled items and items with no monetary amount (informational-only timeline entries), and `_fetch_timeline_feed()` stops paginating a feed as soon as an entire page is already-known (`syncId` already in DB) - since the feed is strictly newest-first, everything further back is guaranteed already synced, which is what keeps every sync after the first fast. The very first sync has no known ids, so it paginates the full available history (deliberate - a "recent window only" default would have missed a lot of a long-time user's spending history for a feature specifically meant to make budget tracking finally work for TR).

### Backup & restore

Two paths, both wrap `pg_dump`/`psql` (full DB dump - schema + data, never a hand-rolled Prisma export, to avoid drift and BigInt/Decimal serialization issues):

- **CLI**: `scripts/backup.sh` / `scripts/restore.sh` - call `docker compose exec db pg_dump|psql`. `restore.sh` pauses `app`/`sync` if present and requires typed confirmation.
- **UI**: Settings → Backup & restore (`components/settings/backup-restore-section.tsx`), backed by `app/api/backup/route.ts` (`GET` streams a gzip dump, `POST` restores from an uploaded file, auto-detecting gzip vs plain `.sql`). This runs `pg_dump`/`psql` from inside the `app` container itself - that's why the `runner` stage in `Dockerfile` installs `postgresql16-client` (must track the `postgres:16-alpine` server version; a client older than the server can't dump it). Hidden entirely in `DEMO_MODE` (matches the auto-sync section's pattern).

Both directions use `pg_dump --clean --if-exists` (so restore drops/recreates objects first) and `psql --single-transaction` (restore is all-or-nothing, no partial state on error). Never echo raw `pg_dump`/`psql` stderr to the client - log it server-side and return a generic error message, per the exception-exposure fix in commit `1ae43c0`.

Implementation notes (post-v1.2.0 audit fixes):

- `buildConnectionString()` passes the *whole* `DATABASE_URL` (password stripped, everything else - including query params like `?sslmode=require` - intact) as a single positional arg to `pg_dump`/`psql`, with the password supplied separately via `PGPASSWORD`. Don't go back to manually extracting `host`/`port`/`user`/`database` into separate `-h`/`-p`/`-U`/`-d` flags - that approach silently drops any connection query params.
- The `GET` handler's `ReadableStream` only closes successfully once **both** `gzip`'s `"end"` (all bytes flushed) and `pg_dump`'s `"close"` (exit code known) have fired, and only if the exit code was `0`. A pg_dump that dies mid-dump after already writing valid-looking output must **error**, not silently succeed - a truncated "successful" backup is far worse than a visibly failed download, since the corruption would otherwise only surface during an actual restore. The `settled` flag guards every controller call this can race with (`enqueue`, `close`, `error`) - including `cancel()`, which must also set it (a client aborting mid-download must not let a still-queued `gzip.on("data")` callback call `enqueue()` on an already-cancelled stream and crash the process).
- After a successful restore, the process calls `process.exit(0)` (gated to `NODE_ENV === "production"`, so local `pnpm dev` isn't killed) so the container's `restart: unless-stopped` policy hands the app a fresh Prisma connection pool - the restore just dropped and recreated the whole schema out from under any pooled connections' cached query plans, the same reason `scripts/restore.sh` stops the `app` container before restoring. `components/settings/backup-restore-section.tsx` polls the current page with a `HEAD` request (never `/api/backup` - that would trigger another full `pg_dump`) until the app responds again before reloading.

### CSV import (transactions & balance history)

For fiat accounts (`CHECKING`/`SAVINGS`/`MEAL_VOUCHER`) not covered by auto-sync - gated by `canImportCsv = isFiat && !isSynced && !account.gocardlessAccountId` in `app/accounts/[id]/page.tsx`. Two independent entry points, both rendered wherever that condition holds:

- **Transactions** - `components/account-detail/import-transactions-dialog.tsx` + `lib/actions/transactions.ts`'s `importTransactions(accountId, rows)`. Writes `Transaction` rows.
- **Balance history** - `components/account-detail/import-balance-history-dialog.tsx` + `lib/actions/balances.ts`'s `importBalanceHistory(accountId, rows)`. Writes `HistoricalBalance` rows at noon UTC (`${date}T12:00:00.000Z`, same convention as `prisma/seed-demo.ts` - avoids a midnight-UTC day shift in negative-offset timezones). Because the dashboard's net-worth-over-time chart (`app/page.tsx`) is built by aggregating `HistoricalBalance` across every account grouped by day, backfilling this way also backfills that chart - no separate "net worth snapshot" model exists or is needed.
  - Deliberately **not** offered for `LOAN` (its balance is computed at runtime via `calcCurrentCapital()`, never stored - importing a raw balance would double as a false asset in the dashboard aggregation, which doesn't know to treat it as a liability) or for `INVESTMENT`/`CRYPTO`/`REAL_ESTATE`/`AUTOMOBILE` (their current-value source of truth is holdings+live price or `manualValueCents`, not the latest `HistoricalBalance` row - importing snapshots there would create a chart whose last point silently disagrees with the value shown in the account header). Fiat accounts are the one type where `HistoricalBalance` is already the authoritative source for both current value and chart history, so there's no such discontinuity risk.

Shared design across both importers:

- CSV parsing, date parsing, header aliasing, and validation live in `lib/domain/csv-import.ts` (`parseCsvDate`, `isFutureDate`, `looksNumeric`, `makeHeaderNormalizer`) - shared by both dialog components so a fix in one place reaches both importers. Parsing and duplicate detection happen **entirely client-side** - no server round-trip until the user confirms. Header aliases (French: `libellé`/`montant`/`solde`/`valeur`) and both `YYYY-MM-DD`/`DD/MM/YYYY` date formats are accepted.
- `looksNumeric()` rejects non-numeric-but-non-empty values (`"N/A"`, `"#REF!"`, `"3.5abc"`) before they reach `parseCents()` - `parseCents()` itself falls back to `0` on `NaN` (a deliberate leniency other callers, like the settings tax-rate inputs, rely on), so without this guard a garbage CSV cell would silently import as a real €0.00 row instead of being flagged.
- `isFutureDate()` rejects balance-history rows dated after today (UTC) - without it, a typo'd date (e.g. `2062` instead of `2026`) would become the account's displayed "current balance" everywhere (`app/page.tsx`, `app/accounts/[id]/page.tsx` both take `history[0]` ordered by `recordedAt desc`), with no delete UI to undo it. Transactions don't get this check - nothing reads "the most recent transaction" as a current-value source, so a future-dated transaction isn't a correctness bug the way a future-dated balance is.
- Both `importTransactions` and `importBalanceHistory` call `lib/actions/csv-import-guard.ts`'s `assertCsvImportEligible(accountId)` before writing anything - it re-derives the same eligibility rule as the page's `canImportCsv` (fiat type, not synced, no `gocardlessAccountId`). **Do not remove this** even though the UI already hides the import buttons for ineligible accounts: Server Actions are directly invocable regardless of what's rendered, and this is the only thing stopping a stale page or a future call site from writing CSV data onto a `LOAN`/`INVESTMENT`/synced account.
- "Duplicate" is advisory, not a hard constraint - flagged rows are unchecked by default but the user can still import them. Transactions: flagged when `date|label|amountCents` matches an existing `Transaction` for that account. Balance history: flagged when a `HistoricalBalance` already exists for that exact date. There is no hash-based auto-merge for transactions specifically, because two legitimately different transactions can share a fingerprint (e.g. two identical recurring debits on the same day) - auto-merging on content hash would silently drop one.
- Existing-row fingerprints/dates are computed server-side in the page and passed down as plain `string[]` props - never pass `BigInt` values to a Client Component, following the same "no BigInt across the RSC boundary" rule as `components/shared/export-accounts-button.tsx`.
- Every imported `Transaction`/`HistoricalBalance` row is stored at **noon UTC** (`${date}T12:00:00.000Z`), not midnight - both importers must agree on this (they didn't originally: `importTransactions` used midnight, causing a one-day shift on negative-UTC-offset deployments that `importBalanceHistory` didn't have). Midnight UTC is one keystroke away from reintroducing that bug - don't "simplify" it back to `new Date(r.date)`.
- Every imported `Transaction` gets a fresh `syncId` (`csv_` + `randomUUID()`); neither importer attempts idempotent re-import matching like the Woob/GoCardless sync paths do with their own bank-provided IDs. Re-importing the same file twice creates duplicates - that's what the client-side duplicate flagging is for.

### Recurring transactions

`/recurring` - subscriptions, bills, and regular income, with auto-detection, cash-flow projection, and missed-payment flagging. All the math lives in `lib/domain/recurring.ts` (pure functions, no DB calls, mirrors `lib/domain/loan.ts`'s "params in, computed stats out, `asOf`-dated" shape) so it stays testable in isolation from the page that calls it.

- **Detection** (`detectCandidates`) groups the last 25 months of `Transaction` rows by `(accountId, normalizeLabel(label))` - **per-account, not cross-account**, because `label` is raw bank-feed text specific to one institution's formatting; matching similar-looking labels across two different accounts risks a false merge in a way `Category` (a deliberately account-independent concept) doesn't. A group needs `MIN_OCCURRENCES = 3+`, at least 70% of its amounts within a median±tolerance band (`10%` of the median or a `5€` floor, whichever is larger - a flat 10% would be too tight for small subscriptions and a unanimous match would false-negative on one bonus month or one price change), and a median day-gap (not average - a single skipped/duplicated occurrence skews an average) landing in a frequency band (weekly 6–8d, monthly 27–33d, yearly 350–380d). The 25-month window is deliberate: a yearly pattern needs ~2 years of history before 3 occurrences exist to detect from, so anything shorter silently kills yearly detection. Detection only ever proposes `intervalCount = 1` - inferring "every 2 months" cadences from noisy gaps is out of scope; fix it via the manual edit dialog instead.
- Confirmed/paused/dismissed all live in the same `RecurringTransaction` row via `active`+`autoDetected` - dismissing a suggestion creates a row with `active: false, autoDetected: true` (`dismissSuggestion` in `lib/actions/recurring.ts`) purely so its `(accountId, normalizeLabel(label))` key is excluded from future detection passes; there's no way to distinguish "paused after being active" from "never-confirmed dismissal" in storage, and the UI doesn't try to - both just show a "Paused" badge with a Resume action.
- **Missed-payment check** (`isMissed`) only ever looks at the single most recent expected occurrence, not every occurrence since `anchorDate` - walking full history would flag a subscription cancelled 2 years ago as "missed" every month forever. `DEFAULT_GRACE_DAYS = 5` window, same amount-tolerance formula as detection.
- **Cash-flow projection** (`projectDailyCumulative`) is a *relative* running total starting at 0 over the next 90 days - deliberately not tied to actual account balances or the real net-worth calculation, to avoid conflating this with `UserSettings.salaryNetCents`/`monthlyExpensesCents` (the Analytics page's Runway/Savings-Rate cards have their own manual-entry semantics that this feature must not silently overwrite or duplicate). `components/recurring/cashflow-chart.tsx` renders this with Recharts `Area type="stepAfter"` (not `"monotone"`, copied from `components/shared/net-worth-chart.tsx`'s scaffold otherwise) - the cumulative total is a step function that jumps on occurrence days, and smooth interpolation between 90 daily points would draw a misleading ramp.
- Month-stepping (`addMonthsClamped` in `lib/domain/recurring.ts`) clamps to the last day of shorter months (anchor on the 31st → lands on Feb 28/29) - `lib/domain/loan.ts`'s `endDate.setMonth(...)` pattern does NOT do this (native `Date` overflows instead of clamping, e.g. Jan 31 + 1 month rolls to Mar 3) and must not be copied here.
- Dates use the noon-UTC convention (`${dateStr}T12:00:00.000Z`) throughout, same as CSV import - `anchorDate` must line up day-for-day against real `Transaction.date` values for missed-payment matching to work.

### Automatic categorization

Three complementary sources, composed in strict priority order by `autoCategorizeTransactions` (`lib/actions/auto-categorize.ts`), against currently-uncategorized `Transaction` rows - manual categorization stops being a per-transaction chore once a merchant (or a salary/dividend/interest deposit label, see below) has been categorized a couple of times, is well-known enough to ship a default for, or carries an official MCC code.

- **1. Self-learned history** (`lib/domain/auto-categorize.ts`'s `suggestCategoryAssignments`) - learns a `(accountId, normalizeLabelForCategorization(label)) -> categoryId` mapping from the user's own already-categorized history. This always takes priority over the other two sources when it has an answer, since it reflects this specific user's actual, confirmed intent, even when that intent disagrees with what MCC or the dictionary would have guessed - same per-account scoping as `detectCandidates` (recurring transactions, above) and the `/budgets` uncategorized-groups UI, for the identical reason (`label` is raw bank-feed text specific to one institution's formatting). Two confidence thresholds: `MIN_HISTORY_OCCURRENCES = 2` (a label needs at least 2 prior categorized occurrences before its majority category is trusted - a single manually-corrected mistake shouldn't immediately start auto-propagating) and `MIN_CONSISTENCY_RATIO = 0.7` (the majority category must clear 70% of that label's history, not just be the plurality winner of a scattered mix). Below either threshold, the transaction is simply absent from the suggestion map - never mapped to a guessed-but-unconfident category.
  - **`normalizeLabelForCategorization`** (also `lib/domain/auto-categorize.ts`) is a looser variant of `recurring.ts`'s own `normalizeLabel`, used only here and by "Correcting a categorization everywhere at once" below - recurring-transaction detection keeps its own separately-tuned `normalizeLabel` untouched. On top of the usual trim+lowercase, it strips a trailing year-like suffix (` 2025`/` 26` - a literal space then 2 or 4 digits, anchored at the end) - a real gap a user hit in production: French Livret interest is credited once a year with a label like "INTERETS 2025"/"INTERETS 26" (banks vary between 4-digit and 2-digit year suffixes), so under plain `normalizeLabel` two occurrences of the *exact same* label could never accumulate (the label itself changes every year, and interest lands only once a year) - `MIN_HISTORY_OCCURRENCES` could never be reached, so self-learning could never fire for this pattern at all. Only a *trailing* token is stripped, not any 2-digit number anywhere in the label - a bare `\d{2}` match with no anchoring would also eat a real arrondissement/store-number suffix like "MCDONALD'S PARIS 15" (a real but low-consequence tradeoff, documented in the function's own comment). The strip anchors on a literal space, not `\s+`, specifically because `\s+` immediately before a quantified group is exactly the shape ESLint's `sonarjs/super-linear-regex` rule flags as backtracking risk - whitespace is collapsed to single spaces *before* the strip runs so the anchor can be a plain space.
  - **`isGenericTransferLabel`/`GENERIC_TRANSFER_LABELS`** (same file) - a small denylist (currently just `"virement sepa"`/`"virement instantane"`) of bank transfer boilerplate that must never be treated as a trustworthy self-learning group, checked in `groupKey` before a label is ever allowed to accumulate history. Found investigating a real production incident: on a real LCL account, "VIREMENT SEPA" appeared on both a same-day, same-amount internal transfer between two of the user's own accounts *and* on unrelated salary-sized credits with no counterparty name attached (the bank doesn't consistently attach one - it does for some transfers, "VIREMENT SOPRA STERIA GROUP"/"VIREMENT M LOIC SERRE", not others, no reliable pattern to detect which). One transaction correctly categorized as salary had propagated (via "apply to similar", below) onto every other "VIREMENT SEPA" transaction in the account, internal transfers included. The same check gates `applyCategoryToSimilarTransactions` (`lib/actions/transactions.ts`) and `createIncomeEventFromTransaction`/`markSimilarTransactionsAsIncome` (`lib/actions/income.ts`) - a generic label never offers or accepts bulk propagation, only ever a one-off manual categorization. This list only prevents self-learning from repeating the mistake for whichever *other* real thing a generic label happens to also mean - it does nothing for the transfer half of the problem itself; see "Internal transfer detection" below for that.

### Internal transfer detection

`lib/domain/internal-transfers.ts`'s `detectInternalTransferPairs` - a pure function finding pairs of transactions that are almost certainly the two sides of one internal transfer (money moving between two of the user's own accounts), independent of label text entirely. Motivated directly by the `GENERIC_TRANSFER_LABELS` incident above: once it was clear a bank's own label text can't reliably distinguish an internal transfer from a real external payment, the fix had to come from somewhere else - the transaction data itself. A transfer between two of the user's own accounts always produces a matching debit on one account and credit on the other, for the exact same amount, within a day or two. This is a single-user app (see the Data model section's v2.0 multi-user note) - every account in the database belongs to the same person, so any such matching pair is safe to treat as an internal transfer without needing a counterparty name at all.

- **Matching**: groups debits by absolute amount, builds every (credit, debit) candidate pair within a configurable tolerance (`3` days by default) on *different* accounts - a same-account "pair" is never considered a transfer no matter how well the amounts happen to cancel out - then assigns pairs globally, closest date-diff first, before looser pairs get a chance to compete for an already-claimed debit. **Not the original design**: v1.9 shipped a simpler per-credit greedy version (iterate credits in whatever order they're listed, each grabs its own closest still-unclaimed debit) that turned out to have a real failure mode found in production - an unrelated same-amount credit processed earlier could permanently claim the one debit that was actually the true same-day match for a credit processed later, since claims were never revisited. Global-priority ordering fixes that specific case (the exact-date pair always outranks a looser one and gets assigned first) without needing a full min-cost matching algorithm - still not provably optimal for every conceivable case, but a personal account rarely has more than a couple of same-amount candidates to disambiguate between.
- **`Transaction.isInternalTransfer`** (`Boolean @default(false)`) is where the result gets persisted - `flagInternalTransfers` (`lib/actions/auto-categorize.ts`) runs this pass first, unconditionally and **never scoped to a single account** (unlike the rest of `autoCategorizeTransactions` - transfers are inherently cross-account), against every not-yet-flagged transaction in the whole table. Once flagged, a transaction is permanently excluded from the `isInternalTransfer: false` candidate pool on every future run, keeping each pass bounded to genuinely new transactions rather than rescanning history every time.
- Flagged transactions are excluded from the uncategorized pool all three categorization sources draw from (self-learning/MCC/dictionary never assign them a category), from `/budgets`' monthly spend total and its uncategorized-groups nagging list, but **not** from being manually categorized via the transaction row's own dropdown - the flag only suppresses the automatic sources, exactly the same "flag doesn't block manual, only automatic" shape as `GENERIC_TRANSFER_LABELS` above.
- **Retroactive cleanup, deliberately narrow**: the same `flagInternalTransfers` pass also clears `categoryId` for any newly-flagged transaction whose *current* category is named exactly `"Revenus"` - undoing the specific damage the reported incident caused. It does **not** clear any other category a newly-flagged transaction might already have - a different category could reflect a deliberate manual choice (some users may want to track internal transfers under their own category), which this pass has no business overriding.
- **2. Merchant Category Code** (`lib/domain/mcc-categories.ts`'s `matchMccCategory`, `MCC_CATEGORIES`) - the card network's own 4-digit merchant classification (ISO 18245), when the account's bank actually populated `Transaction.merchantCategoryCode` - see "GoCardless" above for where that field comes from (GoCardless/PSD2-synced accounts only; Woob, Trade Republic, and CSV import have no equivalent concept). Ranks above the text dictionary because it's assigned by the card network at merchant registration time, not guessed from a label substring - a genuinely more authoritative signal, when present. Every code/description in `MCC_CATEGORIES` was checked against [github.com/greggles/mcc-codes](https://github.com/greggles/mcc-codes), not written from memory - MCC numbers are easy to misremember and a wrong mapping here would mis-categorize real transactions silently. Deliberately excludes 6011 (ATM cash disbursement) and 4829 (wire transfer/money order) - a withdrawal or transfer isn't "spent" on a category, so leaving those unmapped (uncategorized) is the honest behavior, not a gap to fill.
- **3. Merchant dictionary** (`lib/domain/merchant-categories.ts`'s `matchMerchantCategory`, `MERCHANT_PATTERNS`) - a flat `pattern -> categoryName` map of well-known brand-name substrings (Carrefour, Netflix, SNCF, Uber, EDF, etc.), consulted last, only for transactions neither of the above had an opinion on - the same flat-map shape as `mcc-categories.ts`'s `MCC_CATEGORIES`, not an array of per-category objects (an earlier draft used that shape; SonarQube's copy-paste detector flagged it as duplicated code, since the same `{ categoryName, color, patterns: [...] }` object structure repeating 7 times is indistinguishable from real duplication once literals are normalized for comparison). This exists for the cold-start case self-learning alone can't help with: a brand new user, or any user's first-ever transaction from a well-known merchant, has no history yet to learn from - and unlike MCC, it works for every sync source, not just GoCardless. Deliberately small and not attempting global/every-country coverage (unlike everywhere else in this app - see "Tax treatment" below - this one piece is intentionally opinionated/French-leaning by design, extend the list as real gaps show up rather than guessing every merchant up front); a plain substring match against the lowercased label, not fuzzy matching, since real bank labels are typically boilerplate wrapped around one clear merchant name.
  - **Real production bug, found post-release**: Trade Republic's own transaction labels are German and built from the traded instrument's name ("Kauf"/"Verkauf"/"Sparplan ausgeführt"). `"spar"` (matched for the Spar supermarket chain) is a substring of "Sparplan" (savings plan) - TR's standard wording for every recurring investment purchase, crypto or stock - so every Sparplan execution was silently landing in Alimentation. Removed. The broader class this exposed is still only partially addressed: several other patterns (`totalenergies`, `orange`, `engie`, `veolia`, `axa`, `allianz`, `shell`, `esso`, `"bp "`, `"air france"`) are simultaneously a real French merchant/utility/insurer *and* a stock a French investor might hold via TR - "TotalEnergies - Kauf" and a real fuel purchase are indistinguishable by text alone. Not yet fixed pending confirmed real-world examples (`scripts/debug-categorization.sh` is the tool for that) - see the comment above `MERCHANT_PATTERNS` before touching this list further.
- **Both default-category sources share the same taxonomy** (Alimentation, Transport, Abonnements, Logement, Santé, Shopping, Loisirs, Revenus - 8 broad categories, not one per merchant type) and the same creation path: `resolveDefaultCategoryIds` (`lib/actions/auto-categorize.ts`) takes an explicit name->color map from whichever source matched, so it's reusable for both MCC and the text dictionary without needing to know which one called it. This is the one place auto-categorization creates a `Category` rather than only assigning an existing one - exactly so a brand new user with zero categories still gets somewhere useful for a well-known merchant or MCC to land. The first 7 are deliberately consolidated by **payment nature, not life domain**: restaurants/fast food fold into Alimentation rather than a separate "Restaurants" category, and gym memberships, telecom bills, insurance premiums, and streaming subscriptions all fold into Abonnements even though they're unrelated domains - the shared trait is "recurring, subscription-style payment", per an explicit user design call ("réunie par exemple streaming et salle de sport ça va dans abonnement") made after an earlier, more granular draft. **Revenus** is the one category that isn't spending - currently seeded by exactly one pattern, `"zinsen"` (German for "interest"), Trade Republic's own literal title for interest payouts on uninvested cash, confirmed from a real captured API response in `sync/tests/test_sync_tr.py` rather than guessed.
- **Salary and dividends are still not detected as a special case** - they're just another label the user categorizes once (into "Salaire"/"Dividendes"/whatever they call it) and the self-learning engine recognizes on every future occurrence, exactly like any merchant; there's no reliable universal *brand name* or MCC for a salary (every employer's label is different) the way there is for Carrefour or Netflix, and no confirmed real label text for dividends yet (see `scripts/debug-categorization.sh`'s query 2). **Interest is the one exception**, added to the dictionary directly (see `"zinsen"` above) precisely because it isn't a guess at an employer/brand name - it's Trade Republic's own structural vocabulary for what kind of event the transaction is, which is a safe signal in a way a company name isn't. This was also a deliberate scope decision for `IncomeEvent` specifically: `sync_tr.py`'s timeline items carry no ISIN/ticker in what reaches `Transaction.label`. *Silently auto-creating* `IncomeEvent` rows from a guessed keyword match against label text was considered and rejected for that reason - `autoCategorizeTransactions` itself only ever writes to `Transaction.categoryId`. A *manual, per-transaction-confirmed* path was added later though - see "Mark as income" under "Interest & dividend income tracking" below - which sidesteps the rejected idea entirely: the user picks the specific transaction each time, the system never decides on its own.
  - **Correction**: an earlier version of this comment claimed TR's raw timeline items have no structured event-type field at all ("grepped - it doesn't exist") - that was wrong, found later while investigating a real inter-account-transfer mis-categorization report. The raw item dict *does* carry a top-level `eventType` string (`"ACCOUNT_TRANSFER_INCOMING"`, `"INTEREST_PAYOUT"`, `"CARD_SUCCESSFUL_TRANSACTION"`, etc. - confirmed against `pytr`'s own `event.py`/`tests/all_events_test.json` fixtures on GitHub, not guessed) - `sync_tr.py`'s `_timeline_item_to_transaction()` just never reads it, only `title`/`subtitle`/`amount`/`status`/`timestamp`. Capturing it would be a materially more reliable signal than text matching for telling a transfer apart from a card payment or a dividend - a real, not-yet-implemented improvement opportunity, tracked as a follow-up rather than done here since it needs a real account's data to confirm which raw `eventType` strings actually distinguish an inter-account transfer from external incoming money (pytr's own mapping collapses several distinct raw strings - `ACCOUNT_TRANSFER_INCOMING`/`BANK_TRANSACTION_INCOMING`/`INCOMING_TRANSFER`/`PAYMENT_INBOUND` - into the same coarser `DEPOSIT` bucket for its own purposes, which doesn't by itself prove TR's backend distinguishes "from one of your own accounts" from "from an external payer" at the raw-string level).
- **Four trigger points**, all funnelling through the same `autoCategorizeTransactions(accountId?)`: CSV import (`importTransactions` in `lib/actions/transactions.ts`, scoped to the imported account, right after the rows are inserted), the sync-triggered `POST /api/transactions/auto-categorize` route (every account, called from `sync/main.py`'s `_run_all()` right before `_check_alerts()` - same NEXTAUTH_SECRET bearer-token pattern as that call, and ordered first so a category assignment made this cycle can make a `BUDGET_OVERRUN` custom alert rule fire in the same run instead of lagging a cycle behind), `syncGocardlessTransactions` (right after new GoCardless transactions land, so a populated MCC gets a chance to match in the same sync), and the manual "Auto-catégoriser" button on `/budgets` (`components/budgets/auto-categorize-button.tsx`, calls `runAutoCategorizeNow` across every account - useful for a first backfill, or to seed default categories on a fresh install with no categorization history at all). Same `proxy.ts` matcher exclusion as `api/alerts` (no browser session on that call path). All four only ever touch currently-uncategorized (`categoryId: null`) transactions - a transaction that was auto-categorized *wrong* (like the Sparplan bug above) is never revisited automatically, since re-running these sources can't tell "already correctly categorized" from "already wrongly categorized" apart. See "Correcting a categorization everywhere at once" below for how a wrong batch actually gets fixed.
- Applies suggestions from all three sources via one `updateMany` per distinct target category (grouping the merged suggestion map by `categoryId` first), not one write per transaction.

**Correcting a categorization everywhere at once.** Fixing `setTransactionCategory` (`lib/actions/transactions.ts`) one `<select>` at a time doesn't scale when a dictionary/MCC/self-learning miss hit every occurrence of a label at once (the Sparplan bug above being the motivating real case) - the user explicitly asked for this after finding it painful in practice. `setTransactionCategory` now also counts how many *other* transactions in the same account share the same `normalizeLabelForCategorization(label)` but currently sit in a different category (including uncategorized), returning `{ siblingCount }`. `TransactionCategorySelect` (`components/shared/transaction-category-select.tsx`) only opens a confirmation dialog when that count is `> 0` - a label with no siblings never interrupts the user with an empty prompt. Confirming calls `applyCategoryToSimilarTransactions(transactionId, categoryId)`, which re-derives the label match server-side from the source transaction (not client-supplied ids, same trust boundary as `bulkAssignCategory`) and `updateMany`s every match in that account, unconditionally overwriting whatever category (or none) they currently have - this is the one categorization path in the app that *does* touch already-categorized transactions, by design, since it's always a direct, explicit user correction rather than an automatic guess. Scoped per-account, same reasoning as every other label-based grouping in this codebase (label is raw bank-feed text specific to one institution's formatting). Using the year-stripping `normalizeLabelForCategorization` here too (not just for self-learning) matters for the same Livret-interest case: correcting one year's "INTERETS 2025" now offers to also fix "INTERETS 2026" and any other year already sitting in the account, not just other transactions from the exact same year.

**`scripts/debug-categorization.sh`** - read-only diagnostic queries (investment/crypto transactions and their assigned category, uncategorized dividend/interest-looking labels, per-account-type breakdown of a given category) for troubleshooting categorization issues directly against a running instance's database, same `.env`-sourcing/`docker compose exec` convention as `scripts/backup.sh`.

### Interest & dividend income tracking

`/income` - `IncomeEvent` rows (`DIVIDEND` or `INTEREST`, optional `ticker`, gross `amountCents`, optional `taxWithheldCents` for foreign withholding tax, `date`), created either by typing the form on `/income` from scratch or via "Mark as income" from a real `Transaction` (see below). Either way this is a real, user-confirmed record, distinct from the estimate described below - nothing here is auto-synced or silently auto-detected without the user confirming a specific transaction.

- Net amount is always computed as `amountCents - (taxWithheldCents ?? 0)`, never stored. `ticker` is free text (not a FK to `Holding`) so a sold position's dividend history survives the holding being deleted.
- The Analytics page's "Passive income" card shows real year-to-date `IncomeEvent` totals (dividends/interest, net of withholding) with a link to `/income` - **this replaced an estimate** that used a hardcoded `DIVIDEND_YIELDS` map and unauthenticated Yahoo Finance dividend-history fetches, plus French regulated-savings rates matched by account **name substring** (`"livret a"`, `"ldds"`, etc.). Being a **year-to-date** figure, it's legitimately €0 for most of the year for an account whose interest is credited only once, in December - a real UX complaint, not a bug, and not something "Mark as income" below changes (it makes recording the event easier, not the YTD framing different).
- That estimate machinery (`DIVIDEND_YIELDS`, `ISIN_TO_YF_SYMBOL`, `fetchYFDividendForSymbol`, the name-matched savings rates in `app/analytics/page.tsx`) is **not removed** - it still feeds the separate "Dividend calendar" section (upcoming per-holding ex-dividend dates), a genuinely different, forward-looking concept that this feature doesn't replace. Don't confuse the two `taxRate` variables in that file: `dividendEffectiveTaxRate()` is dividend withholding tax (ISIN country + `investmentSubtype`-based), unrelated to the latent capital-gains tax described below.
- `createIncomeEvent`/`updateIncomeEvent`/`createIncomeEventFromTransaction` (`lib/actions/income.ts`) all call `assertIncomeEventEligible(accountId, type)` before writing anything - `DIVIDEND` on `INVESTMENT`/`CRYPTO`/`CHECKING` accounts, `INTEREST` on `CHECKING`/`SAVINGS`. This mirrors `components/income/add-income-dialog.tsx`'s client-side account filter and `assertCsvImportEligible`'s rationale: Server Actions are directly invocable regardless of what's rendered, so the eligibility rule has to be enforced server-side too, not just via which accounts populate the dialog's dropdown. `DIVIDEND` allowing `CHECKING` (not just `INVESTMENT`/`CRYPTO`) is a real, later addition - see "Trade Republic transaction history" above: every TR timeline event (trades, dividends, interest, card payments) lands on one shared `CHECKING`-typed "Compte espèces" account, so a real dividend payout can legitimately need recording against a `CHECKING` account.

**"Mark as income"** (`components/account-detail/mark-as-income-button.tsx`, on eligible rows in the account's transactions table) creates an `IncomeEvent` directly from a real `Transaction` instead of the user retyping amount/date by hand - a real gap the user hit in production: typing "the right title" and finding the right transaction manually for every dividend/interest payment was, in their words, too tedious to be worth using. Only shown for a transaction that's a credit (`amountCents > 0`), on an eligible account type, with no `IncomeEvent` linked yet (`Transaction.incomeEvent`, the reverse side of `IncomeEvent.transactionId` below). Amount and date are pre-filled from the transaction and **not editable** in the dialog - editing them would desync the record from the transaction it's supposed to represent, defeating the point of linking it; only `ticker` and `taxWithheldCents` are user input. The type toggle (Dividende/Intérêts) only appears when the account is genuinely ambiguous (`CHECKING`, per the TR case above) - a `SAVINGS` account locks to `INTEREST`, since `DIVIDEND` isn't even eligible there.

- `IncomeEvent.transactionId` (`String? @unique`) is the link - nullable for every pre-existing row and for anyone who still prefers the manual form, `@unique` so the same real payment can't be marked twice, `onDelete: SetNull` (not `Cascade`) since deleting the source transaction shouldn't destroy an already fiscally-relevant income record, only its provenance link.
- **Propagation, same shape as "Correcting a categorization everywhere at once" above**: after marking one transaction, `createIncomeEventFromTransaction` returns how many *other*, not-yet-linked, credit transactions in the account share the same `normalizeLabelForCategorization(label)` (the auto-categorization module's own year-stripping normalization, reused here for the identical reason - a once-a-year interest credit's label changes every year). When that count is `> 0`, a confirmation dialog offers `markSimilarTransactionsAsIncome`, which creates an `IncomeEvent` for each match in one `createMany`. Unlike the categorization version, this one **skips** already-linked transactions rather than overwriting them - marking as income always creates a new fiscal record, it never corrects an existing one, so a sibling that's already recorded is left untouched instead of being double-recorded.
- This is deliberately still a **manual, per-transaction-confirmed** action, not automatic creation from a guessed keyword match - the "Automatic categorization" section above explains why that specific idea (auto-creating `IncomeEvent` from unverified label text) was considered and rejected for `sync_tr.py`'s timeline items. The difference here is that the user is the one selecting/confirming the specific transaction each time (even in bulk, they chose the source transaction and reviewed the resulting count before confirming) - the system never silently decides a transaction is income on its own.

**"Autres revenus"** (also `/income`) - a second, separate section listing every `CategoryKind.INCOME` category (see "Data model" below) with its year-to-date total, linking each into its own `/budgets/[categoryId]` drill-down. This is where salary lives - typed as its own `Category` (e.g. "Salaire") rather than an `IncomeEvent`, and deliberately **not merged into the `IncomeEvent` list above**, for a concrete reason: `/tax-report` queries `prisma.incomeEvent.findMany` directly to build the annual dividend/interest tax summary, and French salary income has nothing to do with that report (it's taxed via an entirely different mechanism, PAYE/prélèvement à la source) - adding a `SALARY` `IncomeType` would have silently polluted a report that's specifically about investment income. Keeping salary as a `Category` instead means it naturally reuses everything already built for categorization (self-learning, "apply to similar", the drill-down page) with zero risk to the tax report's scope. The resulting overlap - Trade Republic's "Zinsen" interest can show up on *both* this section (via the auto-created "Revenus" category) and the `IncomeEvent` list above (if the user also used "Mark as income" on the same transaction) - is accepted, not a bug: the two mechanisms serve different purposes (broad/automatic vs precise/tax-reportable) and a user is free to use either, both, or neither for a given payment.

### Tax treatment

Latent (unrealized capital-gains) tax is a **per-account** setting, not a global one: `Account.taxTreatment` (`TaxTreatment` enum: `EXEMPT` | `DEFERRED` | `TAXABLE`) + `Account.taxRatePct` (0-1 ratio, meaningful only when `TAXABLE`). `lib/domain/tax.ts`'s `getAccountTaxRate(account)` is the single shared resolver - `EXEMPT`/`DEFERRED` both return `0`, `TAXABLE` returns `taxRatePct` - used by all four pages that compute latent tax (`app/page.tsx`, `app/accounts/page.tsx`, `app/accounts/[id]/page.tsx`, `app/analytics/page.tsx`), replacing 4 previously-duplicated `account.type`/`investmentSubtype` branching helpers.

- This exists so non-French wrappers have somewhere to go: a UK ISA or US Roth IRA is `EXEMPT`, a PER/401k is `DEFERRED` (not taxed until withdrawal - not taxed for latent/net-worth purposes today either), anything else is `TAXABLE` at whatever rate the user enters. `investmentSubtype` (`"PEA"`/`"CTO"`, cosmetic label only) is fully decoupled from this - an ISA doesn't need to pretend to be a "CTO" to get taxed correctly.
- Set at account creation (`components/accounts/add-account-dialog.tsx` + `createAccount`, rate pre-filled with a hardcoded 17.2%/31.4% suggestion based on the PEA/CTO/Crypto choice, always editable) or afterward via an inline form in the account detail page's fiscal summary (`updateAccountTaxTreatment` in `lib/actions/accounts.ts`, same `<form action={...}>` pattern as `updateInvestmentStartDate`) - there was no prior UI to edit `investmentSubtype` post-creation either, so this is the first edit surface for either field.
- `UserSettings.taxRatePea`/`taxRateCto`/`taxRateCrypto` (Settings → Fiscalité) still exist, but only as **defaults offered when creating a new account** - they are no longer read per-render for existing accounts. Migration `20260727141819_add_account_tax_treatment` backfilled every pre-existing account's `taxRatePct` from these same global rates at the time it ran, so upgrading never changes a displayed number: CRYPTO → `taxRateCrypto`, PEA → `taxRatePea`, CTO → `taxRateCto`, INVESTMENT with no subtype set → `EXEMPT` (reproducing the old chain's `null` = "no tax computed" outcome exactly, not a claim that the account is a real tax-exempt wrapper).

### Realized gains & annual tax report

Before this feature, selling a holding meant retyping a smaller `quantity`/`costBasisCents` on the existing `Holding` row (`upsertHolding` in `lib/actions/holdings.ts`) - a blind overwrite with no history, no gain ever computed. `Sale` (`ticker`, `quantity` sold, `proceedsCents`, `costBasisCents` of the *sold portion*, `date`) now records disposals as discrete events, the same shape as `IncomeEvent`. Realized gain is always `proceedsCents - costBasisCents`, never stored.

- **Recording a sale** (`components/account-detail/sell-holding-dialog.tsx`, "Sell" button next to each holding row in `app/accounts/[id]/page.tsx`) uses the **average-cost method**, not per-lot FIFO/LIFO: the sold portion's cost basis defaults to `holding.costBasisCents * (soldQty / holding.quantity)`, always user-editable. `recordSale` (`lib/actions/sales.ts`) wraps creating the `Sale` row and adjusting the `Holding` in one `prisma.$transaction` - full disposal (`quantitySold >= holding.quantity`) deletes the `Holding`, partial disposal reduces `quantity` and `costBasisCents` proportionally, then calls the same `refreshAccountBalance` helper `upsertHolding`/`deleteHolding` already use (exported from `lib/actions/holdings.ts` for this reason). `recordSale` also rejects a sold-portion `costBasisCents` that's negative or exceeds the holding's own remaining `costBasisCents` - without that guard the remaining `Holding.costBasisCents` can go negative, which then inflates the displayed gain (and latent tax) beyond the position's actual market value indefinitely.
- **No backfill and no `updateSale`**: past sales already lost to the old overwrite behavior can't be reconstructed, and editing a past `Sale`'s quantity/proceeds after the fact would need the same retroactive-holding-adjustment problem `deleteSale` already punts on (**record-only deletion** - it does not reverse the `Holding` change, since the holding may have had further buys/sells/price updates since; correcting a mistake means deleting the `Sale` row *and* manually fixing the `Holding` via the existing edit dialog).
- **`/tax-report`** aggregates `Sale` + `IncomeEvent` for a given calendar year (`?year=` search param). Estimated tax on gains reuses `getAccountTaxRate()` from "Tax treatment" above (`EXEMPT`/`DEFERRED` sales show €0 tax, same semantics as latent tax elsewhere) - it does not attempt to model additional income tax on dividends/interest beyond what `IncomeEvent.taxWithheldCents` already nets out, by design (country-agnostic scope, not a French PFU/social-charges calculator). No sidebar nav item - linked instead from the Analytics "Passive income" card and the account detail page's fiscal summary, to avoid further crowding the already-7-item mobile bottom nav.
- The estimated tax figure **nets gains and losses per account for the year** before taxing (grouping `Sale` rows by `accountId`, only taxing a positive net) - same convention as the account-detail page's aggregate tax figure. The per-row "Tax" column in the sales table is a per-sale reference figure only (as if that were the year's only sale) and intentionally won't sum to the displayed total whenever an account had both a gain and a loss sale that year - disclosed in the page's footnote.
- Markdown export (`components/shared/export-tax-report-button.tsx`) reuses `lib/utils/markdown-export.ts`'s `fmt`/`sign`/`downloadFile`, same convention as `components/shared/export-analytics-button.tsx`/`components/shared/export-accounts-button.tsx` - this is the "country-agnostic, exportable" part of the roadmap wording; the report itself is presented as an estimate for informational purposes, not an official tax document or a literal French IFU form mapping. Unlike those other two exports, every per-row figure here (sale proceeds/cost basis/gain/tax, each dividend/interest line) is passed `fmt(x, 2)` explicitly rather than `fmt`'s own 0-decimal default - matching the page's own `formatCurrency(x)` calls for these same rows (2 decimals, no override), which the export originally didn't. Found in production: a real dividend of 0,46€ was rounding to "0 €" in the downloaded file while the page correctly showed "0,46 €" right next to it - real money silently disappearing from a document whose whole purpose is being accurate enough to declare. The summary card figures stay at the export's 0-decimal default, matching the page's own `formatCurrency(x, 0)` summary cards.

### Benchmark comparison

`app/analytics/page.tsx`'s "Comparaison aux indices" section, right after the investment performance table. Deliberately **not** a historical overlay chart: `investCAGR` (the portfolio's own aggregate CAGR, see the performance table above it) is itself a point-in-time snapshot - current value vs. cost basis, annualized over a cost-basis-weighted average holding duration (`investCAGRWeightedYears`) - not a smooth time series (investment `HistoricalBalance` snapshots are event-driven, created only when holdings change, not on a schedule, so there's no reliable daily series to chart against an index). This feature applies the identical snapshot-to-snapshot methodology to 3 reference indices instead of inventing a different, inconsistent one.

- `fetchYFPriceHistory(symbol)` reuses the exact same unauthenticated Yahoo chart endpoint, headers, and `next: { revalidate: 3600 }` caching as the existing dividend fetch (`fetchYFDividendForSymbol`) - that endpoint already returns OHLC `close`/`timestamp` arrays that the dividend fetch just discards (it only reads `events.dividends`/`meta.regularMarketPrice`); this fetch reads those arrays instead, with `interval=1mo&range=max` (not a fixed window - see `computeIndexCAGR` below for why) and no `events` param.
- `BENCHMARK_SYMBOLS`: `sp500: "^GSPC"`, `cac40: "^FCHI"` (real index tickers), `msciWorld: "URTH"` (the iShares MSCI World ETF - Yahoo has no clean "^" ticker for the real index, so this is a proxy with a small expense-ratio drag, disclosed in the UI footnote).
- `computeIndexCAGR(series, startDate, now)` finds the closest historical close to `startDate` (via `priceAt`, nearest-timestamp match - the fetched series is monthly, not daily) and to `now`, then applies the same `(end/start)^(1/years) - 1` formula as `investCAGR`, over the identical `investCAGRWeightedYears` lookback so the comparison is apples-to-apples. The "years" divisor is derived from the **actual matched data points' dates**, not the requested `startDate` - `investCAGRWeightedYears` can exceed however far back the fetched series reaches (a PEA opened over 10 years ago, URTH's own Feb-2012 inception, etc.), and dividing by the *requested* span while priceAt silently clamps to the *oldest available* point would produce a self-inconsistent (understated) CAGR instead of gracefully reflecting the window actually available.
- Only rendered when `investCAGR !== null` (same gate as the aggregate CAGR itself) and per-index only when that index's fetch actually returned data (Yahoo being unreachable degrades to that one row being omitted, not a crash - same `try/catch` → empty-array fallback as the dividend fetch).

### Portfolio rebalancing

`Holding.targetPct` (0-1 ratio, nullable - same convention as `taxRatePct`) adds a target counterpart to the per-holding "Poids" (current weight) column that already existed on `app/accounts/[id]/page.tsx`'s holdings table (`pct = marketValueCents / accountTotal`). This is scoped **within one account's own holdings** - unrelated to the Analytics allocation chart, which only buckets by account *type* (cash/savings/investments/crypto/realEstate/auto), never per-ticker.

- Set via the existing `components/account-detail/add-holding-dialog.tsx` edit form (one more optional field, not a new dialog), input as a 0-100 percentage and converted to a 0-1 ratio in `upsertHolding` (`lib/actions/holdings.ts`). Same optional-update semantics as `costBasisCents`: leaving it blank on an edit does not clear a previously-set target.
- Targets are **not required to sum to 100%** - a holding with `targetPct: null` is simply excluded from the rebalancing plan (e.g. an untouched legacy position the user doesn't want to manage this way).
- The "Rééquilibrage" section on the account detail page (only shown when at least one holding has a target set) computes, per targeted holding: drift in points (`pct - targetPct*100`) and a suggested trade (`driftValueCents = marketValueCents - accountTotal*targetPct`; positive → suggest selling that amount, negative → suggest buying it), plus an approximate share count from `driftValueCents / lastPriceCents`. The suggested-trade line is only rendered when `driftPts !== 0` (not just `driftValueCents !== 0`) - `driftPts` is two independently-rounded integer percentages, so a holding can sit at e.g. an exact 38.98% weight against a 39% target and show "0 pts" drift while the raw cents-level `driftValueCents` is still technically nonzero; showing a suggested trade next to an "on target" reading would visually contradict it.
- **Informational only** - the suggestion is displayed as text, not wired to pre-fill `AddHoldingDialog`/`SellHoldingDialog` (neither currently accepts external suggested-quantity props, and both are already one scroll up in the same holdings table for the user to act on manually). Keeps this change to one field + one read-only section, no changes to two already-working dialogs' APIs.

### Multi-currency

`Holding` positions can be entered in USD, GBP, or CHF and are converted to EUR **once, at entry time** - `lastPriceCents`/`costBasisCents` stay exactly what they've always been (plain EUR cents), so every existing calculation (net worth, tax, rebalancing, the tax report, the 3 chart components) keeps working completely unmodified. This is deliberately narrower than a "live multi-currency ledger": holdings aren't live-refreshed today either except via sync, so a snapshot-on-entry FX rate matches the app's existing "manually update the price when you check in" paradigm.

- `lib/services/exchange-rate.ts`'s `fetchExchangeRateToEur(currency)` reuses the same unauthenticated Yahoo Finance chart endpoint/headers/`revalidate: 3600` caching convention as the dividend/benchmark fetches in `app/analytics/page.tsx`, via the `EURUSD=X`/`EURGBP=X`/`EURCHF=X` pairs (Yahoo quotes these as "X per 1 EUR", so the raw price is inverted to get "EUR per 1 X"). Extracted to `lib/` rather than kept page-local since it's the first Yahoo fetch called from a Server Action rather than a page.
- `upsertHolding` (`lib/actions/holdings.ts`) reads `currency` from the form (default `"EUR"`, unchanged path - the 3 new fields stay `null`). For a foreign currency, it fetches the rate and **throws if the rate can't be fetched** - no silent fallback to a stale/wrong rate - then stores `nativePriceCents`/`nativeCostBasisCents` (exactly what the user typed) and `fxRateToEur` (the rate captured at entry time) alongside the EUR-converted `lastPriceCents`/`costBasisCents`. Switching a holding's currency back to EUR on an edit nulls out all three native fields.
- `fxRateToEur` is only **re-fetched** when the entered `currency`/native price/native cost basis actually differ from what's already stored (compared against the existing row before deciding) - otherwise the existing rate/EUR values are reused as-is. Without this, editing any unrelated field (renaming the position, setting a rebalancing target) would resubmit the same pre-filled native price and silently re-roll the conversion against whatever the market rate happens to be *today*, shifting the holding's EUR valuation even though nothing about the position's price actually changed - contradicting the "captured at entry time" design above.
- `components/account-detail/add-holding-dialog.tsx`'s price/cost-basis inputs pre-fill from `nativePriceCents`/`nativeCostBasisCents` when set (not `lastPriceCents`) so re-opening the edit dialog on a foreign-currency holding shows back exactly what was typed (e.g. "150.00"), not a lossy back-converted approximation.
- The holdings table (`app/accounts/[id]/page.tsx`) shows a small muted currency-code badge next to the ticker (e.g. "AAPL · USD") when `currency !== "EUR"` - no new table column, to avoid the mobile-width concerns already worked through for this same table (see "Portfolio rebalancing" above).

### Data model

- `Institution` → many `Account`
- `Account` (`AccountType`: `CHECKING | SAVINGS | INVESTMENT | REAL_ESTATE | MEAL_VOUCHER | CRYPTO | AUTOMOBILE | LOAN`)
  - Fiat (CHECKING, SAVINGS, MEAL_VOUCHER): `HistoricalBalance` (balance in cents as `BigInt`)
  - Investment/Crypto: `Holding` (ticker + `Decimal` quantity) + live price at runtime. `investmentSubtype` = `"PEA"` or `"CTO"` (cosmetic label only). `taxTreatment` (`TaxTreatment` enum) + `taxRatePct` drive the actual latent-tax rate - see "Tax treatment" below
  - Real Estate & Automobile: `manualValueCents` + optional `liabilityCents`
  - LOAN: capital computed at runtime via `calcCurrentCapital()` from `lib/domain/loan.ts`. `loanPaidOffAlertSent` is a one-way dedup flag for the "nearly paid off" alert - see "Alerts & webhooks" above.
- `Holding` - unique on `(accountId, ticker)`. `costBasisCents` for P&L. `targetPct` (0-1 ratio, nullable) drives the "Portfolio rebalancing" feature below - independent of any other field. `currency` (`HoldingCurrency` enum, default `EUR`) + `nativePriceCents`/`nativeCostBasisCents`/`fxRateToEur` (all null when `currency = EUR`) drive "Multi-currency" below - `lastPriceCents`/`costBasisCents` are always EUR regardless of `currency`
- `HistoricalBalance` - daily balance snapshots
- `Transaction` - bank movements. `amountCents`: positive = credit, negative = debit. Deduplicated via `syncId`. Optional `categoryId` → `Category` (`onDelete: SetNull` - deleting a category un-categorizes its transactions instead of deleting them). Optional `merchantCategoryCode` - GoCardless-only (PSD2's Berlin Group schema), null for every other sync source - see "Automatic categorization" below. Reverse-linked from at most one `IncomeEvent` (`incomeEvent`) when "Mark as income" created one from it - see "Interest & dividend income tracking" below. `isInternalTransfer` (`Boolean @default(false)`) - set when this transaction is matched as one half of a same-amount, cross-account transfer pair - see "Internal transfer detection" below.
- `Category` - user-defined category (name, hex `color`, `kind: CategoryKind` (`EXPENSE` default | `INCOME`), optional `budgetCents`). `budgetCents` is a single ongoing monthly envelope, not a per-month history - editing it takes effect immediately, including retroactively on the current month's progress bar (no historical record of past amounts), and is meaningless (never stored) for an `INCOME` category - a spending cap has no equivalent for money coming in. `/budgets` only ever lists `EXPENSE` categories and computes each one's current-calendar-month spend via `prisma.transaction.groupBy({ by: ["categoryId"] })` filtered to `amountCents < 0` (debits only) - a `categoryId: null` bucket in that same query is the "uncategorized spend" figure. `INCOME` categories (default-seeded "Revenus", or a user-created one like "Salaire") instead get their own section on `/income` - see below. Clicking a category name links to `/budgets/[categoryId]`, a drill-down page listing every transaction (across all accounts) tagged with it regardless of kind, reusing `TransactionCategorySelect` so a mis-tagged row can be recategorized in place.
  - **Why `kind` exists, and why it's explicit, not inferred**: an earlier version tried to make a single category's `/budgets` card automatically switch between "spent" and "received" framing based on which dominated that specific month's transactions - rejected after direct user pushback before shipping: the same category's card would silently flip behavior month to month (no spending this month → "received" framing; some spending next month → back to normal), which is a genuinely worse UX than a stable, explicit choice made once at creation, and doesn't match how any real budgeting app (YNAB, Bankin', Firefly III) separates income from expenses - they use a fixed type, not monthly inference. `kind` is chosen via a toggle at creation/edit time (`components/budgets/add-category-dialog.tsx`), defaults to `EXPENSE` (`Category`'s own schema default) for every existing call site that doesn't pass one.
  - **"Reste à vivre"** (`app/budgets/page.tsx`) - a summary card showing every credit minus every debit for the current month, deliberately computed across *all* transactions regardless of category or `categoryId: null`, not scoped to `INCOME`-kind categories specifically - it's meant to answer "how much came in vs went out this month", which shouldn't require perfect categorization to be true. Internal transfers (`isInternalTransfer`) are excluded from both sides, same as everywhere else.
  - **Bulk categorization**: `/budgets` also lists the top `MAX_UNCATEGORIZED_GROUPS` (8) uncategorized-transaction label groups by total absolute spend (`components/budgets/uncategorized-group-card.tsx`, grouped in-memory by `normalizeLabel()` from `lib/domain/recurring.ts` - same normalization the recurring-detection heuristic uses, since it's the same "same real-world thing, different bank-feed casing" problem). `bulkAssignCategory(transactionIds, categoryId)` in `lib/actions/transactions.ts` sets one category on an arbitrary batch of transaction ids in one `updateMany` - the ids come from a server-computed group, never from client-supplied label matching, so there's no risk of a stale/forged id list touching the wrong rows.
  - Recurring-suggestion candidates (`detectCandidates` in `lib/domain/recurring.ts`) carry a `categoryId` guess: the majority (mode) category already assigned among the matched transactions, if any. This is why confirming a long-standing subscription's suggestion often needs no manual category pick - it's inherited from however you'd already tagged that label's past transactions, not re-guessed from scratch.
- `RecurringTransaction` - a subscription/bill/regular-income template (`label`, signed `amountCents`, `frequency` enum `WEEKLY|MONTHLY|YEARLY`, `intervalCount`, `anchorDate`, optional `categoryId`). `active: false` means either user-paused or a dismissed auto-detection suggestion - both states are excluded from projections and from resurfacing as a suggestion (see below), there's no separate "dismissed" table
- `IncomeEvent` - a real, user-confirmed dividend or interest payment (`type` enum `DIVIDEND|INTEREST`, optional `ticker`, gross `amountCents`, optional `taxWithheldCents`, `date`, optional `transactionId` linking back to the source `Transaction` when created via "Mark as income" rather than typed from scratch). See "Interest & dividend income tracking" below - distinct from the Analytics page's separate Yahoo-Finance-based dividend/interest *estimate*.
- `Sale` - a recorded disposal of part or all of a `Holding` position (`ticker`, `quantity` sold, `proceedsCents`, `costBasisCents` of the sold portion, `date`). See "Realized gains & annual tax report" below - realized gain is `proceedsCents - costBasisCents`, never stored.
- `SyncLog` - per-run log entries: `source` ("lcl" | "trade_republic"), `status` ("success" | "error" | "auth_required"), optional `message`
- `UserSettings` - singleton (`id = "singleton"`): salary, expenses, savings goal, monthly saved, `taxRatePea`/`taxRateCto`/`taxRateCrypto` (Float, defaults 0.172/0.314/0.314) - now only defaults suggested when creating a new account, see "Tax treatment" below. Also holds the alert channel config, dedup state, and per-trigger toggles (`ntfyTopicUrl`, `alertEmailTo`/`smtp*`, `netWorthAlertThresholdCents`/`netWorthAlertLastAbove`, `lastSyncFailureAlertCheckedAt`, `loanAlertsEnabled`/`syncFailureAlertsEnabled`) - see "Alerts & webhooks" above.
- `ShareLink` - a token-gated read-only dashboard link (`token` unique, plaintext, optional `label`, optional `expiresAt`, `lastAccessedAt`). See "Read-only share links" above.
- `AlertRule` - a user-defined alert (`kind: ACCOUNT_BALANCE | BUDGET_OVERRUN | ACCOUNT_OVERDRAFT | INVESTMENT_VALUE | HOLDING_PRICE | UNREALIZED_GAIN`, `active`, optional `message`), parallel to the 3 fixed triggers on `UserSettings`. See "Custom alert rules" above.

### Net worth calculation

**Gross = fiat balances + holdings market value + real estate/automobile manualValueCents**
**Net = Gross − liabilityCents − loan remaining capital − latent taxes**

Latent tax rate: per-account via `getAccountTaxRate()` - see "Tax treatment" above. `UserSettings`'s PEA/CTO/Crypto rates (Settings → Fiscalité) are only the defaults suggested when creating a new account.

### Container image hardening

`docker.yml`'s `trivy-scan` job scans the published `app`/`sync` images for OS-package-level CVEs (npm audit/pip-audit only ever see `package.json`/`requirements.txt`, never what's baked into the base image layer). Two things have already been removed from the runtime images because they were pure dead weight *and* a real CVE surface, not just untested risk:

- **`Dockerfile` (app)**: `node:22-alpine` bundles `npm` (and its own vendored `node_modules`) even though this project only ever uses `pnpm` via `corepack` - `npm`/`npx` are never invoked anywhere in this Dockerfile or its `CMD`. Removed via `rm -rf /usr/local/lib/node_modules/npm /usr/local/bin/npm /usr/local/bin/npx` at the end of the `runner` stage. Verified `pnpm`/`node`/`prisma` still work with it gone; confirmed 0 CRITICAL/HIGH findings afterward (previously 6, including one CRITICAL in a vendored `tar`).
- **`sync/Dockerfile`**: `gcc`/`g++` (and the headers/`libc6-dev`/`linux-libc-dev` they pull in via `apt-get autoremove`) are only needed to compile `requirements.txt`'s native extensions (woob's `lxml`, `cryptography`, `psycopg2`) - the compiler itself is dead weight once the `.so` files exist. Removed right after `pip install` in the same `RUN` layer. Verified all sync modules (`woob`, `pytr`, `playwright`, `psycopg2`) still import fine afterward; this alone accounted for 47 of 117 CRITICAL/HIGH findings.
- **`sync/Dockerfile`, round two**: `git` is only needed for `pip install` to clone `pytr`'s pinned git commit (no PyPI release) - never used again afterward, and removing it cascades (via `apt-get autoremove`) to `perl`/`liberror-perl`/`libcurl3t64-gnutls`, which nothing else needs either. `xvfb`/`xserver-common` come bundled with `playwright install --with-deps chromium`'s headed-**and**-headless dependency union, but this project only ever launches Chromium headless (`setup_tr.py`) and never starts an X server (grep confirms `Xvfb`/`DISPLAY` are never referenced in `sync/`) - removing them cascades to the Mesa GL/Vulkan/X11-window-manager stack they alone pulled in (Chromium's own `ldd` output has no `libGL`/`libEGL` dependency - it ships its own software renderer for headless use). Verified together, not just individually: after removing all of it, headless Chromium still launches, executes JS, renders a canvas element, and produces a correct screenshot (byte-identical across two independent test runs) - cut CRITICAL/HIGH findings on this image roughly in half (66 → 33; see #22 for the full investigation, including why `perl-base` specifically is *not* touched - it's a Debian-essential package apt itself refuses to remove without `--allow-remove-essential`).

**Known accepted risk**: the sync image still has ~33 CRITICAL/HIGH findings (`libglib2.0`, `perl-base`, the `util-linux`/`ncurses` family, a handful of single-count Debian base packages) - either genuine Chromium runtime dependencies (`libglib2.0`, `libblkid1`, `libmount1` are all in its own `ldd` output) or Debian-essential base packages nothing here installed on purpose. `trivy-scan` therefore runs **non-blocking** (`exit-code: 0`) for the `sync` matrix entry specifically, while staying fully blocking (`exit-code: 1`) for `app`, which is clean. This is deliberately narrower than the `find-my-way`/`valibot` exemptions under "pnpm overrides" below (those are unreachable *code paths* in an otherwise-used dependency; this is Chromium's own real runtime footprint) - it's accepted because `sync/`'s HTTP API is Docker-network-only per `SECURITY.md`, never internet-exposed, not because the CVEs don't matter. Findings still upload to the Security tab either way (`if: always()` on the SARIF upload), so they stay visible.

**Three real, distinct bugs made `trivy-scan(app)` look broken across v1.4.4-v1.4.10, in order**: (1) `aquasecurity/trivy-action` pinned as `@0.36.0` instead of the real tag `@v0.36.0`, failing before any scan ran; (2) a raw `${{ github.repository }}`-built `image-ref` scanning `ghcr.io/LoicSERRE/...` (capitalized, matching this repo's real GitHub owner) instead of the required-lowercase GHCR path, also failing before any scan ran - fixed by lowercasing it explicitly, then hardened further by scanning `build-app`/`build-sync`'s own `digest` output instead of the mutable `:latest` tag (immune to any registry tag-propagation lag, a real but secondary bug this surfaced); (3) `/root/.cache/pnpm` (410MB of npm-registry metadata left over from `pnpm install --prod`, never read at runtime) made Trivy's secret scanner slow enough to occasionally exceed its 5-minute default timeout mid-scan - reproduced locally with the exact same timeout, fixed by removing that cache (keep `/root/.cache/node/corepack` though, that one **is** needed at runtime - see the `Dockerfile` comment). After all three were fixed, one real (if minor) finding was still failing the gate: a MEDIUM-severity `tar` DoS (`GHSA-r292-9mhp-454m`) vendored *inside* corepack's own cached pnpm single-executable build, not this project's dependency tree. It was slipping through a `severity: CRITICAL,HIGH` filter that should have excluded it, because `aquasecurity/trivy-action`'s `format: sarif` mode builds its report **"with all severities" regardless of the `severity` input** unless `limit-severities-for-sarif: true` is also set - a real trivy-action gotcha, not a workflow logic bug, and the actual root cause of most of this saga's apparent flakiness. All fixed; see the commit history around v1.4.4-v1.4.11 for the full trail if this class of "images build and push fine, but the gate after them behaves unpredictably" resurfaces.

### CI quality gates

`quality.yml` is a second, separate scanning workflow from `docker.yml`'s `trivy-scan` above - lightweight, stateless scanners (actionlint, zizmor, SonarQube, a duplication/complexity ratchet) adapted from an internal template workflow set. Tool versions are pinned inline in `run:` lines rather than via `uses:`, so Dependabot's `github-actions` ecosystem entry won't auto-bump them - bump manually on a new CVE class or rule-pack update. `zizmor` (workflow security posture) runs non-blocking by design: this repo pins actions by tag, not SHA, and that's its dominant finding class - informational until that's revisited.

The duplication/complexity ratchet job compares each run against a baseline artifact from a prior run via `gh api`; a transient GitHub API error on that lookup used to hard-fail the whole job instead of just skipping the comparison. Both the "list artifacts" and "download artifact zip" calls now fail open (treated as "no baseline yet") - don't re-tighten this to fail closed, a flaky `gh api` call isn't a real quality regression.

### Prisma client

This project uses **Prisma 7** with the `@prisma/adapter-pg` driver adapter (not the legacy built-in engine). `lib/db/prisma.ts` creates the client via a `pg.Pool` → `PrismaPg` adapter. Always import `prisma` from `@/lib/db/prisma` - never instantiate `PrismaClient` directly. The client is a module-level singleton (cached on `globalThis` in dev to survive HMR).

The client is generated to `app/generated/prisma` (gitignored, never committed). `pnpm install` runs it automatically via the `postinstall` script; re-run `pnpm exec prisma generate` manually after editing `schema.prisma` without reinstalling. In `Dockerfile`, the `deps` and `runner` stages run `pnpm install --frozen-lockfile` with `--ignore-scripts` because `prisma/schema.prisma` isn't copied into those stages yet - the `builder` stage generates the client explicitly once the full source is present.

### Server vs Client boundary

- All Prisma queries and third-party API calls **must** live in Server Components or Server Actions.
- Chart and interactive UI components are `"use client"`. Pass pre-fetched data as props.

### Amounts & precision

All monetary values stored as **integer cents** (`BigInt`). Arithmetic via `Decimal.js`. Use helpers from `lib/utils/format.ts` for conversion and display (do not inline formatting logic). Institution logos are fetched at runtime via Google Favicons using domain mappings in `lib/domain/institutions.ts` - add new institutions there, not inline.
